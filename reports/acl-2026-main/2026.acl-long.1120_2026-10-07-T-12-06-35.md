**In short:** after fixing two silent bugs in the release, and writing the missing probe-data and evaluation scripts, Safe-FedLLM's main
claim holds in every setting we could run. All three defense levels (Step/Client/Shadow) make the federated model much
safer than FedAvg and the two robust-aggregation baselines (Multi-Krum, Trimmed Mean) under a 30% malicious-client
attack. This holds on both backbones (Llama-3.1-8B, Qwen2.5-7B) and both attack sources (BeaverTails, MaliciousGen).
The LoRA-Probe separates benign from malicious ΔLoRA almost perfectly. The **Rule** metric is mostly within a few points of the paper.
On **Qwen** the Shadow-Level MD-Judge numbers also match (93.9/93.7 vs 96.0/96.4). On **Llama** our MD-Judge numbers are roughly half
the paper's for *every* model, including the attack-free FedAvg 10:0 reference (26.3 vs 53.9). The ranking is unchanged,
but the absolute numbers don't match. The baselines' RM scores are consistently better than reported (≈-2.1 vs ≈-3.5),
so the RM gain is smaller than in the paper. The release **as shipped does not reproduce anything**. With Llama-3.1/Qwen2.5,
every training example is fully masked (loss = 0, LoRA never changes). The trained probe cannot be loaded by the FL script (`main_sft.py`),
so the defense silently falls back to FedAvg. There are also no scripts to build the probe's training data or to evaluate.

## What was attempted

Paper's main experiments: Table 2 (Llama-3.1-8B, 30% malicious clients, 4 data combinations, Safe-FedLLM's 3 variants vs.
FedAvg and 7 robust aggregators; metrics Rule / MD-Judge / RM on AdvBench + MT-1 on MT-Bench) and Table 3 (same with
Qwen2.5-7B). Supporting: Table 1/8 (FedAvg at different ratios), Table 4 (efficiency), Table 7 (probe detection quality).

What we ran (every run at the paper's full scale: 10 clients × 500 samples, 100 rounds, 3 clients/round, 10 local steps,
batch 16, lr 5e-5 with cosine decay, seq len 256, LoRA r=8/α=16 on 8-bit base model, AdamW-bnb-8bit, R_f=20, γ=0.95, η=7,
τ_cls=0.8, τ_skip=0.2; all are the release's defaults / `run_sft_example.sh` values):

* **Llama-3.1-8B, 7:3 (Table 2), both WildChat combinations** (BeaverTails&WildChat, MaliciousGen&WildChat):
  FedAvg, Multi-Krum, Trimmed Mean, Step-Level, Client-Level, Shadow-Level (12 runs).
* **Llama-3.1-8B FedAvg 10:0 on WildChat** (Table 1 reference; one run serves both WildChat columns since no malicious data is used).
* **Qwen2.5-7B, 7:3 (Table 3/9)**: FedAvg and Shadow-Level on both WildChat combinations, Step-Level and Client-Level on
  BeaverTails&WildChat (6 runs).
* **LoRA-Probe training data** (paper App. A): first 10 rounds of a 5:5 (50% malicious) federation with `--prefilter_id true`
  (excludes the first 4000 benign / 2500 malicious samples used for FL training), all per-step ΔLoRA-B of the first layer
  saved, for both WildChat combinations; one probe per backbone trained on the pooled 600 samples with the released
  `lora_classifier_train.py` (default hyper-parameters, L2 normalisation, threshold 0.8).
* **Evaluation**: AdvBench (520 prompts) with the FedLLM-Attack protocol that the paper says it follows (alpaca template,
  sampling T=0.7, max 1024 new tokens via vLLM with the trained LoRA adapter), then Rule (refusal-prefix match),
  MD-Judge (OpenSafetyLab/MD-Judge-v0.1, greedy, safe iff output == " safe") and RM (mean logit of
  OpenAssistant/reward-model-deberta-v3-large-v2). Table 7 detection metrics computed from the release's own
  `prefilter_classifier_result.json`.

### Settings that differ from the paper / were not run
* **LMSYS-Chat combinations (half of Tables 2/3) not run**: `lmsys/lmsys-chat-1m` is licence-gated on HF and our account is
  not on its authorized list (HTTP 403). This is a third-party access issue, not a release defect.
* **MT-1 not computed**: it needs GPT-5-mini as judge (closed API, no key) → `CLOSED_JUDGE_UNAVAILABLE`.
* **Baselines**: only Multi-Krum and Trimmed Mean (of 7 robust aggregators, all implemented in `fed_global.py`) were run,
  on Llama only, because of the 48 h budget (one run = 1h45m–3h30m on the single H200; GPU-bound, concurrency did not help).
* **Qwen Step/Client-Level on MaliciousGen&WildChat, ratio sweeps (Tables 5/6/8), Table 4 memory** not run (time).
* **Probe training data**: the paper does not say whether one probe is trained per data combination; we pooled the two
  WildChat combinations (600 ΔLoRA samples per backbone). Probe hyper-parameters are the release defaults.
* **Evaluation**: vLLM with the LoRA adapter instead of writing a merged fp16 model (same function); one sampled
  generation per prompt (T=0.7, seed 0) as in FedLLM-Attack; MD-Judge run offline via vLLM instead of a vLLM HTTP server.
* **Detection metrics (Table 7)** for Step/Client-Level only cover the first R_f=20 rounds (the code only classifies then);
  the paper does not state its window.
* Environment: bitsandbytes 0.45.5 / peft 0.14.0 instead of `bitsandbytes>=0.43` (0.43.3 int8 matmul crashes on H200:
  "cublasLt ran into an error!"; peft 0.12/0.13 are incompatible with bnb 0.45).

* **Claim 1, FedLLM is vulnerable** (Table 1): reproduced. Rule drops from 81.3 (10:0) to 48.3/47.3 (7:3) (paper 84.8/82.3 → 49.4/48.1).
* **Claim 2, the probe separates ΔLoRA** (Table 7): reproduced. 0% FPR / 100% precision everywhere. TPR is 99–100% for Step/Client,
  and 90.3% / 98.4% for Shadow (paper 100%).
* **Claim 3, Safe-FedLLM restores safety and beats robust aggregation** (Tables 2/3): reproduced as a trend. All three variants beat
  FedAvg, Multi-Krum and Trimmed Mean on every metric in every setting run. Rule numbers are within 4–10 points of the paper (Client-Level on
  MG&WC is 19 points lower). On Qwen, Shadow-Level reaches 93.9/94.2 Rule and 93.9/93.7 MD-Judge (paper 97.5/97.7 and 96.0/96.4).
  The Llama MD-Judge values are ~half the paper's for all models, including the attack-free 10:0 reference. Relative to that reference,
  Shadow-Level recovers 88–93% of attack-free MD-Judge safety; the paper's numbers give 95–97%.
* **"Shadow-Level performs best"**: mixed. On Llama/WildChat, Shadow ≈ Step > Client (Step is best on MG&WC).
  On Qwen BT&WC, Shadow (93.9) > Step (86.7) ≈ Client (85.4), as in the paper (97.5 > 83.7 ≈ 83.9). The Qwen Step/Client Rule values
  are within 5% of the paper, and their MD-Judge values are higher than reported (85.4 / 79.8 vs 72.1 / 75.8).
* **Qwen2.5-7B, all runs (Rule / MD-Judge / RM)**: FedAvg 63.3 / 44.6 / -1.36 (BT&WC) and 51.2 / 21.0 / -2.07 (MG&WC);

* **Efficiency (Table 4)**: not reproduced as stated. Llama wall-clock on one H200: FedAvg 1h46m, Step 1h49m, Client 1h48m, Shadow 3h26m

## Why not fully reproduced
1. Half of the main tables (LMSYS-Chat columns) can't be run: gated third-party dataset, no access.
2. MT-1 needs a closed judge (GPT-5-mini).
3. Budget: only 2 of 7 robust baselines, no ratio sweeps, Qwen Step/Client only on one combination.
4. Llama MD-Judge absolute values and baseline RM values differ substantially from the paper, even for attack-free FedAvg.
   We checked the MD-Judge pipeline by hand: the "unsafe" verdicts are correct, e.g. the models give harmful how-tos wrapped in
   disclaimers, which Rule counts as refusals. Our Qwen MD-Judge values do match the paper. We found no code difference that explains
   the Llama gap. Candidate causes are generation sampling (T=0.7 single sample), the EOS token being masked in training (pad = eos), and
   undocumented evaluation details. The authors ship no evaluation code and no outputs/checkpoints to compare against.

## Codebase completeness: MISSING_SCRIPTS

The method (LoRA-Probe training script, three defense strategies, FL loop, robust aggregators) is implemented.
The main-experiment pipeline is incomplete, and two bugs silently change results:

Changes to the released code (left uncommitted in `./codebase`; `git diff` shows them):
* `main_sft.py` (response-template ids): `tokenizer.encode(response_template.lstrip("\n"), ...)` instead of
  `tokenizer.encode(response_template, ...)`. With Llama-3.1/Qwen2.5 BPE, `"\n\n"` is one token, so the ids of
  `"\n### Response:"` never occur in a tokenized example. `DataCollatorForCompletionOnlyLM` then masks every label,
  training loss is exactly 0 and the LoRA never moves. **Result-changing bug (MAJOR).** Upstream FedLLM-Attack uses `[2:]` slicing for this;
  Safe-FedLLM dropped it.
* `lora_classifier/fed_lora_classifier.py`: registers `lora_classifier.lora_classifier_common` under the module name
  `lora_classifier_common`. `lora_classifier_train.py` (run from inside `lora_classifier/` as the README says) pickles the
  probe module under that top-level name, so `main_sft.py` fails to load it ("prefilter init failed") and every
  defense silently degenerates to plain FedAvg (all weights 1). **Result-changing bug (MAJOR).**

Scripts we had to write (in `./scripts`):
* `collect_probe_data.py`: generates the probe's labelled ΔLoRA training set (App. A). No such script exists, and the
  released `DeltaTracker` can only save deltas once a trained classifier already exists. The wrapper stubs the classifier with
  the released `DeltaSaver` and runs the released `main_sft.py` unchanged.
* `run_fl.sh`: non-interactive version of `run_sft_example.sh` (which reads GPU id / client counts from stdin).
* `eval_advbench.py` (+ `md_judge_template.txt`): AdvBench generation + Rule / MD-Judge / RM. Ported from the upstream
  FedLLM-Attack evaluation code; the Safe-FedLLM repo has no evaluation code at all.
* `detection_metrics.py` (Table 7), `make_tables.py` / `make_status.py` (tables), `queue.sh` / `eval_loop.sh` (job orchestration).

Environment fixes: `bitsandbytes==0.45.5` (0.43.x int8 kernels crash on Hopper/H200), `peft==0.14.0` (API compatibility with
bnb 0.45), plus `rich` (needed by trl 0.8.6 but not in requirements).

## Notes
* Detection (Table 7) is *better* than the paper's for Step/Client-Level (0 FPR vs 2.5–11.75%). This may be because the window is the first 20
  rounds only, and our probe was trained on the same WildChat combinations.
* Client-Level on MG&WC is the weakest variant (Rule 61.2). Its frozen weights for malicious clients are 0.06–0.15 rather than ≈0,
  because of the soft two-stage calibration combined with history averaging. Detection was still 100%.

  fix. It logged `prefilter init failed ... No module named 'lora_classifier_common'` and ran as FedAvg, and was killed after 2 rounds.
  A second run was killed only because we stopped running two jobs at once (two concurrent jobs gave lower total throughput).
