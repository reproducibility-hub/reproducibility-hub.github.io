### Bottom line

The paper's central quantitative claims reproduce well on Llama3-8B-Instruct and Qwen3-8B, using the paper's models and released data:

* Entity and relation indices are linearly decodable from layer-15 attribute activations. PLS R² reaches ≈0.89 with 2 components and ≈0.95–0.98 with 5–10 (Fig. 2), and the projected activations form a grid by entity and relation index.
* Cross-context R² matrices (Fig. 8a / Fig. 25a): every diagonal entry is within 0.01–0.02 of the paper and in-context R² is 0.97–0.99. Off-diagonal entries are within ≈0.1 of the paper's, with the same pattern.
* With the cell-wise translation vector Δ (Fig. 8b / 25b), every cell becomes 0.97–0.99 (paper: 0.96–0.99).
* Perturbing along the CBR subspace (Fig. 5 / 70) drives attribute accuracy from base level (which matches the paper) to ≈0–0.13 by α=0.8, as in the paper.
* Relation-index steering (Fig. 6 / 77a) reproduces the paper's bar heights almost exactly: 39 of 40 values within 0.05.

Caveats:

1. **The random-subspace control in Fig. 5/70 depends on a bug in the released code.** The released `activation_perturbing.py` overwrites `W_CBR` with `W_rand` inside the batch loop. As a result, 49 of 50 examples get `W_randᵀ W_rand h` instead of Eq. 3's `W_randᵀ W_CBR h`.
   * With the bug kept, our random-control curves match the paper's flat grey lines (e.g., Llama at α=0.8: city 0.94, relation 1.00, job 0.92).
   * Implementing Eq. 3 as written, the random control is still much less harmful than CBR perturbation, but **not** "little or no effect": Llama at α=0.8 gives city 0.55, relation 0.58, job 0.70, object 0.27, country 0.38.
   * So the CBR-vs-random gap holds, but the paper's control looks cleaner than its own equation produces.
2. **The Fig. 8b improvement relies on a cell-specific Δ**, which uses the gold (ei, ri) label of each test point. This is what Eq. 8 defines, so it is not a code bug, but it means the "w/ Δ" R² is partly label information. A single label-free translation vector (difference of context means) gives essentially no improvement over "w/o Δ" (see table below).

### Settings, and where they differ from or are unspecified in the paper

* I used the release's own defaults everywhere, which the paper mostly does not state:
  * notebook: `nb=200` samples per input type; Fig. 2 = story only, 50/50 split; Fig. 8 = template+story, 70/30 split, **15 PLS components** (notebook call `analyze_generality(pls_dim=15)`). I also report 5 components in `results/pls_*_l15.json`; the pattern is the same and R² is ≈0.01–0.04 lower.
  * `W_CBR` for perturbation: 10-component PLS on table+template+story, QR-orthonormalised.
  * perturbation: 100 samples, layers 10–19, α ∈ {0.1, …, 1.2}.
  * steering: 150 samples, α grid {0.15, …, 1.2}, best α per domain.
* `nb_loop` (repeats used for the error bars) defaults to 1 in the code. I used 3 for perturbation and steering, because the paper's plots show error bands.
* Fig. 4 sampling: 400 instead of 10⁴ grid points (reduced for compute: the released loop runs one forward pass per grid point per cell, ≈0.9 s per point). All 5 domains, Llama only.
* Environment: `environment.yml` pins torch 2.0.1 / transformers 4.35, which cannot load Qwen3. I used python 3.10, torch 2.4.1, transformers 4.51.3, scikit-learn 1.2.2 (same as pinned), numpy 1.26.4 and baukit from git.
* Batch sizes were changed for memory only. This doesn't affect results: every example is processed independently, with left padding.

Interpretation:
* The landscape is clearly organised by cell, well above chance: moving an attribute's activation within the 2-D PLS plane changes whether it can still be retrieved, depending on where it lands.
* But at this resolution it is far less crisp than the paper's Fig. 4. Only 4–5 of 12 peaks land in their own cell, and high-probability regions concentrate in the middle of the plane.
* Contributing factors:
  * 400 vs 10⁴ points, with 50 noisy samples per point;
  * the grid excludes the outer 15% of the range on each side, where several extreme cells (e.g. ei:1/ri:1, ei:3/ri:4) lie;
  * the released code steps *away* from the grid point (β<0, see Discrepancies), which compresses the landscape.

I count this item as qualitatively supported but not quantitatively verified (NOT_COMPARABLE, scaled down).
