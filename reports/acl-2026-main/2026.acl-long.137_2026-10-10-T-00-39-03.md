## What was attempted

Goal: the paper's main experiment — online continual merging of 40 single-task LoRAs (5 problem types × 8 languages)
into a budget of K = 1…8 adapters, scored with the normalised aggregate score S(γ) (Eq. 4), averaged over 3 random task
orderings (seeds 0/22/44), for Llama-3.2-1B-Instruct and Qwen-2.5-1.5B-Instruct (Fig. 3 / Tables A.4–A.5), plus the
ordering-robustness study (Table 1, Llama) and the threshold ablation (Table A.6). The release contains no trained
LoRAs, so the whole pipeline had to be re-run: data preparation (tone re-writing with the RedPajama tone model,
machine translation with OPUS-MT / M2M100), training of 2 × 39 single-task LoRAs, then all continual-merging runs.

Pipeline actually run (all inside `./codebase`, env `./env`):
1. `python process_data.py --dataset text-correction` (W&I, as released) and `scripts/prep_data.py` (our thin driver around
   the released `change_tone_of_dataset` / `translate_dataset`, see deviations) for the 4 tones and 7 × 4 translated datasets.
2. `scripts/run_training.sh` — the released `train_loras_{llama,qwen}.sh` argument sets (`--attn_lora --lora_r 32
   --lora_alpha 128 --lora_dropout 0.05`, GA 64 / GA 4 for tone & non-English GEC, lr 5e-5 default, 1 epoch, AdamW-8bit)
   with the deviations listed below; `run_experiments.py --do_train`.
3. `scripts/run_merge.sh` — the released `scripts/{llama,qwen}/run_all_k_*.sh` argument sets
   (`--shuffle_loras --lora_merge_strategy=… [--threshold_sim=0.020|0.028] --tone=generic --do_predict --k_lora_budget=K --seed=S`),
   i.e. the released merging code in `run_experiments.py` / `merge.py`; with `KMERGE_DUMP_DIR` set, our addition dumps the
   final cluster adapters + task→cluster map + formatted test prompts instead of running the HF-pipeline generation.
4. `scripts/vllm_eval.py` — generation for every task with its assigned cluster adapter via vLLM (same chat template,
   greedy, 128 new tokens, same stop tokens), scored with the released `utils.compute_task_metrics`.
   Validated against the released HF-pipeline evaluation on two full 39-task runs: mean |Δ| = 0.06 points (zero-shot)
   and 0.20 points (single-task LoRAs) per task, S identical to 3 decimals.
5. `scripts/make_tables.py` — S(γ) per run, normalised by our own single-task LoRAs (run `k_39_single`, i.e. K = #LoRAs so
   every task keeps its own LoRA; same test samples), and also by the paper's hard-coded single-LoRA scores
   (`compute_s_score.py`, as released).

Two evaluation scales were run:
* **capped**: ≤ 200 test samples per task (all 7 methods × K=1..8 × 3 seeds × 2 models, Table 1, threshold ablation);
* **full**: the release's own protocol (no `--max_test_samples`: QA/Smart-reply 1000, SAMSum 819, tone 4×642, GEC full)
  for single / zero-shot / K-Merge / K-Merge++ / Linear / TIES × K=1..8 × 3 seeds × 2 models.

## Why not fully reproduced
1. **Compute.** Translating the full training splits (225k + 65k + 15k examples × 7 languages, beam search, batch 4 as released) and training on them was infeasible in 48 h on one GPU. We used 20k / 10k / 7k subsets with greedy MT, which gives weaker single-task LoRAs on translated tasks.
2. **Data access.** Italian GEC (MERLIN via MultiGEC) requires an access request, so 39 of 40 tasks were run.
3. **K-Merge++ calibration not reproducible.** The threshold-calibration LoRAs (held-out tasks: TED translation, XLSum titles; pt/tr/sr) have neither code nor data in the release. The fixed s=0.020 does not transfer to our LoRAs.
4. **Results differ from the paper.** Even with these caveats, the large K-Merge vs Linear gaps reported in the paper did not appear, because Linear is much stronger in our runs. The K-Merge++ advantages hold only for Qwen at small and medium K.
