"From Inheritance to Saturation: Disentangling the Evolution of Visual Redundancy for Architecture-Aware MLLM Inference Acceleration". Code: https://github.com/civilizwa/HalfV (linked from the paper).

The paper's headline claim is that on Qwen2.5-VL HalfV keeps 96.8% of performance at a 4.1× FLOPs speedup. We get **95.8%**, measured against our own vanilla run, using the paper's hyperparameters. Each benchmark score is within 0–2 points of Table 3. Two caveats:
- The 4.1× speedup does not follow from the paper's own FLOPs formula: it gives 3.85×.
- The released code's second (SSR) stage does not do what the paper describes.

## What the paper claims / what we targeted

- **Main experiment:** Table 3. HalfV is compared with vanilla and 6–12 token- or layer-pruning baselines, on 4 backbones and 8 benchmarks: GQA, MME, POPE, SQA, TextVQA, VizWiz, MMB-en, AI2D.
- **What can be run:**
  - The repo has a HalfV implementation only for **Qwen2.5-VL-7B-Instruct**, in `lmms-eval-0.5v/.../qwen25_halfv/modeling_qwen2_5_vl_self.py`.
  - The LLaVA side (`lmms-eval-0.35v`) imports `llava.model.language_model.my_modeling_llama` and `HalfV_llama_mistral`. These live in `lmms-eval-0.35v/LLaVA/`, which is in `.gitignore` and was never committed. The git history confirms this.
  - No baseline code is released.
- **So we reproduced:** the Qwen2.5-VL-7B rows "Vanilla" and "HalfV (Ours)" of Table 3. We also checked the TFLOPs column analytically.

## What we ran

Environment:
- conda env with Python 3.10, torch 2.9.0 (cu128), transformers 4.57.1, `lmms_eval` installed editable from `lmms-eval-0.5v`, plus accelerate, qwen-vl-utils[decord] and the bundled `representation-itl`.
- `datasets==3.6.0`, `fsspec<=2025.3.0`.
- One H200 GPU. Up to 5 eval processes shared it concurrently.

Commands: the README command, looped over tasks by `scripts/run_all.sh`, run from `runs/`:
```
accelerate launch --num_processes=1 -m lmms_eval --model qwen2_5_vl \
  --model_args=pretrained=Qwen/Qwen2.5-VL-7B-Instruct,max_pixels=12845056,interleave_visuals=False \
  --tasks <T> --batch_size 1 --log_samples --output_path ./halfv/ \
  --halfv_attention_ratio 0.1 --halfv_ivr_layer_index 2 --halfv_ivr_prune_ratio 0.25 \
  --halfv_ssr_layer_index 21 --halfv_ssr_prune_ratio 0.05            # HalfV (= README example = Table 9)
#   vanilla: same, with --halfv_ivr_layer_index -10 --halfv_ssr_layer_index -10 (no pruning happens)
```
- Tasks (lmms-eval names): `gqa` (testdev-balanced, 12,578), `mme` (2,374), `pope` (9,000; F1 reported), `scienceqa_img` (2,017), `textvqa_val` (5,000), `vizwiz_vqa_val` (4,319), `mmbench_en_dev` (4,329), `ai2d` (3,088).
- All runs used full splits, greedy decoding and batch size 1.

Settings that differ from the paper:
- **Vanilla is run differently from the README.** We used the released modeling file with both pruning layers set to indices that never fire, instead of the README's manual class swap. The forward pass is then identical to stock Qwen2.5-VL, and the vanilla numbers match Table 3.
- **Hardware differs.** The paper used an RTX 4080S with PyTorch 2.1.2. We used an H200 with torch 2.9.0, as the README instructs for Qwen.
- **MMBench evaluator.** It falls back to GPT only when an answer can't be parsed. That never happened: 0 fallback calls, so there was no judge dependence.
- **VizWiz data cache.** VizWiz was loaded through a local `HF_DATASETS_CACHE`, because the shared cache held a copy that is incompatible with the newer `datasets` version. The data itself is the same `lmms-lab/VizWiz-VQA` val split.

### Extra: the SSR-stage selection bug and a corrected variant

**The bug.** In `HalfV.forward`, after IVR pruning at layer 2 only 25% of the visual tokens remain. At layer 21, `calculate_attention_weight` still slices the keys as `[image_start : image_start + original_image_length]`. That range covers the surviving visual tokens *and all following text tokens*.

**Measured effect.** Measured on 30 MME samples (`scripts/diag_ssr.py`): in **100% of samples, about 93% of the "Top-5% visual tokens" picked at the SSR stage are text positions.** As a result:
- Almost all visual tokens are dropped at layer 21.
- The selected text tokens are duplicated in the hidden-state sequence.

The paper (Sec. 3.3 (2), Table 9) instead describes keeping the top-5% *visual* tokens.

**Corrected variant.** We ran it via a monkeypatch, so the codebase itself was not edited for this (`scripts/run_fixed_ssr.py`). It slices only the surviving visual tokens:

| | GQA | MME | POPE | SQA | TextVQA | VizWiz | MMB | AI2D | Avg % |
|---|---|---|---|---|---|---|---|---|---|
| HalfV as released (crash-fixed) | 58.2 | 2248.2 | 84.5 | 85.0 | 75.5 | 67.5 | 80.3 | 79.2 | 95.8 |
| HalfV, SSR corrected | 58.6 | 2240.3 | 84.4 | 84.8 | 75.2 | 67.9 | 80.4 | 79.1 | 95.8 |

The correction changes each score by ≤0.5 pt (GQA +0.4, VizWiz +0.4, MME −7.9 points on the 2800-point scale) and leaves the average unchanged at 95.8%. In practice, the deep layers of Qwen2.5-VL barely need visual tokens either way, which is consistent with the paper's "secondary saturation" thesis. The paper's numbers were evidently produced by the as-released behaviour.

## Codebase completeness: MISSING_CORE

**Missing pieces:**
- **LLaVA HalfV implementation.** The `lmms-eval-0.35v/LLaVA/` package and its modules `my_modeling_llama.py`, `HalfV_llama_mistral.py` and the modified `llava_llama.py` are absent; they are gitignored. Without them, `lmms-eval-0.35v/lmms_eval/__main__.py` fails on import, and 3 of the 4 Table-3 backbones cannot be run.
- **Other backbones.** There is no code for Qwen2-VL / Qwen3-VL (Table 4) or for video (Table 5).
- **Baselines.** No baseline implementations are released.

**Changes to the released code** (left uncommitted in `./codebase`):
1. `lmms-eval-0.5v/lmms_eval/models/simple/qwen25_halfv/modeling_qwen2_5_vl_self.py`, class `temp_cache`:
   - Added `halfv_frozen_layer_index=100`. `HalfV.__init__` reads this attribute, but it was never defined, so the model crashed at load time. Setting it to 100 means no layer uses the LLaVA-style frozen-visual decoder layer. The paper's Qwen SSR strategy is token sparsity, not layer freezing, so this matches the paper.
   - Added `cal_cosine_similarity=False`. It is referenced in `Qwen2_5_VLTextModel.forward`, which HalfV does not use.

**Environment-only fixes:**
- `pip install -e representation-itl`: `repitl` is imported unconditionally but is not in the README install steps.
- `matplotlib` and `seaborn`.
- `datasets==3.6.0` and `fsspec<=2025.3.0`, because the newest `datasets` conflicts with the `huggingface_hub` version that transformers 4.57.1 requires.

**Scripts we wrote (outside `codebase/`, in `scripts/`):**
- `run_all.sh`: loops the README command over tasks.
- `diag_ssr.py`: diagnostic for the SSR selection.
- `run_fixed_ssr.py`: the corrected-SSR ablation, done by monkeypatch.
- `aggregate.py`: builds the results tables.
- `write_status.py`: writes status.json.

**Other observations:**
- lmms-eval catches task errors and still exits with code 0.
- Text-only samples would crash the Qwen wrapper, because of `input_ids.index(151655)`. This does not occur on the evaluated image-only splits.

## Discrepancies

1. **code_vs_paper, major, affects results (≤0.5 pt here): SSR selection.** The paper keeps the Top-K_SSR *visual* tokens. The code mostly keeps text positions, because the key slice uses the pre-pruning image length, and it duplicates those text tokens. See above.
2. **code_vs_paper, minor: default anchor ratio.** The CLI default is `--halfv_attention_ratio 0.2`, whereas Table 9 gives R_S = 0.1 for Qwen. The README example passes 0.1, which is what we used.
3. **paper_internal: TFLOPs.** Table 3's HalfV TFLOPs, and so the "4.1× speedup" in the abstract, cannot be recovered from Eq. 43–44 with the Table 9/11 settings: the formula gives 9.51 TFLOPs / 3.85× for Qwen2.5-VL. The vanilla values do match the formula exactly.
