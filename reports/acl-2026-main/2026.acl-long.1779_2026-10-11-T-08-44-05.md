**Summary.**
- **Released checkpoint matches Table 2.** The checkpoint (`Comet-Qwen3-4b-on-Scrolls`, Kaggle) scores Avg **39.69 vs. 40.10** in the paper's Table 2 on the full released SCROLLS validation set (7,455 samples), run through the released `workflows/inference.py`. 13 of the 14 per-task numbers are within 1 point. NarrativeQA is the exception: 20.5 vs. 22.6.
- **GovReport depends on the generation cap.** The paper's numbers are reached only with `--max_new_tokens 1024`. The released `scripts/infer.sh` uses 512, which cuts off 94% of GovReport summaries and gives 54.8/27.2/29.6 instead of 62.5/31.1/33.4.
- **Training could not be re-run at the paper's scale.** The released training pipeline (`workflows/train_pre_tokenize.py` + `workflows/train_from_qwen3.py`) runs on 1×H200 with no source edits. However, the paper's 3 epochs (~48k packed 32k-token sequences, ~750 steps at batch 64) would take about 190 GPU-hours here. Our run of 56 steps × 64 sequences (~7.5% of the paper's training tokens) lowered the training loss from 4.8 to about 2.4. The resulting model is still far from usable: it generates repetitive text and never emits EOS. So we could not confirm that training reproduces the checkpoint.
- **Baselines were not run.** No baseline code was released, so the "beats other efficient methods" claim is checked only against the paper's own baseline numbers.

## What the paper claims / what was targeted

The main claim behind the abstract and conclusion that the release lets us test is **Table 2 (SCROLLS)**:
- Setup: CoMeT on Qwen3-4B-Instruct-2507 (512 global + 2,048 temporary memory, chunk 2,048, one compression token every 8 tokens, RLA rank 8), fine-tuned for 3 epochs on the mixed SCROLLS training set (≤32k tokens).
- Claimed result: Avg 40.10, the best among the efficient methods, and on par with fine-tuned full attention on summarization (GovRep, SumScr).

Released by the authors (all public, downloadable without authentication):
- Code: https://github.com/LivingFutureLab/Comet (method, training, inference; Qwen3 backbones only).
- Data: SCROLLS train/eval jsonl in the authors' ChatML format (Kaggle dataset `liulangmingliu/scrolls-by-comet`; the eval file is also on HF as `OpenStellarTeam/scrolls_by_comet`). It has 41,496 train / 7,455 validation samples, matching Appendix C exactly.
- Checkpoint: Kaggle model `liulangmingliu/comet-qwen3-4b-on-scrolls`.

Not released, or not runnable here:
- Code for every baseline (Full-Attn FT, SWA, Transformer-XL, HMT, ICAE, 500xCompressor, Activation Beacon, (Long)LLMLingua(2), EXIT).
- Passkey task (Fig. 1/8/10): no data generator, script or checkpoint.
- The 2WikiMQA/HotpotQA training mix (Table 3).
- Table 5: Qwen3-14B and Llama-3.1-8B checkpoints are not released, and the code implements Qwen3 only.
- UQA and Terminal-Bench (Table 4): proprietary data.
- Layer-level pipeline-parallel speedups: these need several GPUs.

## What we ran (exact commands)

Environment: conda env `env/` with Python 3.10, torch 2.8.0+cu128 and transformers 4.53.2, as in `pyproject.toml`. The following needed fixes, all environment-only:
- **apex:** the code imports apex's `fused_weight_gradient_mlp_cuda` even for inference. We built only that extension from NVIDIA/apex sources with CUDA 12.8 (`tools/apex_fwg/setup.py`).
- **quack:** `pyproject.toml` lists pip package `quack`, which is an unrelated package. We installed `quack-kernels==0.2.2`, which provides `quack.cross_entropy`.
- **Undeclared dependencies:** we installed `ossfs` (needed by the chunked data loader) and `accelerate` (needed by `from_pretrained(device_map=...)`).
- Hardware: 1×H200 (141 GB), 113 GB host RAM.

1. **Released checkpoint → Table 2.**
   - Command, run in 4 (or 8) shards via `tools/run_infer_shards.sh`:
     `python workflows/inference.py --model_path=<kaggle ckpt> --tables=<shard of scolls_32k_chatml_eval.jsonl> --max_input_length 32256 --max_new_tokens 512 --dtype bf16`
     These are the `scripts/infer.sh` settings.
   - Long tasks were split into extra parallel shards for speed (`eval/{shard,mid,tail}*.jsonl`); this does not change the outputs.
   - GovReport was then re-run with `--max_new_tokens 1024` (`eval/released_gov1024/`).
   - Scoring: `tools/score_scrolls.py` (our script) parses the `Outputs:` log lines and computes the SCROLLS metrics:
     - ROUGE-1/2/L via `rouge_score` with stemming, max over references;
     - SQuAD-normalised token F1 for Qasper, NarrativeQA and QuALITY (the paper reports F1 for QALT);
     - normalised exact match for ContractNLI;
     - the paper's "Avg", which uses the geometric mean of R-1/2/L for summarization tasks; this reproduces Table 2's Avg column exactly (CoMeT 40.10, FA-FT 42.23, FA 7.87).
     - We report ROUGE-L, not ROUGE-Lsum; ROUGE-L matches the paper's scale.
2. **Training, scaled down.**
   - Tokenize: `python workflows/train_pre_tokenize.py --tokenizer_path Qwen/Qwen3-4B-Instruct-2507 --data_file scolls_32k_chatml_train.jsonl --seed 0 --save_dir train_data/scrolls_32k_epoch_0`. This gives 15,996 packed 32k sequences, about 412M tokens per epoch.
   - Train with `tools/train_comet.sh`, a 1-GPU copy of `scripts/train.sh` with the same hyperparameters: chunk 2048, global 512, stride 8, temporary budget 2048, lr 5e-5, 10 warm-up steps, cosine decay to 0, β=(0.9, 0.999), wd 0, ZeRO-3 plus recompute, bf16. Two changes:
     - backbone set to the paper's Qwen3-4B-Instruct-2507 (the script points to Qwen3-0.6B);
     - `--gradient_accumulation_steps 64` to reach the paper's batch of 64 on 1 GPU.
   - Run length: `--max_steps 56` (3,584 sequences, ~92M tokens, ~22% of one epoch, ~7.5% of the paper's 3 epochs). It took 15 h (≈16 min/step).
   - Evaluation: same inference command on a stratified random subset of 40 samples per task (280 samples, seed 0, `eval/sub_ids.txt`), with `--max_new_tokens 512`. The subset was needed because the model never emits EOS, so every generation runs to the cap. The released checkpoint was scored on the same subset from its full-run outputs.
   - Loss probe: the lr≈0 runs (`logs/lossprobe_*.log`) compare per-sequence training loss for the base model, the released checkpoint and ours on the first 5 training sequences.

**Why training was not reproduced:** insufficient compute. The paper's run is ~48k packed 32k-token sequences. At the measured ~15 s/sequence on one H200, that is ≈190 GPU-hours, against a 30-hour job limit. The release's own `train.sh` assumes 8 GPUs, and the paper mentions 16×80 GB GPUs for the 128k runs.

## Codebase completeness: MISSING_SCRIPTS

No source files in `./codebase` were modified (`git status` is clean).

Issues found:
- **Missing evaluation step.** `workflows/inference.py` only prints generations (`tprint("Outputs: ...")`). It does not save predictions and computes no SCROLLS metric. We wrote `tools/score_scrolls.py`: a log parser plus ROUGE/F1/EM following the SCROLLS definitions, and the geometric-mean "Avg" the paper uses.
- **Dependency problems (environment-level):**
  - `pyproject.toml` lists the wrong `quack` package; `quack-kernels` is needed.
  - It does not list `ossfs`, `accelerate`, or apex's `fused_weight_gradient_mlp_cuda`, which is required even for inference because `modeling_qwen3.py` imports `talos.ops.linear_cross_entropy`.
- **Config defaults that differ from the paper:**
  - `scripts/train.sh` points `model_path` at Qwen3-0.6B, and its 8 GPUs × micro-batch 1 × GA 1 gives a global batch of 8 rather than 64.
  - `scripts/infer.sh` uses `max_new_tokens 512`, which truncates GovReport.
  - `scripts/train.sh` also hard-codes `CUDA_VISIBLE_DEVICES=0..7` and torchrun with 8 processes. On our 1 GPU we used our own copy, `tools/train_comet.sh`.

Scripts we wrote (all outside `./codebase`, in `tools/`):
- `score_scrolls.py`: the scorer.
- `run_infer_shards.sh` and `stop_shards_at_tail.sh`: parallel sharding of `inference.py`.
- `train_comet.sh`: single-GPU copy of `train.sh`, same hyperparameters.
- `launch_train_after.sh` and `launch_eval_after_train.sh`: sequencing.
- `apex_fwg/setup.py`: builds only the needed apex extension.
