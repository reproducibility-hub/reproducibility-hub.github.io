## What the paper claims and what was targeted
The paper compares six tokenizers trained on Hindi wiki + Marathi wiki + SQuAD: GC (proposed), GPE, WordPiece, Unigram, BPE, and ITR+BPE.
- Table 1: intrinsic metrics on FLORES-101.
- Table 2: QA accuracy, with an automated POS/sentence-similarity judge, on XQuAD-hi and MahaSQuAD for monolingual, multilingual and noisy models.
- Table 3: TyDiQA-en.
- Table 5: multilingual word-level tasks, i.e. G2P (WikiPron + SIGMORPHON-2020 hi) and Dakshina transliteration, with 4-layer T5 models.

Claims: GC is "better than or competitive with" the popular tokenizers; BPE is consistently poor on Devanagari; Rényi efficiency is highly correlated with QA accuracy, but not with word-level tasks. I targeted Table 1 and Table 5 in full, with the paper's model sizes, epochs, optimizer and data sizes. Table 2/3 could not be run.

## Why it was not fully reproduced (concrete reasons)
1. **QA data not released (Tables 2, 3; the Rényi–QA correlation claim).** The paper (footnote 1) says "the source code and dataset is available", but the repo has no QA data. The training scripts read `datasets/wiki_squad_{hi,mr,en}_*.json(l)` (GPT-4o-mini-generated, 50k Hindi / 70k Marathi contexts), and nothing like it is on the HF Hub or in the authors' GitHub org. Regenerating it would need the OpenAI API and the authors' (unreleased) prompts and augmentation scripts. The automatic QA evaluator also needs fastText embeddings the authors trained on C4 (`embed_ft.py` only), so even the evaluation is incomplete without retraining those. I didn't attempt this.
2. **Tokenizer vocabularies and the exact corpus snapshot are not released.** With the released code on the corpus the paper describes (Kaggle Hindi wiki, 137,823 train articles; Marathi wiki, 59,875; SQuAD contexts), the grapheme-cluster vocabularies come out larger than the paper's (multilingual 23,613 vs ≈16,800; Hindi-only 20,598 vs ≈12,850; IPA 24,088–24,563 vs ≈17,400). Marathi-only matches (10,467 vs ≈10,500). This points to a smaller or cleaner Hindi corpus than the one stated. Two consequences:
   - The released GPE trainer computes `num_merges = target − |initial graphemes (min_freq=2)|`, which is negative on our corpus, so **GPE performs 0 merges**. It degenerates to a frequency-pruned grapheme-cluster vocabulary, whereas the paper's GPE clearly had merges.
   - Unigram never learns proper English pieces (English fertility 6.8 vs paper 3.6).
3. **G2P data versions.** WikiPron has been re-scraped since 2020. About 22% of the SIGMORPHON-2020 Hindi test words (the paper's test set) have a different pronunciation in today's (and the 2024) WikiPron, so models trained on current WikiPron hit a ~22% WER floor on that test. With the current WikiPron pronunciation also accepted as a reference (supplementary table), our as-released GC/GPE Hindi numbers (13.8/4.1, 17.1/4.8) land close to the paper's (12.67/3.46, 17.11/5.57). Marathi (4,872 vs paper 4,126 pairs) and English pair counts also differ from the paper's.
4. **Released bug in the tokenizer character filter (affects G2P).** `clean_text` keeps only the Devanagari, IPA-Extensions, Spacing-Modifier and Combining-Diacritics blocks plus ASCII. It silently strips Latin-1 (`æ`, `ð`), Latin Ext-A (`ŋ`) and Greek (`θ`), although the same files' `IPA_RANGES` list these blocks as IPA. With the released code these phones (4.0% of G2P target phones for GC; `æ` alone is 4,915 tokens) cannot be in any tokenizer vocabulary, so the models can only emit `<unk>` for them. I fixed the ranges and retrained the six IPA tokenizers and G2P models. That helped English and Marathi but left Hindi unchanged or worse.
5. **No language tag in the G2P input.** Hindi and Marathi share the script but use different IPA conventions (Marathi WikiPron has no vowel length). Models trained with the released input format mix the two conventions, and which way a given run leans varies between runs (e.g. the fixed GC seed-42 model wrote Marathi-style `a` for Hindi words). Single-run G2P rankings between close tokenizers (GC vs GPE) are therefore not stable.
6. **Paper's Rényi order.** The paper says α=2.5, but the code default is α=2, and only α=2 reproduces the paper's numbers (GC Hindi 0.6511 vs paper 0.651; α=2.5 gives 0.625).

## Codebase completeness: MISSING_SCRIPTS
The tokenizers, the T5 training loops and the evaluation are implemented, and the intrinsic-metric code ran unchanged. Missing:
- All data preparation: the G2P splits (WikiPron + SIGMORPHON, stratified Marathi/English sampling), the Dakshina splits (direction, sampling, references), and the IPA-transliterated Wikipedia used to train the G2P tokenizers.
- The QA dataset and its generation pipeline.
- Trained tokenizer files and models.
- A requirements file with versions. `requirements-vm.txt` lists names only, and the code needs `tokenizers<0.20` and `pandas<3`.

It also needed a result-affecting logic fix (the `clean_text` ranges), which on its own would be MAJOR_FIXES.

Changes to the released code (left uncommitted in `./codebase`):
- `train_llm/train-t5-gc-gtp.py`, `train_llm/train-t5-dks.py`:
  - The tokenizer is chosen with `--tok` instead of commenting/uncommenting blocks (same constructors and files).
  - `device` set to `cuda:0` (was `cuda:1`/`cuda:2`).
  - `resume_from_checkpoint=False` (the G2P script was set to resume from the authors' local `model_step_37479.pt`).
  - `save_steps=10**9` (was 100: ~0.3 GB full-optimizer checkpoints every 100 steps). Best and per-epoch models are still saved, and training is unchanged.
  - G2P only: ITRANS transliteration of the input applied only for the ITR+BPE model. The released file applied it unconditionally, i.e. it was left in the ITR+BPE configuration.
  - G2P only: seed configurable through the `SEED` env var (default 42, as released), used for the second run.
- `training_tokenizers/{gc_tokenizer_hf,gbpe_tokenizer_hf,bpe_tokenizer_hf,wp_tok,sent_tok,itrans_tokenizer_hf}.py`: the `clean_text` character class was extended with ` -ɏ`, `Ͱ-Ͽ` and `ᴀ-ᶿ` (the files' own `IPA_RANGES`). This edit was made **after** the multilingual tokenizers (Table 1, transliteration) were trained, so those results are from the unmodified filter. Only the six IPA/G2P tokenizers were retrained with it.
- Environment-only fixes:
  - `transformers==4.44.2` and `tokenizers==0.19.1`. With tokenizers≥0.20, BPE merges are serialised as lists and `merge_str.split(' ')` in `bpe_tokenizer_hf.py`/`itrans_tokenizer_hf.py` crashes.
  - `pandas==2.3.3`. Under pandas 3, `astype(str)` keeps NaN, so English words such as "null" become floats and crash Aksharamukha or the default collate.
  - `PYTHONPATH=<repo root>`.
  - FLORES-101 dev copied to the path the script expects (`intrinsic_eval/floresp-v2.0-rc.3/dev/dev.{hin_Deva,mar_Deva,eng_Latn}`).
