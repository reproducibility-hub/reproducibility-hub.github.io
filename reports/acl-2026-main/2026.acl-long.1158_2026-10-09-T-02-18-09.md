**Summary.** Running the authors' released per-model scripts reproduces **the numbers in Table 2** (3 backbones × 3 tasks ×
{SFT baseline, EyeMulator}, 60 numbers): 52/60 are within tolerance and the rest have the paper's sign of improvement.
The released pipeline yields the large "EyeMulator" gains the paper reports (+30–40 CodeBLEU/H-Exact on completion,
+11–34 CodeBLEU on translation, +16–22 BERTScore on summarization).

**However, the released code does not implement the method the paper describes, and the comparison behind Table 2 is
confounded.**
1. The training code that produced these results has **no token-level DPO term and no pseudo-scan-path generation**.
   The "gaze weight" is a **single per-example scalar (≈3.0–4.2, sd ≈0.15)** applied uniformly to all target tokens.
   Under AdamW this is close to a constant loss rescale.
2. The "Standard SFT" baseline is trained and decoded differently from EyeMulator in ways unrelated to gaze:
   - Its EOS label is masked (pad = EOS with `DataCollatorForLanguageModeling`), so it never learns to stop.
   - Its loss covers the prompt.
   - It uses a different prompt template and LR schedule.
   - At evaluation it is decoded with **sampling (T=0.6, top-p 0.9, repetition penalty 1.15) and a 128-token cap**, while
     EyeMulator is decoded **greedily with 512 tokens**.
3. **Control C2 (ours):** we ran the released EyeMulator training script with every gaze weight set to 1.0 (i.e. standard
   SFT in the same pipeline, no gaze information) and evaluated it with the same protocol. Over all 30 metric cells,
   **EyeMulator − C2 = +0.03 points on average** (median +0.22; 22/30 within ±1 point; range −13.7 to +8.6, with the
   extremes on the noisy completion H-Exact). The paper's claimed gains average +24.9 (range +3.6 to +43.9), and the
   released baseline reproduces them (+24.3). The reported gains therefore come from the baseline/eval confounds, not
   from mimicking human attention. The paper's central causal claim ("gains stem directly from replicating human attention dynamics")
   is not supported by the released code.

**Why MIXED (→ PARTIALLY_REPRODUCED) rather than NUMBERS_MATCH:** the paper's reported numbers reproduce, but the effect the paper attributes to the method (EyeMulator vs 'Standard SFT on the same data without gaze weights') does not. When the gaze weights are switched off inside the released EyeMulator pipeline (control C2), the improvement disappears. Both result-match fields are the same because no source logic was edited: the main runs use the released scripts with configuration-only edits, and C2 monkey-patches the weight function from outside the repo. Flag BASELINE_STRONGER_THAN_REPORTED: the 'Standard SFT' baseline described in the paper, run through the released pipeline (C2), is far stronger than the Table 2 baseline row (see the extra comparison rows in status.json).

## Discrepancies

1. **[code_vs_paper, severity **major**; affects results: True]** *src/training/train_{llama,deepseek,starcoder}_eyemulator.py (and train_unified.py)*  
   Paper: Sec. 2.4 / Alg. 1: composite objective L = L_SFT + gamma*L_DPO (gamma = 0.1), with a token-level DPO term that prefers the pseudo-scan path over its complement; pseudo-scan paths are re-generated per batch by sampling rho ~ Beta(alpha_agg, beta_agg) and greedy n-gram matching.  
   Code/other: The training scripts behind the results use only a weighted cross-entropy (Trainer + custom forward). There is no DPO/preference term, no reference model, and no per-batch pseudo-path sampling; the precomputed 'mask' field of the jsonl is used. A DPO-style term exists only in the non-executed reference template example/weighted_sft_template.py, whose own comment says the precomputed mask 'is what our small-scale runs did'.
2. **[code_vs_paper, severity **major**; affects results: True]** *train_*_eyemulator.py: preprocess_and_weigh / calculate_weight*  
   Paper: Per-token weights w_j = w_base + 1/log(freq(g_j)+2) + E[theta_{s_j}] for each (sub)token j (AST-level weights projected to BPE shards), scaling each token's CE term.  
   Code/other: A single scalar per example, max_j w_j over the INPUT code tokens, is applied uniformly to every OUTPUT (target) token; prompt tokens are masked. Measured on the released train splits, this scalar is 3.0-4.2 (mean 3.40/3.24/3.29, sd 0.19/0.13/0.12 for completion/translation/summarization). It is effectively a near-constant loss rescale, which AdamW largely normalises away, so there is no token-level salience signal.
3. **[code_vs_paper, severity **minor**; affects results: True]** *train_*_eyemulator.py: calculate_weight (base_weight)*  
   Paper: Table 5: base token weight w_base = 1.0  
   Code/other: base_weight = 3.0 (unmasked tokens get 1.0)
4. **[code_vs_paper, severity **major**; affects results: True]** *train_*_baseline.py vs train_*_eyemulator.py (training recipe of the 'Standard SFT' baseline)*  
   Paper: Sec. 3: Standard SFT baseline is 'fine-tuned on the same data without gaze weights'; App. B.2: identical hyper-parameters for all runs, so the only difference should be the gaze weights.  
   Code/other: The baseline differs from EyeMulator in more than the weights. (i) It uses DataCollatorForLanguageModeling with pad_token = eos, so every EOS label is set to -100 and the baseline never learns to stop; EyeMulator keeps the EOS label. (ii) The baseline computes loss on the whole prompt+answer, EyeMulator only on the answer. (iii) The prompt templates differ ('### Java Code:/### C# Code:' vs '### Input Code:/### Output:'). (iv) The LR schedules differ (baseline cosine with 3% warm-up; EyeMulator HF-default linear without warm-up). (v) The StarCoder baseline pads every sequence to 1024.
5. **[code_vs_paper, severity **major**; affects results: True]** *src/evaluation/eval_*_baseline.py vs eval_*_eyemulator.py*  
   Paper: Table 2 compares EyeMulator against the baseline on the same benchmark; no difference in decoding is described.  
   Code/other: The two arms are decoded differently. The baseline uses do_sample=True, temperature 0.6, top_p 0.9, repetition_penalty 1.15 and max_new_tokens = 128. EyeMulator uses greedy decoding with max_new_tokens = 512. The 128-token cap truncates long completion targets, and sampling plus the repetition penalty hurt exact match.
6. **[code_vs_paper, severity **minor**; affects results: True]** *src/evaluation/eval_*_eyemulator.py (prompt) vs train_*_eyemulator.py*  
   Paper: n/a (prompting not described)  
   Code/other: EyeMulator models are trained with the '### Input Code:' / '### Output:' template but evaluated with the baseline's '### Java Code:' / '### C# Code:' / '### Summary:' / '### Completion:' template (comment says 'Must match training').
7. **[code_vs_paper, severity **major**; affects results: True]** *src/analysis/cross_task_evaluation.py, src/compute_metrics.py: crystalbleu()*  
   Paper: App. A.1.1: CrystalBLEU is a BLEU variant that ignores the top-k most frequent 'trivially shared' n-grams of the training corpus.  
   Code/other: 'CrystalBLEU' is computed as sacrebleu.corpus_chrf(preds, [refs], word_order=2), i.e. chrF++. The released crystalbleu package is pinned in the environment file but never used.
8. **[code_vs_paper, severity **minor**; affects results: True]** *src/evaluation/eval_*.py: DATA_FILE; corpus/data*  
   Paper: Sec. 3: translation uses the standard split of 10,300 training and 500 test pairs; results are on the test set.  
   Code/other: The legacy eval scripts score the *valid* split (translation 431, completion 1,005, summarization 518). corpus/data has 8,701 translation training pairs, 431 valid and 836 test. The Table 2 numbers correspond to the valid split (e.g. the released paper_results/rq4_ablation_metrics.json gives DeepSeek translation 65.661 = 283/431, the Table 2 H-Exact).
