# Reproduction report: 2026.acl-long.2036
**The Bitter Lesson of Diffusion Language Models for Agentic Workflows: A Comprehensive Reality Check** (Lu et al., ACL 2026)

## Verdict
- **Verdict: PARTIALLY_REPRODUCED**
- **Result match (after our additions): MIXED** — the headline claims hold qualitatively: dLLM backbones collapse on embodied tasks (Table 1), no dLLM solves any BFCL multi-turn case, dLLMs make about 2× more retry loops (Fig. 3), and dLLMs work about as well as the AR LLM as memory modules (Table 3). But several specific numbers and orderings differ:
  - With our reconstruction of the unreleased dLLM server, **LLaDA-8B and DVar-8B beat Ministral-8B on BFCL single-turn non-live** (61.0 / 58.3 vs 50.0; paper 23.0 / 35.0 vs 49.8). LLaDA also beats Ministral on Live-simple and Live-multiple.
  - Qwen-as-memory comes out best in our Table 3. The paper has every dLLM memory module ahead of it.
  - Dream fails completely as a tool-call editor (0 vs paper 13.0).
  - The AR baselines are 4–10 points lower than the paper on AlfWorld and BabyAI.
- **Result match as released: DOES_NOT_RUN** — the release has no dLLM backend. Every dLLM experiment, which is the subject of the paper, needs an HTTP server that is not in the repo. The AR-only parts did run with no source edits.
- **Coverage: SCALED_DOWN**
  - Table 1: the dLLMs got 1 run instead of 3 (the AR models got 3).
  - Tables 2 and 3: full scale. Table 3 lacks the "w/o" rows because the release has no config for them.
  - Table 10: the Qwen-8B agent only, Selector and Editor only. dLLM modules ran on a 40-sample subset (10 per multi-turn category) instead of 200, because of compute. The AR modules ran on all 200.
  - Not run: Figure 6 (early exit), Appendix D tables, the Ministral half of Table 10, and Selector+Editor.
- **Codebase completeness: MISSING_SCRIPTS** — the DiffuAgent agents, modules and clients are released and ran unmodified. The dLLM serving component ("Fast-dLLM served through FastAPI") is missing, and we had to write it from the paper's one-sentence description.

## What the paper claims (targets)

- **Table 1** (AgentBoard: AlfWorld 134 / ScienceWorld 90 / BabyAI 112 tasks, one-pass ReAct, 30 steps): dLLM backbones
  (LLaDA-8B, Dream-7B, Fast-dLLM-v2-7B "FdLLM", dLLM-Var-8B "DVar") get success rates < ~10 % and progress rates < ~20 %,
  far below the AR LLMs Qwen3-8B (non-thinking) and Ministral-3-8B.
- **Table 2** (BFCL-v3, ≤50 samples per category, 758 samples): dLLMs underperform the AR LLMs on single-turn and
  multi-turn tool calling; no dLLM solves any multi-turn instance.
- **Figure 3**: dLLMs show many more retry-loop failures than AR LLMs.
- **Table 3** (DiffuAgent, memory-augmented agents): with Qwen-8B / Ministral-8B as the acting agent, dLLMs used as the
  memory-summarisation module perform comparably to (often better than) the AR LLM as memory module.
- Table 10 / Figure 7 (BFCL multi-turn selector/editor ablation), Figure 6 (early-exit), Appendix D tables: secondary;
  not run (see "Not run").

## What the release contains / what we had to add

The repo (https://github.com/Coldmist-Lu/DiffuAgent) contains *overlay code* for AgentBoard (enhanced ReAct agents,
memory / early-exit mixins, enhanced tasks, prompts, modular configs, OpenAI-style and dLLM HTTP clients) and for BFCL
(DiffuAgent handlers incl. selector / editor, 52 model registrations, the v3 sample id list). It must be merged into
upstream AgentBoard and gorilla/BFCL (documented in the installation.md files; we followed them).

**Missing:** the dLLM backend. All dLLM experiments call an HTTP server (`/generate`, `/tokens`, `/models`) that the paper
describes only as "Diffusion LLMs (Dream-7B, Llada-8B, FdLLM-7B) are reproduced using NVIDIA Fast-dLLM and served through
FastAPI" (Sec. 3.3). No server code, decoding algorithm choice or per-model generation settings beyond the client-side
request fields (`gen_length`, `steps`, `block_size=32`, `threshold=0.9`, `dual_cache`, `temperature`) are released.
We wrote it (`scripts/dllm_multi_server.py`):
- LLaDA-8B-Instruct and Dream-v0-Instruct-7B: Fast-dLLM v1 code (NVlabs/Fast-dLLM, `v1/llada`, `v1/dream`),
  confidence-threshold parallel decoding (threshold 0.9), block 32, dual cache when the client asks for it, else prefix
  cache. For Dream we use `alg="confidence_threshold"` (the only Fast-dLLM Dream mode that uses the `threshold` field).
- Fast_dLLM_v2_7B: the model's own `generate` (block 32, small block 8, threshold 0.9, `use_block_cache=dual_cache`).
- dLLM-Var (maomaocun/dLLM-Var): the model's own `generate` (block 32, threshold 0.9, eos 126348).
- Output truncated at the first EOS/stop token, chat template applied.
- Two speedups that we verified to be **output-identical** to the Fast-dLLM originals (`scripts/test_equiv.py`: 0/24
  mismatches for LLaDA dual+prefix cache, 0/12 for Dream): stop after the first finished block containing a stop token,
  and compute the per-block warm-up proposals only on the current block (`scripts/llada_generate_fast.py`,
  `scripts/dream_generation_block_fast.py`).
- All four dLLMs are hosted in one process and requests are served one at a time (batch size 1) behind a single lock;
  separate processes on the single shared GPU suffered >10x slow-downs from CUDA context time-slicing (CUDA MPS is not
  usable inside this Slurm cgroup).

### Sensitivity check: Dream decoding mode (not in the paper)
The release does not say how Dream was decoded. We used Fast-dLLM's confidence-threshold parallel decoding, because the client sends `threshold=0.9`. In that mode Dream-Instruct almost always emits EOS after a few tokens. This explains our Dream scores of about 0 on BFCL and the 3-retries-per-step pattern in AlfWorld.

Re-running BFCL single-turn with Fast-dLLM's other Dream mode (`alg="entropy"`, one token per step) gives:

| Metric | Paper Dream-7B | Our threshold-mode Dream | Our entropy-mode Dream |
|---|---|---|---|
| Non-Live | 4.2 | 0.0 | 59.3 |
| Live S / M / P / PM | — | — | 62.0 / 38.0 / 56.2 / 29.2 |
| Live Avg | 1.5 | 0.0 | 46.4 |
| Rel. | — | — | 56.2 |
| Irrel. | — | — | 64.0 |

The paper's Dream sits between our two variants. The dLLM tool-calling numbers in Table 2 therefore depend strongly on decoding settings the release does not specify; LLaDA's high scores are the same issue. The paper's Figure 1 throughput for Dream (5 tok/s) suggests a non-parallel mode.

## Why it is not fully reproduced
1. **Missing dLLM server.** The decoding algorithm, cache mode, generation length and stopping are reconstructions. The sensitivity check shows that BFCL scores for dLLMs move by tens of points with the decoding mode. This most likely explains:
   - LLaDA and DVar being much stronger on BFCL than in the paper.
   - Dream and FdLLM differences on BabyAI and AlfWorld (Dream BabyAI SR 17.0 vs 8.9; FdLLM AlfWorld 12.7 vs 3.3 — the paper itself notes FdLLM's ±3.3 and that decoding changes matter).
2. **AR baselines are lower than reported.**
   - Our 3-run means: Qwen AlfWorld 69.2±1.5 vs 76.1, BabyAI 21.7±0.8 vs 32.1; Ministral AlfWorld 39.1 vs 45.5, BabyAI 26.2 vs 36.6.
   - We found no code difference to explain this. Serving details are not specified (vLLM version and sampling backend, Qwen non-thinking via chat-template flag, Ministral-3 text-only).
3. **BFCL v3 vs v4.** The release's handlers only run on BFCL v4, so the v3 sample was evaluated with v4 data and checker. 756 of 758 ids exist.
4. **Compute.** One shared H200 instead of one A800 per model. Batch-size-1 dLLM serving made the multi-agent ablation (Table 10) too expensive at full scale, so we ran a subset.

## Discrepancies
The first two are code vs paper; the last four are internal to the paper.

1. **Memory update schedule (code vs paper, minor).**
   - Paper (§5.1 and footnote 6): memory is updated every k_mem = 5 steps, keeping the last two interactions.
   - Code (`configs/base/agents.yaml`): `stored_memory_max: 12`, `update_num: 8` (2 items per step). The first update happens after 6 steps, then every 4 steps, and the last 2 steps stay raw.
   - Affects Table 3 slightly.
2. **BFCL version (code vs paper, minor).**
   - Paper: BFCL-v3.
   - Code: the DiffuAgent BFCL handlers use the BFCL v4 API. The README says "use the v3 codebase", which is not provided. 2 `live_relevance` v3 ids do not exist in v4, and v4 data and checker differ slightly.
3. **FdLLM fluctuation (paper-internal).** §4.1 says FdLLM-7B's success rate "shows a fluctuation of ±3.8%". Table 1 reports 3.3 ±3.3.
4. **"Below 2%" claim (paper-internal).** §4.3 says FdLLM-7B and DVar-8B have "average success rates below 2%". Table 1 gives FdLLM-7B an average success rate of 3.1.
5. **No-memory baselines (paper-internal).**
   - Table 1, one-pass ReAct with only recent history: Qwen-8B AlfWorld SR 76.1, Ministral 45.5.
   - Table 3 "w/o" (no memory, only recent interactions): 36.6 and 22.4.
   - Table 3 Qwen+Qwen-memory: 54.5.
   - These nominally comparable no-memory or Qwen settings differ by up to 40 points, with no explanation. In our runs the one-pass and Qwen-memory results agree (69.2 and 70.9).
6. **Retry-loop definition (paper-internal, minor).** The text defines a retry loop as "three or more consecutive repetitive actions". The Figure 3 caption says "more than 3 consecutive steps".
