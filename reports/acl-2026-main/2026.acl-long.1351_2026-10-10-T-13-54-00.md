## Paper claims targeted

Main result: Table 1 (IID, COMT and VSP, Qwen2.5-VL-7B and Qwen3-VL-8B), ILVR Stage 1 and Stage 2 rows. Of this, only **COMT × Qwen2.5-VL-7B** is runnable with the release:
- the data repo `shuai22/comt` contains only COMT;
- the checkpoint repo `shuai22/comt_ckpt` holds a stage-1 COMT model;
- the code only patches Qwen2.5-VL.

Table 2 (OOD: trained on a Zebra-CoT 10k subset, evaluated on EMMA, VisuLogic and held-out Zebra-CoT) needs the subset and test splits, which are not released. Its open-ended scoring also uses a Qwen2.5-VL-72B judge, which is open but its prompt isn't released. Not run.

## What we ran (exact commands)

Environment: conda env at `./env`, Python 3.11.
- `pip install -r requirements.txt` (torch 2.6.0+cu124)
- `torchvision==0.21.0`, which was missing from requirements.txt
- prebuilt `flash-attn 2.7.4.post1` wheel
- `pip install -e codebase/transformers` (the authors' modified transformers 4.50.0.dev0)
- `torchao==0.10.0`, needed for our single-GPU optimizer
- `CUDA_HOME=/sw/eb/sw/CUDA/12.6.0`, because `import deepspeed` fails without it

Data: downloaded `shuai22/comt` (TRAIN.jsonl 3450, TEST.jsonl 400, comt.tar.gz) and extracted it to `data/images_comt/`. All 3,850 samples' image paths resolve. TEST was split per subtask into `data/test_split/{creation,deletion,selection,update}_with_prompt.jsonl`, the layout `eval.sh` expects.

1. **Released checkpoint eval.** We downloaded `shuai22/comt_ckpt` (config `stage: stage1`, `latest` = global_step810; 810 = 54 steps/epoch × 15 epochs, matching 8 GPUs × grad-accum 8).
   - Command: `MODEL_DIR=ckpt/comt_ckpt OUTPUT_DIR=results/released_ckpt bash scripts/eval_comt.sh`, run from `data/`.
   - `scripts/eval_comt.sh` is the released `eval.sh` with its empty path variables filled in.
   - Settings: greedy decoding, max_new_tokens 4096, the released `eval.py` (task branch `zebra-cot`, exact match on "final answer"), forced K=8 latent tokens through the release's logits processor and generation code.
   - No source edits.
2. **Stage-1 training from scratch** (Qwen2.5-VL-7B-Instruct → ILVR stage 1 on COMT TRAIN):
   - Command: `EPOCHS=15 GRAD_ACCUM_STEPS=64 WARM_UP_STEPS=40 SAVE_STEPS=200 bash scripts/train_stage1.sh`.
   - The script is `run_training.sh` adapted to 1 GPU; it calls `src/main.py --stage stage1 --latent_size 8 --ce_weight 1 --sim_weight 1 ...`.
   - Grad-accum 64 on 1 GPU gives the same effective batch (64) as the authors' 8 GPUs × 8. lr 1e-5, weight decay 0.01, seed 42, λ_sim=1, K=8 (code defaults).
   - 795 optimizer steps = 14.75 epochs (HF drops the remainder batch on 1 GPU; the authors had 810).
   - Wall-clock 17.3 h. Evaluated as in step 1.
3. **Stage-2 training** (latent relaxation: the hidden state is fed back recursively at latent positions, text-only CE):
   - Command: `STAGE=stage2 MODEL_NAME=ckpt/comt_ckpt_bf16 SIM_WEIGHT=0 EPOCHS=2 GRAD_ACCUM_STEPS=8 WARM_UP_STEPS=43 SAVE_STEPS=108 STAGE2_NO_TEACHER=1 STAGE2_NESTED_GC=1 bash scripts/train_stage1.sh`.
   - Starting point: the released stage-1 checkpoint, converted to bf16 safetensors (see "Changes"). We chose it because it matches the paper's stage 1, so this run tests stage 2 alone.
   - Effective batch 8, matching Table 7: grad-accum 1 × 8 GPUs.
   - **Only 2 epochs instead of 15**: stage 2 runs one full prefix forward per latent token, ~63 s per 8 samples on one H200, so 15 epochs would take ~110 h.
   - Wall-clock 15.2 h. We evaluated checkpoints at 0.25 epoch, 1 epoch and the final 2 epochs.

### Settings that differ from the paper
- **Hardware:** 1×H200 instead of 8×H200. DeepSpeed ZeRO-3 with an fp32 AdamW and an EMA teacher copy does not fit one 141 GB GPU for a 7B model.
- **Optimizer, our main deviation:** DeepSpeed was disabled and torchao `_AdamW` used instead. It keeps bf16 params and bf16 Adam moments, with bf16 stochastic rounding; lr, betas, eps and weight-decay groups are the same. The paper/DeepSpeed setup uses fp32 master weights and fp32 moments. This may explain part of the stage-1 gap.
- **Warmup:** 40 steps (stage 1) and 43 steps (stage 2). The release leaves `WARM_UP_STEPS` blank; the paper says only "moderate warmup ratio".
- **LR schedule:** linear, the code's default (the paper says cosine; see Discrepancies).
- **Stage 2:** 2 epochs instead of 15, started from the released stage-1 checkpoint rather than our own.

## Why it isn't fully reproduced
1. **Missing data (release):** no processed VSP trajectories, no Zebra-CoT 10k subset, no OOD test splits or judge prompts. The Table 1 VSP column and all of Table 2 can't be run. The Qwen3-VL-8B backbone isn't supported by the code.
2. **Compute:** the paper used 8×H200 with ZeRO-3. On one H200 we had to change the optimizer precision (bf16 moments plus stochastic rounding). Stage 2 at the paper's 15 epochs (~110 h) didn't fit the 48 h budget, so we ran 2 epochs.
3. **No baseline code:** the comparisons with Zero-shot, Direct-FT, CoT-FT and Mirage can't be re-run.

## Codebase completeness: MISSING_DATA (+ PARTIAL_DATA)

The method (stage-1 teacher selection with alignment loss, stage-2 recursive latents, latent-mode generation) is implemented, and the training and eval scripts exist for stage 1. The levels below MISSING_DATA would be MINOR_FIXES (paths, environment) plus a missing stage-2 script.

Changes we made to the released code (all left uncommitted in `./codebase`; full diff in `logs/codebase_changes.diff`):
- `src/task_deepseed.py`: `TRAIN_IMAGE_ROOT` was hard-coded to `/mnt/public/...`; it can now be overridden with env `ILVR_TRAIN_IMAGE_ROOT`. Path fix.
- `src/main.py`, compute only, all behind env flags:
  - `ILVR_NO_DEEPSPEED=1` disables the hard-coded `configs/config_stage3.json`;
  - `ILVR_TORCHAO_OPTIM` sets `trainer.optimizer` to a torchao `_AdamW`/`AdamW8bit` with the same hyperparameters and weight-decay groups, plus bf16 stochastic rounding. We only used `_AdamW`; the 8-bit run OOM'd for other reasons and was discarded;
  - `ILVR_STAGE2_NESTED_GC=1` sets `gradient_checkpointing_kwargs={"use_reentrant": False}`.
- `src/trainer.py`, speed only, same results:
  - the teacher forward (identical inputs) ran once for the user-side pooling and once per latent segment; it now runs once and the output is reused;
  - the student's no-grad vision pass over helper images, whose output is discarded (only needed for ZeRO-3 gathering), is skipped when DeepSpeed is off.
- `src/trainer.py`, stage 2 only, same results: `ILVR_STAGE2_NO_TEACHER=1` skips the EMA teacher. With `sim_weight=0`, every latent input embedding is overwritten by the recursive hidden state before it is read, so teacher latents have no effect. This saves 16.6 GB.
- `transformers/.../modeling_qwen2_5_vl.py`, stage 2 memory only: with `ILVR_STAGE2_NESTED_GC=1`, `latent_step_forward` keeps per-layer gradient checkpointing inside its outer checkpoint. Without this, one recompute of a ~16k-token deletion sample OOMs on 141 GB. Also added `import os`.
- No change to the method, losses, data processing or evaluation logic.

- The README says `DATA_PATH` is a directory, but `main.py` loads it as a jsonl file.
- `run_training.sh` leaves `WARM_UP_STEPS`, `SAVE_STEPS`, `DATA_PATH` and `HF_HOME` empty; `eval.sh` leaves all of its paths empty.

## Discrepancies

1. **code_vs_paper, major (`src/trainer.py`): the EMA teacher is never updated.**
   - Paper: the teacher is a momentum model with τ=0.999.
   - Code: the EMA update sits in an `optimizer_step` override that neither HF `Trainer` nor TRL `SFTTrainer` ever calls, so the "momentum teacher" is a frozen copy of the initial model.
   - The released checkpoint was presumably trained with this code; our runs keep the released behaviour.
2. **code_vs_paper, major (`_teacher_build_latents`): the teacher query uses a shorter history than Eq. 4.**
   - Paper: q_i averages u, the text hidden states of *all* steps 1..i, and the latents of *all* steps 1..i−1.
   - Code: it uses only the current step's text span and only the previous segment's selected features.
3. **code_vs_paper, minor: selection rule.** The paper says top-K. The code takes a softmax over cosine similarities, applies a top-p cutoff at p=0.9, then caps at K. In practice this almost always gives K.
4. **code_vs_paper, minor: LR schedule.** The paper says cosine; the code uses the HF default linear schedule (`lr_scheduler_type` is never set).
5. **code_vs_paper, minor: group size L.** The paper says L=784; the code default is `helper_group_L=256` and no script overrides it.
6. **code_vs_paper, minor: noise on the alignment target.** The code adds Gaussian noise (σ=0.01) to the alignment target; the paper doesn't mention it.
7. **code_vs_paper, minor: no stage-2 entry point.** Stage 2 has no script, and with `--stage stage2` the alignment loss stays on unless `--sim_weight 0` is passed. The paper says stage 2 removes it.
8. **paper_internal: Table 2 "Total" doesn't match any average we can compute.** It is neither the mean of the three benchmark averages (ILVR S1: 33.8 computed vs 34.8 reported; S2: 36.8 vs 37.5) nor the mean over the 9 subtasks, and the paper states no weighting. This doesn't affect our target.

Not discrepancies: Table 1's averages and the in-text deltas (+4.8, +5.5, +5.2, +4.5, +3.2, +8.0, +5.9) are arithmetically consistent.
