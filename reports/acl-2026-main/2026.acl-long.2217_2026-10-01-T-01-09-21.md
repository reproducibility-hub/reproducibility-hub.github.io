## 2. Setup and exact commands

* Conda env `env/` (Python 3.11): `vllm==0.10.2` (pulls torch 2.8.0), `transformers==4.56.2`, `huggingface_hub<1.0`, `datasets==4.1.1`, `dspy==3.4.0`, `spacy` + `en_core_web_sm`, `nltk` (punkt), `accelerate`, `scipy`, `pandas`. The repo has **no requirements file**, so these versions are my choice.
* Judge: `python -m vllm.entrypoints.openai.api_server --model openai/gpt-oss-20b --port 7502 --gpu-memory-utilization 0.40 --max-num-seqs 128`. The README offers SGLang or vLLM; the paper used SGLang on 2×A6000.
* Data: ARC-Easy and OpenbookQA come from HF (`allenai/ai2_arc`, `allenai/openbookqa`), as the code does. StrategyQA `data/strategy_qa/{dev,train}.json` is **not shipped and not documented**. I used the official StrategyQA repo's split (`eladsegal/strategyqa`, `data/strategyqa/dev.json` = 229 questions, which matches the paper's Total = 229).
* Models: `meta-llama/Meta-Llama-3-8B-Instruct` (as in the config). `meta-llama/Llama-3.2-3B-Instruct` and `google/gemma-3-4b-it` are gated for this account (HTTP 403), so I used the public re-uploads `unsloth/Llama-3.2-3B-Instruct` and `unsloth/gemma-3-4b-it` (config edit). Their safetensors shards have exactly the same byte sizes as the gated originals; the gated repos hide hashes, so identity is not fully verifiable.
* Each job is exactly the command from the repo's `scripts/*.sh`, one job at a time (`run_bf_job.sh`, `run_post_job.sh`, `run_fur_job.sh` in this directory):
  * BF: `python biasing_instructs.py --model-config configs/<M>.json --dataset <D> --results results/bf_results/<D>_<M>_biasing_inst_<H>.json --bias-pattern <H> --bias-kwargs university_name=Stanford`
  * Filler Tokens: `python filler_tokens_analysis.py ... --only-unfaithful-ones`
  * CMA: `python hinted_cot_effect.py ...`
  * faithful@k: `python biasing_instructs_sampling.py ... --num-samples 128 --k-list 1 2 4 8 16`. For subsets, `--records-file` points to a seed-0 random subset of the BF records file.
  * FUR: `python parametric_faithfulness.py ... --fur-config configs/fur_<D>_<M>.json --only-unfaithful-ones` (released learning rates). For subsets, `--records-file` is a seed-0 random subset of the BF-unfaithful records that have matching CoT/no-CoT predictions and a non-empty CoT, which is the same "usable" filter the code applies.
* Aggregation: `aggregate.py` and `make_tables.py` (mine) compute the paper's quantities from the released scripts' outputs. FUR faithfulness uses the code's own definition (`utils/parametric_stats.instance_changed_prediction`: an instance is faithful if the no-CoT prediction flips at any unlearning epoch of any step).

### Settings that differ from the paper
* **Scale reductions:** faithful@k on subsets (StrategyQA full; OBQA/ARC Professor only, 150 random records each; Metadata/Black Squares StrategyQA only). FUR on random subsets of 20–30 usable instances for the larger settings (each row shows the evaluated n). Reason: on one shared H200, faithful@k (128 samples × 300 tokens per record, plus up to 128 high-reasoning judge calls) ran at roughly 30–70 s per record, and FUR at roughly 30–60 s per unlearning step. The full grid would take several GPU-days; the paper reports "several hours to multiple days, ... exceed one week".
* **Batched greedy CoT generation** (`GEN_BATCH_SIZE=32`, left padding) instead of the code's batch size 1, for speed. Greedy decoding is the same, but padded bf16 batching can flip a few near-tie tokens, so the BF records are not bit-identical to batch-1 runs.
* Judge served with vLLM instead of SGLang. DSPy 3.4 sends no temperature (server default) where DSPy ≤3.0.3 sent `temperature=0.0, max_tokens=4000`. I re-judged gemma/OpenbookQA/Professor with temperature 0: 159 vs 155 unfaithful, 209/273 labels identical, so this is not the cause of the gemma/Professor gap.
* Section 7 models, Logit Lens and the Appendix D strict subset were not run.

## 5. Codebase completeness: MINOR_FIXES

The repo ships the method and an experiment script for every section. I needed only environment, config and robustness fixes; none of them changes the method, prompts, metrics or evaluation logic. Every source edit is marked `[repro]` and left uncommitted in `./codebase` (`git diff`).

Problems in the release:
* No `requirements.txt` or environment file. Versions are unpinned and DSPy's `dspy.LM` default temperature changed across versions (see above).
* `data/strategy_qa/{dev,train}.json` is hard-coded but neither shipped nor documented. I took them from the official StrategyQA repo (229 dev questions, matching Table 1).
* README install line (`python -m spacy download` with no model) is incomplete. FUR needs `en_core_web_sm` plus NLTK punkt.
* `biasing_instructs.measure_faithfulness` raises `ZeroDivisionError` (`q/(N-2)` with N=2) for StrategyQA. This happens after the results JSON is written, so it is harmless for the outputs.
* `hinted_cot_effect.py` crashes (`torch.vstack` on an empty list) when no eligible instance exists (Llama-3-8B / StrategyQA / Black Squares: 0 of 43). The paper also excludes that cell.
* FUR (`utils/parametric_utils.cot_to_otfd`) samples 4 other CoTs as the retain set, so it raises `ValueError: Sample larger than population` when a setting has fewer than 5 usable instances. This is why Llama-3-8B Black Squares (3 / 4 / 1 usable instances on StrategyQA / ARC / OBQA; the paper had 4 / 5 / 0) has no FUR row. These are the only 3 of 27 FUR cells missing.
* `scripts/search_hyperparam_pf.sh` always uses `configs/fur_strategy_qa_llama-3.2-3b.json` as the base config (lr is overridden). This is minor and I did not run it.

Edits I made to the released code:
1. `configs/llama-3.2-3b.json`, `configs/gemma-3-4b.json`: model id switched to the ungated `unsloth/...` re-uploads (no access to the gated repos).
2. `utils/parametric_utils.py`: added the two `unsloth/...` ids to `WHITESPACE_CHARS`, with the same values as the originals. Needed because of edit 1.
3. `model.py` (`Engine.generate` / `get_cot_explanations`): optional batched greedy CoT generation via env `GEN_BATCH_SIZE` (default 1 = original behaviour), plus stripping of right-padding tokens in batched decoding. Without that stripping, gemma's `<pad>` (id 0) survives `_clean_eot` because of the code's `if pad_token_id` check. Speed only.
4. `biasing_instructs.py`: (a) `dataset.map(..., new_fingerprint=uuid)`. Without it `datasets` dill-hashes a lambda that captures the whole Engine/model, which transiently used ~80 GB of host RAM and caused cgroup OOM kills. (b) The per-instance `judge_cot` calls run in a thread pool (env `JUDGE_THREADS`, default 1). Same calls, speed only.
5. `judge.py`: thread count of `judge_cot_batch` configurable via env (default 4 = original), and an eager `import litellm` (DSPy's lazy import races when called from threads: "partially initialized module 'litellm'").

Scripts I wrote outside the repo, in the attempt directory: `run_bf_job.sh`, `run_post_job.sh`, `run_fur_job.sh` (single-job equivalents of `scripts/*.sh`, plus seed-0 random subsetting), the GPU-memory-aware schedulers `fk_sched*.sh` and `fur_sched*.sh`, `aggregate.py` and `make_tables.py` (compute the paper's tables from the outputs), and `rejudge_temp0.py` (judge-temperature ablation).

`result_match_as_released`: the unmodified code computes the same quantities. My edits only change speed, memory and thread-safety, plus model ids that are interchangeable for this account. I did not separately re-run the fully unmodified, sequential code (it needs roughly 10 h per ARC setting at batch size 1), so the as-released level equals the after-fix level.

## 6. Discrepancies

* **code_vs_paper (major, affects results): Black Squares hint.** §2/§3.1 says the hint marks "the correct answer with black squares in the few-shot demonstrations **as well as marking the suggested answer in the main example**". In `biasing_instructs.Evaluator.create_hint`, `formatted_question.replace(choice_line, f"{choice_line} ⬛")` discards its return value, so the target question is never marked. The hint is only the four ⬛-marked demonstrations. Because the target question carries no mark, the hint contains no information about which label is the "hinted" one. Flips to the (randomly drawn) hinted label are driven by the demonstration context plus chance, not by a cue the CoT could verbalize. Our Black Squares rows match the paper's (e.g., gemma ARC 74/74 vs 69/69 changed/unfaithful), which suggests the paper's numbers were produced with this same code.
* **code_vs_paper (minor): faithful@k k-range.** Fig 13 / Appendix A report k up to 32, but `scripts/run_biasing_sampling.sh` uses `--k-list 1 2 4 8 16`, so instances are filtered on n ≥ 16 and k=32 is never computed. I report k=32 post hoc on instances with n ≥ 32.
* **code_vs_paper (minor): judge configuration not pinned.** The paper says gpt-oss-20b via DSPy. The code passes `reasoning_effort=high` but no temperature or max_tokens, so the effective sampling depends on the unpinned DSPy version. Temperature 0 vs default made no material difference here (159 vs 155 unfaithful).
* **paper_internal (minor): "at least 80%".** §3.2 says "at least 80% of instances are classified as unfaithful" for all settings, but Table 1 gives gemma-3-4b / OpenbookQA / Professor = 233/292 = 79.8%.

## 7. Notes on the main deviation (gemma + Professor)

The only systematic mismatch is BF unfaithfulness for gemma-3-4b with the Professor hint: 0.55–0.58 vs the paper's 0.80–0.83. Generation is not the cause: the "Changed" counts match (1408 vs 1427, 273 vs 292, 99 vs 102). gemma mentions "Stanford professor" in 247/273 hint-flipped OBQA CoTs, and the gpt-oss-20b judge splits those borderline cases ("The Stanford professor's opinion aligns with this understanding") differently from the paper's run. Judge temperature is not the reason. The paper itself reports low judge precision/recall (36%/31%) against humans, so this metric is noisy across serving stacks. Downstream, this gap only changes which and how many CoTs enter the Filler Tokens / FUR / CMA pools for gemma-Professor. The rates measured on those pools still match the paper (Filler Tokens ARC 0.443 vs 0.450, OBQA 0.135 vs 0.146, SQA 0 vs 0).
