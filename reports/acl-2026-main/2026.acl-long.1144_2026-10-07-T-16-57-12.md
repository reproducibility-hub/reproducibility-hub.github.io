# Reproduction report — FOREVER: Forgetting Curve-Inspired Memory Replay for Language Model Continual Learning (ACL 2026, 2026.acl-long.1144)

Code: https://github.com/WoodScene/FOREVER (linked in the paper, footnote 1). Commit `bbeb549`.

## Verdict

| Field | Value |
|---|---|
| **Verdict** | **PARTIALLY_REPRODUCED** |
| Result match (after my fix) | **MIXED**: OP reproduces on all three benchmarks and BWT on Standard CL and Long Sequence. On SuperNI, BWT is much worse (−5.6 vs −2.9) once the replay buffer actually holds 2% of past data, as the paper says. |
| Result match as released (no source edits) | **NUMBERS_MATCH**: all six Table-1 FOREVER numbers are within tolerance. SuperNI only matches because of a sampler bug that replays 100% of past training data. |

| Codebase completeness | **MAJOR_FIXES**: a one-block bug in the replay-buffer sampler changes the SuperNI results. Other issues are path/config level. |

**Bottom line**
- The released FOREVER code, run with the authors' own script settings, reproduces the Table 1 FOREVER row:
  - Standard CL: 72.86 / −4.53 vs 72.9 / −4.7
  - Long Sequence: 68.83 / −5.73 vs 69.4 / −5.0
  - SuperNI: 42.00 / −2.99 vs 42.1 / −2.9
- On SuperNI (12 of 15 tasks are generation tasks), `load_memory_buffer` samples "one example per distinct output string". Almost every output is unique, so the "2% memory buffer" contains the **entire** training set of every earlier task: 7,343 samples vs 212 by the last task of order 7.
- With the buffer capped at the 2% the paper specifies, SuperNI OP is roughly unchanged: 41.55 vs 42.1. BWT degrades to −5.64 vs −2.9.
  - That is worse than the paper's reported SuperNI BWT for VBM (−3.7), AIMMerging (−3.4), Recurrent-KIF (−5.0) and SSR (−5.4). It is better only than SAPT (−6.2) and the weaker baselines.
  - So the paper's claim of best BWT on SuperNI does not survive the fix. I only compare against the paper's own baseline numbers here, because no baseline code is released.

## Why it is not fully reproduced
- The released replay-buffer sampler (`utils/load_data.py::load_memory_buffer`) samples `max(1, num_samples // num_classes)` examples per distinct `output` string.
  - For generation tasks, almost every output is distinct, so `num_classes ≈ len(task)`. It selects one example per output, i.e. the whole task.
  - The memory buffer therefore grows to 100% of all earlier SuperNI tasks (160 / 2,203 / 7,343 samples at tasks 1 / 5 / 14 of order 7, versus 3 / 69 / 212 with the 2% cap). This contradicts §3: "we store 2% of the original training data from each task".
  - It also makes SuperNI training ~10× slower: ~18 h per order as released vs ~2.5 h fixed.
- The paper's SuperNI numbers (Table 1, Table 2, Tables 3/5/6/7 for order 7) are reproduced only with this bug.
  - With a real 2% buffer, BWT drops by ~2.7 points. The improvement over VBM/AIMMerging claimed in Table 1 / Figure 3 no longer holds on SuperNI, based on the paper's reported baseline numbers.
  - I cannot tell whether the paper's own baselines were run with the same sampler (no baseline code is released). If they were, the relative comparison in the paper could still be internally consistent, but the "2% memory" description would be wrong for all SuperNI rows.

## Codebase completeness: MAJOR_FIXES
Changes to the released code (left as uncommitted diff in `./codebase`):
1. `utils/load_data.py::load_memory_buffer`: after per-"class" sampling, cap `sampled_indices` at `num_samples` with `random.sample`. This fixes the 100%-buffer bug on generation tasks. **Affects SuperNI results**: no-op for classification, changes SuperNI BWT by ~2.7 points.

Things done without editing source (counted as config/path fixes):
- The train/generate/eval scripts assume a flat `/workspace` layout and mutually inconsistent working directories:
  - `templates/` is resolved relative to the cwd.
  - `utils` must be importable.
  - `../data_superni` is hard-coded in `generate_*.py` even for the Long Sequence data.
  - Evals read `../output/<name>`.
  
  I ran from `sn/run` or `ls/run` directories with symlinks (`templates`, `utils`, `../data_superni`, which for Long Sequence points at `data_longsequence`), plus `PYTHONPATH=codebase`.
- `scripts/*.sh` call `finetune_cl_ours_qwen.py`, but the file is `finetune_cl_our_qwen.py`. They also hard-code `/workspace/...` paths and `CUDA_VISIBLE_DEVICES`. I re-implemented them in `run/run_order.sh` with the same arguments.
- `finetune_cl_our_qwen.py` sets `TRANSFORMERS_CACHE=/workspace/CL_Memory/cache` and `cache_dir=/workspace/...`. Harmless when `--base_model` is a local path; I passed `--cache_dir`.
- Checkpoint and output directory names are built from `basename(base_model)`. With an HF snapshot path, this becomes the snapshot hash (`c1899…lora_cl_dataset_id_X`). It is consistent across train, generate and eval, so nothing breaks.
- Eval scripts have defaults that do not match the training outputs (`service_end_id=2`, `method_name=vanilla`). I passed `--service_end_id 14` and the correct `--test_data_name*`.
- No seed argument (`set_seed(42)` hard-coded) although the paper averages 3 runs. For seeds 43/44 I used a copy of the training script with an env-var seed (`run/seedpkg/finetune_cl_our_qwen.py`); this is outside the codebase.

Scripts I wrote, all in `run/`:
- `common.sh`, `run_order.sh` (+ variants `_fix`, `_seed`, `_seedorig`, `_seedrel`, `_paperhp`, which differ only in PYTHONPATH, training-script path or hyper-parameters)
- `eval_all.sh`, `summarize.py`, `st.sh`
- `fixpkg/` (fixed loader copy), `origpkg/` (pristine loader copy), `seedpkg/`

## Discrepancies
Code vs paper:
1. **major**, `utils/load_data.py::load_memory_buffer`. Paper: "store 2% of the original training data from each task". Code: on generation tasks it stores 100% (one sample per unique output string). Affects SuperNI results (BWT −2.9 → −5.6 when fixed).
2. minor, `scripts/run_train_cl_ours_qwen.sh`. Paper (App. H): batch size 8. Script: `--batch_size 32` (micro 4 × 8 accumulation steps). Affects results (see `paperhp`).
3. minor, `scripts/run_train_cl_ours_qwen.sh`. Paper: "each new task is trained for 10 epochs". Script: `--first_task_epochs 60` for the first task.
4. minor, `finetune_cl_our_qwen.py` default `lora_alpha=16`, not overridden by the script. Paper (App. H): α=32.
5. minor, end-of-task consolidation. Algorithm 1 line 23: "one short epoch". Code: `memory_epochs` (=2) epochs.
6. minor, number of runs. Paper: "averaged over three independent runs". Code: hard-coded `set_seed(42)` with no option to vary it.
7. minor, γ in Eq. 10: no value given in the paper. Code: `beta_scale=1.0`; β_base = 1e-3 is implemented as `0.001*beta_t` with `beta_base=1.0`, which matches the paper. Noted only for completeness; not counted.

Paper-internal:
1. §3 and App. G: Standard CL has "five text classification tasks" (AG News, Amazon, Yelp, DBpedia, Yahoo). Table 14 orders 1-3 (and the code) use 4 tasks without Yelp.
2. App. B.3: the text says the S-sensitivity results are "on the SuperNI benchmark (task order 4)", but the Table 6 caption says task order 7, and order 4 is a Long Sequence order.
