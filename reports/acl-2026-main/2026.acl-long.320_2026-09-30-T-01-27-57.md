The CoT (Sampling) baseline reproduces the paper's Qwen3-8B numbers well: 4 of 5 benchmarks and the average are within tolerance. SeLaR's central claim does **not** reproduce. The paper reports +3.88 average over CoT, driven by +6.7 on AIME24 and +13.3 on AIME25. With the released code I get the opposite:

- **Averages (seed 41):** SeLaR averages 74.53 against CoT's 78.97.
- **AIME, two seeds each:** SeLaR averages 68.3 vs CoT 73.3 on AIME24, and 60.0 vs 71.7 on AIME25.

I found and fixed a real bug in the released SeLaR: soft embeddings are gated per *batch*, not per sample. The fixed version does no better than CoT either (AIME24 70.0; AIME25 70.0 and 66.67 on seeds 41/42, against CoT 70.0 / 73.3).

## What I ran

- **Code:** https://github.com/Parker-rfu/SeLaReasoning (linked from the paper), cloned into `./codebase`. A pristine copy, `./codebase_released`, was used for every "as released" run.
- **Environment:** conda env at `./env` with Python 3.12, torch 2.7.0+cu128 and transformers 4.51.0. Versions follow `requirements.txt`, plus `math-verify` and `latex2sympy2_extended`, which the grader imports but `requirements.txt` doesn't list.
- **Model:** Qwen/Qwen3-8B, bf16, one H200.
- **Settings:** taken from the paper. Decoding uses T=0.6, top-p 0.95, top-k 20 and min-p 0 (the `run.py` defaults). SeLaR uses k=3 with the App. B per-dataset thresholds: τ=0.6 for GSM8K, 0.5 for MATH500, 0.7 for GPQA, 0.4 for AIME24 and 0.5 for AIME25. `max_new_tokens` is 32768 (38912 for AIME, matching the authors' released result filenames). Seed is 41, the `run.py` default, plus an extra seed 42 on AIME. Datasets are the ones shipped in `codebase/datasets` (GSM8K test 1319, MATH500 500, GPQA-Diamond 198, AIME24 30, AIME25 30).
- **Command (per dataset):**
  ```
  cd codebase_released   # or codebase (fixed) / codebase_released_s42 / codebase_fix_s42
  PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True torchrun --standalone --nproc_per_node 1 ../run_capped.py \
     scripts/run.py --model_name Qwen/Qwen3-8B --dataset_name <ds> --batch_size <bs> --max_new_tokens <32768|38912> \
     --method <selar|cot> --selar_topk 3 --entropy_threshold <tau> [--seed 42]
  ```
  This is driven by `run_suite3.sh` and the `slot*.sh` chains. Batch sizes were 30 for AIME, 33 for GPQA, 64 for MATH500 and 128 for GSM8K; the README example uses 256.
- **`run_capped.py`:** a launch wrapper I wrote; it changes no released source. It does three things:
  - caps each process at 49% of GPU memory, so two runs can share the GPU;
  - adds a GQA-aware attention for single-token decode steps. It is mathematically identical to HF's sdpa but skips the 4× `repeat_kv` copy. I checked it against stock sdpa: max logit diff about 0.3 in bf16, same argmax.
  - swaps in a preallocated, chunk-growing KV cache in place of HF `DynamicCache`, which re-copies the whole cache with `torch.cat` every step. On a test with forced reallocations and `batch_select_indices`, its logits were bit-identical to DynamicCache (max diff 0.0).

  Together these made the long AIME/GPQA runs roughly 2× faster. Without them, two runs sharing the GPU OOMed and one AIME run took more than 7 h.

### Settings that differ from the paper

- **Hardware and batching:** 1×H200, with batch sizes chosen for memory, instead of 4× RTX PRO 6000. In the released code SeLaR's behaviour **depends on batch composition** (see the bug below), so batch size is effectively a hyperparameter the paper doesn't report.
- **Seeds:** a single seed, as in the paper. I added seed 42 for CoT, released SeLaR and fixed SeLaR on AIME, because 30-problem sampled accuracies have a binomial sd of about 8 points.
- **Fixed SeLaR scope:** the per-sample-gating fix was only run on AIME24/25 (seed 41) and AIME25 (seed 42), for lack of time.
- **Not run:** Qwen3-1.7B and Qwen3-32B rows; CoT (Greedy); Soft Thinking (no code in the release); SwiR (code is in the release, but its per-dataset hyperparameters are only implied by result filenames); the Table 2 ablations; the Table 3 sensitivity sweep; Figures 3–5.

Sanity checks:

- **Output lengths:** our SeLaR and CoT lengths match the authors' released result files (e.g., AIME25 CoT averages 18.4k tokens vs their 19.1k; SeLaR 18.2k vs their 17.3k).
- **No degenerate generations:** about 2–3 of 30 AIME samples hit the token limit, for every method.
- **Different seeds, different problems:** the authors' released AIME25 SeLaR file has 24/30 correct; ours has 19/30 (seed 41) and 17/30 (seed 42).
- **Activation rate:** the diagnostic (`gating_bug_stats.json`, below) measured 12.3% of tokens as exploratory on AIME25. That is consistent with the paper's Fig. 5 (≈10%), so the entropy gate itself behaves as described.

## Why it was not reproduced

1. The headline AIME gains do not appear: over two seeds, released SeLaR is 5–12 points *below* CoT on AIME. Single-seed 30-problem AIME accuracies have sd ≈ 8 points, so the paper's single-run +6.7 / +13.3 gaps are well within sampling noise. Our runs give no sign of a systematic gain.
2. On GSM8K, MATH500 and GPQA, SeLaR ≈ CoT (−0.4, 0.0, +1.5), which matches the paper's small differences there. These datasets can't carry the average-improvement claim.
3. The released code has a batch-level gating bug (below), so the method that was run differs from Eq. 7. Fixing it did not recover the gains either.

## Codebase completeness: MAJOR_FIXES

The repo has the method (`src/generation_utils.py::generate_selar`), the evaluation driver (`scripts/run.py`), the grader and all five datasets, and it runs end to end. Issues found:

- **Bug that changes results (fixed in `./codebase`, uncommitted).** In `generate_selar`, the next-step input is chosen per batch: `if use_soft_input.any(): inputs_embeds = soft_embeds`. And when any sample is high-entropy, `soft_embeds` is computed for *every* sample. So whenever one sample in the batch is at an exploratory step, every other sample also gets its top-k soft mixture plus contrastive push instead of its sampled token's embedding. This includes the math-symbol tokens the code explicitly means to keep discrete.
  - I measured it with `measure_gating_bug.py` (Qwen3-8B, AIME25, batch 30, first 2500 steps). 12.3% of tokens are exploratory, as intended. A further **13.0% of low-entropy tokens** get a soft input that differs from their sampled token's embedding, purely because of the batch-level gate.
  - The effect grows with batch size, so results depend on batch size and batch composition.
  - Fix: `src/generation_utils.py`, new kwarg `per_sample_gating` (default True), which takes `torch.where(is_high_entropy, soft, E[next_tokens])`; plus the `--per_sample_gating/--no-per_sample_gating` flag in `scripts/run.py`.
- **Missing dependency:** `math-verify` and `latex2sympy2_extended` are imported by `src/grader.py` but absent from `requirements.txt` (installed manually).
- **`scripts/merge.py`:** it globs `logs/{model}_{ds}_{method}_{max_new_tokens}_rank*.json`, which never matches SeLaR/SwiR filenames (those contain `_k3_t0.5_` / `_a.._s.._`), so multi-GPU SeLaR results can't be merged. I didn't need it (single GPU) and left it unedited.
- **Defaults and docs:** the default `--entropy_threshold` is 0.5 and the README example uses τ=0.5 for GSM8K, while App. B says τ=0.6. Per-dataset thresholds had to be set by hand. No script reproduces Table 1.
- **Scripts I wrote, outside the release:**
  - `run_capped.py` (memory cap, GQA decode attention, chunked KV cache; performance only);
  - `run_suite*.sh` and `slot*.sh` (job chains);
  - `analyze.py` and `make_status.py` (tables);
  - `measure_gating_bug.py` (diagnostic);
  - `test_attn.py` and `test_cache.py` (equivalence tests).

## Discrepancies

1. **code_vs_paper, major (affects results):** batch-level instead of per-sample entropy gating in `generate_selar` (described above). Eq. 7 / Alg. 1 gate each sequence by its own H̄_t.
2. **code_vs_paper, major (affects results):** `generate_selar` forces discrete inputs whenever the sampled token is one of ~200 "math symbol" tokens (digits, letters, operators, LaTeX commands; inherited from SwiReasoning). The paper's gate (Eq. 7, Alg. 1) is purely entropy-based and never mentions this. (In the released code this rule is mostly overridden by bug 1.)
3. **code_vs_paper, minor (affects results):** the paper computes top-k entropy and soft weights from p_t (Eq. 1, 4), while the code uses the distribution after temperature 0.6 and top-k/top-p filtering.
4. **code_vs_paper, minor:** `run.py` defaults to τ=0.5 (and the README GSM8K example uses τ=0.5, batch 256), while App. B uses τ=0.6 for GSM8K.
5. **code_vs_paper, minor (affects results):** the authors' released Qwen3-8B GPQA SeLaR result file is `..._selar_k5_t0.5_...` (k=5, τ=0.5), while App. B says k=3 and τ=0.7 for all main results.
6. **paper_internal (no effect):** Figure 5 labels GSM8K with τ=0.5; App. B "Final Selection" says τ=0.6 for GSM8K.
7. **paper_internal (no effect):** Eq. 7 uses discrete if H̄_t ≤ τ; Alg. 1 uses discrete if H̄_t < τ (the code uses soft if H̄_t ≥ τ).
