## What I did
Repo: https://github.com/xiangchensong/sae-feature-consistency → `./codebase`. The environment is a conda env with Python 3.11, with pip-pinned versions taken from `uv.lock`: torch 2.7.1, nnsight 0.3.7, transformers 4.52.4, datasets 3.6.0, numpy 2.2.6, scipy 1.15.3, einops 0.8.1, plus ipywidgets, ipykernel and plotly.

All LLM runs were launched from `codebase/examples` with `CUBLAS_WORKSPACE_CONFIG=:4096:8`. Each process trains its SAEs in parallel on one shared activation buffer, as the release does.

- **Run A — the release's exact command for TopK** (from `pythia-160m-ds16k.slurm`, without wandb; 18 SAEs, 20.9 h):
  `python run_single.py --save_checkpoints --save_dir output/top_k/resid_post_layer_8 --model_name EleutherAI/pythia-160m-deduped --dataset_name monology/pile-uncopyrighted --layers 8 --architectures top_k --random_seeds 42 43 44 --dictionary_widths 16384 --learning_rates 3e-4 --device cuda:0`
- **Run B — best configuration for each of the other 6 architectures** (18 SAEs, 13.2 h, run concurrently with A):
  `python ../../scripts/run_best.py <same args> --architectures batch_top_k matryoshka_batch_top_k jump_relu standard gated p_anneal --target_l0s 20 40 --sparsity_penalties 0.06 0.025`
  - `scripts/run_best.py` is a thin wrapper that runs the unmodified `run_single.py` through `runpy`. It only filters the trainer configs down to the App. F.1.2 best values:
    - BatchTopK k=20, Matryoshka k=20, JumpReLU L0=40;
    - Standard 0.06, Gated 0.06, P-Anneal 0.025.
  - It is needed because the CLI applies one list of target L0s / penalties to every architecture.
- **Run C — extra sweep points** to check hyperparameter selection (15 SAEs, 11 h): `BEST_JSON='{"batch_top_k":[40,80,160],"gated":[0.04,0.08]}' python ../../scripts/run_best.py ...`
- **PW-MCC:**
  - `scripts/compute_mcc.py` uses the release's `dictionary_learning.utils.MCC` (Hungarian matching on decoder cosine) and the decoder loader from `evaluate_mcc.py`. It runs over all 17 saved checkpoints, for 3 seed pairs each.
  - Cross-check: the release's `examples/evaluate_mcc.py`, run **unmodified**, on final checkpoints. Its hard-coded `output/pythia-160m-ds16k` path was satisfied with a symlink to a view directory (`output_view/`). It printed identical values (`logs/release_evaluate_mcc.log`).
- **Table 1 / Table 2 counts** (no release code for these):
  - `scripts/feature_freq.py` measures per-feature activation frequency over 10M tokens of the training stream. It uses the release's `ActivationBuffer` and `load_dictionary`.
  - `scripts/table1.py` matches TopK k=20 seed-42 vs seed-43 features (Hungarian), then bins pairs by min(freq) (per 1M tokens) and by cosine.
- **Synthetic Fig. 1/2:**
  - `python generate_data.py`.
  - The two notebooks were executed headless with `scripts/run_notebook.py`. This applies text substitutions at run time only (the notebook files are not edited): `"cuda:1"`→`"cuda:0"` and `fig.show()` removed.
  - Results are in `codebase/synthetic/output/*.pkl`.

**Settings that differ from the paper:** none within the runs that were done. Steps were 244,140 (= 5e8 / 2048), with lr 3e-4, warmup 1000, sparsity warmup 5000, decay starting at 0.8, bf16 autocast, normalized activations, and seeds 42/43/44. The only reduction is in which hyperparameter grid points were trained (see Coverage).

## Codebase completeness: MINOR_FIXES
I made **no edits to any release source file**; `git diff` in `./codebase` is empty. The issues and workarounds:
- `examples/evaluate_mcc.py`:
  - It hard-codes `output/pythia-160m-ds16k`. I satisfied this with a symlink `codebase/examples/output -> ../../output_view` (a view directory of symlinks to the trained SAEs).
  - It uses `tqdm.notebook`, which requires ipywidgets. Ipywidgets is listed in pyproject; I first forgot it, then installed it.

  - It hard-codes the authors' venv and paths. I ran the same `run_single.py` command directly instead.
  - `run_single.py`'s CLI can't give different hyperparameter values to different architectures in one process. My wrapper `scripts/run_best.py` filters configs; it only selects grid points.
- `synthetic/group_topksae.ipynb`:
  - It hard-codes `cuda:1`. This was replaced at run time on a 1-GPU job.
  - Both notebooks need `synthetic/` on `PYTHONPATH` (`from models import ...`).
- **Scripts I wrote myself** (no release code exists for these analyses): `scripts/feature_freq.py` and `scripts/table1.py`, covering Table 1, the Table 2 counts and the activation-frequency analysis. I also wrote `scripts/compute_mcc.py`, `scripts/run_notebook.py` and `scripts/mcc_loop.sh`.
- **Missing from the release:**
  - The model-organism code (Sec. 4.3 / App. D).
  - Table 1 / Table 2 / Fig. 7 analysis code.
  - The auto-interpretation and GPT-judge pipeline (App. F.4).

  The main LLM experiment (Fig. 6 / App. F.1.2) and Fig. 1/2 are fully covered by the release.

## Discrepancies
1. **code_vs_paper, minor — synthetic matched setting dimensions** (`synthetic/generate_data.py`, both notebooks). The paper (Sec. 4.2) says m=8, d_gt=16, k=3. The code uses activation_dim=16, dict_size=32, k=3. Our Fig. 1 numbers come from the code's setting and match the paper's reported values anyway.
2. **code_vs_paper, minor — synthetic data generation** (`generate_data.py`). The paper says A_gt ~ standard normal and active coefficients are "independent Gaussian samples". The code row-normalizes A_gt to unit norm and uses |N(0,1)| (non-negative) coefficients.
3. **code_vs_paper, minor — synthetic TopK training loss** (`group_topksae.ipynb`). The TopK SAE is trained with MSE + 0.01·L1 (l1_coeff=1e-2). The paper describes the TopK SAE without an L1 term.
4. **code_vs_paper, minor — which "Standard" SAE.** The paper reports 7 variants including "Standard". The release's slurm array trains 8 (adding `standard_new`, the Anthropic April-update trainer with unconstrained decoder norms), and `evaluate_mcc.py` evaluates both. The paper doesn't say which one "Standard" refers to. I used `standard` (StandardTrainer) and matched the paper's 0.4739.
5. **paper_internal — Gemma seeds.** Table 7 says 3 seeds (42, 43, 44) is a "common training parameter shared across all SAE architectures and language models". Table 9 (Gemma-2-2B) lists seeds 42, 43 only. This doesn't affect our results (Gemma was not run).
