# Reproduction report: STELA — A Linguistics-Aware LLM Watermarking via Syntactic Predictability (2026.acl-long.2115)

## Verdict
- **Verdict: PARTIALLY_REPRODUCED.** Every number I ran matches the paper. The verdict is "partial" only because coverage is SUBSET: secondary experiments were not run, and the SWEET/EWD/MorphMark baselines are not in the release.
- **Result match: NUMBERS_MATCH** (after fixes); **as released: NUMBERS_MATCH**. The only code edit swaps gated HF repo ids for identical-weight mirrors.
- **Coverage: SUBSET.** Table 2 (STELA, all 9 LLM×language cells, 500 prompts each, paper scale) and Table 3 (STELA with UD tagset, all 9 cells) were run in full. KGW was also run as a baseline. Not run: SWEET/EWD/MorphMark (no code in the release), the Figure 3 k-ablation, Figure 5 synonym attack, Table 4 Dipper attack, Figure 4/6 z-score decomposition, and the Appendix D GPT-5.1 judge (closed model, flag CLOSED_JUDGE_UNAVAILABLE).
- **Codebase completeness: MINOR_FIXES.**

## What the paper claims (target)
STELA scales the KGW bias by a POS-n-gram linguistic indeterminacy λ(c_t) (δ'_t = δ·λ) and weights detection the same way. Main result (Table 2): STELA has the highest 3-language average TPR@5%FPR and Best F1 for each of Llama-3.2-1B-Instruct, Qwen3-0.6B and HyperCLOVAX-SEED-0.5B. It is top on Chinese and Korean for every LLM. On English it is competitive, with KGW/EWD sometimes better. Table 3: STELA works with both UD and language-specific tagsets, and the language-specific tagsets help especially for Korean.

## What I ran
- Repo: https://github.com/Shinwoo-Park/stela_watermark (commit as cloned 2026-10-01), in `./codebase`.
- Env: conda `env/` with Python 3.10, torch 2.5.1+cu124, transformers 4.53.2, spaCy 3.8.16 (+ en_core_web_sm, zh_core_web_sm, ko_core_news_sm 3.8.0), kiwipiepy 0.24, hanlp 2.1.5, scikit-learn, pandas. The repo has no requirements file.
- The experiment is the repo's own `experiment.py`, unmodified apart from model ids, with the repo's 6 configs (`config/STELA_{en_lang_k2,zh_lang_k4,ko_lang_k4,en_ud_k2,zh_ud_k4,ko_ud_k4}.json`). These are exactly what `run_*.sh` use: γ=0.5, δ=2.0/E[λ] (3.48/3.83/4.21 lang; 2.92/3.11/3.09 UD), k=2 (en) / 4 (zh, ko), temperature 0.7, max_new_tokens 512, seed 42. Datasets are the 500-prompt files shipped in `watermark_datasets/` (WritingPrompts/en, THUCNews/zh, OSCAR/ko).
- Per job: `python experiment.py --model <m> --algorithm STELA --dataset <d> --dataset_path shards/<d>_<s>.jsonl --output_dir out`. Each job ran in its own run dir `runs/<group>_<lang>_<model>_s<shard>/` holding a private `config/STELA.json` and symlinks to the codebase.
- `scheduler.py` / `scheduler2.py` (mine) ran the 135 jobs (3 groups × 3 langs × 3 models × 5 shards of 100 prompts) with 9–12 processes in parallel on the single H200. `merge_results.py` (mine) pools the 5 shards and recomputes TPR@5%FPR and Best F1 with the repo's own `calculate_detection_metrics` over all 500 positive/negative pairs. `make_comparisons.py` builds the tables below. Raw outputs are in `runs/*/out/`, the pooled numbers in `merged_results.json` / `merged_results.txt`.
- KGW baseline: `extra_configs/KGW.json` runs the same code with a constant λ=1 table and δ=2.0, no POS tagger. With λ≡1 the insertion and the weighted z-score reduce exactly to KGW, matching MarkLLM's default KGW config (γ 0.5, hash_key 15485863, prefix_length 1, f_scheme time, window left), which the paper says it used with δ=2.0.

### Differences from the paper's setting
- Llama-3.2-1B-Instruct and Llama-3.2-3B (the PPL reference model) are gated on HF for the available token (HTTP 403), so I used the ungated re-uploads `unsloth/Llama-3.2-1B-Instruct` and `unsloth/Llama-3.2-3B` (same weights; unsloth's generation_config also sets pad_token_id).
- Sharding: each 100-prompt shard reseeds with seed 42, so sampled texts differ from a single sequential 500-prompt run. Sampling noise is expected anyway: the binomial SE of TPR at n=500 is about 0.01 for TPR≈0.95.
- No other hyperparameter, data or metric changes.

## Discrepancies
1. **code_vs_paper (minor, affects results):** detection z-scores and PPL are computed on the full decoded sequence: the instruction, the human prompt and the continuation, because `generate` output is decoded whole. The paper speaks of scoring the generated texts. Both positive and negative samples include the same prompt, which dilutes the z-scores.
2. **code_vs_paper (minor, affects results):** insertion re-tags the decoded prefix at every step, whereas detection tags the full text once and snapshots tags by character offset. Detection-time POS contexts can therefore use right context and differ from those used at insertion. The paper's Eq. 8/Alg. 3 describe c_t reconstructed from preceding tokens.
3. **code_vs_paper (minor):** contexts missing from the λ table fall back to the count-weighted global mean (e.g. 0.619 en), while the δ calibration uses the unweighted mean E[λ] (0.575 en).
- No paper-internal inconsistencies found among the numbers I checked: Table 3's E[λ] values agree with §5.4, and the deltas agree with 2.0/E[λ].
