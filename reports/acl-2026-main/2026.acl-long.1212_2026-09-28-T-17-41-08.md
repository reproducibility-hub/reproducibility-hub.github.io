## What the paper claims (target)

- **Table 1**: StepFlow (OEB in the bottom ¼ of layers + SMI in the top ¼, τmax = 0.15, α = 0.06) improves accuracy on AIME24/25, AMC23, MATH-500, GPQA-D and LiveCodeBench for 6 backbones. It uses no retraining and a single decoding pass. Decoding: T = 0.6, top-p = 0.95, up to 32,768 new tokens, avg@16 on AIME/AMC, 8 samples on GPQA, 1 sample on MATH-500/LCB.
- **Table 2**: ablation on GPT-OSS-20B medium. OEB-only and SMI-only each help; the combination helps most (AIME25: 62.0 → 64.5 / 64.0 / 69.2).

## What the release contains / what I could run

- The StepFlow interventions (`src/interventions/{attention_manager,bridge_guard_oeb,smi,state_controller}.py`) patch only `transformers.models.gpt_oss.eager_attention_forward`. **Only GPT-OSS is supported.** DeepSeek-R1-Distill and QwQ have no attention patch, even though `model_config.py` has a `deepseek-qwen` entry. Four of the six Table-1 backbones therefore cannot run StepFlow with the released code.
- The only evaluation driver is `eval/Math-main/evaluation/math_eval_gptoss.py`: GPT-OSS, math datasets only. There is **no GPQA-D or LiveCodeBench evaluation code**, no benchmark data files, no run script for Table 1/2 (`sh/*.sh` are leftover Qwen2.5-Math scripts), and no seed averaging.
- **No baseline code** (Budget Forcing, Hint-Infer, PS+, Attn-Interv, Act. Steering). Baselines were not run, and claims of the form "StepFlow beats X" are **NOT_COMPARABLE**.

So I ran the sub-table I could reproduce faithfully: **GPT-OSS-20B (low and medium reasoning effort) × {AIME24, AIME25, AMC23, MATH-500} × {vanilla, +StepFlow}**, plus the **Table 2 ablation on AIME25 (medium)**.

## Setup and exact commands

- Env: conda (py3.11) with torch 2.8.0+cu128, transformers 4.56.2 (has `gpt_oss`; MXFP4 weights run via `kernels`/triton on the H200), plus the eval requirements (sympy 1.12, antlr4 4.11.1, pebble, word2number, timeout-decorator …).
- Model: `openai/gpt-oss-20b` (HF). Eager attention (required by the patch).
- Data (the repo ships none): `HuggingFaceH4/aime_2024` (30), `math-ai/aime25` (30), `math-ai/amc23` (40), `HuggingFaceH4/MATH-500` (500). These were written to `codebase/eval/Math-main/evaluation/data/datasets/<name>/test.jsonl`.
- Each shard is one call of the release driver:
  ```
  cd codebase/eval/Math-main/evaluation
  python -u math_eval_gptoss.py --model_name_or_path <gpt-oss-20b> --data_names <aime24|aime25|amc23|math500> \
     --data_dir data/datasets --output_dir outputs/<effort>_<method>_seed<k>/<shard> --start S --end E \
     --seed k --temperature 0.6 --top_p 0.95 --max_tokens_per_call 32768 --reasoning-effort <low|medium> --save_outputs \
     [StepFlow:  --use-smi --smi-strength 0.06 --smi-min-layer 18 --use-oeb --oeb-max-layer 5 --tau-max 0.15]
     [OEB only:  --use-oeb --oeb-max-layer 5 --tau-max 0.15]      [SMI only: --use-smi --smi-strength 0.06 --smi-min-layer 18]
  ```
  GPT-OSS-20B has 24 layers, so OEB runs on layers 0–5 (bottom ¼) and SMI on layers ≥ 18 (top ¼), matching Table 8. α = 0.06 and τmax = 0.15 as in the paper; the script defaults (α = 0.2, OEB max layer 8, SMI min layer 48 for a 64-layer model) were overridden.
- Orchestration (my scripts, in `scripts_repro/`): `runner.py` runs 7 shard processes in parallel on the GPU. `aggregate.py` merges shards and grades with the release's `evaluate()`. `make_tables.py` averages over seeds and runs a paired bootstrap (10k resamples over problems). Raw generations are in `outputs/`, and summaries in `results_summary.json`, `results_table.json`, `aggregate_final.txt`, `tables_final.txt`.

The MATH-500 gap is partly grader strictness: the release's `extract_answer` falls back to the last number when GPT-OSS does not box its answer, and keeps `\,`, `\displaystyle`, `x=` and similar. ## Why it is not a full reproduction
1. **Compute**: the released pipeline is HuggingFace `generate` with batch size 1 and Python hooks in eager attention. That gives about 8–10 tok/s per process, about 60–70 tok/s total with 7 processes on the H200. Medium-effort AIME traces average 9–13k tokens, with 5–20% reaching the 32k cap. The paper's full protocol (16 samples × AIME/AMC × 2 efforts × 2 methods, plus GPQA × 8) would need several times the 48 h budget.
2. **Missing code**: no GPQA/LCB evaluation, no data, no non-GPT-OSS attention patch, no baselines.
3. **Results**: with the samples that fit, StepFlow's effect on GPT-OSS-20B is small and inconsistent. It is +9 on low/AIME25, about +2 on medium AMC23/MATH-500, 0 on low/AIME24 and medium/AIME25, and −5 on low/AMC23. None of the differences is significant.

## Codebase completeness: MISSING_SCRIPTS

Changes to the released code (left uncommitted in `./codebase`; see `git diff`):

1. `src/interventions/smi.py`: **bug fix**. `StepMomentumInjectionWrapper` passed the raw `min_layer` argument (None by default) instead of `self.min_layer` to the intervention. The result was `TypeError: '<' not supported between int and NoneType` on the first deep layer, so SMI could not run with the eval script.
2. `eval/.../math_eval_gptoss.py`:
   - **Bug fix that affects results**: generation now uses `past_key_values=DynamicCache()` (a full cache). With transformers ≥ 4.56, GPT-OSS's sliding-window layers keep only 128 keys in the cache. The OEB/SMI code indexes keys and values by absolute position using full-length segment masks. On sliding layers this made OEB silently skip, and made SMI never inject: in a smoke test, SMI fired 0 times, because layer 18 is a sliding layer and it "consumes" the pending window before doing nothing. The sliding window is still enforced through the attention mask, so the model computation is unchanged.
   - Honour `--temperature/--top_p`: the script hard-coded greedy decoding. This enables the paper's T = 0.6 / top-p 0.95.
   - New CLI flags `--smi-min-layer` and `--tau-max`. The README advertises `--tau-max`, but the script lacked it, and the SMI layer default (48) assumes a 64-layer model.
   - Also saves `oeb_stats` and `num_gen_tokens`, and sets `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`.
3. `src/interventions/bridge_guard_oeb.py`: **performance only**. I verified that it produces identical greedy output and identical trigger counts against the original on a 400-token test, and runs 2.7× faster.
   - Per-head statistics are accumulated as GPU tensors instead of about 770 `.item()` syncs per token.
   - Segment masks are cached once per decoding step.
   - The current-segment choice is read from the CPU label list rather than via GPU boolean syncs.
   - The early `if not torch.any(active)` sync was removed; inactive rows already get λ = 0.
4. `eval/.../parser.py`: **grading bug fix**. For `math500`, `parse_ground_truth` re-ran `extract_answer` on the raw, un-boxed GT answer. That picks the last number: `\frac{14}{3}` became `3`, `Evelyn` became empty. The already-parsed `gt` is now used. Before the fix, MATH-500 accuracy read about 55% instead of about 80%.
5. `eval/.../utils.py`: `load_jsonl` skips a malformed (truncated) line instead of `exit()`. This protects resume after an interrupted append; the shared scratch quota briefly filled once during the run.

Pieces I had to write myself (outside the release):
- Dataset preparation to jsonl (AIME24/25, AMC23, MATH-500).
- `scripts_repro/runner.py`: parallel sharded run queue with restart and resume.
- `scripts_repro/aggregate.py`: merges shards, grades with the release `evaluate()`, and adds a secondary normalized score.
- `scripts_repro/make_tables.py`: seed averaging and paired bootstrap.
- `scripts_repro/check.sh`, `wait.sh`, `tokcount.py`: monitoring.

Other release issues noted:
- `model_config.py` gpt-oss defaults (64 layers, OEB ≤ 15, SMI ≥ 48) do not match GPT-OSS-20B (24 layers).
- The SMI implementation "consumes" the step window at the first eligible deep layer. Only one layer (the first layer ≥ min_layer, here layer 18) receives the momentum, not all top-¼ layers as the paper's Algorithm 1 implies. I kept the released behaviour.
- The injection is added to the per-head attention output (before `o_proj`), not directly to the residual stream.
- The resume logic in `prepare_data` matches output files by prefix, so a baseline run would pick up StepFlow outputs sitting in the same directory. I avoided this by giving each configuration its own output directory.
