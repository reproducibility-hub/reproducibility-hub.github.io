- Code: https://github.com/WisdomShell/ADG (linked from the paper), cloned to `./codebase` (uncommitted edits kept as a diff)
- Hardware: 1 x NVIDIA H200 (141 GB), ~111 GB host RAM, 47.8 h wall-clock limit
- **Verdict: FAILED** (result match **NO_MATCH**, coverage **SCALED_DOWN**, codebase completeness **MINOR_FIXES**)
- `result_match_as_released` is also **NO_MATCH**. The only source edits were config-level (placeholder paths and constants turned into env-var overrides, plus a score dump), so the "as released" numbers are the same runs.

## 1. What the paper claims and what I targeted

ADG samples K=5 answers per instruction (T=1.4, top-p 0.9, max_new_tokens 180) from the backbone. It embeds each answer with hidden states from the last layers and scores the instruction by s(x) = (1-λ)·D(x) + λ·I(x), where D(x) is dispersion (tr(Sc)/K) and I(x) is anisotropy (1-γ1/Σγ), with λ=0.4. It then picks the top-scored items inside 1,000 k-means bins with proportional quotas (budget 10K). The headline claim (Table 1) is that fine-tuning on the 10K ADG examples "consistently outperforms strong selectors on six benchmarks" for 2 backbones × 3 pools. The ablations (Table 2) say the Top-10K beats the Middle and Tail segments by a wide margin, and that both D and I are needed.

**What I reproduced:**
- **Table 1 / Tables 11–12, Alpaca-GPT4 pool (52,002 examples), both backbones** (LLaMA3-8B-Instruct, Qwen2.5-7B-Instruct): ADG vs the Random baseline. Also an un-finetuned reference.
- **Table 2, LLaMA3-8B + Alpaca-GPT4**: (A) Top/Middle/Tail 10K, and (D) D-only (λ=0) and I-only (λ=1).

**Not reproduced:**
- The WizardLM and CoT pools: not enough time on 1 GPU. Each pool needs ~6 h of answer generation and scoring per backbone before any training.
- The other baselines (All Data, IFD, SuperFiltering, SelectIT, Rethinking, ZIP, MIG, SCAR): their code isn't in the release. Random is the only baseline I ran, because it needs no code.
- Tables 3–5, 7–10, 13.

## 2. Pipeline and exact commands

All steps use the release's scripts with paths set through environment variables (see §6). Everything ran in `./env` (Python 3.12.9, torch 2.9.0, transformers 4.57.3, lm-eval 0.4.9.1, vllm 0.12.0, datasets 4.0.0).

1. **Data.** Alpaca-GPT4 `alpaca_gpt4_data.json` (52,002) from the GPT-4-LLM repo. `scripts/prep_alpaca.py` converts it to the README schema `{id, instruction, input, output}`. A non-empty `input` is folded into the instruction as `"\nInput: ..."`, because the released generation script drops the `input` field (see discrepancies).
2. **Answer sampling** (`codebase/generation/generation.py`, HF `generate`, fp16, batch 256, K=5, T=1.4, top-p 0.9, `ADG_MAX_NEW_TOKENS=180`):
   `ADG_MODEL=meta-llama/Meta-Llama-3-8B-Instruct ADG_OUT_DIR=work/llama ADG_OUT_FILE=llama_gpt4.jsonl ADG_MAX_NEW_TOKENS=180 python generation.py --input_file data/alpaca_gpt4_adg.json --batch_size 256` (2h59m). The same for Qwen (`work/qwen/qwen_gpt4.jsonl`, ~4h, partly running alongside other jobs).
3. **LLaMA scoring and selection**: `python codebase/ADG/ADG_llama.py`, with `ADG_*` env vars for paths, K_CLUSTERS=1000, FINAL_SELECT_COUNT=10000, weights 0.6·D + 0.4·I. It computes its own instruction embeddings and clusters (MiniBatchKMeans, 1000 bins). Took 3h20m. Output: top/middle/bottom = **9,593 / 9,781 / 9,593** items.
4. **Qwen scoring and selection**: `generation/embedding/embed.py` (instruction embeddings plus 1000-cluster k-means), then `ADG/ADG_qwen.py`. The released ADG_qwen scores one answer at a time and would have taken >5 h. I parallelised it with a thin wrapper, `scripts/adg_qwen_shard.py`, which calls the released `process_single_item` on 7 disjoint shards and then the released `cluster_based_selection` on the merged list. Output: top = **9,562** items.
5. **λ ablation**: `scripts/reselect_llama.py` re-runs the released `ADG_llama.cluster_based_selection` on the saved per-item D/I values with weights (1,0) and (0,1). With (0.6,0.4) it gives exactly the same top set as the original run (verified).
6. **Random baseline**: `random.sample(pool, 10000)` with seeds 42, 2, 3. Note that Random gets 10,000 items while ADG gets ~9.6K.
7. **Fine-tuning** (`scripts/train.sh`, wraps `codebase/train/training/stanford_alpaca/train_{llama,qwen}.py`): full fine-tuning, 3 epochs, lr 1e-5, cosine, warmup 0.03, per-device batch 2, max length 2048, bf16, gradient checkpointing.
   - On 1 GPU I used grad-accum 32 to keep the release's global batch of 64 (4 GPUs × 2 × 8).
   - **Optimizer `adamw_bnb_8bit`**: fp32 AdamW for an 8B model OOMs on one 141 GB GPU (FSDP on 4 GPUs in the release).
   - Training seeds: 42, 2, 3. Each run takes ~40 min.
8. **Evaluation** (`scripts/eval_model.sh`): the same 6 tasks and few-shot counts as `codebase/eval/eval.sh` (bbh 3-shot CoT, gsm8k 8-shot, mmlu 4-shot, truthfulqa_mc2 0-shot, mbpp 1-shot, humaneval 0-shot), lm-eval 0.4.9.1 default task configs, no chat template.
   - I used the lm-eval **vLLM** backend instead of `hf`, for speed.
   - GSM8K is reported with the `flexible-extract` filter; `strict-match` is given in §4.
   - Aggregates are computed as in the paper: Reason = (BBH+GSM8K)/2, Know = (MMLU+TQA)/2, Code = (HumanEval+MBPP)/2, Avg = mean of the three.
9. Orchestration: `scripts/queue.sh`, `scripts/queue2.sh`, `scripts/run_job.sh`. Aggregation: `scripts/collect.py`, `scripts/make_tables.py` → `results/tables.json`, `scripts/make_status.py`.

| Alpaca `input` field | n/a | folded into `instruction` (release drops it) |

## 5. Interpretation and why it doesn't reproduce

- **The baseline is much stronger than reported.** The paper's Random is 46.06; here it is 54.79 with the same training recipe and eval tasks. So is our ADG (53.66 vs 50.85). LLaMA's GSM8K and BBH barely move with the choice of subset (GSM8K 58–64 in every run), whereas the paper reports 33–47.
- **The ordering signal is weak in this pipeline.**
  - With the released weights (0.6·D + 0.4·I), the combined score is dominated by I(x). D has mean 0.034 (std 0.023) and I has mean 0.53 (std 0.11). The default top set overlaps 83% with the I-only selection and 16% with the D-only selection.
  - The paper's large Top ≫ Middle ≫ Tail gaps (Table 2) don't appear. Fine-tuning on the lowest-scored 10K gives the same benchmark scores as the highest-scored 10K.
- **Things I could not match that may matter:**
  - The authors' exact prompt preprocessing (how `input` was merged).
  - Their 4-GPU FSDP fp32-AdamW training (I used 8-bit AdamW on 1 GPU).
  - Their lm-eval version and backend (I used vLLM).
  - Their 5 seeds.
  
  None of these is expected to turn an 8–13 point ablation gap into zero, but the 8-bit optimizer and the eval backend are real deviations. The paper's absolute numbers on GSM8K (LLaMA) and MBPP (Qwen) also could not be matched with the harness defaults it says it used.

## 7. Discrepancies

### Code vs. paper
1. **Answer representation** (`ADG_llama.sentence_vec` / `ADG_qwen.answer_vec_new`).
   - Paper (Eq. 1): mean over the answer's output tokens, averaged over the last four layers (28–31).
   - Code: pools over the *instruction + answer* text (`instruction + " " + answer`, re-encoded). Punctuation tokens get weight 0 and digit tokens 1.3×. It uses `hidden_states[-4:-1]`, i.e. 3 layers that exclude the final layer's output. ADG_qwen computes `answer_start_idx` but never uses it (`H_answer = H`).
   - **Severity: major**; affects which items are selected.
2. **Alpaca `input` field dropped** (`generation.py`).
   - README schema has `input`.
   - The generated JSONL keeps only id/instruction/output, so `input` never reaches the sampling prompt, the scoring, or `top.json`. Training then uses `example.get("input","")=""`, so ~40% of Alpaca examples would be trained without their input.
   - **Severity: major**; affects results. I worked around it by merging input into instruction.
3. `generation.py` `MAX_NEW_TOKENS=256`; paper 180. **Minor** (set to 180).
4. `train_*.sh` `--num_train_epochs 5`; paper 3 epochs. **Minor** (set to 3).
5. **Bin quota** (`cluster_based_selection`).
   - Paper Eq. 8: m_b = round(M·|B_b|/N), giving exactly M items.
   - Code: floor with a minimum of 1, and clusters with fewer than 3 items are excluded from Top. Result: 9,593 / 9,562 items instead of 10K.
   - **Minor**.
6. Generation prompt truncated to `max_length=80` tokens (~2% of prompts lose `### Response:`); not in the paper. **Minor**.
7. The training script has no final `save_model()` (relies on FSDP step checkpoints every 50 steps). **Minor**, no effect on results.

### Paper-internal
1. Table 11 gives LLaMA3 ADG (Alpaca-GPT4) BBH = 57.83. Table 1's Reason = 50.11 implies (BBH+42.84)/2, i.e. BBH = 57.38, and Tables 9 (K=5 default) and 10 (10K ADG) both report BBH = 57.38. Recomputing Avg from Table 11 gives 50.93, not 50.85.
2. Table 12, Qwen SCAR (Alpaca-GPT4): Code = (56.15+63.20)/2 = 59.67, but Table 1 says 59.78.
