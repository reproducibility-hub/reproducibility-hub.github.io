## What was run (1× H200, conda env at ./env, Python 3.10.15)
Environment:
- Packages: the repo's `requirements.txt` (torch 2.4.0, vllm 0.6.2, transformers 4.45.1, trl 0.8.6, peft 0.12.0, deepspeed 0.16.5, sentence-transformers 3.4.1).
- LLaMA-Factory v0.9.1 (compatible with those pins).
- flash-attn 2.6.3 (prebuilt wheel).
- `cuda-nvcc 12.1` from conda, with `CUDA_HOME=env`. deepspeed, imported by trl, crashes without CUDA_HOME.

Data:
- Authors' Google Drive folder (README link):
  - `test_data/{musique,2wikimqa,multifieldqa_en,narrativeqa,longbook_qa_eng}.jsonl`, with 200/200/150/200/351 samples (= Table 4).
  - `train_data/raw_data_42_8k_16k.jsonl` (8972 MuSiQue samples with 8–16k contexts).
  - `train_data/{llama3,qwen2}_longmab_dpodata_2k.jsonl` (2250 / 2112 pairs).

Runs, in order (driver: `tools/run_all.sh`, then `tools/run_all2.sh`; logs in `logs/`):
1. **Eval** (`codebase/src/evaluation/eval.py`, unmodified):
   `python eval.py --model_path <model> --input_dir ../../data/test_data --output_dir <out> --temperature 0.0 --batch_size {10|50}`.
   - Settings: greedy decoding, max_input_len 100k with middle truncation, max 1024 output tokens, SubEM/F1 on the extracted answer.
   - Qwen gets YaRN factor 4: a local copy of the config with `rope_scaling={yarn, factor 4}`, identical to the config.json in the authors' released Qwen checkpoint. Without it, vLLM refuses `max_model_len=102000` for Qwen.
2. **DPO on released pairs:** `llamafactory-cli train train/{llama3,qwen2}_released_data.yaml`.
   - These yamls are the repo's `scripts/*_qlora_dpo.yaml` with only these changes:
     - `dataset_dir` points to our `train/dataset_info.json`.
     - `gradient_accumulation_steps 1 → 4`, so 1 GPU matches the scripts' 4 GPUs × batch 1 = effective batch 4.
     - deepspeed removed (1 GPU).
     - `report_to none`.
     - `flash_attn fa2`.
     - For Qwen and the later runs, `eval_strategy "no"`: the periodic validation-loss eval only. `val_size 0.1` is kept, so the training data is identical.
   - Kept from the yamls: LoRA (all modules; LLaMA-Factory default rank 8 / alpha 16), lr 2e-5, 2 epochs, cosine schedule, warmup 0.1, beta 0.1, `pref_ftx` 0.1 (Llama) / 0.2 (Qwen), cutoff 8500.
   - Then `llamafactory-cli export` merged the LoRA weights. The merged Qwen model gets the same YaRN config. Then eval.
3. **Full pipeline, Llama:**
   - `gen_probe.py`: 5000 raw samples [0:5000], chunk 1500, MiniCPM-Embedding. 2124 probes passed the answer check.
   - `rollout.py`: T=30, K=4, probe-similarity init, `--batch_size 500`. This is a CLI throughput setting only; each item's bandit is independent.
   - `construct_po_data.py`: max_prompt_length 8192 → 1916 pairs.
   - Then DPO with the same yaml as in step 2, merge, and eval.
4. **Released checkpoints:** `rocketduan/Llama-3.1-8B-Instruct-LongMab-PO` and `rocketduan/Qwen-2.5-7B-Instruct-LongMab-PO` were evaluated with the same eval.py.

Settings that differ from the paper or the repo:
- 1 GPU with grad-accum 4 instead of 4 GPUs with ZeRO-2.
- Larger vLLM batch sizes, which only affect throughput.
- No periodic validation eval during Qwen and full-pipeline training.
- Single seed; the paper reports no std.
- The full pipeline was re-run for Llama only; Qwen used the released pairs.

### Interpretation
* **Vanilla baselines match:** Llama avg 33.82/41.75 vs 33.23/41.03; Qwen avg 32.45/33.34 vs 32.03/33.29. A few single cells are off by 2–3 points (Llama MuSiQue, Qwen En.QA/MFQA). This confirms the eval setup.
* **Authors' checkpoints match Table 1** within tolerance on the averages. The checkpoint is evidence for the paper's numbers, but not for the training being reproducible.
* **Our DPO on the released pairs:**
  - Llama:
    - SubEM avg matches (40.34 vs 40.95).
    - F1 avg is lower (44.08 vs 47.43), with 2WikiMQA F1 and En.QA F1 not above vanilla.
    - The released checkpoint (trained on the same pairs) is stronger than our own training. Possible causes: 4-GPU ZeRO-2 vs 1-GPU grad-accum, seed, or LoRA defaults; LoRA rank is not stated in the paper.
  - Qwen:
    - F1 avg matches (41.76 vs 42.26).
    - SubEM avg is lower (34.94 vs 37.06) but still above vanilla.
* **End-to-end re-run of the released pipeline (Llama):**
  - Gain over vanilla: +1.7 SubEM / +2.8 F1 (paper +7.7 / +6.4).
  - The MuSiQue gain reproduces (in-domain: 48.5/51.0 vs paper 50.0/52.2).
  - 2WikiMQA and NarrativeQA SubEM fall below vanilla.
  - The bandit itself behaves as described. Mean rollout reward drops during exploration at round 2 (0.26), then rises to 0.43 by round 30 (round 1: 0.40). The best-of-30 reward is 0.85.
  - Hence the `RERUN_WEAKER_THAN_RELEASED` flag. Re-running the released code gives clearly weaker models than the released pairs and checkpoints. The only concrete code/paper difference found that could explain part of it is the pair-selection reward (see Discrepancies). Pair statistics differ markedly (rejected-response length and answer presence), so the released pairs were likely produced with some setting not in the repo.

## Discrepancies
1. **code_vs_paper (major)** — pair-selection reward.
   - Paper (Eq. 4; App. A.2): r = (SubEM(full response ỹ, y*) + F1(Ans(ỹ), y*))/2. A.2 says full-response SubEM is better than answer-based SubEM.
   - Code: `rollout.py::evaluate_output` uses full-response SubEM for the bandit reward. But `construct_po_data.py::evaluate_output`, which picks chosen/rejected, uses **answer-based** SubEM, and scores responses without an "answer:" prefix as 0.
   - Affects which pairs are built.
2. **code_vs_paper (minor)** — expected-reward update.
   - Paper (Eq. 12): μ_i(t+1) = (μ_i(t)(t−1) + r)/t, using the global step t.
   - Code (`UCBChunkSampler.update`): a per-chunk running mean, μ += (r−μ)/(n_i+1), with the probe-similarity prior counted as one observation.
   - Same idea, different normalization.
3. **code_vs_paper (minor)** — chunking.
   - Paper: "n equal-length chunks" of 1,500 tokens.
   - Code: sentence-boundary chunks of ≤1500 tokens, with a 2-sentence overlap between chunks.
4. **code_vs_paper (major)** — training loss.
   - Paper (Eq. 2): pure DPO loss.
   - Released yamls: `pref_ftx: 0.1` (Llama) / `0.2` (Qwen), which adds an SFT (NLL) term on the chosen response to the DPO loss. Not mentioned in the paper.
5. **code_vs_paper (minor)** — held-out data and undocumented hyperparameters.
   - The yamls hold out 10% of the pairs (`val_size: 0.1`), so only 90% are used for training.
   - Neither the paper nor the yamls give the LoRA rank (LLaMA-Factory default 8). The paper gives no batch size (4 GPUs × 1).
6. **code_vs_paper (minor)** — SubEM definition.
   - Paper (§4): SubEM checks whether the gold answer appears "in the model's output".
   - `eval.py`: computes SubEM only on the text after the last "answer:", and scores 0 if there is no such prefix.
   - This is the same protocol for all models we evaluated. It may differ from the baselines' protocol.
