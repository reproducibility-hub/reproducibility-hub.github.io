**Bottom line.** With the released code and Llama-3.1-8B-Instruct:
- On RULER, IntentKV with a 4K cache tracks FullKV closely. Avg: ours 86.5 vs FullKV 89.4; paper 87.0 vs 88.8.

So the central claim reproduces at our (scaled-down) scale: IntentKV keeps most of FullKV's performance while cutting the KV cache from 128K to 2–4K. RULER deviates most at 64K/128K (ours −3.2/−3.5 vs the paper's numbers), but stays within 5 % relative.

The paper's comparative claims against SnapKV and StreamingLLM could not be checked: their code and configs are not in the release, so those claims are `NOT_COMPARABLE`.

## What the paper claims / what I targeted

Main experiments (Sec. 6.2):
- **Table 1** — RULER (13 tasks, 4K–128K), KV cache 4096, 4 models, FullKV/StreamingLLM/SnapKV/IntentKV.
- **Table 2** — InfiniteBench (10 tasks), KV cache 2048, block 16 (128 for Retr.KV), same models and methods.

The release contains the IntentKV implementation (`intentkv/`), the RULER and InfiniteBench evaluation pipelines (Llama-3.1 + IntentKV, with `MODEL_FRAMEWORK=hf`/no `--enable_intentkv` for FullKV), and an efficiency benchmark. It does **not** contain SnapKV or StreamingLLM implementations or configs.

Targeted: Llama-3.1-8B-Instruct (the model the release is set up for), IntentKV and FullKV, on both tables. Other models (Llama3-262k, Qwen2.5-7B, Yi-9B-200K) and baselines were dropped for time (1×H200, 48 h).

## What I ran (exact settings)

Environment: conda env `env/` with Python 3.10, torch 2.4.1+cu121, transformers 4.46.3, flash-attn 2.6.3 (prebuilt wheel), `pip install -e codebase --no-deps`, plus evaluate/rouge/jieba/nltk/wonderwords etc. Model: `meta-llama/Llama-3.1-8B-Instruct` (HF cache), bf16, greedy.

### RULER (Table 1)
- Data: `scripts/ruler_prepare.sh`. It is the data-prep loop of `codebase/evaluation/ruler/run.sh` run once, so both methods use identical samples: 13 tasks × {4K,8K,16K,32K,64K,128K}, `NUM_SAMPLES=25` (the value in the released `run.sh`; the paper does not state a sample count), `MODEL_TEMPLATE_TYPE=base` (as in `run.sh`), seed 42.
- Prediction: `scripts/ruler_pred.sh` (the prediction/eval loop of `run.sh`):
  - IntentKV: `call_api.py --server_type intentkv --init_q_window 64 --max_capacity_prompt 4096 --block_size 16`.
  - FullKV: `--server_type hf` (the release's way to disable IntentKV; HF pipeline with flash_attention_2).
- Scoring: the release's `eval/evaluate.py`; I report the 13-task mean per length (`scripts/agg_ruler.py`).
- Cache 4096 is the paper's value (Sec. 6.1 / Table 1 caption). The released `run.sh` uses 2048, so I also ran 2048 (see "Extra runs").

### InfiniteBench (Table 2)
- `scripts/ib_run.sh` reproduces `codebase/evaluation/infinite_bench/run.sh`: `run_infinitebench.py --max_seq_length 131072 [--enable_intentkv] --block_size 16` (128 for kv_retrieval), with `--max_capacity_prompt 2048 --init_q_window 64` as defaults. Data is from HF `xinrongzhang2022/InfiniteBench`.
- Scoring: the release's `compute_scores.get_score_one`, on the example ids both methods completed (`scripts/agg_ib.py`).
- Scale-down, forced by time: IntentKV decoding in the released cache is slow (it calls `torch.cuda.empty_cache()` per layer per decoding step, ~100 ms/token), and FullKV summarization at 128K is slow too, so the full ~3.5K examples × 2 methods did not fit.
  - En.Sum: all 103.
  - En.QA: all 351 for both methods.
  - En.MC, En.Dia, Zh.QA, Code.Debug: the first 150 examples.
  - Retr.KV, Retr.PassKey, Retr.Num and Math.Find are **ordered by needle depth / question type** in the dataset, so a "first N" subset is badly biased. For example, the first 150 Retr.KV examples have needles only in the first 30 % of the context. On those first 150, FullKV scored 36.0 vs IntentKV 46.7; on a depth-uniform subset, 59.0 vs 52.0.
  - For these four tasks I therefore built stratified subsets (`scripts/make_strided.py`): every 5th Retr.KV (100), every 6th PassKey/Num (99 each), every 2nd Math.Find (175, all 7 question types). The release's runner was run unchanged on these files (`data/InfiniteBench_strided`).
- Runs shared the single GPU as 2–4 concurrent processes. CUDA OOMs from sharing were retried automatically; the runner resumes from saved predictions, so results are unaffected.

### Shipped predictions vs re-run (flag RERUN_WEAKER_THAN_RELEASED)
The repo ships `results_2k/Meta-Llama-3.1-8B-Instruct/prediction_kv_retrieval_intentkv.jsonl`, which holds only ids 0–53 of 500.
- On those same 54 ids: shipped IntentKV predictions score 46.3, my re-run of the released code 29.6, and FullKV 16.7.
- Only 2/54 outputs are identical. The shipped outputs never echo the key, which mine do (`The value associated with the specified key "…" is …`). That suggests a different prompt/chat template or library version.
- I tried no chat template, a user-role message and FA2 on 10 examples (`runs/diag/`); none reproduced the shipped outputs.
- With depth-stratified sampling the re-run matches the paper (52.0 vs 50.6), so this does not change the conclusion.

## Discrepancies

**code_vs_paper**
1. *`intentkv/intentkv_cluster.py::update_kv`, intention boundary.* Paper (Alg. 1, Eq. 5): l = argmax of the first difference of the √JSD sequence, one boundary. Code: per attention head, `argmax(js[i+8] + js[i+11] − js[i+6] − js[i+5]) + 5` over window positions 5…~51. That is a smoothed second-order difference, it forces at least ~13 intention tokens, and the boundary is computed per head. Same idea, different estimator. Minor; affects results (magnitude unknown).
2. *Same function, budget allocation.* The code always keeps the last α=64 window tokens plus the `n mod β` remainder, and picks `(S − α − rem)/β` blocks from the rest. Alg. 1 picks ⌊S/β⌋ blocks over the whole sequence. Minor.
3. *`evaluation/ruler/run.sh`.* `MAX_CAPACITY_PROMPT=2048`, while the paper says the RULER cache is 4096 (Sec. 6.1, Table 1). Minor; affects results (I used 4096; 2048 is run as an extra).
4. *`evaluation/ruler/run.sh`.* `MODEL_TEMPLATE_TYPE="base"` (raw prompt, no chat template), while Sec. 6.1 says "we use the default chat template for all instruction fine-tuned models". Minor; may affect absolute scores. I used the released value; FullKV still matches the paper.
5. *`evaluation/infinite_bench/run_infinitebench.py::load_model`.* FullKV is loaded without `attn_implementation`, i.e. sdpa, while App. C.1 says FlashAttention-2 is used. Minor; no effect on accuracy in my check (FullKV Retr.KV 59.0 with both).

**paper_internal**
1. Alg. 1 scores block i over keys [iβ, min((i+1)β, n)) but builds the mask from keys [(i−1)β, min(iβ, n)]: an off-by-one between scoring and selection. Does not affect the reported results (the code is consistent with itself).

Observation, not counted as a discrepancy: in Table 2, En.MC is identical for all four methods for Llama3.1 (69.0), Llama3 (63.8) and Qwen (45.0). That includes StreamingLLM, which keeps only 128 initial + recent tokens of a 100K+ book, which is surprising.
