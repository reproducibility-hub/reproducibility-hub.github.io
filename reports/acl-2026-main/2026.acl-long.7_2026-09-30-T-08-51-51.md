## Summary
The released code was re-run end-to-end for all seven models and every main experiment. Most outputs match the released result files **bit-for-bit** (or within ±1 sentence pair / ±6 units of floating-point tie noise): 2-fold cross-validation (Fig. 1), BLiMP-Control, zero-ablation for all 7 models (Fig. 2, Sec. 4.1 per-model drops), all non-Gemma BLiMP×BLiMP overlap matrices (Figs 3–5), BLiMP-Lex (App. I), Gemma CV on RuBLiMP/SLING (App. J), and MultiBLiMP (Fig. 8, ρ = 0.459 vs. 0.460).

**One real discrepancy.** All released **Gemma cross-overlap** matrices (BLiMP×BLiMP, RuBLiMP×RuBLiMP, SLING×SLING, BLiMP×RuBLiMP, BLiMP×SLING) have 691-unit masks on the diagonal, but 1% of Gemma's 34×2560 units is 870. I localized over only the **first 27 of 34 decoder layers** (`gemma27_overlap.py`), and this reproduces **every cell** of all five released Gemma matrices exactly. The paper (Sec. 3.3: "outputs of all Transformer layers") and the released code both use all 34 layers. The plotting code also divides these 691-unit overlaps by 870. So the paper's Gemma overlap numbers (part of Figs 3–5 averages, and all of Figs 6–7) cannot be reproduced with the released code. With the released code, Gemma overlaps are larger:
* English agreement results (Figs 4–5, averaged over 7 models) move only slightly; most numbers are within tolerance and the conclusions hold.
* Russian/Chinese overlaps rise by 20–50%. Agreement categories still sit near the top in both languages, and cross-lingual overlap is still RU–EN > ZH–EN and still far below within-language overlap. But in Russian, word_inflection overtakes anaphor agreement and NP agreement drops to 4th, so the paper's "anaphor and NP agreement are in the top three" does not hold (ranks 2 and 4).

So the paper's conclusions survive, but some Gemma-based numbers are not reproduced as reported.

## What was run (exact commands)
Env: `conda create -p ./env python=3.10`; `pip install -r codebase/requirements.txt` (torch 2.6.0, transformers 4.50.0, minicons 0.3.31, …) plus `protobuf sentencepiece`.

Per model (`run_model.sh <hf_id>`, run from `codebase/`, outputs to `results/english/...`):
```
python cross_validation.py --model-name M --dataset blimp          --savedir ../results/english/cross-validation --percentage 1.0

python cross_overlap.py --model-name M --dataset-1 blimp --dataset-2 blimp               --savedir ../results/english/cross-overlap

python cross_overlap.py --model-name M --dataset-1 blimp --dataset-2 blimp-v-sub-concat  --savedir ../results/english/cross-overlap
```
Models: openai-community/gpt2-xl, **unsloth/Llama-3.2-3B**, tiiuae/Falcon3-3B-Base, microsoft/Phi-4-mini-instruct, **unsloth/gemma-3-4b-pt**, deepseek-ai/deepseek-llm-7b-base, mistralai/Mistral-7B-v0.3 (fp32, batch size 1, last-token pooling, as in the code).

Gemma multilingual (`run_gemma_ml.sh`): `cross_validation.py` and `cross_overlap.py` on rublimp and sling, `cross_overlap.py --dataset-1 blimp --dataset-2 {rublimp,sling}`, and `multiblimp.py --phenomenon "SV-#"`.

Numbers are extracted by `analyze.py`, which re-implements the number extraction of the repo's plotting scripts (it imports `cross_overlap_bar.aggregate_across_models`, `cross_overlap_agreement.aggregate`, and `plot_utils.load_model_matrices`). It was first validated on the **released** result files: from those files it reproduces every paper number checked (`analysis_released.json`). Our numbers are in `analysis_ours.json`. `analysis_paperlike.json` holds our results with Gemma overlaps swapped for the 27-layer variant; it reproduces the released Gemma values in Figs 6–7 exactly. Figures from the repo's plotting scripts on our results are in `results/**/*.png`.

## Why it is not fully reproduced
The released code (34-layer localization) does not produce the paper's Gemma cross-overlap figures. Those figures came from a 27-layer localization; 27 is the number of layers in Gemma-3's vision tower, which hints at a config read from the wrong sub-config in an earlier code version, but that is speculation. Everything else reproduces numerically.

## Discrepancies
1. **code_vs_paper, major (affects results).** The Gemma overlap matrices behind Figs 3–7 come from masks localized over the first 27 of 34 layers (691 units), but the paper's method (Sec. 3.3) and the released code use all layers (870 units). Re-running the code gives larger Gemma overlaps; e.g. RuBLiMP–BLiMP agreement 11.75% vs. 9.99%, SLING–BLiMP 2.93% vs. 2.22%, and a changed RuBLiMP category ranking.
2. **paper_internal (affects results).** Gemma overlap percentages in Figs 4–7 divide 691-unit set overlaps by an 870-unit target size, so they are not on the stated "% of 1% target set" scale. Gemma CV (App. J) and MultiBLiMP (Fig. 8) use 870-unit sets.
3. **code_vs_paper, minor.** SLING: the paper says 38 phenomena; the data/results have 32.
