# Reproduction report: Latom — Corpus-Dependent Subcharacter Encoding via HMM-Guided Code Assignment (ACL 2026, 2026.acl-long.1596)

## Verdict

| Result match as released | **DOES_NOT_RUN** (the release has no pipeline for any table or figure) |

**Short version.** The released repo (https://github.com/tatHi/latom) contains the method (HMM on N-repeated text, then a Hungarian code assignment) plus encode/decode and a toy notebook on the English Genesis text. It does not include the pipelines behind the paper's experiments: tokenizer sweeps, bigram perplexity, Byte/Random baselines, the Amazon classification models, or the LM decoding-error experiment. I wrote all of these from the paper's description (`scripts/`). The method code ran unmodified; I only wrapped it so the HMM runs on CPU and patched pomegranate for speed, with numerically equivalent results.

- **Holds:**
  - Table 2 and Table 10 (|C| and K) match exactly.
  - Japanese intrinsic curves (Figs 2/3) match the paper closely.
  - English and German keep the large compression gain at |V|≈|C|.
  - Classification, Transformer at |V|=|C|: Character is clearly the worst encoding in 5 of 6 languages (Zh: all encodings within ~1 point), as in the paper.
  - Atom codes are "competitive" with Byte, usually within about 1 F1 point.
  - Table 6: atoms at N=2 make fewer decoding errors than Byte in every language.
- **Does not hold:**
  - The paper's statements that Ours "typically slightly outperforms Random" (Table 5) and is "consistently better than Random" (Table 6). Over 5 seeds, the Ours−Random sign is essentially random; see the paired table below.
    - Table 5: Ours beats Random in 24/48 (setting, language) cells (paper: 30/48). Across all 240 runs, Ours−Random averages +0.04 F1 (median −0.05; Wilcoxon p=0.42). The paper's own average margin is only +0.09 F1, well below the seed std of 0.3–1.8.
    - Table 6: Ours has fewer decoding errors than Random in 5/12 cells (paper: 12/12).
  - Our absolute F1 is 2–5 points below the paper in many cells, most strongly for |V|=8000.
  - At |V|=8000 the Transformer does best with Character (best or within 0.25 F1 of the best in every language), whereas the paper has Ours N=2 ahead of Character in all 6 languages.
- **Overall:** the core claim that atom codes are a viable, reversible alternative to bytes reproduces. The claimed advantage of HMM+Hungarian over random codebooks does not.

## What the paper claims and what I targeted

1. **Intrinsic (Sec 4, Table 2, Figs 2/3):** Genesis in English, German and Japanese; N∈{2..5} with the smallest K such that K^N ≥ |C|; SentencePiece BPE at |V| = 50…3000 (step 50) with whitespace-crossing tokens. Metrics: token count and bigram perplexity, character-level minus atom-level. Baselines: Character, Byte, Random codebook.
2. **Text classification (Sec 5.1, Table 5):** Amazon Reviews (mteb/amazon_reviews_multi), 6 languages, 200k/5k/5k splits, weighted F1. BiLSTM and Transformer; |V|=|C| and |V|=8000; encodings Character, Byte, Random and Ours at N=2,3. The paper uses 5 seeds and builds a new codebook every run.
3. **Decoding errors (Sec 5.2, Table 6):** Transformer LM at |V|=|C|, best checkpoint by validation perplexity, 10,000 samples of up to 64 tokens (T=1, top-50), random start token; reports the share of generations that cannot be decoded.

## What I ran (exact commands)

Environment: `conda create -p ./env python=3.10`, torch 2.4.1+cu124, pomegranate 1.1.2 (the version pinned in the release's requirements.txt), scipy 1.15.3, sentencepiece 0.2.2, scikit-learn, numpy 2.2. Hardware: 1×H200 shared with other jobs (node load average ~200), 14 CPU cores.

- Data: Genesis extracted from `christos-c/bible-corpus` (`bibles/{English,German,Japanese}.xml`, book GEN, 1,533 verses). The English file is identical line for line to the release's `data/English.txt`. Amazon: `mteb/amazon_reviews_multi` `{lang}/{train,validation,test}.jsonl`, using the `text` field (title + body). |C| reproduces Tables 2 and 10 exactly.
- Release sanity check: `cd codebase; python latomHmmHungarian.py --data data/English.txt --seed 123 --nDigits 2 --statesPerDigit 8 --output ...`. It runs as-is and reproduces the notebook's codebook (up to a 3-symbol swap in one row).
- Intrinsic: `python scripts/intrinsic.py --workers 6`, then `python scripts/analyze_intrinsic.py`. This calls the released `hmmHungarian()` with seed 42 for N=2..5, builds Random codebooks, and trains one SentencePiece BPE per |V| ∈ {|C|, 50, 100, …, 3000}.
- Amazon codebooks: `scripts/build_amazon_codebooks*.sh`. These call the released CLI unchanged: `latomHmmHungarian.py --data train.jsonl --seed S --nDigits N --statesPerDigit K --useDense --maxCharSize 2000000`, via `scripts/run_released_cpu.py`. One codebook per (language, N, seed), seeds 0–4.
- Extrinsic: `python scripts/scheduler.py 5` runs, for each (seed, language, encoding, vocabulary):
  - `scripts/prepare_amazon.py`: encode, train SentencePiece BPE on the training split, tokenize.
  - `scripts/train_cls.py --arch lstm --epochs 5` and `--arch tf --epochs 20` (batch 128, 4 validation checks per epoch, test F1 taken at the best validation F1).
  - `scripts/train_lm.py --epochs 10` (|V|=|C| only).
  - Then `scripts/recompute_lm_errors.py`, `scripts/make_tables.py` and `scripts/build_comparisons.py`.

### Claim-level summary

- "Byte often outperforms Character [at |V|=|C|], especially with the Transformer": **holds** for the Transformer (5/6 languages, by 1.9–6.4 points; Zh tie). With the BiLSTM, Character ≥ Byte in 5/6 languages (De: tie).
- "Ours is competitive with Byte and Random": **holds**. Means are mostly within ~1 F1 point.
- "Ours typically slightly outperforms Random": **does not hold** (see the Ours−Random table; roughly half the cells, and the paper's own margins are smaller than seed-to-seed noise).
- "Subcharacter encodings remain effective for Ja/Zh at larger |V|": **not observed**. At |V|=8000 our Character baseline is as good as or better than the atom codes.
- Table 6, "Random and Ours at N=2 consistently reduce decoding errors relative to Byte": **holds** (6/6 languages).
- Table 6, "For Ja/Zh, N=3 also outperforms Byte": **holds**, though our Byte error rate for Ja/Zh is much lower than the paper's 11.8/11.5%.
- Table 6, "Ours is consistently better than Random": **does not hold** (5/12 cells; mean Random−Ours = −0.41 points, median −0.05, Wilcoxon p=0.10). French Ours N=3 includes two of five seeds with 9–15% errors, whose LMs generate many misaligned atoms.

Absolute numbers: many Table 5 cells fall within the 5%-relative tolerance (see `comparisons` in status.json), but our models are systematically 2–5 points weaker at |V|=8000. Our Table 6 error rates follow a different metric definition and are not directly comparable in magnitude.

## Codebase completeness: MISSING_SCRIPTS

The method itself is implemented: `hmm.py`, `hungarian.py`, `latomHmmHungarian.py`, `encode.py`, `decode.py`, a naive `bpe.py` and a toy notebook. **No edits were made to `./codebase`**; `git status` is clean apart from `__pycache__`.

Missing from the release, and written by me from the paper:
- intrinsic sweep with Byte/Random baselines and bigram PPL (`scripts/intrinsic.py`, `common.py`, `analyze_intrinsic.py`);
- Amazon data handling and tokenization (`prepare_amazon.py`);
- BiLSTM/Transformer classifiers (`train_cls.py`);
- LM training, generation and decoding-error check (`train_lm.py`, `recompute_lm_errors.py`);
- Random codebook baseline (`common.build_random_codebook`);
- job orchestration (`scheduler.py`, `build_amazon_codebooks*.sh`) and tables (`analyze_extrinsic.py`, `make_tables.py`, `build_comparisons.py`).

Wrappers and environment-level changes (not edits to the release):
- `scripts/run_released_cpu.py` runs the released CLI with `hmm.DEVICE=cpu`.
- `scripts/fast_categorical.py` monkeypatches pomegranate's `Categorical.summarize` (vectorized) and disables pomegranate's input validation. Performance only; equivalence was checked.

Observations about the release:
- `fitHmm` sets `model.stop_threshold`, but pomegranate 1.1.2 reads `tol` (default 0.1), so the 1e-3 threshold is ignored. `hmmHungarian` hard-codes `maxIters=8`; the paper gives no iteration count.
- `randomSelectData` (`--maxCharSize`) shuffles before any seed is set, so subsampled codebooks are not deterministic.
- The README only points to the toy notebook; there are no instructions for the paper's experiments.

## Discrepancies

- **paper_internal:**
  - Tables 14–17: the "Radical" rows are identical to the "Myte" rows for Ja/Zh in every block (e.g. Table 14, |V|=|C|, BiLSTM: Myte 55.15/54.08 and Radical 55.15/54.08), whereas Table 11 gives different values (Myte 54.75/53.08, Radical 55.37/54.42). This looks like a copy error. It does not affect the main claims.
  - The abstract says Latom "improves text classification accuracy". The body reports weighted F1 and says Ours is "competitive" with Byte/Random and "sometimes outperforms" them (Sec 5.1.2). Minor overstatement in the abstract.

The release also exposes a `--maxCharSize` subsampling path that the paper does not mention, with unseeded sampling. Whether the paper used it is unknown. It doesn't affect the released defaults (−1 = all data).
