# DarwinTOD (ACL 2026, 2026.acl-long.2050) — reproduction report

**Verdict: FAILED** — result match **NO_MATCH** (as released: **DOES_NOT_RUN**), coverage **SUBSET**,
codebase completeness **MISSING_SCRIPTS** (it also needed MAJOR_FIXES).

The released code implements the DarwinTOD agents and the Evolvable Strategy Bank (ESB). It does not
include the paper's main experiment: there is no corpus-based evaluation, no train-then-test protocol and
no standard metrics, and the evolution step is commented out. I fixed the bugs, set the paper's
hyperparameters, and wrote the missing pipeline (an evolution pass over all 8,438 MultiWOZ 2.1 training
dialogues, then a standard mwzeval evaluation on the 1,000 test dialogues). With Qwen3-8B, the system
scored **Inform 31.0 / Success 5.4 / BLEU 2.8 / Combine 21.0**. The paper reports **99.62 / 94.18 /
20.33 / 117.23** (Table 1, MultiWOZ 2.1, DarwinTOD Qwen3-8B). Evolution raised Combine by only about
1–2 points over the strategy bank before training (19.9 → 21.0, peak 22.0 at 60 %); the paper reports
about 25 points (Table 2, Fig. 3). The release's own metrics with its own self-play protocol show no gain
in task success either.

## 1. Paper and target
* Claims: DarwinTOD (multi-agent DST/DP/NLG pipeline + peer critique + ESB with Genesis / Mutation /
  Consolidation / Pruning and Boltzmann selection) reaches SOTA on MultiWOZ 2.0/2.1/2.2 (Table 1).
  Performance also rises steadily as the ESB evolves over the training set (Fig. 3, Table 2: "w/o
  Evolution" is 25 Combine points worse).
* Target: Table 1, **MultiWOZ 2.1**, **DarwinTOD (Qwen3-8B)**, the paper's main open backbone.
  * MultiWOZ 2.1 is the only version whose data and loader ship with the repo.
  * Qwen3-8B is also the backbone of the ablation table.
  * I ran the paper's protocol (App. B.4): start from an empty ESB, process the training dialogues
    sequentially with offline evolution after each one, and evaluate on the full test set before training
    and after 10/30/60/100 % of training.
* Not run: MultiWOZ 2.0/2.2 and SGD, the other backbones (Llama3-8B, Qwen2.5-7B, GPT-5.1), and the
  ablations. Baselines are all quoted from their original papers, so there is nothing to run.

## 2. Code
* Repo: https://github.com/carsonz/DarwinTOD (linked in the paper), cloned to `./codebase` (commit 73cc916).
* Environment: conda env, Python 3.10, `pip install vllm` (0.31.0, torch 2.13) plus `requirements.txt`.
* Serving: Qwen/Qwen3-8B on vLLM on a single H200. Needed `VLLM_USE_FLASHINFER_SAMPLER=0` because there
  is no nvcc for the FlashInfer JIT.

### What the release can run, and what is missing
* `src/run.py multiwoz N` is the only entry point. It runs N randomly sampled (unseeded) **test**
  dialogues in **self-play**:
  * only the first user utterance comes from the data;
  * every later user turn is generated by the LLM user simulator (the paper's "UserSim Prompt2",
    App. G.5, which the paper uses only for the simulated-user study in App. D.3).
* The paper's main protocol reads all user utterances from the dataset. The UserSim there only critiques
  (Prompt1, App. G.4), and Inform/Success/BLEU are measured against ground truth. None of this is in the
  release.
* Evolution is disabled: `self.esb_evolver.process_evolve(...)` is commented out in
  `dialogue_manager.py`. Run as released, the system only ever uses gen-0 Genesis strategies.
* `MetricsCalculator` does not compute the paper's metrics:
  * **Success** = the DST belief state matches the goal's inform slots. Requests are never checked, so a
    dialogue that ends after one turn counts as a success.
  * **Inform** = fraction of goal slots in dialogues the user simulator declared finished.
  * **BLEU** = a hard-coded 0.5 placeholder on the `run.py` path. On raw logs it is the BLEU of the system
    turn against the *user* turn.
  * **Combine** is on a 0–1 scale, so the 0.5 placeholder alone is worth 50 "points".

### Scripts I wrote (in `./scripts`, outside the release)
* `driver.py` — runs a list of dialogues through the released `DialogueManager` in an isolated working
  directory with its own ESB file. Options:
  * `--evolve` turns evolution on.
  * `--corpus` is the paper's protocol: the user simulator is replaced by the ground-truth MultiWOZ user
    turns; DST/DP/NLG run as released.
  * Loads bge-small-en-v1.5 once on CPU instead of re-loading it on every merge.
* `genesis.py` — builds the gen-0 ESB (the release's `cold_start`) for all 48 domain combinations.
* `launch_train.py` — the training pass.
  * Every domain-combination strategy pool is evolved sequentially by its own worker, in parallel. This
    is possible because pools are isolated: recall needs an exact domain-set match, and
    mutate/merge/prune work within a pool.
  * Training order is ConvLab's `shuffled_dial_ids.json[0]`, shipped in the repo.
  * The ESB is snapshotted after every 10 % of each pool.
  * Side effect: it avoids the release's strategy-id collision bug (see discrepancies).
* `assemble_snap.py`, `launch_eval.sh`, `auto_eval.sh` — snapshot assembly and parallel evaluation
  (16–32 shards).
* `score_corpus.py` — scores corpus runs with the standard **mwzeval** evaluator (Nekvinda & Dušek 2021).
  * Lexicalized LLM output is delexicalized with DB values and regexes first.
  * Also computes sacreBLEU against the lexicalized MultiWOZ 2.1 system turns.
  * Sanity check: ground-truth system turns pushed through the same delexicalizer score Inform 91.6 /
    Success 84.7 / BLEU 87 (`scripts/sanity_delex_gt.py`). The delexicalizer is therefore not what
    makes our scores low.
* `eval_metrics.py` — computes the release's own `MetricsCalculator` metrics exactly as `run.py` does,
  plus a stricter DB-grounded Inform/Success check, for self-play runs.
* `prep_data.py`, `prep_test_full.py`, `collate.py`, `progress.sh`.

### Settings that differ from the paper
* **Qwen3 thinking mode disabled** (vLLM `--default-chat-template-kwargs '{"enable_thinking": false}'`).
  * The paper does not say. With thinking on, about a quarter of the calls hit the release's hard-coded
    `max_tokens=5000` and returned unparsable output, and a turn took about 1 minute.
  * A 200-dialogue check with thinking on is given below.
* No GPT-5.1, Llama or Qwen2.5 backbones; MultiWOZ 2.1 only.
* Training processes the pools in parallel rather than as one global sequence. Consequences:
  * fitness normalises the generation index within a pool rather than globally;
  * "x % of training" means x % of every pool's dialogues.
* The ESB was frozen during test evaluations. The paper does not say whether it evolves on the test set.
* Training used the release's only interaction mode, self-play with the LLM user simulator. It generates
  critiques and success signals for evolution. Prompt1 (critique-only UserSim on corpus turns) is not
  released.
* Inform/Success/BLEU come from mwzeval applied to delexicalized output. That is the standard MultiWOZ
  evaluator, but the paper does not name its evaluator or say whether responses were delexicalized.

## 4. Why it was not reproduced
1. **Missing pipeline.** The corpus-based protocol, standard metrics, and train-then-evaluate scripts
   are absent, and I had to write them. The released metrics are not the paper's metrics.
2. **Logic bugs in the release.**
   * evolution commented out;
   * dead strategies still selectable;
   * belief state aliased between turns;
   * UserSim critique dropped;
   * strategy-id collisions across domain pools;
   * hyperparameters different from Table 5.

   After fixing them, the method still does not reach the reported performance with Qwen3-8B. Thinking
   mode does not close the gap.
3. **Compute:** sufficient. The full training set and full test set were run.

## 5. Discrepancies
**Code vs. paper, major** (all affect results):
* **Protocol.** The paper reads user turns from the dataset and its UserSim only critiques (Prompt1). The
  release only does self-play with a generating LLM user simulator (Prompt2).
* **Metrics.** The release's Success, Inform, BLEU and Combine are not the standard ones (details in
  Section 2).
* **Evolution disabled.** `process_evolve` is commented out.
* **No protocol script.** There is no train-then-evaluate-every-10 % script; `run.py` samples random test
  dialogues.
* **Dead strategies selectable.** `recall_strategies` does not filter `alive`.
* **Shallow-copy bug.** The belief state is aliased between turns.
* **Lost critique.** The UserSim→NLG critique is never stored.
* **Strategy-id collisions.** Every Genesis pool uses the same ids (`dp-001-000` …). In a single ESB, the
  helpful/harmful updates and the generation-suffix lookup hit the first strategy with that id, usually
  from another domain pool.
* **Composite Genesis.** The paper merges one strategy per constituent domain for multi-domain dialogues;
  the code generates 10 strategies directly for the combination string.

**Code vs. paper, minor:**
* fitness weights and ε (Eq. 2);
* Boltzmann τ 0.5 vs 1.0;
* sampling temperature 0.1 vs θx = 0.7 / θe = 0.8;
* mutation is triggered only for critiqued agents, and the child gets zeroed counts instead of inheriting
  the parent's metadata;
* the user-sim strategy is passed into the wrong argument (`prev_agent_result`);
* only MultiWOZ 2.1 data is provided (the paper uses 2.0/2.1/2.2), with a `multiwoz21` path mismatch;
* the DST error-branch NameError.

**Paper-internal:**
* Sec. 3.2 says merge when cosine *distance* exceeds δ; Table 5 and App. B.4 treat δ = 0.8 as a
  *similarity* threshold.
* Sec. 4.2 says "Qwen3-4B outperforms both Llama3-8B and Qwen2.5-7B", but in Table 6 Qwen3-4B is below
  Qwen2.5-7B on all three MultiWOZ versions and below Llama3-8B on 2.2.
