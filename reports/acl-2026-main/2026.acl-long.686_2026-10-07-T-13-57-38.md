- Typical gap is 1–4 AUC points, in either direction.

The training data differs (PTB substitution, below), and best-layer selection is made on an almost flat dev-AUC curve. Both plausibly explain the numeric gaps.

## What I ran

The pipeline is the repo's own code, run per model with `scripts/run_model.sh <codebase> <model> <multilingual 0/1>`:

1. **Inference.** For each dataset in synthetic, blimp, cola, syntaxgym, plausibility (plus scala, itacola, rucola, jcola, sling, blimp-nl for the Llama and Gemma models):
   `python -m baseline.inference --data <ds> --model <model> --batch_size 64`
   This is the repo's inference with my added batched path. It writes last-token hidden states for every layer input plus the LM-head input, and the LM-logprob baseline metrics.
2. **L2 sweep** over every layer, alpha = 2^-2..2^5, 80/20 split, selecting by dev AUC:
   `python -m probe.l2_classifier --data synthetic --model <model> --start_exp -2 --end_exp 5`
3. **Evaluation.** For each eval dataset:
   `python -m probe.test_classifier --model <model> --eval_data <ds> --train_data synthetic --start_exp -2 --end_exp 5`
4. **Metrics.** `scripts/summarize.py` and `scripts/compare.py` collect the metrics. Spearman correlations are computed from the per-example probe scores and logprobs that the repo saves.

**Models.**
- Gemma-2-2B, Gemma-2-9B and Llama-3.1-8B: English and multilingual sets.
- OLMo-2-1124-7B and Olmo-3-1025-7B: English only; the paper also does not test OLMo multilingually.

**Settings that differ from the paper:**
1. **PTB substitution.** The Penn Treebank (LDC99T42, licence-gated, not accessible to me) was replaced by the free NLTK 10% WSJ sample (wsj_0001–0199). It is placed in the repo's expected directory layout and combined, as in the code, with the public Gutenberg-DPO data.
   - Generated synthetic set: 46,289 good/bad pairs (paper size not stated).
   - My estimate is that PTB now supplies about 8% instead of about 20% of the 50k sentences.
2. **Batched inference** (batch 64, length-sorted, right-padded) instead of the released one-sentence loop. That loop runs at about 9 sentences/s in 8-bit, i.e. about 7.5 h per model for the English data alone. I kept the released 8-bit LLM.int8 loading. With int8 the hidden states depend somewhat on batch composition, by about the same amount as int8-vs-fp16 itself.
3. **Llama-3.2-1B** was not run (gated).
4. **Multilingual probe AUC.** I report AUC over the real sentences. The repo's evaluator also counts zero-padded fake "ungrammatical" rows; those values are given in the table and in status.json.

Everything else follows the repo/paper:
- 8-bit models, fp16 autocast;
- last-token states of every layer;
- per-dimension z-scoring;
- SnapML GPU logistic regression with `tol=1e-6, max_iter=1000`;
- alpha grid 2^-2..2^5;
- best layer by dev AUC;
- full benchmark sizes. BLiMP has 67k pairs; SLING 40k pairs; BLiMP-NL 9k pairs. CoLA has 9,594 labeled sentences (the code drops the unlabeled test split).

## Why it is not a full reproduction

- **Missing model.** Llama-3.2-1B is gated (this account has no access). The rest of the main experiments ran; the secondary analyses listed above were not run.
- **Different synthetic training data.** Partly caused by the licensed PTB, partly by the released code's deletion bug, which I fixed. The paper's synthetic dataset itself is not released.
- **Numeric gaps.** The probe numbers are frequently outside the paper's bootstrap CIs, though the direction of every main comparison holds except OLMo-3-7B BLiMP paired accuracy. Likely contributors:
  - the different training text;
  - batch-dependent int8 hidden states;
  - a flat dev-AUC curve that makes best-layer selection fragile.
- **OLMo-2-7B baseline is stronger than reported:**

  | OLMo-2-7B logprob | Ours | Paper (CI) |
  |---|---|---|
  | BLiMP ACC | 0.815 | [0.77, 0.78] |
  | BLiMP AUC | 0.628 | [0.61, 0.61] |
  | CoLA AUC | 0.707 | [0.67, 0.69] |

  This shrinks the probe's margin, although the probe still wins (0.842 / 0.752 / 0.802). A 600-pair check showed batching does not inflate it (unbatched 0.788 vs batched 0.778). The cause is unknown; possibly a different checkpoint revision.

## Discrepancies

1. **Deletion perturbation never applied** (code vs. paper, major, affects results). In `data/helpers.py` the deletion perturbation never fires because of the `is_exp` attribute. The paper describes and illustrates deletions (Sec. 2.1, Table 1).
2. **Padded rows in multilingual AUC** (code vs. paper, major, affects results). In `probe/helpers.py`, the single-sentence multilingual benchmarks (ScaLA, ItaCoLA, RuCoLA, JCoLA) are evaluated with N extra all-zero rows labeled ungrammatical, which changes probe AUC. Example: Gemma-2-2B JCoLA is 0.547 with the rows vs 0.615 without; the paper reports 0.61. For ItaCoLA and JCoLA the paper's numbers agree better with the "real rows" values.
3. **Unlabeled RuCoLA test sentences counted as unacceptable** (code vs. paper, major, affects results). The RuCoLA evaluation includes 2,789 unlabeled test sentences (label -1) counted as unacceptable. The paper's Table 5 counts (13,445 / 57.6%) confirm the paper's RuCoLA numbers were computed this way, which is not a valid acceptability evaluation for those sentences.
4. **8-bit quantization** (code vs. paper, minor, affects results). Models are loaded in 8-bit LLM.int8 with fp16 autocast. The paper does not mention quantization.
5. **Eval-set normalization** (code vs. paper, minor, affects results). Evaluation sets are z-scored with their own mean/std rather than with training-split statistics (App. D describes training-split statistics).
6. **CoLA size** (code vs. paper, minor). Table 5 lists 10,657 sentences; the code evaluates 9,594 labeled ones.
7. **Duplicate sentences in ScaLA and JCoLA** (code vs. paper, minor). The Table 5 sizes for ScaLA (10,762) and JCoLA (9,154) come from concatenating all HF splits, which includes duplicates: ScaLA `full_train`, and JCoLA's two identical out-of-domain validation splits.

Paper-internal note, not counted as a discrepancy: Table 11 gives identical logprob CIs for Gemma-2-2B and Gemma-2-9B. Our runs show the two models' logprob scores are genuinely almost identical (BLiMP 0.755 / 0.580 vs 0.753 / 0.580; CoLA 0.636 vs 0.633), so this is plausible.
