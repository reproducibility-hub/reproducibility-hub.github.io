## Not reproduced from scratch (and why)
* **Unigram surprisal for acontextual (L/T) and contextual inventories**: the released chunked estimator ran >30 min for a
  single sample on our node (paper: ~20 s / 60 s / 8 min per sample; ≥3 h / 8 h / 2–3 days for 500 samples even at that speed).
  With the node heavily loaded by other jobs (load avg ~95 on 14 allotted cores) and memory growing ~14 GB per worker
  (one of my processes was OOM-killed when running 10 workers), this was infeasible in the 48 h budget. These inventories use the
  released unigram files in Stages B; Stage A uses the released files throughout, as the README instructs.
* **Character text_units/subject_units**: `units-surprisal pipeline --transducer character` sat >45 min at ~48 GB RSS building/
  applying the 50k-token→byte FST, and was stopped; the released files were used (other inventories regenerate identically).
* Raw-MECO fixation extraction (`preprocessing/meco_preprocessing.py`, from Re et al. 2025) was not rerun; `meco_preproc` was taken
  from the HF dataset.

## Codebase completeness: MISSING_SCRIPTS
The README's reproduction route (download released dataframes → `run_all_gamm.sh`) ran with **no code edits** and reproduces
Table 9 exactly. The level reflects the from-scratch pipeline:
* The unigram→GAMM step is missing: none of the released estimators (`unigram/estimate.py` `_run_estimation`,
  `run_model_tokens_estimation`, `run_character_estimation`) writes the `unit_original` column that `run_gamm.R` requires
  (`stop("Unigram file is missing 'unit_original'; regenerate with the new aggregator.")`); the "new aggregator" isn't released.
  For tokens the released estimator also merges `The`/` The` into one stripped unit (logsumexp), whereas the released file has one
  row per whitespace-inclusive form. I wrote `scripts_mine/unigram_tokens_per_form.py` (per-form RB estimator) and added
  `unit_original = unit` for characters.
* The Makefile's `all`/`surprisal` targets never run the `unigram` stage; the CLI `unigram --n-samples` default is 10000 (paper 500)
  and the chunked mode/aggregation used for the paper isn't exposed in the CLI (I wrapped the library's existing
  `chunk_start`/`aggregate_chunks` in `scripts_mine/unigram_job.py`).
* `units-surprisal surprisal --transducer model_tokens` crashed with CUDA OOM inside genlm-bytes' `AsyncTokenByteTrie` on a 141 GB
  H200 (memory grows until full, with vLLM at 0.9 or 0.3 of the GPU); `--transducer character` was host-OOM-killed (>28 GB, growing)
  while building the FST. Replaced by `direct_token_surprisal.py` and `char_surprisal_genlm_bytes.py`.
* genlm-backend's default vLLM `gpu_memory_utilization=0.9` leaves the trie no room; `scripts_mine/cli_patched.py` caps it
  (environment-level, no logic change). vLLM itself had to be installed (optional extra).
* `scripts/plot_gamm_results.py` (figures) was not run; I tabulated the summaries with `scripts_mine/table9.py`.
No files in `./codebase` were modified (`git status` clean apart from the git-ignored downloaded data).

## Discrepancies
1. code_vs_paper (major, affects from-scratch results): App. E/F define unigram surprisal per unit with its attributed whitespace
   (GAMM joins on `unit_original`); released `rb_model_tokens.py` sums the stripped and space-prefixed token probabilities into one
   stripped unit and no released estimator emits `unit_original`; the paper's unigram files came from an unreleased aggregator.
2. code_vs_paper (minor, no effect on reported numbers): §6.3 says token surprisal "is read directly from p_Σ"; the released
   `surprisal --transducer model_tokens` marginalizes through an identity byte FST + genlm-bytes beam. Released numbers equal direct
   GPT-2 token surprisal to 1e-4 bits.
3. code_vs_paper (minor): Table 7 caption says character surprisal comes from Vieira et al. (2025) (genlm-bytes) "rather than through an
   FST composition"; the registry routes `surprisal --transducer character` through a token→byte FST + TransducedLM.
4. code_vs_paper (minor): unigram CLI default `--n-samples 10000` vs 500 in Table 6.
No paper-internal inconsistencies found (Table 4 → Table 8 counts, §6.5 text and Table 9/Fig. 5 agree).
