# Reproduction report: GenDis (ACL 2026, 2026.acl-long.107)

**Verdict: PARTIALLY_REPRODUCED** — result match (after fixes): **MIXED**; as released: **MIXED** (no source edits were needed, so both are the same); coverage: **SCALED_DOWN** (fewer seeds than the paper's 4 runs); codebase completeness: **MINOR_FIXES**.

## Summary
- Code: https://github.com/cx9941/GenDis (linked from the paper). It contains the full method (Qwen2/Qwen3/Llama heads, CCA, curriculum pseudo-labelling, dispersion-aware generative pseudo-labelling, SK/K-means evaluation), the five datasets with the fixed known-class splits and labeled subsets, and `scripts/run.sh`. Baseline implementations are not released.
- We ran the released `scripts/run.sh` configuration (Qwen2.5-7B-Instruct, 4-bit QLoRA, seed 2) on **all 15 Table-1 settings** (BANKING, CLINC, HWU, MCID, StackOverflow x KCR 0.25/0.5/0.75, LAR 0.1). We added seeds 1/3/4 for MCID and HWU (all KCRs), so those two datasets are 4-run means like the paper; BANKING/CLINC/StackOverflow are single runs (seed 2).
- Of 60 GenDis numbers in Table 1 (ARI, NMI, K-ACC, N-ACC), **44 are within tolerance** (≤1 point or ≤5% relative), **9** are outside tolerance but still above the best baseline the paper reports, and **7** fall below the paper's best baseline.
  - CLINC and StackOverflow match closely (single run).
  - MCID (4-seed mean) matches on most cells but has a large seed variance (sd up to 12 points).
  - HWU (4-seed mean) matches on NMI and most ACC cells, but ARI is 2.5-6.3 points lower at every KCR (still above the best baseline).
  - **BANKING is consistently lower** (ARI −3.3 to −6.8, K-ACC −6.2 to −8.1; single run). 6 of the 7 cells below the paper's best baseline are BANKING; the 7th is CLINC-0.75 N-ACC.
- So the central claim (GenDis clearly beats prior GCD methods on 5 benchmarks) is supported on most datasets, but not uniformly. This is why the overall label is MIXED.
- Notable finding: the release selects the test checkpoint by dev K-ACC of the K-means-on-MLP view. In 35 of 36 of our completed runs this picked a checkpoint from **before the generative (dual-view) pseudo-labelling stage starts** (epoch 10). So the Table-1-style numbers mostly come from a model that has not gone through Sec 4.4's generative pseudo-labelling. Evaluating the final-epoch checkpoint instead (where we have it) improves BANKING substantially (e.g. BANKING-0.25 ARI 58.7 → 65.8) but hurts StackOverflow-0.5 (ARI 87.4 → 81.2).

- Paper hyperparameters (App. D.5) vs released run.sh, HWU seed 2: the paper config is closer to the paper at KCR 0.25 (ARI 70.4 vs 65.4) and KCR 0.75 (77.5/90.6/86.0/85.0 vs paper 76.7/90.5/84.5/88.3, all within tolerance), but worse at KCR 0.5 (ARI 66.4 vs 73.6). So the released config is not obviously the one behind Table 1, and neither config reproduces every cell.

(`init_parameters.py` overrides num_return_sequences to 4 = paper's k=4, and cca_pseudo_loss_weight to 0.)

Paper-hyperparameter check (App. D.5) on HWU: same command with `--gen_loss_weight/--cca_loss_weight` = (5,1)/(2,0.1)/(5,0.01) for KCR 0.25/0.5/0.75, `--cca_k 32 --num_train_epochs 15` (warm-up epochs kept at 5/10 since the paper does not give them).

Number reported as "ours": following paper Sec 4.5, for each run we take the K-means+Sinkhorn clustering of the two views (generative view = `sk-kmeans_class`, discriminative view = `sk-kmeans_mlp`) and pick the view with higher K-ACC on the validation set (`eval-dev`), then report its test ARI/NMI/K-ACC/N-ACC (`scripts_mine/aggregate.py`). We also show the plain `kmeans_mlp` variant (the view the code uses for checkpoint selection) in `tables.md`/`results_*.json`.

Settings that differ from the paper: (1) released run.sh hyperparameters instead of App. D.5 (see Discrepancies); (2) single seed (seed 2, the run.sh seed) for BANKING/CLINC/StackOverflow, vs. mean of 4 runs in the paper; (3) up to 5 jobs shared one H200 concurrently (no effect on results except two OOM crashes that were resumed from checkpoints: CLINC-0.5 resumed from epoch 7, BANKING-0.25 from epoch 2; MCID-0.5 seed 3 crashed during eval and was re-evaluated).

## Why not fully reproduced
- Compute/time: the full Table 1 needs 60 runs of 7B QLoRA training with generation-based pseudo-labelling (~3-9 GPU-hours each on a shared H200); within 48 h we ran all 15 settings once plus extra seeds on the two smallest datasets.
- BANKING is consistently below the paper. Possible causes: the hyperparameter gap between run.sh and App. D.5, seed variance (single seed), and the checkpoint-selection behaviour (the final-epoch checkpoint is much closer to the paper on BANKING). We cannot determine which config produced the paper's numbers.
- Baselines are not released, so "beats baseline X" is only judged against the paper's own baseline numbers.

## Discrepancies
- **[code_vs_paper, minor] scripts/run.sh (gen_loss_weight, cca_loss_weight)** — paper: App. D.5: (lambda_gen, lambda_cca) = (5.0, 1.0) for KCR=0.25, (2.0, 0.1) for KCR=0.5, (5.0, 0.01) for KCR=0.75; code: run.sh uses gen_loss_weight=1, cca_loss_weight=0.01 for every KCR. Affects results: True.
- **[code_vs_paper, minor] scripts/run.sh (cca_k)** — paper: CCA subspace dimension d = 32; code: cca_k=16. Affects results: True.
- **[code_vs_paper, minor] scripts/run.sh (num_train_epochs)** — paper: 15 training epochs; code: num_train_epochs=12 (semi warm-up 5, generative warm-up 10). Affects results: True.
- **[code_vs_paper, minor] code/init_parameters.py (gradient_accumulation_steps default 2) + run.sh per_device_train_batch_size=32** — paper: batch size 32; code: effective batch 64 (32 x grad-accum 2). Affects results: True.
- **[code_vs_paper, minor] configs/args.json** — paper: LoRA PEFT on Qwen2.5-7B-Instruct (no quantization mentioned); code: QLoRA: base model loaded in 4-bit NF4 with double quantization (use_4bit_quantization, use_nested_quant), LoRA r=8, alpha=16, all-linear; embeddings resized for added ChatML special tokens. Affects results: True.
- **[code_vs_paper, minor] code/models/modeling_qwen2.py::compute_loss** — paper: L_gen = L_auto + L_con, the whole L_gen scaled by lambda_gen; code: gen_loss_weight scales only the full-sequence LM loss (L_auto); the label-token loss L_con is weighted by class_loss_weight=1 independently. Affects results: True.
- **[code_vs_paper, minor] code/utils/metric.py::compute_metrics / trainer.test (test-time view selection)** — paper: Sec 4.5: K-means + Sinkhorn-Knopp on each view, choose the view with higher K-ACC on the known-class validation set; code: evaluation writes 10 variants (kmeans / sk-kmeans on class, mlp, com hidden states; argmax / SK of mlp & com logits); the validation-based view selection is not implemented (we implemented it in scripts_mine/aggregate.py). Affects results: True.
- **[code_vs_paper, minor] code/utils/utils.py::get_best_checkpoint + Trainer(metric_for_best_model=kmeans_mlp_K-ACC, save_total_limit=2)** — paper: Sec 5.1: model tuned using a known-class validation set; the method is described as a 3-stage pipeline ending with dual-view (generative) pseudo-label learning; code: test loads the LOWEST-numbered surviving checkpoint (= dev-best unless dev-best is the last epoch, in which case it silently loads the second-to-last). In our runs the dev-selected checkpoint was from epochs 1-9 in 35/36 runs, i.e. before the generative pseudo-labelling stage (epochs >= 10) ever ran, so the reported numbers mostly come from a model that never used dual-view pseudo-label learning. Affects results: True.
- **[code_vs_paper, minor] scripts/run.sh dataset loop** — paper: five datasets; code: loop also includes 'ecdt', which is not shipped (would crash after the five real datasets; set -o errexit). Affects results: False.
