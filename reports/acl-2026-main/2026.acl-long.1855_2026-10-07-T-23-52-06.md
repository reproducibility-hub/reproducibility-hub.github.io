# Reproduction report — HiEdit: Lifelong Model Editing with Hierarchical Reinforcement Learning
ACL 2026 (long), Anthology ID 2026.acl-long.1855 — code: https://github.com/yangfanww/hiedit (commit 1d76ab4, linked in the paper)

## Verdict
**PARTIALLY_REPRODUCED** — result match **MIXED**, coverage **SUBSET**, codebase completeness **MINOR_FIXES**.

* HiEdit's own numbers on Llama-3-8B-Instruct reproduce well. The ZsRE MEND cell was run twice (83.69/81.93/44.49/74.00 and 84.18/82.50/41.94/75.60 vs paper 83.58/81.88/41.75/73.73). That covers all three Llama-3 HiEdit cells I ran (ZsRE MALMEN-style = Table 1, ZsRE MEND-style = Table 5, CounterFact MEND-style = Table 1), and the pre-edited rows match almost exactly.
* The central claim is that HiEdit beats RLEdit (8.48 % on average). It only partly holds when RLEdit is run through the same released pipeline (HiEdit with K = L, which the paper itself says "degenerates into RLEdit").
  * HiEdit consistently wins on Specificity and Edited Retention.
  * On Efficacy and Generalization it is ~0.4–1.8 points *behind* RLEdit in two of three settings.
  * The re-run RLEdit baselines are 3–5 points stronger than the paper reports in the MALMEN setting (flag `BASELINE_STRONGER_THAN_REPORTED`).
* The released training procedure is very fragile. The hypernetworks get a single Adam step after the whole 8000-edit trajectory. In one of two RLEdit (K = 12, MEND) runs, that step made the per-layer edit learning rate negative for all gate_proj layers, and the model collapsed to 0 on every metric.
* The code also differs in important ways from the method the paper describes (see Discrepancies). The high-level router receives gradient only from the L2 penalty, and only at the first training step. As a result, every HiEdit run edited one fixed set of K layers rather than making instance-dependent layer choices.
* Gemma-2-9B (half of Table 1) was not run: one Gemma run took ≈15 s/step, ≈34 h for the 8000-step training alone, which does not fit the 48 h budget alongside the Llama runs.

## Setup
* Environment: conda env `./env` (Python 3.10), torch 2.4.1+cu121, transformers 4.45.2, hydra-core, omegaconf, swanlab (`SWANLAB_MODE=disabled`), scikit-learn, datasets. The repo has no requirements file; versions were chosen by me.
* Hardware: 1× H200 141 GB, shared by up to 4 concurrent runs.
* Models: `meta-llama/Meta-Llama-3-8B-Instruct` (the README names the Instruct model; the paper says "Llama-3-8B"), loaded from the shared HF cache via `codebase/hugging_cache/llama-3` (symlink).
* Data: `data/raw/{zsre,counterfact}` shipped in the repo. Training uses the train split (shuffled, unseeded, first 8000). Evaluation edits the first 8000 items of the eval split sequentially, one per edit, then evaluates all of them. Ret = mean(Eff, Gen) over the first T0 = 500 edits.
* Settings follow paper Table 4 and the repo configs:
  * ZsRE: gate[11-15] + up[18-24], L = 12, K = 6.
  * CounterFact: gate[22-30] + up[22-30], L = 18, K = 9 (config `config/model/llama-3-cf.yaml`, written by me from the commented-out lines of `llama-3.yaml` + Table 4).
  * MEND style: rank 1920; MALMEN style: rank 1024; other hyperparameters at repo defaults; 1 epoch.
* Baseline "RLEdit" = the same pipeline with `editor.n_layers = L` (K = L: mask is all-ones, the intrinsic reward is 0). The paper (Table 5 "w/o HiNet (RLEdit)", App. C.2/C.5) defines RLEdit as exactly this degenerate case. The original RLEdit codebase was not used.

Commands (all run from `codebase/`, via `run_one.sh TAG <overrides>`; logs in `logs/TAG.log`):
```
python main.py dataset=zsre model=llama-3 editor=hieditmm num_seq=8000 num_pre=500 glue_step=0 editor.n_layers=6  editor.rank=1024   # llama_zsre_mm_k6
python main.py dataset=zsre model=llama-3 editor=hiedit   num_seq=8000 num_pre=500 glue_step=0 editor.n_layers=6  editor.rank=1920   # llama_zsre_mend_k6 (+ _rep2)
python main.py dataset=counterfact model=llama-3-cf editor=hiedit num_seq=8000 num_pre=500 glue_step=0 editor.n_layers=9 editor.rank=1920  # llama_cf_mend_k9
# RLEdit baselines: same with editor.n_layers=12 (ZsRE, MEND: llama_zsre_mend_k12 and _rep2; MALMEN: llama_zsre_mm_k12) and n_layers=18 (CF: llama_cf_mend_k18)
```
* The evaluation phase of `llama_zsre_mend_k6` ran out of GPU memory: 4 jobs shared the GPU, and its training had already finished. I re-ran only `sequential_valid` from the checkpoints the run had saved (`scripts/eval_from_ckpt.py`, log `logs/llama_zsre_mend_k6_eval.log`).
* The Pre-edited rows come from `scripts/pre_edit_eval.py`, which uses the repo's own data classes and `succ_ratios`.

## Discrepancies
1. **code_vs_paper, major — high-level router training** (`editor/hiedit.py` / `hieditmm.py`, `train()`; `nets.py: HiNet`).
   * Paper (Eq. 5, 7, 9): the high-level policy is trained with the intrinsic reward r_high = r_low(partial) − r_low(full), via a straight-through TopK.
   * Code: `loss_hi = loss_low − full_loss.detach()`. The edit and locality losses are computed on a model whose weights were changed in place via `.data +=`, so they carry no autograd path to the mask. HiNet therefore gets gradient only from the L2 term `reg_coef·Σ‖mask·ΔW‖²`.
   * After the first step, `hi_net.requires_grad` is left False when the next step's forward pass runs, so HiNet receives gradient only at step 1 of 8000.
   * Verified with `scripts/check_hinet_grad.py`: with `reg_coef=0` the HiNet gradient is exactly 0, and the accumulated gradient norm is constant from step 1 on (`logs/check_hinet_grad.txt`).
   * HiNet's own input normalizer (`Encoder.normalizer`) is never updated (mean 0, std 0 → inputs divided by 1e-7).
   * Consequence: in every HiEdit run, exactly K of the L modules ever received a low-level gradient, and the other K kept their initial learning rate of 1e-6 (`logs/checkpoint_lr_values.txt`). The two MEND/ZsRE HiEdit runs used different fixed sets (modules {0,1,5,6,7,8} vs {0,3,5,6,7,8}), i.e. the selection depends on the random initialisation. The router selected one fixed set of K layers for all 8000 training edits, not an instance-aware selection.
   * Affects results: yes.
2. **code_vs_paper, major — optimisation schedule.**
   * Paper (Sec. 4.3): hypernetworks are optimised after traversing the editing trajectory.
   * Code: gradients are accumulated (and re-clipped every step) over the 8000-edit trajectory, followed by a **single** Adam step (lr 1e-5) for both hypernetworks, with `n_epochs=1`.
   * Since the first Adam step is ≈ lr·sign(g), the per-layer edit learning rate moves from 1e-6 to either 1.1e-5 or −9e-6. In RLEdit run 1 all five gate_proj rates became −9e-6, the edits went in the wrong direction, and the model collapsed (all metrics 0). Outcomes therefore depend on the sign of one accumulated gradient.
   * The paper does not state that only one optimizer step is taken. Affects results: yes.
3. **code_vs_paper, minor — base model.** The paper says "Llama-3-8B"; the README/code use Meta-Llama-3-8B-Instruct. Since the pre-edited numbers match, the paper's numbers were presumably produced with the Instruct model.
4. **code_vs_paper, minor — layer config.** The paper's CounterFact layer range (gate/up 22–30) is only present as commented-out lines; the shipped config is the ZsRE range. run.sh/README only give ZsRE examples with `num_seq=2000`, not 8000.
5. **paper_internal — Table 1 vs Table 5.**
   * Table 1 says RLEdit and HiEdit rows use "the style yielding optimal performance". For Llama/ZsRE, Table 1 reports MALMEN-style HiEdit (82.10 / 79.99 / 48.42 / 75.16), while Table 5's MEND-style HiEdit has higher Eff/Gen (83.58 / 81.88) but lower Spe/Ret.
   * The CF MALMEN-style RLEdit in Table 5 (58.60 …) differs from Table 1's RLEdit (66.35, which is MEND-style).
   * The selection is not stated per cell. Minor, does not change conclusions.
6. **paper_internal — layer numbering.** Fig. 6 lists layers 11–15 and 18–24 as `layers.x.mlp.gate_proj`, but layers 18–24 are up_proj in Table 4 / config. Cosmetic.
