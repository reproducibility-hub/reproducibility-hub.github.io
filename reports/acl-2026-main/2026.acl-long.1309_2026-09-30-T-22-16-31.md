No checkpoints or processed data are released, so RAM was **retrained from scratch** following the paper's recipe (Sec. 4.1) on 1× H200. The training data was a 100K mixture with 20K samples each from NQ, HotpotQA, 2WikiMQA, NarrativeQA and MultiNews. Settings: 20K-token truncation, batch 32, lr 1e-5 with linear decay, 1 epoch = 3125 steps, segment size 50, α ∈ {2,4,8,16,32} sampled per sample, contrastive loss with τ = 0.1. Training took 12 h 14 min. Evaluation used the full test sets with bs = 1 and greedy decoding.

## What was run (exact commands)

All paths are relative to the attempt directory.

1. **Environment.** `conda create -p ./env python=3.10`, then `pip install torch==2.4.0 (cu118) transformers==5.1.0 datasets==4.3.0 peft==0.13.0 deepspeed==0.18.7 accelerate==1.13.0 safetensors==0.7.0` (the README pins). FlashAttention was not installed; the code uses the default SDPA attention.
2. **Data.** `env/bin/python scripts/prep_data.py`, which I wrote:
   - **NQ:** QGC's processed NQ from the Google Drive link in the QGC README; this is the "processed version (Liu et al. 2024a; Cao et al. 2024)" the paper cites. 20 docs per question, 2,655 test questions, gold document at position 0 in both train and test. 20K training questions sampled.
   - **HotpotQA:** HF `hotpotqa/hotpot_qa` distractor split; validation has 7,405 questions; 20K train.
   - **2WikiMQA:** HF `framolfese/2WikiMultihopQA`. The *dev* split (12,576) was used because the test split has no answers; the paper's Fig. 4 example is dev[0]. 20K train.
   - **NarrativeQA:** HF `deepmind/narrativeqa`, full story text. Test was filtered to ≤32K Qwen tokens, giving 1,093 questions with average 16.6K and max 32.6K tokens (this matches the paper's "avg 16K, max 32K"). Train documents were truncated to 20K tokens; 20K train questions.
   - **MultiNews:** HF `alexfabbri/multi_news` raw files. The "question" is `Write a summary of the news articles above.`; 5,621 test samples; 20K train.
3. **Training.** `bash scripts/train_full.sh` runs `torchrun instruction_finetune.py` with Qwen/Qwen3-4B-Instruct-2507 and these flags:
   - `--per_device_train_batch_size 1 --gradient_accumulation_steps 32 --learning_rate 1e-5 --lr_scheduler_type linear --warmup_ratio 0.1 --weight_decay 0.01 --max_steps 3125`
   - `--compression_rate 50 --sample_compression_rates 2,4,8,16,32 --use_contrastive_loss True --contrastive_loss_weight 1.0 --contrastive_temperature 0.1`
   - `--use_transform_layer True --num_mem_fusion_layers 1 --model_max_length 20000`
   - Environment variable `RAM_FP32_MASTER=1`.
   - Log: `train_full.log`.
4. **Evaluation.**
   - `scripts/eval_one.sh <ckpt> <dataset> <keep_ratio> <out> [max_new_tokens]` wraps `ft_inference.py` with `--compression_rate 50 --model_max_length 32768`, bs = 1, greedy. Here 4x means keep_ratio 0.25 and 8x means 0.125, i.e. k = ⌊N/α⌋ (Eq. 3).
   - QA uses max_new_tokens 100 (the code's value). MultiNews uses 512 (100 is too short for ~216-word summaries; our predictions average 214 words).
   - Fig. 3 runs NarrativeQA at keep 0.5 / 0.0625 / 0.03125.
   - Drivers: `scripts/run_all_evals.sh`, `scripts/chain2.sh`, plus manual launches of the two MultiNews runs. Logs are in `logs/eval_*.log`, raw predictions and metrics in `runs/eval/`, and the aggregate in `runs/summary.json` (`scripts/summarize.py`).
5. **Latency.** `python scripts/latency_ram.py 100` measures the first 100 NarrativeQA test questions (5 warm-up samples excluded) with bs = 1 on an otherwise idle H200. Compression time is the timed `generate_encore_memorys` call (parallel encoding, selection and skimming); inference time is the decoder's generation. Output: `runs/latency_ram.json`.
6. **Sanity check only.** `scripts/orig_prompt_baseline.py` feeds the uncompressed context to Qwen3-4B-Instruct with my own chat prompt. The paper's prompt is unknown, so this is not comparable and is not used for any judgement. Results: NQ EM 3.7 / F1 20.6 / answer-containment 68.5. The model is verbose, so strict EM is low.

Metrics are the code's own (`eval_utils.py`): SQuAD-normalised strict EM and token F1, each taken as the max over reference answers, reported ×100. I also report an answer-containment accuracy ("acc") in `runs/summary.json`.

## Settings that differ from the paper

- **Backbone:** only Qwen3-4B-Instruct-2507; LLaMA-3.1-8B-Instruct was not run (time budget).
- **Hardware / precision:** 1× H200, with no DeepSpeed and fp32 master weights under bf16 autocast. The paper used 8 GPUs; the released config is DeepSpeed ZeRO-2 with CPU offload, which needs more than the 111 GB host RAM available here, and the GPU-only ZeRO-2 variant produced NaNs after step 1. The effective batch size is identical: 32 = 1 × 32 gradient-accumulation steps.
- **Contrastive positives:** the code's answer-string matching was used for all datasets. The paper uses gold positions for NQ/Hotpot/2Wiki and Qwen3-235B labels for NarrativeQA; that labelling is not released. Positives were found for 94% (NQ), 90% (HotpotQA), 65% (2Wiki), 20% (NarrativeQA) and 0% (MultiNews) of training samples.
- **Warmup and seed:** warmup ratio 0.1 (from train.sh; the paper doesn't say) and a single run with seed 42 (the paper reports no seeds or std).
- **Prompting:** the decoder prompt is the code's `Question:{q}\nAnswer:`, with no chat template. For MultiNews the summarisation "question" and the 512-token generation cap are my choices; the paper gives neither.
- **2WikiMQA split:** the dev set was used instead of "test" (the test split has no public answers; the size, 12,576, is the same).

### Why our QA numbers are higher (not resolved)

- I found no bug that would explain the gap.
- The paper's NQ numbers are internally inconsistent with the stated metric: EM > F1 is impossible with SQuAD EM/F1 (see Discrepancies). Its metric implementation therefore differs from the released one, at least for NQ.
- Training differs in a few places that could matter:
  - fp32 master weights instead of DeepSpeed;
  - string-matched positives instead of gold/LLM labels;
  - NQ gold documents always at position 0 in the QGC train and test files (the paper likely used the same files).
- Under the code's own metrics our retrained model is simply stronger on QA than reported. No flags apply: no released outputs exist, and no baseline was run through the released pipeline.

- `train_full.sh`: the training launcher with paper settings. train.sh defaults to MAX_STEPS=1, batch 1, cosine, segment 16.

**Changes to the released code:**
1. `ram_modeling.py` — **logic.** Added `--sample_compression_rates`. During training each sample keeps k = ⌊N/α⌋ segments with α drawn uniformly from {2,4,8,16,32}, as in paper Sec. 3.2/4.1. The release only supports a fixed `keep_ratio`, so one trained model could not cover all rates.
2. `ram_modeling.py` — **validator.** `ModelArguments.__post_init__` only allowed segment widths 16/32; relaxed so the paper's 50 is accepted.
3. `training_utils.py` — **bug.** With transformers 5.1.0, `Trainer._save` always writes safetensors for non-`PreTrainedModel` modules, which raises on the tied embedding/lm_head tensors of encoder, decoder and fusion module. No checkpoint, including the final `save_model`, could be written. Added `RAMTrainer._save`, which clones the tensors first. This doesn't affect results.
4. `ram_modeling.py` — **infra.** `RAM_FP32_MASTER=1` loads the trainable modules in fp32 so training under bf16 autocast keeps fp32 master weights. Used because DeepSpeed was dropped: the GPU-only ZeRO-2 path NaN'd after step 1, and the CPU-offload config exceeds host RAM. DeepSpeed also required `module load CUDA/12.6.0` and `torch_adam`.
5. `ram_modeling.py` — **efficiency only.** `logits_to_keep=1` for the encoder and fusion LMs, whose logits are discarded. `instruction_finetune.py`: `datasets.map(num_proc=…)`.
6. `ft_inference.py`, `eval_utils.py`, `ram_modeling.py` — **evaluation.** `--max_new_tokens` (was hard-coded to 100), an `--eval_tag` for output names, and an extra containment metric. The EM/F1 computation is unchanged.
7. Command-line values only: segment 50, linear schedule, batch 32, 3125 steps, and test-time `--model_max_length 32768` (the default 28000 would truncate NarrativeQA).

Note: with transformers 5.1 the Trainer does not divide the loss by the gradient-accumulation steps, because `RAM.forward` takes `**kwargs`. The logged loss is therefore a 32-sample sum. Adam is scale-invariant and this is the README-pinned behaviour, so I left it unchanged.

## Discrepancies

### Code vs. paper
| Where | Paper | Code | Severity |
|---|---|---|---|
| `ram_modeling.py` encoder (`encoder_layers=8`) | Trainable LLM-based encoder | Encoder is the backbone truncated to its first 8 layers | major |
| `_align_compressed_memory` (`use_transform_layer=True` in train.sh/test.sh) | Skimmed vector → W_align only (Eq. 5) | Extra 1-layer transformer "memory fusion layer" before the linear alignment. The README says it is not invoked, but it is. | major |
| `_select_keep_mask` / train.sh | α sampled per training sample from {2..32}; k = ⌊L/(αL_seg)⌋ | One fixed keep_ratio (0.25) during training | major |
| `_compute_contrastive_loss` | Eq. 8: mean over positives of −log softmax_i | −log(sum of positive probabilities), i.e. logsumexp(all) − logsumexp(pos) | major |
| `data_utils.build_positive_segment_mask` | Gold answer positions; Qwen3-235B labels for NarrativeQA | Answer-string token match for all datasets (`isgold` ignored) | major |
| segment width (`compression_rate`) | 50 | Default 16, validator allows only 16/32 | minor |
| train.sh | Batch 32, linear decay | Batch 1, GA 1, MAX_STEPS=1, cosine | minor |
| `model_max_length=28000` | Test up to 32K (NarrativeQA) | Inference truncates at 28K by default | minor |
| `generate(max_new_tokens=100)` | MultiNews summarisation | Hard 100-token cap for all tasks, no summarisation pipeline | minor |

### Paper-internal
- **NQ EM vs F1.** RAM's NQ EM exceeds F1 in Table 1 (Qwen 4x 66.59 vs 59.97; 8x 61.09 vs 56.15; LLaMA 4x 65.35 vs 59.22), in Table 2 and in Table 6. Under the stated SQuAD-style EM/F1 (and the released `eval_utils.py`), EM ≤ F1 for every example, while other rows (e.g. Original Prompt 32.77/44.44) have EM < F1. The RAM NQ EM numbers must therefore come from a different metric.
- **Table 4 vs Table 1.** Table 4's "Default" row (captioned Qwen3-4B, 8x: 62.41/57.14, 39.63/45.24) equals Table 1's **LLaMA-3.1-8B** 8x RAM row. Table 1's Qwen 8x RAM row is 61.09/56.15, 40.24/45.66.
- **Fig. 3 vs Table 1.** Fig. 3 shows NarrativeQA RAM EM of ~20.8 at 4x and ~19.1 at 8x, while Table 1/2 give 19.45 at 4x and 19.92 at 8x.
- **Eq. 2 vs text.** The text says "cosine similarity … followed by a softmax", but Eq. 2 uses the dot product r_qᵀr_i/τ.
