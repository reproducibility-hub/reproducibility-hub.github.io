# Reproduction report — SabreCoder (ACL 2026 long 1189)
"From Logical to Computational Sparsity: Structure-Aware Block-Sparse Attention for Long-Code Completion"

## Verdict
- **Verdict: PARTIALLY_REPRODUCED**
- **Result match (after fixes): MIXED.** As released: **MIXED**. No source edits were made, so the two are identical.
- **Coverage: SUBSET.** SabreCoder and the dense baseline were run on all 5 main-table settings at the paper's scale. Only SabreCoder is released, so the six sparse baselines were not run.
- **Codebase completeness: TRIVIAL_FIXES.** Needed dependency pins and a CWD workaround for a path bug. No code edits.

### Summary
1. **Setup and data reproduce exactly.**
   - The release's data pipeline gives exactly the paper's sample counts: LCC 12k–14k bucket 129/90/95, CCEval 400/400.
   - Dense attention gives the paper's Dense (Triton) row:
     - LCC: exact on EM, F1, ES and PPL, to the second decimal.
     - CCEval: EM exact, F1/ES within 1.3 points.
   - The "w/o Similarity Edges" ablation run through the release reproduces paper Table 7 exactly (LCC EM/F1/ES) and Table 3 EM exactly.
2. **The full SabreCoder accuracy does not reproduce on LCC.**
   - The paper claims SabreCoder is within ~1 EM point of dense. With the release defaults we get:
     - LCC EM 30.23 / 40.00 / 33.68, vs paper 36.43 / 47.78 / 38.95 (Python / Java / C#).
     - That is 6.2–8.9 points below dense.
   - With the paper's Appendix B.4 hyperparameters: 30.23 / 42.22 / 33.68.
   - None of the 12 points of the paper's own tuning grid (App. C.2) recovers the paper's LCC numbers. Best per language: Python 30.23, Java 42.22, C# 35.79.
3. **On CCEval it partly reproduces.**
   - With the Appendix B.4 hyperparameters, EM is 16.00 / 17.25 vs paper 17.25 / 18.75 (dense 17.00 / 19.75), within ~1–2.5 points of dense.
   - The release defaults give 13.25 / 14.75.
4. **Speed: the trend holds, the magnitude is smaller.**
   - Measured fairly on an H200 (warm Triton cache, same kernel with all causal blocks as the dense reference), SabreCoder prefill is:
     - 19–26% faster on LCC,
     - 34–36% faster on CCEval.
   - The paper reports 40–45% and 50–55% on an RTX 3090.
   - Against FlashAttention-backed SDPA the gain is only 9–17% (LCC) and 27–29% (CCEval).
   - The release's own TTFT measurement includes a Triton JIT recompile on almost every sample. Measured that way, SabreCoder is slower than dense SDPA.

## Why it is not fully reproduced
- **Accuracy (main claim).** The release produces the paper's dense numbers and its no-similarity ablation exactly, but not the full method. The released similarity configuration — either the code defaults or the paper's stated defaults — and the documented tuning grid all lose 4–9 EM points vs dense on LCC. The paper reports ≤1.1. The tuned per-dataset configuration that produced Tables 1/2 is not in the release, or was produced by code that differs from the release. On CCEval the paper's B.4 defaults come close (−1.0 / −2.5 EM vs dense).
- **Speed.** Hardware differs, so absolute values can't be compared. The relative speedup is real but roughly half the paper's.
- **Release TTFT harness.** It times a per-sample Triton recompile, which makes SabreCoder look slower than dense FlashAttention on the H200.
- **Baselines.** All non-dense baselines (and the Dense (Triton) kernel) are missing from the release. Claims such as "+47% EM over StreamingLLM", "49% faster than LongCoder" and "283% over general sparse on CCEval" are NOT_COMPARABLE.

## Discrepancies
Code vs. paper:
1. **Similarity hyperparameter defaults** (minor, affects results). Code: p = 0.2, kmax = 8, Mchunk = 128. Paper App. B.4: 0.4 / 16 / 256. The per-language tuned values are not released.
2. **Oracle BM25 retrieval** (major, affects results). `data/cceval_rag/retrieve_bm25.py` uses the ground-truth completion as the BM25 query. The paper describes standard BM25 RAG. This leaks the target into the retrieved context for both dense and SabreCoder.
3. **TTFT timing** (major, affects results). `max_active_blocks` is a `tl.constexpr`, so the kernel is JIT-recompiled for most samples inside the timed prefill. The release's per-sample TTFT is ~3× the warm prefill. The paper says it warms up before each inference.
4. **PPL definition** (major, affects the reported PPL). PPL is computed on the model's own greedy generation, with dense attention (current code cleared → SDPA fallback). It is not the PPL of the ground truth, and not under the sparse mask.
5. **LCC scoring truncation** (minor). The generation is truncated to the ground-truth token length before computing EM/F1/ES. The paper doesn't describe this.
6. **Dead ablation flag** (minor). `--use_block_level_mask` is accepted but never used. The other ablation switches are absent.

Within the paper:
7. **TTFT values disagree across tables.** Table 5 and Table 6 SabreCoder prefill (940.5 ms LCC, 791.2 ms CCEval) differ from the Table 1/2 TTFT (931.19, 804.21).
8. **"Within 3% of dense" doesn't hold for every metric in the paper's own tables.** E.g. CCEval-Java EM is −5.1% relative.
