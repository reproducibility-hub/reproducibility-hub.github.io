## Verdict
- **Verdict: PARTIALLY_REPRODUCED**
- Result match (after fixes): **MIXED**. Table 1 reproduces for CLIP-L/14 and CLIP-L/14-336 (all 24 FreqAdapter numbers within tolerance). It does **not** reproduce for CLIP-B/16: 7–8 points lower on COCO, and the I2T scores fall below zero-shot CLIP.
- Result match as released (no source edits): **DOES_NOT_RUN**. The released code fails at import (`frequency_adapter.models.FrequencyAdaptationCLIP` is missing), crashes on CLIP-B/16, and crashes when saving the CLIP-L/14-336 checkpoint, which happens before evaluation.
- Coverage: **SUBSET**. Table 1 was run in full at paper scale. Table 2 (LLaVA VQA) was not run: no LLaVA code is released, and the benchmarks need a GPT judge.
- Codebase completeness: **MISSING_SCRIPTS**. The retrieval pipeline only needed minor fixes, but the whole LLaVA/VQA pipeline behind Table 2 is missing.
- Flags: CLOSED_JUDGE_UNAVAILABLE

## What the paper claims / what was targeted
- **Main claim, Table 1:** FreqAdapter, trained for one epoch on COCO 2017 train (batch 128, AdamW), improves image-text retrieval on COCO 2017 val and zero-shot Flickr30K val. This holds for CLIP-B/16, L/14 and L/14-336.
- **Main claim, Table 2:** FreqAdapter plugged into LLaVA-1.5 7B/13B improves MM-Vet and LLaVA-Bench scores (both GPT-judged). **Not run:** the release has no LLaVA integration, inference or scoring code, and there is no API key for the GPT judge. The user note asked us to infer the VQA dataset from `frequency_adapter/dataset`. That folder only has COCO/Flickr retrieval datasets, an empty `COCOClassification` stub and CIFAR builders, so the code doesn't identify a VQA dataset. The paper names MM-Vet and LLaVA-Bench.
- **Baselines (CoOp, MaPLe, CLIP-Adapter, MMA, LoR-VP):** not run. No code or configs are released for CoOp, MaPLe, MMA or LoR-VP. `CLIPAdapterCLIPModel` exists but the training script can't run it as-is. So "beats baseline X" claims are NOT_COMPARABLE. We did run the zero-shot CLIP ("-") rows as a sanity check of the data and evaluation.

## What I ran
Environment: conda env at `./env` with Python 3.12, torch 2.4.1+cu121, transformers 4.44.2, torch-dct, pycocotools, loguru. Hardware: 1×H200, with 3 runs sharing the GPU at a time.

Data:
- COCO 2017 train/val + captions from images.cocodataset.org.
- Flickr30K images from HF `nlphuji/flickr30k`.
- `val.txt`/`test.txt` (1000 images each) from the Flickr30k-Entities repo. The paper cites Plummer et al. 2015, and its granularity (I2T in steps of 0.1, T2I in steps of 0.02) implies 1000 images / 5000 captions.
- `results_20130124.token` (the original Flickr30K caption file, which isn't public) was rebuilt from the Flickr30k-Entities `Sentences/*.txt` files by stripping the entity markup. Zero-shot CLIP reproduces the paper's "-" rows to within 0.1, often exactly (e.g. B/16 Flickr val T2I 62.28/85.64/92.14), which validates the data/eval setup.

Commands, run from `codebase/`, are exactly the released scripts (`script/finetune.sh`, `script/finetune_scale_model.sh`):
```
python finetune.py --lr 1e-4 --peft_type freq_adapter --enable_mcfa --enable_mgfa --use_freq_adapter                       # L/14-336 (default)

# Table 3 ablations (finetune_scale_model.sh):
python finetune.py --lr 1e-4 --peft_type freq_adapter --enable_mcfa --use_freq_adapter

# extra B/16 diagnostics:
FREQ_DOWN_NUMBER=2 python finetune.py --lr 1e-4 ... --model_name_or_path openai/clip-vit-base-patch16

# zero-shot baselines (own wrapper around the repo's base_eval_fn):
python ../scripts/zeroshot_eval.py openai/clip-vit-{base-patch16,large-patch14,large-patch14-336}
```

Each run is one epoch on all 591,753 COCO train pairs (4,624 steps, batch 128). `finetune.py` evaluates on COCO val, Flickr val and Flickr test afterwards, with top-k=5 retrieved texts for the cross-modal interaction. Logs are in `logs/` (`train_*.err` holds the metrics). Parsed numbers are in `results.json` and `comparisons.json`.

**Settings that differ from the paper:**
- lr is 1e-4, taken from the released scripts; the paper text says 0.001. With lr=1e-3 on B/16 the results were worse.
- The multimodal weight w=0.01 from the paper doesn't exist in the code. The code uses G+C followed by a 0.1/0.9 residual blend; see Discrepancies.
- Single seed (42, hard-coded), as in the release.
- 3 runs shared one H200 at a time. This only affects speed.

## Why it is not fully reproduced
1. **CLIP-B/16 (Table 1):** the released adapter cannot process a 14×14 patch grid. After a minimal fix (and also with N=2 and with lr=1e-3), the B/16 FreqAdapter falls well short of the reported numbers, with I2T below zero-shot CLIP. I found no released configuration that produces the B/16 numbers.
2. **Table 2 (LLaVA VQA):** there is no released code for integrating FreqAdapter into LLaVA, running MM-Vet/LLaVA-Bench, or scoring them. The scoring also needs a GPT judge, and no API key is available (CLOSED_JUDGE_UNAVAILABLE).
3. **Baselines:** there is no code for CoOp/MaPLe/MMA/LoR-VP, so claims of beating them can't be checked (NOT_COMPARABLE).

## Codebase completeness: MISSING_SCRIPTS
Changes to the released code (uncommitted in `codebase/`, see `git diff`):
- `frequency_adapter/models/__init__.py`, `frequency_adapter/eval/eval.py`: removed the import of the missing module `FrequencyAdaptationCLIP`. Only stale `.pyc` files of it are in the repo, and nothing on the freq_adapter path uses it. Without this the code dies with ImportError.
- `frequency_adapter/models/FreqAdapterModel.py`: `AvgPool2d(..., ceil_mode=True)`, a ceil-sized reshape, and a crop after `repeat_interleave`, so non-divisible grids (CLIP-B/16, 14×14) work. This is a no-op for the 16×16 (L/14) and 24×24 (L/14-336) grids. Also an env knob `FREQ_DOWN_NUMBER` (default 3 = released value), used only for the B/16 N=2 diagnostic run.
- `finetune.py`: `save_pretrained(..., safe_serialization=False)`. safetensors refuses the non-contiguous `visual_projection.weight` of `openai/clip-vit-large-patch14-336`, and the first L/14-336 run crashed there after a 2-hour epoch, before evaluation.
- `finetune.py`: replaced the hard-coded `/home/DATA` paths.

Scripts I wrote (outside the release):

- `scripts/parse_logs.py`, `scripts/make_comparisons.py`: log parsing and tables.

## Discrepancies
- **code_vs_paper (major):** `FrequencyAdapter.visual_freq_adaptation` vs Eq. 6/8. The paper defines X̃ = G + w·C with w=0.01 (retrieval), and the output is the mean over scales. The code uses G + C with no w (no such parameter exists), and the output is 0.1·mean + 0.9·X_v, a residual blend the paper doesn't describe. The reproduced numbers come from the code's version.
- **code_vs_paper (minor):** lr is 0.001 in the paper (Sec. 4.1) but 1e-4 in every released script and the argparse default.
- **code_vs_paper (major):** the paper reports CLIP-B/16 results, but the released adapter (3 scales, pooling kernels 1/2/4) crashes on B/16's 14×14 grid. How the B/16 numbers were obtained is unknown, and we couldn't reproduce them.
- **code_vs_paper (minor):** Appendix C says the top-K texts are averaged. The code computes a softmax(similarity)-weighted average of the top-5 texts' mean-pooled penultimate-layer states.
- **paper_internal:** Appendix B states 475,776 parameters for L/14-336, while Table 4 says 476.4k. The Appendix B formula itself gives 476,352, which is what the code has.
