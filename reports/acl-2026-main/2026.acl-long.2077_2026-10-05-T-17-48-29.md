Summary: I re-trained the full three-phase TInR-U pipeline from Qwen2.5-7B-Instruct on one H200, using the released code and data:
1. tool internalization SFT (memorization, recall and usage);
2. "think" SFT warm-up;
3. GRPO with the released verl/SGLang fork, 20 epochs.

I then evaluated it with the released evaluator on the released in-domain test set (185 seen + 580 unseen instructions).

- **Tool identification (EM/F1) reproduces** within tolerance on both seen and unseen splits.
- **Tool-calling exact match and parameter accuracy do not:** they are 6–8 points lower than the paper (8–13 % relative).
- **RL helps, as in the paper's ablation, on 4 of 5 metrics.** Tool accuracy stays flat.

The out-of-domain BFCL experiment (Table 3) cannot be run. Its test set and the internalized BFCL tool tokens are not in the release. The baselines (ToolGen, ToolRL, retrievers, …) are not in the release either, so "TInR-U beats X" claims are NOT_COMPARABLE. For context only: our tool-calling EM (68.11 seen / 50.69 unseen) is *below* the ToolGen numbers the paper reports (71.89 / 55.86).

## What the paper claims / what was targeted

- **Main claim:** TInR-U is trained in three phases (bidirectional tool internalization → TInR SFT → TInR RL with GRPO) and gets the best in-domain (Table 2) and out-of-domain (Table 3) tool identification and tool calling.
- **Targets:**
  - Table 2: TInR-U on the seen and unseen splits.
  - Table 4: full TInR-U and the "w/o RL" ablation, combined in-domain.
  - Table 3: out-of-domain. Not runnable, because the data is missing.
- **Base model:** Qwen2.5-7B-Instruct, as in the paper.
- **Data:** the released `dataset/` and `training/dataset/`:
  - Phase 1: 2552 usage + 2467 memorization + 2467 recall examples.
  - Phase 2: 1490 think trajectories.
  - Phase 3: 2552 RL prompts.
  - Evaluation: `eval.json` with 765 instructions (185 seen, 580 unseen), which matches Table 1.

## What I ran (exact commands)

All scripts are in `./runs/`. They are single-GPU adaptations of the released `scripts/*.sh`. The environment is `./env` (Python 3.10, torch 2.7.1, sglang 0.4.10.post2, transformers 4.54.1, flash-attn 2.8.3, deepspeed 0.16.9, ray 2.59, and the verl 0.5.0.dev fork installed with `pip install -e codebase --no-deps`).

1. **Phase 1** — `runs/phase1.sh`. This is `training/train.py` on `train_memorization_recall_use.json`:
   - 2467 tool tokens added, initialized from the mean of their sub-word embeddings (the released code);
   - lr 5e-5, batch 64 (4 × 16 accumulation), warm-up 0.1, 8 epochs, max_len 2048, as in paper Appendix A;
   - gradient checkpointing, bf16 autocast with fp32 master weights, 8-bit AdamW.

   Took 1.5 h; final loss ≈ 0.001.
2. **Phase 2** — `MB=1 ACC=64 runs/phase2.sh`. This is `train.py` on `train_think.json`:
   - lr 5e-6, batch 64, warm-up 0.03 (from the script), 4 epochs (the paper; the script says 8), max_len 4096.

   Took 21 min; loss 2.5 → 0.38.
3. **Phase 3** — `runs/phase3.sh actor_rollout_ref.rollout.gpu_memory_utilization=0.4 trainer.total_epochs=20 trainer.save_freq=19 trainer.test_freq=19 trainer.max_actor_ckpt_to_keep=2`.
   - This is the released `examples/sglang_multiturn/run_rlla_multiturn_w_interaction.sh` with the `train_grpo.sh` environment variables, and N_GPUS=1.
   - Settings: GRPO, lr 2e-6, batch 128, n=4 rollouts, no KL, multi-turn interaction (tool docs returned after `<tool_token>`), reward = format + tool Jaccard + parameter Jaccard (`rlla_token_call_token.py`), actor in bf16 as in the released script.
   - 380 steps took 16.6 h (~2.6 min/step).
   - Mean training reward per epoch rose from 2.664 to 2.770 (max 3). Response length went from 651 to 499 tokens.

   Merged with `python -m verl.model_merger merge --backend fsdp --local_dir .../global_step_380/actor --target_dir ckpt/qwen-2.5-7b-...-grpo-2e-6`.
4. **Evaluation** — `runs/eval.sh <model_dir>`. This runs `training/test.py` with greedy decoding, batch 64, max 2048 new tokens per turn, and two turns: tool tokens, then tool call given the returned documentation. Reported metrics:
   - "Tools EM accuracy/F1" → Tool Identification EM/F1;
   - "Tool calls/Tools/Parameters accuracy" → Tool Calling EM / T.Acc / P.Acc.

   Output is printed per setting (580 = unseen, 185 = seen) and overall (765). Predictions are saved in `results_sft_eval_predictions.json` and `results_tinru_eval_predictions.json`.

Logs: `logs_phase1.txt`, `logs_phase2.txt` (`logs_phase2_nan_run.txt` is the failed first attempt), `logs_phase3.txt`, `logs_eval_sft.txt`, `logs_eval_rl.txt`.

### Settings that differ from the paper or the released scripts (all forced by 1 GPU / environment)

- **Hardware:** 1× H200 instead of 4× 48 GB GPUs.
- **Optimizer in Phases 1–2:** 8-bit AdamW (bitsandbytes) with fp32 master weights and no DeepSpeed.
  - Full fp32 AdamW for 7.6B parameters needs about 121 GB and ran out of memory.
  - DeepSpeed ZeRO-2 plus bnb crashes on the single 7.6B-element flat partition.
  - The paper's setup is presumably DeepSpeed ZeRO with fp32 AdamW.
- **Phase 2 micro-batching:** micro-batch 1 × accumulation 64; the effective batch of 64 is unchanged.
  - The first Phase 2 run used micro-batch 2 and diverged to NaN at step 1.
  - Cause: transformers 4.54 FlashAttention-2 drops an all-ones mask and builds varlen sequence lengths from (1, L) `position_ids`, which corrupts batches of more than one unpadded sequence. Evaluation and verl, which unpad sequences, are not affected.
- **Phase 2 epochs:** 4, as in the paper. The released script uses 8; a sensitivity run with 8 is reported below if it finished.
- **GRPO:** SGLang `gpu_memory_utilization` 0.4 instead of 0.68 (memory on one GPU), and 20 epochs (the paper) instead of 46 (the script).
- **Seeds:** one training run. The paper says it trained "several times" and reports the middle one.
