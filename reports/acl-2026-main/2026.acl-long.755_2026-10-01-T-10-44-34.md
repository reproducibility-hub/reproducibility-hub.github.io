## What was run (exact commands / scripts)

Environment: one conda env (`env/`, Python 3.11) with torch 2.8.0+cu128, transformers 4.57.6, flash-attn 2.8.3 (prebuilt wheel),
datasets 5.0.1, sentence-transformers 5.7.0, colpali-engine 0.3.13, peft 0.17.1, mteb 1.16.5 (pinned by the repo; needed to import
the `vidore-benchmark` CLI), `bm25s`+`PyStemmer`, the repo installed with `pip install -e codebase --no-deps`.
Version-specific side packages were installed with `pip --target` inside the attempt directory and put on `PYTHONPATH` only for the
runs that need them: `pydeps/tf449` (transformers 4.49.0, as the ColEmbed pipelines' docstrings require), `pydeps/mteb2`
(MTEB 2.22.1 — has the `ViDoRe(v3)` tasks and the retriever implementations the README points to), `pydeps/st52`
(sentence-transformers 5.2.0 for zerank-2: ST 5.7's CrossEncoder refuses zerank-2's custom chat template),
`pydeps/pylate` (pylate 1.6.0 + sentence-transformers 5.3.0 for LFM2-ColBERT).

Data: the 8 public HF datasets `vidore/vidore_v3_{computer_science,finance_en,pharmaceuticals,hr,industrial,physics,energy,finance_fr}`
(test split; 19,252 pages, 14,514 queries = 2,419 queries x 6 languages). Nuclear and Telecom are private (paper §3.5) and were not available.

Evaluation: always the repo's own pipeline evaluator (`vidore-benchmark pipeline evaluate`, pytrec_eval `ndcg_cut_10`, mean over all
queries of a dataset). With no `--language` filter all 6 query languages are evaluated against the (English or French) corpus, which is
the paper's cross-lingual Table 1/2 setting (every language subset has the same size, so the overall mean equals MTEB's mean over
language subsets). Monolingual Table 9/10 numbers are read from the per-language breakdown the evaluator stores.

| Paper rows | How it was run |
|---|---|
| ColEmbed-3B-v2 (T1) | repo `pipeline_implementations/nemotron_colembed_3b_v2.py` (`{"batch_size":32,"scoring_batch_size":32,"top_k":100}`), transformers 4.49 |
| Qwen3-8B textual (T1) | repo `pipeline_implementations/qwen3_embedding_8b_pipeline.py` (`batch_size` 16/4) |

| Jina-v4 visual + jina-reranker-m0 (T2) | repo `pipeline_implementations/jinav4_vision_jinavisualreranker_pipeline.py` (`{"rerank_batch_size":20}`), **English queries only** (`--language english`) |
| BM25S (T1) | `bm25s_pipeline.py` (written here): bm25s defaults (k1=1.5, b=0.75), English stopwords + English Snowball stemmer, page markdown |
| BGE-M3, Qwen3-0.6B, Jina-v4 textual, LFM2-ColBERT-350M (T1) | `mteb_model_pipeline.py` (written here) with `modality: text`: the MTEB 2.22.1 model implementation encodes the page markdown |
| ColQwen2.5, ColQwen2, ColPali, ColNomic-3B/7B, Nomic-3B/7B, Jina-v4 visual, ColEmbed-1B/3B v1 (T1) | `mteb_model_pipeline.py` with `modality: image`: the MTEB 2.22.1 model implementation encodes page images |

`mteb_model_pipeline.py` is a `BasePipeline` that calls the MTEB model implementation's own `encode`/`similarity` (MaxSim for
late-interaction, dot/cosine for dense), encodes the page corpus once per dataset and searches all 6 languages against it (top-100).
Running `mteb.evaluate(model, mteb.get_tasks(["ViDoRe (v3)"]))` as the README shows works too, but MTEB re-encodes the identical page
corpus for each of the 6 language subsets (6x the cost; measured on ColQwen2.5/H.R.), which did not fit the 48 h budget for ~17 models.
Run drivers: `run_pipeline.sh` (repo CLI), `run_pipeline2.sh`/`run_pipeline3.sh` + `vidore_cli_mteb2.py` (the repo CLI imported without
executing `vidore_benchmark/__init__.py`, whose legacy retrievers import the mteb-1.16 API, so MTEB 2.x can be on the path),
`lane*.sh` (job queues), `summarize.py`, `make_comparisons.py`, `write_report.py`, `write_status.py`. Logs are in `logs/`, per-dataset
result JSONs in `results/` (cross-lingual), `results_en/` (English-only), `results_fp16_mteb_default/` and `results_aside/` (diagnostic runs).

### Settings that differ from the paper / were chosen by us
* Only the 8 public datasets (Nuclear, Telecom are private). The paper's "Avg." column (10 datasets) cannot be recomputed; we compare
  each dataset and an 8-dataset average recomputed from the paper's per-dataset numbers.
* ColPali-engine models (ColQwen2.5, ColQwen2, ColPali, ColNomic-3B/7B) were loaded in **bfloat16**. MTEB 2.22.1 loads them in float16,
  which produced broken embeddings for ColQwen2.5 on Computer Science (46.1 vs 72.3 in the paper; bf16 gives 74.0; a direct
  colpali-engine bf16 run gives 76.9 English vs 75.2 in Table 9). fp16 diagnostic results are kept in `results_fp16_mteb_default/`.
* Jina-v4 (MTEB implementation): `vector_type="multi_vector"` (Table 1 does not star Jina-v4 as single-vector, and the repo's Jina
  pipelines use multi-vector), `attn_implementation="flash_attention_2"` (as in the repo's Jina pipelines), and on Computer Science the
  `retrieval` LoRA adapter: MTEB 2.22.1 silently switches Jina-v4 to its `code` adapter for tasks tagged with the Programming domain,
  which gives 60.1 (text) / 67.1 (visual) instead of the paper's 64.3 / 71.8; with the `retrieval` adapter we get 64.3 / 71.7.
  Single-vector diagnostic results are in `results_aside/`.
* MTEB processors were pinned to the model revision recorded in MTEB's `ModelMeta` (newer HF revisions add `additional_chat_templates/`
  files that transformers 4.57 cannot load).
* Qwen3-8B pipeline: its `torch_dtype="torch.bfloat16"` string is rejected by current sentence-transformers/transformers, so the
  pipeline's own fallback silently loads the model in fp32 without flash-attention (left as released; results match the paper).
* Visual reranking (Table 2, jina-reranker-m0) was run on **English queries only** (2,419 of 14,514 queries) because reranking
  100 page images per query runs at ~20 s/query on the shared GPU (full cross-lingual run ≈ 80 GPU-hours). It is compared with the
  English results the authors ship in the repo (`results/metrics/jinav4_vision_jinavisualreranker/`) and with the Jina-v4 visual
  English baseline (Table 9); the paper's cross-lingual Table 2 visual-reranker row is not reproduced.
* Rerank depth top-100 (repo default; the paper does not state it).

## Codebase completeness: MISSING_SCRIPTS
The release (github.com/illuin-tech/vidore-benchmark, commit a70f23a) contains the pipeline-evaluation framework (dataset loader with
page markdown, pytrec_eval evaluator, CLI) plus pipelines for ColEmbed-3B-v2, Qwen3-Embedding-8B and both Table 2 rerank pipelines;
for single-model retrievers the README defers to MTEB. But MTEB's ViDoRe v3 tasks have image-only corpora, so there is no released
script/config for the paper's textual retrievers on page markdown other than Qwen3-8B (BM25S, BGE-M3, Qwen3-0.6B, Jina-v4 textual,
LFM2-ColBERT): those pipelines (and the BM25S configuration) had to be written. No generation/judge (Table 3) or grounding (Table 4)
code is released.

Changes to the released code (uncommitted in `codebase/`, see `git diff`):
1. `pipeline_implementations/nemotron_colembed_3b_v2.py`
   * `index()` gained the `dataset_name` argument: the latest commit (a70f23a) makes the evaluator call
     `pipeline.index(..., dataset_name=...)`, so the released pipeline crashed immediately (interface bug).
   * corpus embeddings stored in one preallocated bf16 host tensor instead of a list of fp32 tensors + `torch.cat`: the model returns
     padded fp32 [N, 1802, 3072] tensors, i.e. ~116 GB for Industrial, and the concat needs 2x that (job limit 111 GB).
   * MaxSim scoring moved to the GPU in fp32 with corpus chunks in the outer loop: the released loop runs the einsum on the CPU and
     took hours per dataset. Same formula (max over doc tokens, sum over query tokens). Speed/memory only.
2. `pipeline_implementations/jinav4_text_zerank2textual_pipeline.py`: reranker pairs are scored in length-sorted batches capped at
   64k characters and restored to the original order (speed only; zerank-2 materialises full-vocabulary logits so an unsorted batch of
   32 long pages needed a 36 GB allocation and OOM'd on H.R.). Computer Science was run with the unmodified loop and matches the paper.
   No other source edits. Environment fixes: version pins listed above (transformers 4.49 for ColEmbed; ST 5.2 for zerank-2).

Scripts written for this attempt: `mteb_model_pipeline.py`, `bm25s_pipeline.py`, `vidore_cli_mteb2.py`, `run_pipeline*.sh`, `lane*.sh`,
`summarize.py`, `paper_numbers.py`, `make_comparisons.py`, `write_report.py`, `write_status.py`, `debug/*.py`.

### Result as released (no source edits)
* ColEmbed-3B-v2 pipeline: crashes (`index() got an unexpected keyword argument 'dataset_name'`) → DOES_NOT_RUN as released. With only
  that one-line interface fix it runs but scores on the CPU (hours per dataset) and needs > 111 GB RAM on Industrial.
* Qwen3-8B and both Jina-v4 rerank pipelines run unmodified (given the environment pins); the zerank-2 pipeline needs ST ≤ 5.2.
  Computer Science of the Table 2 textual pipeline was produced by the unmodified code (82.3 vs 82.1).
* `mteb.evaluate` (README route) runs but with MTEB 2.22.1 defaults gives wrong numbers for ColQwen2.5 (fp16) and Jina-v4 on
  Computer Science (code adapter) — these are MTEB-side behaviours, not repo code.
Overall `result_match_as_released`: the main pipelines that run unmodified (Qwen3-8B, Table 2 textual) match the paper; the
ColEmbed-3B-v2 pipeline does not run as released.

## Notes on process
* GPU/RAM contention: up to 5 job lanes shared the single H200; several runs hit CUDA OOM and were retried automatically (the
  evaluator writes a result only on success), and a memory watchdog killed only our own ColEmbed-3B-v1 Industrial worker twice when the
  job's anonymous memory exceeded 98 GB; that dataset was finally run with 128-page encoding blocks. No processes other than our own
  were touched.
* Interim result files of runs that were aborted (OOM) were never written; every number in the tables comes from a completed run log in `logs/`.
