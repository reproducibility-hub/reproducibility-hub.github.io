# Reproduction report — Exons-Detect (ACL 2026, 2026.acl-long.1211)

## Verdict

- **Verdict: FAILED** (result match `NO_MATCH`, coverage `SUBSET`, codebase completeness `MISSING_SCRIPTS`)
- **result_match (after fixes): NO_MATCH**. No fixes were needed. The released code ran unmodified, and its scores are identical to my runner's (max |diff| = 0.0).
- **result_match_as_released: NO_MATCH**. Same numbers. The released CLI was run unmodified on DetectRL Multi-LLM and gave AUROC 88.62 / F1 84.37.

**In short:** the setup is validated. Binoculars, computed from the same forward passes, matches the paper's Binoculars row to within 0.1 AUROC on all four benchmarks. The paper's F1 numbers are matched exactly once F1 is defined as best-threshold F1 with human as the positive class.

Exons-Detect's own AUROC lands 0.3–2.2 points below the paper:
- M4 and RealDet are within 0.5 points;
- both DetectRL settings are about 2 points low;
- the 4-benchmark average is 90.89 vs 92.14.

**What fails is the paper's central claim.** The claim is that exon-aware token reweighting (the paper's contribution) gives a 2.2% relative AUROC gain over DNA-DetectLLM on DetectRL, and 1.4% on average.
- Running the released scoring with the reweighting switched off (Δw = 0, i.e. Eq. 9 with uniform weights) gives an average AUROC of **90.89**. That is exactly the same as the full Exons-Detect (**90.89**).
- The Δw = 0 variant reproduces the paper's own DNA-DetectLLM row closely (90.89 vs 90.86 average; per dataset within 0.15).
- On DetectRL Multi-LLM and Multi-Domain, Exons-Detect (88.62 / 88.30) is *below* both the Δw = 0 variant (89.03 / 88.37) and the paper's DNA-DetectLLM numbers (88.97 / 88.23).
- Sweeping θ, α, mapping function and number of layers (0.05–0.25 / 2–50 / exp & linear / 2–32) did not find any setting that comes near the paper's 90.5–90.9 on DetectRL. Every setting stays at 88.2–89.0.

## What I ran

- Repository: https://github.com/Xiaoweizhu57/Exons-Detect (commit 239862c), cloned into `./codebase`. It contains:
  - the method (`src/exons_detect/{detector,metrics,cli}.py`);
  - the four 2,000-sample test sets (`text_data/*`, 1,000 human + 1,000 machine each), which match the paper's description.
- Environment (`./env`): Python 3.11, torch 2.5.1+cu124, transformers 4.46.3, sklearn. `pip install -e codebase`.
- Hardware: 1× H200. Paper: A100.
- `scripts/run_scores.py` (written by me):
  - constructs the released `ExonsDetect` with observer = `tiiuae/falcon-7b` and performer = `tiiuae/falcon-7b-instruct` (README defaults), FP32, max_token_observed = 1024, tau = 0.15, alpha = 10, hidden_num = 32;
  - for every text, scores it with the released `weighted_score` (batch size 1, as the CLI does);
  - from the same forward pass, also saves per-token quantities: CE of the gold token, CE of the argmax token, cross-entropy, and the per-layer cosine distance.

  Command: `env/bin/python scripts/run_scores.py` → `results/{M4,multillm,multidomain,RealDet}.pt`.
- `scripts/evaluate.py` (written by me):
  - AUROC (sklearn), with lower score = machine;
  - best-threshold F1 with machine as positive (`F1(m)`), and with human as positive (`F1(h)`);
  - offline variants: Δw = 0 (uniform weights, with/without ŝ); w/o g (Δw = δ); linear mapping; θ/α/L sweeps.

  As a sanity check, the official score recomputed from the saved tensors matches to within 0.01 AUROC. Output: `results/metrics.json`, `results/metrics_table.txt`.
- Released CLI, unmodified (`scripts/run_extra.sh`): `exons-detect --input codebase/text_data/multillm_{human,machine}_test.json ... --observer tiiuae/falcon-7b --performer tiiuae/falcon-7b-instruct` → `cli_out/`. Scores are identical to `run_scores.py`.
- Numerics check: Multi-LLM was rerun with `attn_implementation="eager"` (`scripts/run_scores_eager.py`, monkeypatch only). Max score difference vs SDPA was 1e-6, giving identical AUROC.
- Table 2 model-family ablation: ran the Mistral-7B-v0.1 / Mistral-7B-Instruct-v0.1 pair (`results_mistral/`). The LLaMA-2-7B and LLaMA-3.2-1B pairs are gated on HF and not accessible with the configured token, so they were not run.

**F1 definition:** the paper does not define how F1 is computed. Best-threshold F1 with **human as positive** reproduces the paper's Binoculars F1 almost exactly (87.41/82.87/80.31/90.53 vs paper 87.40/82.87/80.20/90.51). It also reproduces the paper's DNA-DetectLLM F1 (87.56/84.91/84.97/90.53 vs 87.72/84.85/84.94/90.58), so I use it as the paper-comparable F1.

**Differences from the paper's setting:**
- GPU: H200 instead of A100.
- Library versions are unknown in the paper.

Everything else (models, data, θ, α, L, FP32, 1024 tokens) is as in the paper.

## Discrepancies

1. **code_vs_paper (minor; affects results: probably not)** — `metrics.weighted_entropy` vs Eq. 1 (Sec. 3.1, Sec. 4.1):
   - The paper defines X-PPL = −Σ w_t P_M(x_t) log P_M̃(x_t), with M = Falcon-7B-Instruct (the reference/scoring model) and M̃ = Falcon-7B.
   - The code computes −Σ w softmax(observer = Falcon-7B) · log_softmax(performer = Falcon-7B-Instruct), i.e. the roles in the cross-entropy are swapped relative to the notation. This is the Binoculars convention.
   - The log-PPL term uses the instruct model, consistent with the paper.
   - Since my Binoculars numbers match the paper's, the code convention is likely what was used.
2. **code_vs_paper (minor)** — mutation-repair term (Sec. 3.5, Eq. 9) vs `metrics.weighted_sum_perplexity_dual`:
   - The paper describes incorporating DNA-DetectLLM's mechanism, "quantifying the difficulty of iteratively repairing mutated tokens".
   - The code computes a single-pass weighted CE of the per-position argmax token under the original prefix. This is consistent with Eq. 9's definition of ŝ, but it is not an iterative repair.
3. **paper_internal (minor)** — Table 5 (L=16, θ=0.15, α=10) gives Multi-LLM / Multi-Domain = 90.20 / 89.37. That equals Table 4's *Forward* L=16 row, not the *Reverse* L=16 row (90.63 / 90.55).
   - Fig. 5's quoted drops (1.9% / 3.1% from L=32→4) also match the Forward rows.
   - The released `hidden_num` takes the *last* layers (Reverse). Which extraction direction Table 5 and Fig. 5 use is not stated.
