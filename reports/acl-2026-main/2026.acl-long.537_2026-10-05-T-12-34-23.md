## 1. Paper and target
The paper's main claim (abstract, Table 1, Sec. 4.2): aPSF beats API-only prompt optimizers and the unoptimized seed prompt.
- **Method:** an Architect LLM factorizes a prompt into semantic factors, then does error-guided, single-factor interventional updates.
- **Benchmarks:** GSM8K, AQUA-RAT, MultiArith and GSM-Hard.
- **Setup:** N=4 candidates, T_max=10, |D_val|=50, worker temperature 0, architect temperature 0.7, 5 runs.

We targeted **Table 1**: aPSF and Zero-shot CoT for
- Worker ∈ {Qwen2.5-7B-Instruct, Llama-3.1-8B-Instruct}
- Architect ∈ {Qwen3-8B, gpt-oss-120b}

Secondary check: the efficiency claim of Sec. 4.4 / Fig. 5 (MultiArith: peak validation at step 1 with ≈206K tokens).

**Code:** https://github.com/T-Lab-CUHKSZ/aPSF, the repo linked in the paper (commit `933d10e`), cloned to `./codebase`.

## 2. What was run
- **Environment:** `conda create -p ./env python=3.11`; `pip install vllm` (0.31.0, torch 2.13 cu130); `pip install -r codebase/requirements.txt`.
- **Serving:** each model runs behind an OpenAI-compatible vLLM endpoint, as the README suggests (`start_vllm.sh`). All engines share the one H200 through CUDA MPS.
  - `--generation-config vllm`: only the sampling parameters in `config.py` apply. Worker: T=0, top_p=1, max_tokens=8192. Architect: T=0.7, top_p=1, max_tokens=8192. Without this flag vLLM silently applies Qwen2.5's `repetition_penalty=1.05`, which contradicts Table 15.
  - `VLLM_USE_FLASHINFER_SAMPLER=0`: there is no nvcc for flashinfer's JIT.
- **Data:** the release ships no data, and the README gives only folder names. Those names match google-deepmind/opro `data/`, which we used. GSM-Hard `gsmhardv2.jsonl` comes from HF `reasoning-machines/gsm-hard`. Splits are produced by the code itself (seed 42).
- **Per-run command** (`run_one.sh`; each run in its own dir under `runs/`):
  ```
  PYTHONPATH=<attempt dir> python -m codebase.run_experiments --dataset {gsm8k,aqua,multiarith,gsm_hard} --method apsf --initial-prompt cot
  PYTHONPATH=<attempt dir> python -m codebase.run_experiments --dataset ... --method empty_cot --initial-prompt cot   # Zero-shot CoT
  # Llama worker: APSF_WORKER_MODEL=meta-llama/Llama-3.1-8B-Instruct APSF_WORKER_BASE_ID=llama_vllm
  # gpt-oss architect: APSF_ARCH_MODEL=openai/gpt-oss-120b APSF_ARCH_BASE_ID=oss_vllm
  ```
- **Runs completed:**
  - aPSF: 4 settings × 4 datasets × 5 runs = 80 runs.
  - Zero-shot CoT: 2 workers × 4 datasets, 1 run each. It is deterministic; the paper also reports ±0.00.
  - All 20 Qwen2.5 × Qwen3-8B runs (the paper's default setting) used **unmodified method code**, executed sequentially as released.
  - Some runs used the opt-in speed-only thread pool (`APSF_EVAL_THREADS=8`, see §5):
    - Llama × Qwen3-8B: r4–r5 on all datasets, and r1–r3 on AQUA/GSM-Hard.
    - All gpt-oss-architect runs.
- **Logs and scripts:** per-run logs in `runs/*/run.log`. Aggregation: `aggregate.py` → `results_raw.json`; `make_comparisons.py` → `comparisons.json`; `render_table.py`. Aborted or superseded runs are kept in `runs_aborted/`. Those were the first launch before fixing the vLLM sampling defaults, plus sequential Llama runs that were replaced by threaded ones.

**Settings that differ from the paper:**
- **Test-set sizes** are what the released code produces, not Table 16:

  | Dataset | Code | Paper (Table 16) |
  |---|---|---|
  | GSM8K | 1269 | 1319 |
  | AQUA | 200 | 254 |
  | MultiArith | 430 | 180 |
  | GSM-Hard | 1006 | 1006 |
- **Scoring** is the released LLM-based judging/extraction, not App. O.2's regex exact match.
- **Hardware:** 1×H200 shared via MPS, instead of 2×A100. vLLM continuous batching makes T=0 outputs non-bit-exact.

## 4. Discrepancies
**Code vs paper:**
1. **[major] Algorithm 1 is not what the code runs.** The paper has a warm-start pass (optimize each factor once), then error-guided selection, with early stop at val=1 or after patience P. The code uses error-guided selection from step 1, has no patience, and at val=1.0 prints "No errors, optimization complete!" and keeps looping.
2. **[major] Scoring protocol.** App. O.2 says regex extraction + exact match. The code instead uses:
   - GSM8K: the *Worker LLM itself* judges its own answer YES/NO.
   - MultiArith/AQUA: Worker-LLM answer extraction.
   - GSM-Hard: answer extraction by the thinking Architect LLM.
3. **[major] Baselines are missing.** Table 1/2 baselines (OPRO, APE, ProTeGi, GrIPS, DSPy, Zero-shot CoT) are routed to undefined functions; ZERA and CriSPO are absent.
4. **[minor] Test sizes differ from Table 16:** see §2. The GSM8K config's `test_size=1495` even suggests an 80/20 re-split of the train set was used at some point.
5. **[minor] No stop sequences.** Table 15's worker stop sequences `["\n\n", "—"]` are not passed by the code.
6. **[minor] Seed prompt default.** Table 1 starts every method from "Let's think step by step", but the code defaults to from-scratch mode; `--initial-prompt cot` is required.
7. **[minor] Fallback candidates.** When the Architect's JSON fails to parse, only 2 template "fallback" candidates are evaluated instead of N=4.

**Paper-internal:**
1. The abstract claims "+4.29 pp on average", but Table 1 / Sec. 4.2 give at most +2.16 pp over the strongest baseline (74.90 vs 72.74), and no setting in Table 1 yields +4.29.

## 6. Notes and practical issues
- **gpt-oss-120b empty outputs.** Its vLLM endpoint occasionally returns `content=None` when all 8192 tokens go to reasoning. The code then catches `'NoneType' object has no attribute 'strip'` and returns an "Error: …" string. This happened 40 times in ≈25K architect calls on GSM-Hard, where it falls back to regex extraction.
- **Shared GPU.** Three vLLM engines shared one GPU via user-space CUDA MPS. The pipe dir had to be short because of the 108-char Unix-socket limit.
- **Server swaps.** Servers were restarted twice, with clients paused via SIGSTOP/SIGCONT. Only the openai SDK's automatic retries were involved, and no request errors appeared in the logs.
- **Process hygiene.** Every process we started was killed by recorded PID/PGID. The conda env is removed at the end.
