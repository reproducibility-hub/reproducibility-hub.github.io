## Summary
- **Target:** Table 1, the GRASPrune rows on LLaMA-2-7B at param ratios 0.8 / 0.6 / 0.5 / 0.4, plus the "Original" dense row. Metrics are WikiText-2, PTB and C4 perplexity and zero-shot accuracy on ARC-C, ARC-E, HellaSwag, PIQA and WinoGrande. This includes the abstract's headline result of 12.18 Wiki PPL at 50%.
- **Settings:** the paper's own: 512 × 512-token WikiText-2 train sequences, 4 epochs, AdamW with lr 1e-2, τ = 1.5, bf16. All are the release defaults.
- **Seeds:** the release default (seed 42) is the main comparison. I also ran seeds 0, 1 and 2 at every ratio, for 4 seeds per ratio.
- **Sanity check:** the dense model through the release's eval code reproduces the paper's "Original" row exactly. PPL is 5.4911 / 27.028 / 7.2745, and average accuracy is 0.6894 against 0.6896.
- **What holds:** GRASPrune's WikiText-2 and C4 PPL reproduce at 0.8 and 0.6. Wiki PPL is close at 0.5: 13.17 for seed 42 and a 12.72 ± 0.30 mean, against 12.18. The large PPL gap to the paper-reported baselines (FLAP / SliceGPT / LLM-Pruner) holds at every ratio.
- **What doesn't:**
  - Zero-shot accuracy is systematically 1.5–3.6 points below the paper, mostly ARC-C and ARC-E.
  - At 0.4, all PPLs are much worse: Wiki 21.7 for seed 42, 18.7 ± 2.0 mean, against 16.65.
  - PTB PPL is highly seed-dependent and does not match.
  - With our accuracy numbers, GRASPrune's average would fall *below* the paper-reported FLAP average at every ratio. For example, at 0.5 it is 0.4294 for seed 42 and a 0.4426 mean, against FLAP's 0.4449. So the "best average zero-shot accuracy" claim isn't supported by our reruns. The baselines themselves are not in the release, so this comparison uses the paper's baseline numbers and is not a like-for-like check.

## Why not fully reproduced
- **Accuracy gap:** the zero-shot accuracy deficit is consistent across seeds. ARC-C is about 3 points low and ARC-E 4–5 points low at 0.8 and 0.5. I found no code or config difference that explains it.
  - The eval stack is the paper's own: lm-eval 0.4.1, acc_norm where available. The dense row matches, so the eval itself is fine.
  - Plausible causes are seed or hardware variance, which is large for this method, or an unreleased configuration difference.
- **Ratio 0.4:** PPL there is very seed-sensitive, and none of our 4 seeds reaches the paper's 16.65 (best 17.45).
- **Baselines:** LLM-Pruner, SliceGPT and FLAP are not in the release. I did not reconstruct them, so the "beats X" claims are NOT_COMPARABLE.
- **Not run:** Table 2 (LLaMA-7B, Vicuna-7B and LLaMA-2-13B at 0.4) and the appendix tables. Hence coverage is SUBSET.

## Codebase completeness: MINOR_FIXES
- There are **no edits** to `./codebase` source; `git status` is clean (the added `data/` folder is gitignored).
- **C4 data:** `data/c4-validation.json` is required for C4 eval but not shipped. The README just says "prepare" it. I built it from allenai/c4 `en/c4-validation.00000-of-00008.json.gz`; the dense C4 PPL matches the paper exactly.
- **Model:** used the ungated model id (an access issue, not a code issue).
- **Scripts I wrote** (all outside the codebase):
  - `scripts/eval_dense.py`: dense eval using the release's `evals.py`.
  - `scripts/train_seed.py`: sets the seed, since there is no CLI flag.
  - `scripts/debug_ptb.py`, `scripts/collect.py`, `scripts/compare.py`, `scripts/write_status.py`.
  - `run_all.sh`, `run_seeds.sh`, `reeval_acc.sh`.
- **Eval-code quirk (not changed):** `evals.evaluate_perplexity` computes cross-entropy on bf16 logits and takes the mean in bf16. Reported PPL is therefore exp of a bf16 number, quantized in steps of about 1.6–3%.
  - This explains identical PTB values across different checkpoints, e.g. 87.2476 = e^4.46875.
  - The paper's numbers show the same quantization (12.1824 = e^2.5, 9.6371 = e^2.265625), so the authors used this same code.
  - An fp32 recomputation for the seed-42 0.5 checkpoint gives Wiki 13.20 and PTB 86.25, against 13.17 and 87.25 reported.
  - The function also silently skips batches with non-finite logits; none occurred.
- **Infra failures:** two of the 16 runs had lm-eval crash on a race in the shared HF datasets cache. Their checkpoints were re-evaluated with the release's `eval_pruned_acc.py`.

## Discrepancies
1. **code_vs_paper (minor), `pipeline.train_rescale`.** The paper says the scaling factors γ are fit on "the same calibration set", i.e. 512 WikiText-2 *train* sequences. The code uses the WikiText-2 *validation* split, for 1 epoch, with the parameterization γ = 1 + 0.5·tanh(g).
2. **code_vs_paper (minor), budget definition.** The abstract says the method "removes 50% of parameters". The code applies the budget only to FFN channels and KV groups; embeddings and lm_head are excluded. As a result, the exported checkpoints keep 0.808 / 0.616 / 0.519 / 0.424 of total parameters at the nominal 0.8 / 0.6 / 0.5 / 0.4.
3. **paper_internal.** Table 5 (0.5, w/ scale) gives PTB 92.87, C4 27.45 and Avg 0.465. Table 1's GRASPrune 0.5 row gives PTB 123.04, C4 27.886 and Avg 0.4654.
   - Many other "duplicate-looking" values across the paper's tables are explained by the bf16 PPL quantization above, so I do not count them as inconsistencies.
