**Short version.**

* **The released checkpoints reproduce Table 1.** RoT-Qwen3-VL-4B and RoT-Qwen3-VL-2B (HF `TencentBAC/RoT-Qwen3-VL-{4B,2B}`) were run through the released `scripts/evaluate.py` with its README default decoding (greedy, `--temperature 0.0`, 32 latent tokens). The numbers match the paper's RoT rows on all four benchmarks:
  * 4B average: 55.33 (paper 55.4).
  * 2B average: 37.01 (paper 37.0).
* **The paper's stated decoding protocol gives clearly lower numbers.** The paper says it uses temperature 1.0, top-p 0.9 and the mean over 5 seeds; the released code has no top-p, so I added it. Under that protocol the averages are 50.98 (4B) and 30.45 (2B). The paper's numbers are therefore consistent with greedy decoding, not with the protocol it describes.
* **Table 4's token-budget sensitivity does not reproduce.** With the released 4B checkpoint, GSM8k accuracy is nearly flat from 8 to 256 latent tokens (36.2–38.2). The paper reports 1.89 for 8 tokens and 11.4 for 16 tokens.
* **Training could only be re-run at about 1% scale.** The released training code works per sample with an autoregressive rollout:
  * Stage I: about 2 s per sample.
  * Stage II: about 10 s per sample.
  * The paper's 1 + 2 epochs over 385k samples would take more than 2,000 GPU-hours on an H200. The paper reports 56 h on one H20.
  * I trained Stage I (1 epoch) and Stage II (2 epochs) on 3,200 GSM8k-Aug samples. That model is reported as NOT_COMPARABLE.
* **The released training pipeline has a results-affecting bug.** The Stage I → Stage II handoff drops the randomly initialised `<img>` token row. Embeddings are tied, so that row is also an `lm_head` row. Because it is lost, Stage II starts from a corrupted state: LM loss 0.22 at the end of Stage I becomes 14–18 at the start of Stage II. I fixed it (MAJOR_FIXES).
* **The Table 1/3 baselines (SFT-w/o CoT, SFT-CoT) and Table 2 (iCoT, Coconut, CODI, CoLaR) are not in the release.** Claims relative to them are NOT_COMPARABLE.

## What the paper claims and what I targeted

* **Main claim** (abstract, Table 1): RoT on Qwen3-VL-2B/4B and LLaVA-1.6-7B gets competitive Pass@1 with 32 latent tokens. The 4B average is 55.4 versus 79.3 for SFT-CoT at 108 tokens, i.e. 3–4× token compression.
* **Targets:**
  * Table 1 RoT rows for Qwen3-VL-4B and Qwen3-VL-2B. Their checkpoints are released; LLaVA has no checkpoint and could not be trained in budget.
  * Table 4 (decoding budgets, 4B, GSM8k).
  * A scaled-down re-run of the two-stage training (4B, GSM8k-Aug).
* **Not run:**
  * Table 3 (MATH): needs MATH training; no checkpoint; no budget.
  * Tables 2/8/9 baselines: not released.
  * Fig. 4 timing: the GPU was shared by concurrent jobs, so wall-clock times would not be comparable.
  * Tables 5/6 ablations: each needs full training.

## Setup

* **Environment:** conda env `./env` with Python 3.10, torch 2.8.0+cu128, transformers 4.57.1, peft 0.21.2, deepspeed 0.17.6, qwen-vl-utils 0.0.14. DeepSpeed needs `CUDA_HOME` (`/sw/eb/sw/CUDA/12.8.0`).
* **Hardware:** 1× H200 (141 GB), shared between training and up to 6 eval processes.
* **Models:**
  * `Qwen/Qwen3-VL-4B-Instruct`, `Qwen/Qwen3-VL-2B-Instruct`.
  * `TencentBAC/RoT-Qwen3-VL-4B` (global_step4000).
  * `TencentBAC/RoT-Qwen3-VL-2B` (global_step2500).
  * The released safetensors were converted with the repo's own `scripts/convert_from_safetensors.py`.
* **Data** (public HF copies, converted to the repo's documented JSONL format by `scripts_own/prep_data.py`):
  * GSM8k-Aug-NL: `whynlp/gsm8k-aug-nl`, 385,620 train / 1,319 test.
  * GSM-Hard: `reasoning-machines/gsm-hard`, 1,319.
  * SVAMP: `ChilleD/SVAMP` train+test, 1,000.
  * MultiArith: `ChilleD/MultiArith` train+test, 600.
  * This follows the CoLaR protocol the paper cites (full SVAMP/MultiArith, as in `xiaomi-research/colar/data_preprocessing`). The release ships only 5 example rows.
* **Eval command** (via `scripts_own/run_eval.sh`):

  ```
  python scripts/evaluate.py --config <cfg> --checkpoint <ckpt> --stage1_checkpoint <ckpt> \
      --data_file data/GSM8k-Aug-NL/<ds>_test_processed.jsonl --max_new_tokens 64 \
      --num_vision_tokens 32 {--temperature 0.0 | --temperature 1.0 --top_p 0.9 --seed {0..4}}
  ```

  * Configs: 4B uses the released `configs/stage2_config_qwen3vl_4b.yaml`. 2B uses the same config with the 2B model path and `projection_hidden_dim: 4096`, which is the shape of the released 2B projection head.
  * The README default (greedy) is the "as released" setting; sampling needs my top-p patch.
  * Pass@1 is computed by the repo's `extract_answer`/`compare_answers`.
  * A sign-aware strict re-score (`scripts_own/aggregate.py`) differs by at most 0.25 points (see Discrepancies).
* **Training (scaled down)**, released `scripts/train.py` via DeepSpeed, 1 GPU:
  * Settings set to the paper's values:
    * total batch 16 (`batch_size 16`, `gradient_accumulation_steps 1`);
    * lr 2e-5;
    * AdamW, wd 0.01;
    * LoRA r16/α32/dropout 0.05;
    * λ = 10;
    * projection hidden dim 4096;
    * font 20 px, height 32 px, padding 4 px;
    * seed 0;
    * Stage I 1 epoch, Stage II 2 epochs.
  * Data: a 3,200-sample random subset (seed 0) of GSM8k-Aug, with samples whose rendered CoT the Qwen image processor rejects removed (aspect ratio > 200; 35 of the first 3,235).
  * Stage I took 3.7 h. Stage II took 19 h (fixed run).

## Why it is not fully reproduced

1. **Compute.** The released training implementation is latency-bound: a per-sample Python loop with a KV-cached rollout of about 64–70 vision tokens per sample, and backprop through the whole rollout in Stage II. Measured on an H200:
   * Stage I: 30 s per 16-sample batch.
   * Stage II: 155–270 s per 16-sample batch.
   * The paper's schedule needs about 200 h (Stage I) + about 2,100 h (Stage II).
   * Only a 3,200-sample run fit into the 48 h budget, so the training claim is tested only qualitatively.
2. **Missing baselines.** No code or configs for SFT-w/o CoT, SFT-CoT, iCoT, Coconut, CODI or CoLaR-on-Qwen3 are released.
3. **Decoding protocol.** The paper's numbers are reproduced only with greedy decoding, not with the T=1.0/top-p 0.9 protocol the paper states.
4. **Table 4** contradicts the released 4B checkpoint's behaviour.

## Codebase completeness: MAJOR_FIXES

The method (rendering, projection head, both training stages, latent decoding) is implemented and the released checkpoints run as-is. Issues found and changes made:

**Changes to released code (left uncommitted in `./codebase`):**

1. `scripts/train.py`: the Stage-I checkpoint now also saves the `<img>` token embedding row, and the Stage-I→II loader restores it. Without this, Stage II starts with a re-randomised `<img>` row; because embeddings are tied, that row is also an `lm_head` logit row.
   * Diagnosis (`scripts_own/diag_loss.py`):
     * In-process Stage-I LM loss at the end: 0.22.
     * Reloaded checkpoint: 14.3.
     * Reloaded with the `<img>` row restored: 0.08.
   * As-released Stage II started at an LM loss of 18.6.
   * This is a bug that affects results.
2. `scripts/evaluate.py`: restores the same `<img>` row when evaluating a Stage-I-only checkpoint. It also adds `--top_p` and `--seed`, because the paper's protocol (top-p 0.9, 5 seeds) is not implemented.
3. `models/cot_compressor.py` `generate()`: nucleus (top-p) sampling (softmax in fp32). Greedy decoding is unchanged.

**Config / data workarounds (no code edits):**

* New configs `configs/repro_stage1.yaml`, `repro_stage2(_fix).yaml` and `eval_released_2b.yaml`, setting the paper's values: font 20, projection dim 4096, total batch 16, seed 0. The released defaults differ: font 16, dim 2048, batch 128, seed 42.
* `--lr` must be given on the command line: YAML parses `2e-5` as a string, which AdamW rejects (seen with `--lr 0`).
* The released `run_train_stage*.sh` call `conda activate deepseek_3.10`, so I invoked `deepspeed` directly.
* `run_evaluate.sh` uses `read -p`, so I invoked `evaluate.py` directly.
* Removed training samples that crash the Qwen image processor ("absolute aspect ratio must be smaller than 200"). With the paper's 20 px font this is ~0.5–1.1% of GSM8k-Aug (0.09% even with the release's 16 px). The released code has no handling, so a full epoch crashes.

**Scripts I wrote** (outside the repo, in `scripts_own/`):

* `prep_data.py`: HF datasets → JSONL. The repo's `scripts/preprocess_data.py` is broken: it calls a non-existent `renderer.will_text_fit`, and it only knows gsm8k/math-500 from a local path.
* `filter_processor.py`: drops samples the image processor rejects.
* `eval_wrapper.py`: calls `torch.cuda.empty_cache()` after loading, because loading the fp32 checkpoint onto the GPU leaves ~18 GB cached per process; no behaviour change.
* `run_eval.sh`, `chain.sh`, `fill_missing.sh`, `sweep_t4.sh`, `run_train*.sh`: job runners.
* `aggregate.py`: tables and CIs.
* `diag_loss.py`: handoff diagnosis.

**Other observations:**

* Dynamic termination via `<img_end>` (Table 4 "Special Tokens" row) is not implemented: `stop_threshold` is accepted but unused, and `generate()` always uses the fixed budget.
* There is no inference-time measurement script (Fig. 4).
* The released 4B checkpoint's `training_state.json` shows global_step 16000 micro-batches, i.e. about 512k samples at 16/GPU × 2 GPUs. That is about 1.3 Stage-II epochs, not 2. This is inferred from the save logic, so I am not certain of it.
