## What the paper claims and what I targeted

The paper claims that Transformer blocks from heterogeneous LLMs can be reassembled into new architectures that beat their source models. Reassembly covers vertical recombination plus horizontal operators sub/merge/concat/ens. Glue layers trained by data-free distillation on Gaussian inputs make the blocks compatible, and the architecture is found by a bi-level NSGA-II search.

* **Table 1 (toy example):** LLaMA-2-7B-Chat + Open-LLaMA-7B are reassembled into a 32-block model and evaluated on XNLI (en/zh/fr/es/ar/tr). LEGO-LLM 0.4276 vs 0.4109 / 0.4096 for the sources. **This is what I reproduced.**
* **Tables 2/3 (main):** 6 Llama-3-8B language models; MELA / XNLI. **Not run**, because:
  * the Spanish source model must first be trained with LoRA on 20% of `josecannete/large_spanish_corpus` (multi-day job);
  * six fp32 8B models (≈190 GB) exceed both host RAM (113 GB) and GPU memory (141 GB); fp32 is the only precision in which the released code does not crash or degrade (see below);
  * one candidate evaluation costs ≈5 min even for the 2-model toy, so even a heavily reduced search would not fit next to Table 1 in 48 h.
* Tables 4–7 and Figure 4 (cost, ablation, SeaEval, Flores, cross-lingual) were not run.

**Why LEGO-LLM equals LLaMA-2:**

* The best chromosome the search returned (`runs/toy_main/final/chromosome.json`) is LLaMA-2-Chat layers 0..31 in their original order, all `sub`, with no Open-LLaMA blocks.
* In fp32 every glue layer in this chromosome gets exactly zero distillation loss, so it stays an identity mapping. The saved model's per-language XNLI accuracies are therefore identical to LLaMA-2-Chat's.

**Precision sensitivity** (`results/diag_identity.json`, `diag_cache.json`, `diag_tf32.json`):

* For an identity LLaMA-2 chromosome, bf16 glue distillation lowers 6-language XNLI from 0.413 to 0.366, and the 15-language search score from 0.391 to 0.347–0.349.
* The cause: in bf16 the student and teacher paths differ by kernel noise, giving losses around 1e-4. Adam turns these into steps the size of the learning rate, and the glue weights drift.
* In fp32 (and fp32+TF32) the loss is exactly 0 and the model is unchanged. All reported LEGO numbers therefore use fp32.

## As-released behaviour

* **With the README's pinned environment** (torch 2.1.2, transformers 4.46): the first candidate evaluation crashes with `ValueError: not enough values to unpack` (`logs/smoke.log`, first attempt). The custom decoder layer returns a bare tensor, which only works with transformers ≥4.54 (which in turn needs torch ≥2.6 to load `.bin` checkpoints).
* **With a newer environment:**
  * the default `--dtype auto` keeps everything in fp32 on the CPU, and `HFLM` ignores `device` for pre-built models, so lm_eval runs on the CPU at batch size 1 (`batch_size` is not forwarded to `HFLM`);
  * `--dtype bfloat16/float16` crashes on fp32 glue parameters versus 16-bit blocks.
* Hence `result_match_as_released = DOES_NOT_RUN`.
* **Released search logic with only env/speed/placement fixes** (`LEGO_ASRELEASED_SEARCH=1`, outer 6×2, inner 4×2, 30 unique candidates, 2 h). These are the `ours_as_released` numbers in status.json. The top-level as-released label stays DOES_NOT_RUN, because the truly unmodified code cannot produce them.
  * The run behaves exactly as the bug predicts. Every evaluated architecture uses only LLaMA-2 blocks (model index never 1), and no layer ever gets a secondary branch, so all are `sub`. The inner search degenerates to choosing β; most inner "evaluations" are cache hits of the same decoded chromosome.
  * The returned model is a random permutation (with repeats) of LLaMA-2 layers 0..28 and scores at chance:

## Codebase completeness: MAJOR_FIXES

Changes to the released code (all uncommitted in `codebase/`, diff in `codebase_changes.diff`):

1. `moea_llm_merge/assembly.py: build_reassembled_model`: cast the model to the requested dtype after inserting composite layers. Glue/fuser/adapter parameters were fp32 and crashed against 16-bit blocks. This only matters for 16-bit runs; the main run is fp32, where it is a no-op.
2. `moea_llm_merge/eval_utils.py: evaluate_chromosome`: move the candidate model to CUDA before `HFLM`, which otherwise evaluates on the CPU.
3. `eval_utils.py`: pass `batch_size` to `HFLM` (simple_evaluate ignores it for LM objects). Speed only.
4. `eval_utils.py`: cache lm_eval's `TaskManager` and task dict across candidates (≈100 s per candidate saved). Speed only; verified identical scores.
5. `eval_utils.py`: append every evaluated chromosome and its score to `<csv>.chromosomes.jsonl`. Logging only.
6. `assembly.py: load_source_models`: `device_map` is taken from env `LEGO_SOURCE_DEVICE` (default `cpu`, as released). I used `cuda` because two fp32 7B models plus per-candidate deep copies exceed the 113 GB host RAM. My first bf16 attempt was OOM-killed when a diagnostic ran concurrently.
7. `assembly.py: build_reassembled_model`: load the base model (embeddings/norm/head) once and deep-copy it per candidate, instead of re-reading the checkpoint (≈100 s per candidate). Speed only; verified bit-identical logits in fp32.
8. **`moea_llm_merge/search.py` / `main.py` (bug that changes results):**
   * **Bug:** pymoo 0.6 ignores `minimize(..., x0=...)` and `type_var=np.int_`. The seeded initial populations, which encode the source models (Eq. 6) and the sub/merge baselines, were never used. Genes were sampled as floats and truncated with `int()`, so a gene with upper bound 1 (model index for N=2, `use_secondary`) or the last operator id almost never reaches it.
   * **Demonstration:** `scripts/check_pymoo.py` shows 0% of model-index genes decoding to model 1 as released. In the partial as-released run (`logs/toy_asreleased_init_partial.log`) every layer came from model 0.
   * **Fix:** `integer_nsga2()` seeds `sampling` with the initial population and uses SBX/PM with `RoundingRepair`, following pymoo's integer recipe. `LEGO_ASRELEASED_SEARCH=1` restores the original algorithm.

Scripts I wrote outside the codebase (`scripts/`):

* `eval_xnli.py`: Table 1 evaluation of HF baselines and of saved reassembled models. The repo's `eval_data/Xnli/eval_xnli.py` can only load a plain HF path, but the saved LEGO model needs the rebuild described in `README_load.md`.
* `run_search_tf32.py`: TF32 launcher.
* `diag_identity.py`, `diag_minimal.py`, `check_pymoo.py`, `check_build.py`, `time_build.py`, `status.sh`: diagnostics and monitoring.

Other notes:

* The Spanish LoRA script (`lora_spanish_llm.py`) and the MELA/SeaEval eval scripts exist but were not used.
* The paper's semantic-entropy fairness objective is not wired in. The code uses accuracy variance across languages as a proxy, and the README says so.

## Discrepancies

Code vs paper:

1. **MERGE operator** (`assembly.py: CompositeDecoderLayer._combine`).
   * Paper (Sec. 2, Fig. 1): parameter-level merging, W ← αW_c + βW_e.
   * Code: an output-level softmax-weighted average with `branch_weights` initialised to zeros and never trained, which is exactly the ENSEMBLE operator. The diagnostic gives bit-identical scores (0.3904).
   * Major; affects results.
2. **CONCAT operator.**
   * Paper: horizontal concatenation / layer widening, W ← [W_c; W_e].
   * Code: concatenates the two block outputs and applies a randomly initialised `nn.Linear(2d→d)` that is never trained (distillation only optimises `output_glue`). Any concat layer collapses the model to chance (0.3397).
   * Major; affects results.
3. **Fairness objective** (`semantic_entropy.compute_entropy`).
   * Paper (App. B): the fairness objective is the variance across languages of semantic entropy, computed from sampled generations clustered by bidirectional entailment.
   * Code: the variance of per-language lm_eval accuracies.
   * Major; affects selection.
4. **Lower-level problem** (`search.py: HorizontalSearchProblem`).
   * Paper (Eq. 9): vector-valued, Pareto-based.
   * Code: single-objective (accuracy only).
   * Major.
5. **Initial population / gene encoding** (`main.py`, `search.py`).
   * Paper (Eq. 6): the initial population encodes the original models, so every chromosome is valid.
   * Code: pymoo ignores `x0`. Populations are random float vectors truncated to ints, so the last model, secondary branches and the `ens` operator are almost never sampled.
   * Major; affects results; fixed.
6. **Budget versus reported cost.**
   * Code defaults: outer 30×50 and inner 10×20, i.e. ≈300k glue-distilled candidate evaluations. We measured ≈5 min each for 7B models on an H200.
   * Paper (Table 4): EA cost 1.25–6.25 h.
   * The reported cost cannot correspond to the released defaults. Minor (numeric settings).
7. **Precision.**
   * Paper: Table 4 reports 20–26.5 GB GPU memory for 8B models, which implies 16-bit weights.
   * Code: runs only in fp32. In 16-bit it crashes (dtype mismatch); once patched, the glue drifts even on identity transitions.
   * Minor.
8. **Validity of non-base source models.**
   * Code: embeddings/head/tokenizer always come from `model_paths[0]`, so the "original model" chromosome for any other source (here Open-LLaMA, which has a different tokenizer) is a chance-level model (0.339).
   * Paper: Eq. 6 is said to guarantee valid models, and Sec. 2 assumes embeddings are shared or inherited.
   * Minor.
9. **Search fitness data overlaps the reported data.**
   * Code: the search's fitness data are the first N docs of the XNLI validation split, a subset of the docs used for the final Table-1-style evaluation.
   * Paper: says "small validation sets" without specifying this.
   * Minor.
10. **Final saved model.**
    * Code: the final saved model's glue layers are re-trained (`save_final_outputs`) on fresh Gaussian draws, not the instance that was evaluated during search.
    * Minor.

Paper-internal:

1. Table 1 labels the source "LLaMA-2-7B", but the text (Sec. 5, App. C.2) says LLaMA-2-7B-Chat.
2. App. C.1 says the source models are "derived from the LLaMA-3.1 8B backbone", but the footnote links Meta-Llama-3-8B, and all listed models are Llama-3 (not 3.1) based.
3. Standard deviations:
   * Table 1 source rows have binomial stds (n≈747), while LEGO-LLM rows carry ≈0.03 stds described as "diversity of architectures explored during evolution".
   * Table 3 gives an identical ±0.0100 (±0.0095 for English) for every model regardless of accuracy.
