# Reproduction report: Nature-Inspired Population-Based Evolution of LLMs — GENOME(+) (2026.acl-long.2044)

## Verdict
- **Verdict: PARTIALLY_REPRODUCED**
- **Result match: TREND_MATCH**, both after my fixes and as released. My only code changes were efficiency, timeout and logging changes; none touches the method or evaluation logic.
- **Coverage: SCALED_DOWN.**
  - Covered: the main experiment (Table 1, all 12 datasets, gemma-2-2b-it, the authors' 10 released expert LoRAs). GENOME and GENOME+ ran with all 5 paper seeds; Best Single was evaluated; Model Swarms ran through the released code with 3 of the 5 seeds.
  - Not covered: LoraHub, Pack of LLMs, MERGE3, DARE_TIES, Expert Fusion and Data Merge, and Tables 2–16.
- **Flags:** BASELINE_STRONGER_THAN_REPORTED (Best Single on ARC_C, BBH and MBPP), CLOSED_JUDGE_UNAVAILABLE (the FLORES ensemble needs OpenAI embeddings).
- **Codebase completeness: MINOR_FIXES.** The code ran after environment and efficiency fixes. It does, however, contain several logic deviations from the paper that affect results (see Discrepancies).

**Main findings**
1. **GENOME reproduces.** All 12 datasets are within tolerance (paper std, 5% relative, or 1 point). The average gain is +16.3% over Best Single and +3.9% over Model Swarms (paper: +16.16% / +3.61%).
2. **GENOME+ reproduces partly.**
   - 9 of 11 comparable datasets are within tolerance. GSM8K (47.49 vs 51.24) and DROP (39.48 vs 47.06) are outside it but still above Model Swarms and Best Single.
   - Average gains are smaller than reported: +19.3% vs Best Single (paper +24.06%) and +6.2% vs Model Swarms (paper +10.75%).
   - The headline "+54.8% on DROP" becomes +34% in our run. That figure already includes an oracle DROP "ensemble"; with a fair vote it is +21%.
3. **The GENOME+ ensemble, as implemented, uses test labels.**
   - Ensemble members are ranked by test score.
   - DROP takes the maximum EM over the members.
   - Tied votes get half credit when the gold answer is among them.
   - MBPP votes on test pass/fail flags.
   
   Re-scoring the same runs with validation-only selection and a plain majority vote cuts GENOME+'s advantage over GENOME from +2.5% to +1.1% on average. On DROP it falls from 39.48 to 35.58, below GENOME's 35.98.
4. **Succession bug in GENOME+.** Individuals updated by succession are never re-evaluated, so selection works on stale fitness. In GSM8K seed 3407, the best-by-validation individual (fitness 42.0) scores only 21.8 on test.

   A bug-fixed GENOME+ run (seed 42 only) is listed below for information. It is somewhat better on most datasets but still does not reach the paper's DROP number (39.70 / 36.80 vs 47.06).

## What I ran
- **Repository:** https://github.com/ZhangYiqun018/GENOME (HEAD `1f2ae60`), cloned to `./codebase`. The `datas/**` files are git-LFS pointers; I downloaded the real files from `media.githubusercontent.com` (this produces the data diff in `git diff`).
- **Expert LoRAs:** the authors' release `Estwld/GENOME-gemma-2b-it` on Hugging Face (10 Tulu-v2 experts, rank 8/16), which links back to the GitHub repo. Base model: `google/gemma-2-2b-it`.
- **Environment:** conda env with python 3.10; vllm 0.7.1, torch 2.5.1, transformers 4.48.2, peft 0.14.0, openai 1.61.0, datasets 3.2.0, nevergrad 1.0.8, nltk 3.5, numpy 1.26.4, pandas 1.5.3.

- **Serving:** 3 vLLM OpenAI-compatible servers on one H200 (`start_vllm.sh`, ports 9112–9114, `--enable-lora --max-lora-rank 16 --max-model-len 8192`).
  - The authors' HF card adds `--disable-sliding-window`; that crashes vLLM 0.7.1 with Gemma-2 (`Gemma2Config has no attribute interleaved_sliding_window`), so I dropped it.
  - Up to 14 experiments ran concurrently via `scripts/runner.py`. Commands are in `scripts/jobs.txt` (generated by `scripts/make_jobs.py`); per-job logs are in `runs/logs/`, run states in `runs/ws/*/**/state.json`.
- **GENOME+ command** (per dataset and seed):
  `python run_genomeplus.py --model_path google/gemma-2-2b-it --lora_dir lora_notok --tasks T --test_tasks T --task_weights 1.0 --init_population_size 10 --max_population_size 10 --max_iter 10 --lambda_step 0.5 --phi_lambda 0.95 --phi_inertia 0.2 --phi_cognitive 0.2 --phi_social 0.2 --phi_repel 0.1 --cross_rate 0.3 --individual_mutation_rate 0.3 --gene_mutation_rate 0.2 --sigma 0.001 --do_init --elite_percent 0.1 --seed S --combine_method linear --cross_method linear --method roulette --selection_method roulette --ports 9112 9113 9114`
  - The paper's hyperparameters are cr 0.3, imr 0.3, gmr 0.2, σ 0.001, K=10, N=10, top-3 ensemble.
  - `scripts/genomeplus.sh` instead uses imr=0.0 and gmr=0.1; I used the paper's values.
  - The succession parameters come from `genomeplus.sh`.
- **GENOME command:** `python run_genome.py ... --population_size 10 --iters 10 --cross_rate 0.3 --individual_mutation_rate 0.3 --gene_mutation_rate 0.2 --sigma 0.001 --elite_percent 0.1 --seed S`. `scripts/genome.sh` calls a non-existent `run_ga.py` and uses cr=0, imr=0.1, gmr=0.1.
- **Model Swarms command:** `python run_modelswarms.py ... --population_size 10 --max_iter 10 --lambda_step 0.1 ...`, using `scripts/modelswarms.sh` settings (that script calls a non-existent `run_pso.py`). Seeds 42, 41, 47.
- **Best Single:** each of the 10 experts evaluated on each test set with the repo's own evaluators (`scripts/eval_experts.py`), taking the maximum.
  - The repo's `run_single_eval_baseline.py` only evaluates the validation split.
  - The paper's "best-performing expert" is assumed to be the best on test.
- **Seeds:** {42, 41, 47, 53, 3407}, as in the paper. GSM8K seed 42 was rerun (`*_s42r`) after the first attempt hit OpenAI-client timeouts (see code changes).
- **Reported metric:** whatever the released code reports.
  - GENOME and Model Swarms: `state['final']['test_score']`, the maximum test score over the final population.
  - GENOME+: `state['ensemble_test'][task]['top_3']`.
- **"Validation-selected" column:** my re-scoring of the same runs from a dumped population file, with no test-set selection (`scripts/analyze.py`).
  - Single models: the individual with the highest validation fitness.
  - GENOME+: the top-3 by validation fitness, plain majority vote with ties broken toward the better-validation model. For DROP the vote is over normalised answer strings.
  - MBPP and FLORES: the code's similarity-based selection needs OpenAI embeddings, so these fall back to the top-1-by-validation individual.

## Settings that differ from the paper
- **Hardware:** 1×H200 shared by 3 vLLM servers, vs 4×A100 in the paper. Decoding settings are the code's: temperature 0.2, top_p 0.75, seed 42, and `max_tokens` per task.
- **Model Swarms seeds:** 3 instead of 5, for compute.
- **FLORES-37 GENOME+:** the ensemble needs OpenAI `text-embedding-3-small` (BERTScore-style selection, as the paper also states) and no key was available. The code's ensemble step fails, so there is no as-released GENOME+ number for Flores-37. The validation-best individual scores 22.16.
- **Test sizes:** the code's data has GSM8K test = 1319, ARC-C test = 1172 and MMLU valid = 208 (capped at 200); Table 17 says 1000/1000/200.
- **Baselines not run:** Data Merge, DARE_TIES, Expert Fusion, LoraHub, MERGE3 and Pack of LLMs. Table 2 (multi-task), Table 3 (ablations), Tables 4–16 and Figure 2 were also not run.

## Why it is not fully reproduced
- **Compute:** Model Swarms ran with 3 seeds and the other baselines were not run. Throughput was bounded by Gemma's 256k-vocabulary seeded top-p sampling and multi-LoRA serving on a CPU-limited 14-core allocation; a GENOME/GENOME+ run took about 1.5–3 h (GSM8K up to 6 h).
- **Closed component:** the FLORES ensemble requires the OpenAI embeddings API.
- **Gap in GENOME+'s gains:** GENOME+'s larger gains (especially DROP 47.06 and ARC-C 74.38) did not reproduce. The released code also contains several deviations from the paper's method and protocol (below), some of which use test labels. I found no configuration difference that recovers the paper's GENOME+ DROP/ARC-C numbers.

## Codebase completeness: MINOR_FIXES
Changes I made to `./codebase` (uncommitted; see `git diff -- src`):
1. `src/base/base_individual.py`: cache the tokenizer instead of reloading `AutoTokenizer` for every individual (~20 s CPU each). Efficiency only.
2. `src/utils.py` and `src/swarms/utils.py` (`save_lora_weight`): stop copying the base tokenizer into every individual's LoRA directory.
   - With a tokenizer present, vLLM 0.7.1 loads and caches a separate tokenizer per adapter in its API front-end. That serialised all requests (about 1 req/s) and grew to 30+ GB of RAM.
   - Without it, vLLM uses the identical base tokenizer. I verified that the chat template, vocabulary and encodings are identical for all 10 experts.
   - I also used a tokenizer-free symlink copy of the experts (`lora_notok/`).
3. `src/base/base_method.py`:
   - OpenAI client `timeout=7200`. Under heavy shared load, 4096-token GSM8K generations exceeded the 600 s default. The swallowed exception then left an individual with fitness −100, which crashed roulette selection.
   - An additive dump of each final individual's validation fitness and test predictions (`repro_final_population.json`) for the validation-selected re-scoring. It does not change any computation.
4. `src/evaluate/FLORES101/flores101.py`: reuse the cached tokenizer. The hard-coded `/mnt/shared-storage-user/...` model path was overridden with env `GENOME_MODEL_PATH=google/gemma-2-2b-it`.

Scripts I wrote (outside the codebase): `start_vllm.sh`, `scripts/make_jobs.py`, `scripts/runner.py`, `scripts/eval_experts.py` (Best Single on the test split), `scripts/analyze.py`, `scripts/make_tables.py`, `scripts/make_comparisons.py`, `scripts/check.sh`. `codebase_fixed/` holds the optional bug-fixed GENOME+ (only `src/genomeplus/individual.py` changed).

Other release issues:
- The README example uses arguments that don't exist (`--population_size`/`--max_iter` for `run_genome.py`).
- The shell scripts call non-existent `run_ga.py`/`run_pso.py`, and `expert_fusion.sh` calls `run_lorahub.py`.
- There is no script to produce test numbers for Best Single.
- `datas/` is git-LFS, which a plain clone does not fetch.

## Discrepancies
### Code vs paper
1. **[major] Ensemble ranked by test score.** `BaseMethod.ensemble_test` ranks the GENOME+ top-k ensemble members by `individual.task_scores[task]`, which the test evaluation has just overwritten. The paper selects the top-k by validation fitness.
2. **[major] DROP "ensemble" is an oracle.** `_majority_vote_drop` scores each question with the max EM over the k members; the paper uses similarity-based selection. On DROP this gives 39.48 vs 35.58 with a real vote.
3. **[major] Tie credit uses the gold answer.** `_majority_vote` gives 0.5 credit on a tie if the gold answer is among the tied answers; with 3 distinct answers among the top-3, any correct member earns 0.5.
4. **[major] MBPP ensemble votes on test outcomes.** It votes over pass/fail flags (`predicted_answer` = whether the unit tests passed), whereas the paper selects one output by similarity.
5. **[major] Reported single-model number uses test scores.** For GENOME and Model Swarms it is the max test score over the final population (`save_final_state`). Algorithm 1 in the paper also says "evaluate test fitness, update g", but the text describes validation-based selection.
6. **[major] GENOME+ fitness goes stale after succession.** In `GenomePlus._step`, after the succession (velocity/weight) update the individuals' `evaluated` flags are not reset, so `evaluate()` returns their pre-update fitness. Selection and the ensemble then use stale fitness. Example: GSM8K seed 3407, validation-best individual has fitness 42.0 but test 21.8.
7. **[major] Personal-best term is always zero.** In `genomeplus/individual.py`, `self.p` aliases `self.x` (same dict) and `update_position` is never called, so the "personal/current best" term (p − x) is always 0.
8. **[major] GENOME selection differs.** It is hard-coded to `tournament` (`genome.py _step`), while the paper describes elite plus fitness-proportional selection.
9. **[minor] Succession constants.** The paper gives φ*=(0.95, 0.2, 0.2, 0.1) and λ=0.95. The code/script uses φ=(0.2, 0.2, 0.2, 0.1), λ starting at 0.5 and decayed ×0.95 at every individual update (not per iteration). The code also applies succession before crossover/mutation, whereas Algorithm 2 applies it after.
10. **[minor] Initialisation weights.** The paper draws t~U(0,1); the code uses two U(0,1) weights normalised to sum to 1.
11. **[minor] Shell-script hyperparameters.** `genomeplus.sh` uses imr=0.0, gmr=0.1; `genome.sh` uses cr=0, imr=0.1, gmr=0.1. The paper (§4.1) says cr 0.3, imr 0.3, gmr 0.2.
12. **[minor] Test sizes.** GSM8K 1319 (code uses `gsm8k_test.json`; a 1000-item `test.json` exists but is commented out), ARC-C 1172 and MELD 1232, vs 1000 in Table 17.

### Paper-internal
1. Table 1: the BBH values for Best Single, Data Merge, DARE_TIES and Expert Fusion (30.22, 25.98, 31.85, 31.82) are identical to the MGSM column.
2. Table 3: "w/o cro. & mut." on MGSM is 45.38, higher than full GENOME+ (39.55), yet it is labelled −11.44%.
3. Expert Fusion is described as fitness-weighted merging (§4.1) but as "naive parameter averaging of top experts" in Appendix A.1.5.
