# Reproduction report — SSG: Logit-Balanced Vocabulary Partitioning for LLM Watermarking (2026.acl-long.1702)

## Verdict

- **Verdict: PARTIALLY_REPRODUCED**
- **Result match (after fixes, paper's stated δ=2.0): MIXED**
- **Result match as released (code's effective δ=1, released detection pipeline): MIXED**
- **Coverage: SCALED_DOWN.** All 6 model/dataset settings and all 7 rows of Tables 1 and 2 were run at full dataset scale, but with 1 seed instead of the paper's 5. KGW/EWD pairs got a 2nd seed at δ=2. Tables 3–7 and Figures 1–2 were not run.
- **Codebase completeness: MISSING_SCRIPTS**

### Summary

The method is implemented and runs: `watermark/ssg/ssg.py` in https://github.com/Leileileisa/SSG, which the paper's link https://github.com/AllenG-L/SSG points to.

What holds:
- At the paper's stated setting (δ=2, γ=0.5, h=1, top-k=4), SSG reliably raises TPR@1%FPR when combined with KGW detection (seed 1: 5/6 settings, mean +16.7 points; seed 2: 6/6, mean +18.7) and with EWD detection (6/6 for both seeds, mean +6.5; often only +1 to +3 points once the baseline is already >90%).
- The seed-2 replication agrees on direction.

What does not hold:
1. The claim that SSG improves *every* watermark method does not hold for SWEET. Moreover, the released "SSG+SWEET" detector is not a valid test: it flags **unwatermarked** text as watermarked (TPR@1%FPR on UW text = 34 % Llama-3/GSM8K, 65 % Llama-3/HumanEval, 98 % Qwen/HumanEval). This is because its numerator counts all green tokens unweighted while the expectation uses weights of 0.01 for low-entropy tokens. The paper's SWEET+SSG numbers therefore cannot be taken at face value.
2. The claim that the gains come "without further degrading Pass@1" holds only partly. At δ=2, +SSG lost >3 points of Pass@1/accuracy vs. its baseline in 8/18 pairs at seed 1 (paper: 2/18). Averaged over both seeds the mean ΔP@1 is -2.8 (KGW) and -1.7 (EWD), vs. the paper's +0.6/+0.2. Example: Qwen/HumanEval KGW 29.9→19.5 (seed 2: 26.2→21.3).
3. Absolute numbers mostly do not match.
   - With the paper's stated δ=2, all baselines are much stronger than in the paper (e.g. Qwen/MBPP KGW TPR@1 76.7 vs 37.8), so SSG's headroom and gains are smaller (mean ΔT@1 +7.7 vs paper +20.4).
   - Running the code as released — which silently overrides δ to **1** and duplicates the prompt in the detected text — gives baselines much closer to the paper (e.g. Llama-3/MBPP EWD 88.1 vs 87.7; Llama-3/HumanEval SWEET 7.9 vs 7.9). This suggests the paper's tables were produced with the released code's δ=1, not the stated δ=2.0.
   - In that as-released setting, KGW+SSG is *worse* than KGW on 3 of 4 code settings (e.g. Llama-3/HumanEval TPR@1 22.0→4.9).

## Paper target

The main claims are in Table 1 (HumanEval and MBPP; Qwen2.5-Coder-7B and LLaMA-3-8B) and Table 2 (GSM8K, 10 % sample; DeepSeekMath-7B and LLaMA-3-8B):
- KGW/SWEET/EWD each with and without SSG, plus an unwatermarked (UW) row.
- Metrics: Pass@1/accuracy, TPR at 1 %/5 % FPR, and F1 at 1 %/5 % FPR.
- Settings: δ=2.0, γ=0.5, h=1, max 512 new tokens, "5 runs averaged".

## What I ran

Environment: conda env (python 3.10), torch 2.5.1+cu124, transformers 4.46.3, accelerate 1.1.1, evalplus 0.2.1 (used for the MBPP+ base-test assertions), human-eval data shipped in the repo. The models were run in fp32, as the released code loads them: Qwen/Qwen2.5-Coder-7B, meta-llama/Meta-Llama-3-8B, deepseek-ai/deepseek-math-7b-base. Each process generated one prompt at a time with HF `generate` (do_sample with each model's default generation config), and 4 processes shared the single H200.

The pipeline is driven by `make_jobs.py`, which writes `jobs.json`, and run by `scheduler2.py` (scheduler.py was used for the first 5 h). Every job is `gen.py` followed by `detect.py` with the CLI options listed below. Pass@1 and accuracy come from `eval_quality.py`. Tables are built by `aggregate.py`, `build_comparisons.py`, `claim_summary.py` and `seed_summary.py`.

Three configurations were run:

1. **"ours" — paper setting (`runs/d2`)**
   - `--delta 2.0` (the paper's δ).
   - `--text_mode fixed`: the detector is given prompt + *newly generated text*, instead of prompt + (prompt + generated text).
   - Seeds 0–6, one generation per table row. The three +SSG rows are three independent SSG generations, each detected with SSG's `detection_method` = KGW / SWEET / EWD (`config/SSG_{KGW,SWEET,EWD}.json`, copies of `config/SSG.json`).
   - The UW row uses the EWD detector on unwatermarked generations. The KGW, SSG-EWD and SSG-SWEET detectors were also run on UW text and saved.
2. **"as released" (`runs/d1`)**
   - The default `delta=1` override that `gen.py`/`detect.py` pass to `AutoWatermark.load`.
   - `--text_mode released`: `detect_watermark(prompt+completion, prompt)` exactly as in detect.py, where `completion` already contains the prompt.
   - One SSG generation per setting, detected with the three SSG detection modes (so all three +SSG rows share one generation and one P@1).
3. **seed 2 (`runs/d2s2`)**: KGW, EWD, KGW+SSG and EWD+SSG at δ=2, fixed mode, seeds 21–26.

Data:
- HumanEval: 164 problems (repo file).
- MBPP: 378 MBPP+ problems (repo file), with a 3-shot prompt as in the repo. Pass@1 uses the MBPP+ base-test `assertion` from evalplus.
- GSM8K: the **first 132** test problems with a 3-shot prompt. The paper's "random 10 %" sample is not specified or released.
- Negatives for FPR calibration are the human reference solutions/answers, scored without a prompt, as in detect.py.

Pass@1 / accuracy (my own evaluator, because none is released):
- HumanEval: the completion is truncated at the standard stop sequences (`\nclass`, `\ndef`, `\n#`, `\nif`, `\nprint`), then the official tests are executed.
- MBPP: truncated at the next `"""` / `assert` / `if __name__` / `print(`, then the MBPP+ base assertions are executed.
- GSM8K: the first `#### <number>` in the continuation is compared with the gold answer.

Settings that differ from the paper:
- 1 seed instead of 5 (2 seeds for the KGW/EWD pairs at δ=2).
- The GSM8K subset is the first 132 problems.
- No ">15 token" filter, since none exists in the code.
- top-k=4 (the repo config; the paper does not state k for Tables 1/2).

Wall-clock: about 36 h total (2026-09-29 22:12 → 2026-10-01 ~10:15 CDT), almost all of it generation/detection on the single shared GPU.

## Discrepancies

### Code vs. paper

1. **δ override (minor numeric, affects results).** `gen.py` and `detect.py` call `AutoWatermark.load(..., delta=1)`, and `BaseConfig.__init__` writes this kwarg over the config. So the released pipeline uses δ=1. The paper (§5) and `config/*.json` say δ=2.0.
2. **Prompt duplicated in detected text (major, evaluation protocol, affects results).** `detect.py` scores `prompt + completion`, but `gen.py`'s `completion` is the decode of the full sequence and already starts with the prompt.
   - EWD/SWEET/SSG strip `prompt_len` tokens, so they then score a second, copied prompt as if it had been generated.
   - KGW scores everything.
3. **SSG "SWEET" detection statistic (major, affects results).** In `watermark/ssg/ssg.py`, `SSGUtils._get_weight_from_entropy` and `score_sequence` (`detection_method='SWEET'`) differ from SWEET in several ways:
   - "entropy" is EWD's spike entropy, not Shannon entropy;
   - low-entropy tokens get weight 0.01 instead of being excluded;
   - the numerator counts all green tokens unweighted, while the expectation and variance use the weights.

   Unwatermarked text is flagged at 34–98 % TPR@1%FPR. The paper presents "SWEET+SSG" as SWEET with SSG partitioning.
4. **"+SSG" generation is the same for all three methods (major).** SSG generation never uses SWEET's entropy-gated biasing; only the detection weighting differs. The paper describes SSG as being incorporated *into* each KGW-scheme method.
5. **KGW baseline detection (minor).** `KGW.detect_watermark` ignores the prompt argument and scores the whole text, including the prompt(s). The other detectors strip the prompt. In addition, `SWEET.detect_watermark` tokenizes the text without BOS but the prompt with BOS, so `prompt_len` is off by one for Llama.
6. **Missing protocol pieces (minor).** Several things the paper describes are not in the code:
   - no ">15 tokens" generation filter (§5);
   - no 10 % GSM8K sampling (the detect.py GSM8K branch uses all 1319);
   - no 5-run averaging;
   - no Pass@1 evaluation.
7. **Crash on short texts (minor bug).** In `SSG.detect_watermark` and `EWD.detect_watermark`, `all_greenlist_ids` is undefined after a caught exception, which raises `UnboundLocalError`.

### Paper-internal

1. **Table 1 vs. Table 3.** The LLaMA-3/MBPP UW row lists T@5 = 29.7 but F1@5 = 10.5 in Table 1, which is impossible at 5 % FPR. Table 3 gives 29.7/29.7.
2. **Same generations, different Pass@1.**
   - Tables 1/3 (prompt vs. no prompt at detection) report different UW Pass@1 for LLaMA-3/HumanEval: 34.1 vs 32.9.
   - Tables 2/4 do the same for LLaMA-3/GSM8K: UW 38.6 vs 35.6, KGW 37.1 vs 35.6.
   - Only the detection prompt changes between these tables, so Pass@1 should be identical.
3. **"5 runs averaged" vs. single-run fractions.** The Table 1 caption says each setting is run 5 times and averaged. Yet most entries are exact multiples of 1/164 or 1/132 (e.g. 39.0 = 64/164, 90.9 = 120/132), as expected from a single run.
4. **§5 vs. the paper's conclusion on Pass@1.** §5 claims SSG gains come "without further degrading Pass@1". Table 1's LLaMA-3/HumanEval EWD+SSG (34.1→29.9) and Table 2's LLaMA-3/GSM8K SWEET+SSG (38.6→34.1) show drops of 4+ points.
5. **Minor text errors.** HumanEval is cited as Austin et al. and MBPP as Chen et al. (swapped). §5.2 refers to "Figure 3" for the watermark-strength distribution, which is Figure 2.

## Why the numbers don't fully reproduce

- **δ.** The paper says δ=2.0. The released `gen.py` and `detect.py` call `AutoWatermark.load(..., delta=1)`, and `BaseConfig` overwrites the config's 2.0 with this kwarg. So the released pipeline runs δ=1.
  - At δ=2 the baselines detect far better than the paper reports, which leaves less room for SSG.
  - At δ=1 (as released) the baselines are close to the paper.
- **Detection input.** `gen.py` stores `completion` = decode(prompt + generation). `detect.py` then scores `prompt + completion`, so the prompt appears twice.
  - EWD/SWEET/SSG strip only the first copy, so they score the prompt copy as if it had been generated.
  - KGW scores everything, including both prompt copies.
  - This changes the scores; I fixed it for "ours" and kept it for "as released".
- **SSG + SWEET detector is invalid.** In SSG's `SWEET` detection mode, three things combine:
  - Low-entropy tokens get weight 0.01, and "entropy" is EWD's spike entropy, not Shannon entropy as in SWEET.
  - The numerator counts *all* green tokens unweighted, while the expectation and variance use the weights.
  - The resulting "z-scores" grow with text length: human code ≈ +12…+17 on average, watermarked ≈ +90…+150.
  - **Unwatermarked** generations score above the 1 %-FPR threshold in 34–98 % of cases (`runs/d2/*_UW__det_SSG_SWEET_fixed.json`, logs `logs/extra_uw_ssgsweet_*`).
  - SSG generation is also identical for all three "+SSG" rows. In particular, there is no SWEET-style entropy gating at generation.
- **Variance.** HumanEval has 164 problems and GSM8K 132, so one problem is 0.6–0.8 points. The paper averages 5 runs; I ran 1–2.

## Codebase completeness: MISSING_SCRIPTS

The method (SSG partitioning, logits processor, SSG detection with KGW/SWEET/EWD weighting) is implemented. The pipeline for the main tables is incomplete:
- no Pass@1 / GSM8K-accuracy evaluation;
- `gen.py` has no GSM8K branch;
- the UW row cannot be generated (`--alg UW` is not a registered algorithm);
- no multi-run/averaging driver;
- no 10 % GSM8K sampling;
- no table builder.

`main.sh` only runs one demo (LLaMA-3/MBPP SSG).

### Changes to the released code (uncommitted in `./codebase`; `git diff`)

- `gen.py`:
  - added a GSM8K branch, with the 3-shot prompt copied from detect.py;
  - UW generation now loads a KGW object, because `'uw'` is not in the registry and crashed;
  - added `--config`, `--delta` (default 1 = released behaviour), `--seed`, `--n`, `--out`;

  - added `--config`, `--delta` (default 1), `--n`, `--text_mode {released,fixed}` (fixed = use `gen_only`), `--out` (dumps scores and metrics);
  - added `PYTORCH_CUDA_ALLOC_CONF=expandable_segments` and `torch.cuda.empty_cache()` per sample, so 4 jobs can share one GPU.
- `watermark/ssg/ssg.py`:
  - **bug fix:** `detect_watermark` crashed with `UnboundLocalError` when `score_sequence` raised (≤1 scored token). Now z=-1 is kept as the code intends, and the watermark-strength computation is skipped.
  - **speed-only change:** `get_greenlist_ids(..., as_tensor=True)` returns the same green set as a GPU tensor, using the identical RNG call sequence. It is used in detection and in the logits processor, and I verified it equal to the list version. Qwen/MBPP δ=2 SSG generations were produced before this change; all others after.
- `watermark/ewd/ewd.py`: the same crash fix as ssg.py.
- New files: `config/SSG_KGW.json`, `config/SSG_SWEET.json`, `config/SSG_EWD.json`. These are copies of `config/SSG.json` with `detection_method` changed.
