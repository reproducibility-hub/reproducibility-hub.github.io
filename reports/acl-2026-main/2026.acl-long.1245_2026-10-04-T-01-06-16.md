## Diagnostic: Qwen2.5-7B-Instruct without the HF repetition penalty

Qwen2.5-7B-Instruct's `generation_config.json` sets `repetition_penalty=1.05` (plus `top_k=20`, `top_p=0.8`, which have no effect at temperature 0.01). aw.py does not override it. To test whether this explains the lower Qwen-Instruct numbers, I re-ran Vanilla on the unordered data with `repetition_penalty=1.0` (`scripts/run_norep.sh`, via env var `AW_REPETITION_PENALTY`; this is not part of the main results):

| Dataset | Paper Vanilla | Ours (HF default, rep. penalty 1.05) | Ours (rep. penalty 1.0) |
|---|---|---|---|
| HotpotQA | 0.468 | 0.418 | 0.436 |
| Musique | 0.458 | 0.394 | 0.404 |
| 2WikiMHQA | 0.480 | 0.434 | 0.438 |

Removing the penalty recovers only 0.4–1.8 points of the 4.6–6.4 point gap, so it is not the main cause. The remaining gap is unexplained; it may come from transformers/torch/hardware version effects.

## Why it is not fully reproduced

- No crash or missing component prevents the run: after the fixes below, all 72 Table-5 runs completed on all 500 examples with no skipped samples. The remaining gaps are numerical. (a) Both Qwen models score uniformly lower, including Vanilla, which points to an environment / generation-config difference rather than the method. (b) The method's gain in the ordered setting is much smaller than reported, in all four models, including Vicuna and Llama whose Vanilla numbers reproduce exactly. Results come from a single seed, as in the paper's Table 5. Differences of 1–3 points on 500 questions are within sampling noise of individual cells (one question = 0.2 points), but the ordered-setting averages are consistently below the paper across all 4 models.
- Baselines RankGPT, ICR and SELF-ELICIT (Table 5) are not in the release, so the "beats prior baselines" claim is NOT_COMPARABLE for them. For the one baseline the release does implement (AttentionSort = `fg`), the advantage of DR over it does not reproduce (see the supplementary section).

## Codebase completeness: MISSING_SCRIPTS

Changes to the released code (uncommitted in `./codebase`, see `git diff`):
1. `aw.py` lines 2–3: commented out `DEVICE = "3"; os.environ["CUDA_VISIBLE_DEVICES"] = DEVICE`. It overrides the GPU allocated by Slurm, and on a 1-GPU allocation makes the GPU invisible.
2. `aw.py` `inference_attention_merge`: wrapped `get_sentence_token_spans(...)` in `try/except IndexError` (sentence spans := None). The released `utils.get_sentence_token_spans` indexes past the token list on some inputs, which crashed the Vicuna HotpotQA DR run at sample 399. The sentence spans are only used by aggregation methods 1/2, never by method 0 (DR/DR+DP), so results are unaffected.

Scripts I wrote outside the release:
- `scripts/prepare_data.py`: CAGB → `datasets_processed` conversion (missing from the release; required by `--processed`).
- `scripts/aw_wrap.py`: launcher that imports and runs the unmodified `aw.main()`. It applies only performance/robustness patches, and I verified they give byte-identical outputs on test samples (`ref/`):
  - `torch.cuda.empty_cache()` before each `generate`, so 4–5 runs can share one GPU.
  - Retry of `generate` on CUDA OOM caused by the *other* processes, with the RNG state restored. Without it, aw.py silently drops the sample (DR modes catch the exception) or crashes (vanilla).
  - A fast path in transformers' `to_py_obj` for int lists. `utils.find_text_token_span` decodes O(L) times per sample, which took about 20 s/sample with transformers 4.46.
  - `.float().cpu()` instead of `.cpu().float()`, and batching the per-layer attention copies for each answer token into one GPU→CPU transfer. These give identical fp32 values and identical numpy reductions.
  - An env var `AW_REPETITION_PENALTY`, used only for the Qwen-Instruct diagnostic run, not for the main results.
- `scripts/run_all.py`, `run_rev.py`, `run_claim.py`: job queues. A job is re-run if it crashed or if aw.py skipped any sample, so every reported cell has exactly 500 outputs.
- `scripts/collect.py`, `make_tables.py`, `gains.py`, `write_report.py`: evaluation and report tables.

## Discrepancies

Code vs paper:
1. *minor*, `aw.py` `parser()`: `--max_new_tokens` defaults to 512, while the paper (App. A.2) uses 300, and the README command does not set it. I used 300. Affects results only when an answer is longer than 300 tokens.
2. *minor*, `aw.py` `inference_attention_merge`, DP position score: §4.2/Alg. 1 combine the attention of "the final token preceding the answer" (e.g. ':' of "Answer:") and "the terminating token". The code uses prompt position −2 (the token *before* the last prompt token) and the attention row at generation step `end`, i.e. the query of the last answer token that predicts the terminator, not the terminator itself. Same idea, shifted by one token. It may affect DP slightly.
3. *minor*, `aw.py` `span_attention_one_token`: for DR, each layer's head-averaged attention over the context is renormalised to sum to 1 (`use_norm=True`) before averaging over layers (upper half of the layers). Eq. (1) is a plain average over heads and the "selected layers"; it mentions neither the renormalisation nor which layers are selected.

Paper-internal:
1. Table 15 (Vicuna-13B) labels the method "Our DA + DU" while the rest of the paper calls it "Our DR + DP" (naming only).
