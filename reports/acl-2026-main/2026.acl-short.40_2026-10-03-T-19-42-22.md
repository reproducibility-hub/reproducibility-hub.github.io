- `batch_size` 25 instead of 5, with 3 generation processes sharing one H200. This only affects speed, plus padding layout. Left padding is masked because gen_response adds a distinct `[PAD]` token.

- Test items are the first 1000 per language, as the code does it. The paper says it sampled them randomly.

## Codebase completeness: MAJOR_FIXES
Changes to the released code (left uncommitted in `./codebase`, see `git diff`):
1. `latb/logit_processors.py`, `AdaptiveBoostLogitsScoreProcessor.__call__`: the masks are now rebuilt when the batch shape changes. Before, they were built once and crashed on a smaller final batch (ja 889 and th 826 items are not divisible by the batch size). The fix doesn't change the method.
2. `codebase/.env`: created; the README refers to a `.env.sample` that is not in the repo.

Scripts I wrote outside the codebase:
- `gen_suzume.py` — fixes the Suzume baseline.
  - The released `experiments/sum/baselines/suzume.py` runs only 4 languages, and its `lang_name`/`lang_code` lists are misaligned. French is prompted with the English template ("Please summarize the text in English"), Japanese with the Russian one, and so on. That changes baseline results.
  - Running Suzume through the batched `gen_response.py` instead has its own problem. Suzume's `pad_token == eos`, and `gen_response.py` passes no `attention_mask`, so HF attends to the left padding and padded rows come out as garbage. My first Suzume run hit this (ROUGE-1 ≈ 5; kept in `out/suzume_padbug`, `eval/suzume_padbug`).
  - The wrapper clears the pad token, so `gen_response.py` adds `[PAD]` exactly as it does for Llama3.
- `gen_standard_prompt.py` — injects the Fig. 3 standard-prompt templates, which are missing from the release.
- `run_all.sh`, `run_suzume.sh`, `run_std_retry.sh` — generation drivers. Two standard-prompt jobs (ko, th) hit CUDA OOM from 3 processes sharing the GPU and were simply re-run.
- `eval_all.sh` — runs the released evaluator. It includes a guard that drops responses the evaluator cannot score (NaN / no letters → ZeroDivisionError). This was only needed for the buggy Suzume run; no response was dropped in the final evaluation.
- `compile.py`, `write_status.py` — comparison table and status file.

## Discrepancies
- **code_vs_paper (major)** — `AdaptiveBoostLogitsScoreProcessor`. The paper's p adds α to every token in I: target-language, number, special-character and EOS tokens. The code uses all of I for the flatness test but boosts only target-language tokens + EOS. So numbers and punctuation are not boosted, and with α=1000 they are effectively suppressed at "flat" steps. The paper's numbers were produced by this code, so it is consistent with Table 1/2, but not with the method description.
- **code_vs_paper (major)** — `suzume.py`. It covers 4 of the 8 languages and pairs languages with the wrong prompt templates (see above).
- **code_vs_paper (minor)** — the paper "randomly sample[s] up to 1,000 test instances"; the code takes the first 1000.
- **code_vs_paper (minor)** — only the strict prompt templates are released. The standard-prompt baseline (Fig. 3) is absent.
- **code_vs_paper (minor, no effect)** — `GenerationConfig(temperatue=...)` is a typo, so the argument is ignored. The default T=1.0 matches the paper anyway.
- **code_vs_paper (minor, no effect)** — the flatness test uses `<= β`; the paper uses `< β`.
- **code_vs_paper (minor, not in the main tables)** — the α sweep script uses α ∈ {1, 5, 50, 500}; Appendix C says α was varied from 0 to 50.
- **paper_internal** — Table 2's ja standard-prompt ROUGE (26.42/12.53/16.84) contradicts Table 1's 98.31% response-level confusion for the same setting, and the pattern in all other languages. Our rerun gives 2.12/0.85/1.49.
