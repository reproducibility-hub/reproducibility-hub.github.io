**Short summary.** The repo implements ReX (a custom PEFT tuner "vaelora") plus training/eval scripts, but ships
neither the 10K filtered training set (`mix_datav2/filter_train_10K.json`) nor the evaluation files (`gpqa.json`,
`mmlupro_*.json`, `math500_level3.json`), nor the prompt/instruction text. I rebuilt both from the public sources
exactly as described in Appendix A. On this rebuilt data:

* The **base-model** numbers (Llama-3.2-3B avg 0.233 vs paper 0.234) and the **LoRA** baseline on Llama-3.2-3B
  (avg 0.332 / 0.342 for 2 seeds vs paper 0.333) land very close to the paper, so the rebuilt setup is a faithful proxy.
* **ReX as released** beats LoRA on both backbones and both seeds (Llama-3B: 0.355 / 0.351 vs LoRA 0.332 / 0.342;
  Mistral-7B: 0.225 / 0.244 vs 0.195 / 0.197) but stays below the paper's ReX numbers (0.3805 and 0.2615).
* **However, the released code never trains with the VAE / orthogonality losses that define the method**: the KL,
  reconstruction and orthogonality terms are only collected by transformers' `check_model_inputs` output-recording when
  `output_vaelora_*` flags are set, which nothing sets (and setting them crashes `load_loss_func`). Training loss is
  exactly the CE loss (verified numerically). After fixing this so that the paper's objective (Sec. 4.5) is actually
  optimised, ReX is no longer consistently better than LoRA: Llama-3B 0.321 (seed 42) / 0.374 (seed 123) vs LoRA
  0.332 / 0.342 (2-seed mean +1.1 pt, large seed spread); Mistral-7B 0.185 / 0.155 vs LoRA 0.195 / 0.197
  (2-seed mean −2.6 pt, below LoRA and below the untuned base model).

## What the paper claims (target)

Main claim (abstract, §5.2, Tables 1–2): ReX outperforms task-specific fine-tuning (LoRA) and other PEFT/text
baselines on GPQA-Diamond, MMLU-Pro Chemistry/Economics/Math (200 random each), MATH500 level≥3 (367),
for Llama-3.2-3B-Instruct (ReX avg 0.3805 vs LoRA 0.3332) and Mistral-7B-Instruct-v0.3 (0.2615 vs 0.2425),
trained on 10K samples drawn 3:5 from OpenR1-Math-220k and the science subset of OpenThoughts3-1.2M.

## What I did

### Data rebuild (scripts I wrote: `data_build/build_train.py`, `data_build/build_eval.py`)
* **Training** (Appendix A.1): OpenR1-Math-220k (`default` split; first generation with `correctness_math_verify=True`)
  and OpenThoughts3-1.2M rows with `domain=="science"`; thinking traces removed (text after `</think>`);
  kept samples with total chat-formatted length ≤ 1024 Llama-3.2 tokens and response ≥ 256 tokens; 3,750 math + 6,250
  science = 10,000 (3:5), seed 42. Instruction: `"Please reason step by step, and put your final answer within \boxed{}."`
  (the authors' instruction is unknown; the repo's grader extracts `\boxed{}` answers).
* **Evaluation** (Appendix A.2): GPQA-Diamond (198; options shuffled with seed 42; letter answer),
  MMLU-Pro chemistry/economics/math (200 random each, `shuffle(seed=42)`, options A–J), MATH500 level≥3 (367 — matches
  the paper's count). MC instruction asks for the option letter in `\boxed{}`.
* Same instruction format for train and test; graded by the repo's own `utils_parser.extract_answer` +
  `utils_grader.check_is_correct`.

### Models
`unsloth/Llama-3.2-3B-Instruct` (identical weights to the gated `meta-llama` repo, which this account cannot access;
I removed unsloth's extra pad token so that, as with the Meta tokenizer, pad = eos as the repo code expects),
`mistralai/Mistral-7B-Instruct-v0.3`. Both via local dir `models/` (`HF_CACHE_DIR` in `constant.py`).

### Commands (exactly the repo's `scripts/train.sh` settings; all defaults of the configs)

Training config = repo defaults: 2 epochs, lr 1e-4 cosine, warmup 5%, bs 2×4 accum, paged_adamw_8bit, max_seq_len 1024,
2% validation split, eval every 100 steps, best-eval-loss checkpoint, seed 42; **4-bit NF4 (QLoRA) base model**
(`configs/quant/default.json`, used by `train.sh`); target modules = repo default `--target_modules 4` = `q_proj, v_proj`;
ReX r=8, r_b=16, d_z=8, top-k=8, α=16, β_kl=β_rec=β_orth=0.1, mixer init kaiming_uniform. Greedy decoding,
max_new_tokens=1024, eval batch 24 (hard-coded in `finetune_llm.py`).
`summarize.py` collects the numbers into `results_summary.json`; `make_status.py` builds the comparison list.

### Settings that differ from / are not specified by the paper
* Training and eval data: rebuilt (see above) — exact sample IDs, prompts, GPQA option order and MMLU-Pro subsets differ.
* Llama weights from the unsloth mirror (same weights).
* LoRA baseline alpha (16) and dropout (0.05) chosen by me (paper only gives rank 8; the repo has no LoRA config file).
* Seeds: paper reports single runs; I ran seed 42 and seed 123 for every fine-tuned configuration (LoRA, ReX as
  released, ReX fixed) on both backbones. status.json comparisons use seed 42.
* Hardware: 1×H200 instead of A100-40GB.

### Interpretation
* The rebuilt setup reproduces the paper's Base and LoRA numbers closely on Llama-3.2-3B, so the data rebuild is a
  reasonable proxy — but by the task protocol all comparisons are `NOT_COMPARABLE` because the paper's own data is missing.
* With the code **as released** (which in practice trains ReX with CE loss only + the auxiliary-loss-free router
  balancing), the direction of the main claim holds on both backbones (ReX > LoRA), with smaller gains than reported.
* With the method **as described in the paper** (CE + λ_kl L_kl + λ_rec L_rec + λ_orth L_orth), the gain over LoRA is
  not robust: one Llama seed below LoRA, one above; Mistral below LoRA on both seeds (and below the base model). The paper's Table 3 ablation ("w/o L_kl+L_rec"
  and "w/o L_orth" both hurt) cannot be produced by the released code, in which these losses are inactive in all variants.
* Not run (no code in the release): ICL, LLM+RAG, Self-Refine, Reflexion, HydraLoRA, MoSLoRA, VB-LoRA, SMoRA →
  claims "beats X" for these are `NOT_COMPARABLE`. Table 5 (Llama-3.1-8B), Tables 3/4/6/7 and Fig. 2–4 not run.
