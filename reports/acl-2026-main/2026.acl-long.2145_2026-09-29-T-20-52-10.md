# Reproduction report — EDSD: Entropy-Driven Design for Faster Speculative Decoding (ACL 2026, 2026.acl-long.2145)

## Verdict

**PARTIALLY_REPRODUCED** — result match **MIXED**, as-released **DOES_NOT_RUN**, coverage **SCALED_DOWN**, codebase **MISSING_CORE**.

I ran one target model (Llama-3.1-8B-Instruct, "L31-8B") with about 4% of the paper's training data (21k ShareGPT conversations, responses regenerated by the target, 8 epochs). Under this budget I trained EAGLE-3, EDSD, and the EDTrain ablation the same way, then evaluated them all with the same harness. Results:

* **Training-efficiency claim (Table 2): holds.** EDTrain (Mask-p + Step-n) cut training GPU-hours by **21.9%** against the same EDSD architecture trained without it, with the same epochs. The paper reports 19.9% (stated as "+24.8% efficiency"; ours is +28.0%).
* **Acceptance-length / speedup claim (Table 1): does not hold at this scale.**
  * EDSD reached mean τ **4.557** and SR **2.57×**. Our EAGLE-3, trained on the same data, reached τ **4.605** and SR **2.65×**. So EDSD is **−1.0% τ / −3% SR**, whereas the paper reports **+3.5% τ / +5.1% SR** for L31-8B.
  * EDSD's τ is lower on 4 of 5 benchmarks, but every per-benchmark gap is ≤0.16 tokens, so the two are essentially tied.
* **EDTrain improving τ (Table 2/13): does not hold.**
  * Without EDTrain, τ is 4.633; with EDTrain it is 4.557, i.e. **−1.6%**. The paper reports +4.9% (5.49→5.76).
  * SR is unchanged (2.567× → 2.573×).
  * The architecture alone (EDArch, standard training) gives +0.6% τ over EAGLE-3.
* **Robustness claim (Table 3): not reproduced as a property of EDArch.**
  * Under the paper's 10 alternative system prompts, the **official** EAGLE-3 checkpoint does degrade (−4.8%; paper's EAGLE-3: −2.7%).
  * But our EAGLE-3 trained on the same data as EDSD does not degrade (+1.1%), and neither does EDSD (+1.9%; paper −0.5%).
  * At this scale, the robustness gap comes from the training data/recipe, not from EDArch.
* **Harness check: passed.** The official EAGLE-3 checkpoint reproduces the paper's EAGLE-3 row for L31-8B: mean τ 6.40 vs 6.34, SR 3.78× vs 3.73×.

**Big caveat:** I could not run the paper's data scale (532k ShareGPT+UltraChat, ≈5 days on 8×H800 per model) or its other six target models. EDSD's τ/SR advantage might only appear with more data or longer training, so the negative findings apply only to this scaled-down regime. No EDSD weights were released, so the paper's own drafters could not be evaluated.

## What the paper claims (targets)
- Table 1 (T=0): EDSD has higher SR and τ than EAGLE-3 on all 7 LLMs. For L31-8B: EAGLE-3 3.73× / 6.34 vs EDSD 3.92× / 6.56 (mean of 5 benchmarks).
- Table 2 / Table 13: on L31-8B trained on ShareGPT only, EDTrain gives 3.32× / 5.76 in 64.1 GPUh, vs 3.22× / 5.49 in 80.0 GPUh without Step-n & Mask-p (−19.9% time, "24.8% efficiency").
- Table 3: under 10 alternative system prompts, τ drops −2.7% for EAGLE-3 vs −0.5% for EDArch (L31-8B).

## Code / release
- The paper links `github.com/KerwinKai/EDSD`. It contains only a README and a poster, and points to `github.com/KerwinKai/SpecForge/tree/add_edsd` (commit `592364a`). I cloned that branch to `./codebase`. The other branches (`add_edsd_v2`, `add_edselect`) contain no EDSD/EDSelect code; they are upstream syncs.
- What the release contains (training only):
  - `scripts/train_edsd.py`
  - `specforge/core/edsd.py` (Mask-p entropy masking, Step-n TTT schedule)
  - `specforge/modeling/draft/edsd.py` (EDFuse and the two-layer feature input)
  - a Qwen3-8B config and an example launch script
  - EAGLE-3 training (`scripts/train_eagle3.py`) is also present (upstream SpecForge), so the EAGLE-3 baseline could be trained with the same framework.
- What the release is missing:
  - (a) **EDSelect** (Curvature/Lidar layer selection). Layers are hard-coded in configs; I used the Table 15 layers.
  - (b) **Any inference / evaluation code for the EDSD draft architecture.** SGLang/EAGLE do not support `EdsdDraftModel`, and there are no Spec-Bench scripts.
  - (c) **Released draft weights.** The paper says "we make our draft model weights available", but none exist on GitHub or HF.

## What I did (exact pipeline)
All of this ran in the conda env `./env` (Python 3.11, `pip install -e codebase`; torch 2.9.1, transformers 4.57.1, sglang 0.5.9). CUDA 12.8 nvcc/headers came from the `nvidia/label/cuda-12.8.1` conda channel, plus an `env/lib64 -> lib` symlink, because SGLang JIT kernels need them. See `envrc.sh`.

1. **Data.**
   - `python codebase/scripts/prepare_data.py --dataset sharegpt` (Aeala/ShareGPT_Vicuna_unfiltered, 120,675 convs).
   - Took two random disjoint 16k subsets (seed 0).
   - Regenerated the responses with the target model via an SGLang server and `codebase/scripts/regenerate_train_data.py` (temperature 0.7, max 2048 new tokens).
   - Conversations that start with an assistant turn are rejected by the script, leaving **20,973 conversations** (`data/train_sharegpt_regen.jsonl`, average 1,275 tokens).
2. **Training** (`scripts/train_common.sh`, wrapper around the released scripts; 1×H200, batch 1, lr 5e-5, max length 2048, 8 epochs, TTT/S_max 7, SGLang target backend, flex-attention):
   - EDSD: `train_edsd.py --draft-model-config configs/llama31-8b-edsd.json --drop-ratio-scale 0.03`. The config is the repo's `llama3-8B-eagle3.json` with `architectures=[EdsdDraftModel]`, `target_layer_ids=[15,28]` (= Table 15 "16, 29" in EAGLE's input-of-layer numbering), and intermediate size m=14336.
   - EAGLE-3: `train_eagle3.py --draft-model-config codebase/configs/llama3-8B-eagle3.json` (default aux layers [1,15,28], i.e. "2, L/2, L−3").
   - Ablation "w/o Step-n & Mask-p": `train_edsd.py ... --step-n-schedule 7 --drop-ratio-scale 0.0`.
   - All runs were sequential on an otherwise idle GPU. GPU-hours are the sum of the per-epoch tqdm times (`scripts/epoch_times.py`).
3. **Evaluation** (`scripts/eval_sd.py`, my own script):
   - Uses EAGLE's official tree-decoding implementation (`SafeAILab/EAGLE` @ `cb7e084`, `./eagle_repo`) with fp16 target and greedy decoding (T=0).
   - Tree settings from the paper: depth 8, top-k 6, 60 draft tokens. Max 512 new tokens.
   - Uses EAGLE's own Spec-Bench-style question sets: MT-bench (80, two turns), HumanEval (80), GSM8K (80), Alpaca (80), CNN/DM "sum" (79).
   - Uses EAGLE's default Llama system prompt (the same one SpecForge's `llama3` training template uses).
   - τ = generated tokens / verification steps. SR = tokens/s ÷ tokens/s of vanilla autoregressive decoding in the same harness, averaged over 2 timing rounds for our models (`results/main`, `results/main_r2`). τ was identical across rounds. Timing noise between rounds is about ±5% per benchmark.
   - For EDSD I wrote an inference port of the draft model, `eagle_repo/eagle/model/cnets_edsd.py`. `scripts/test_edsd_port.py` checks that it matches SpecForge's `EdsdDraftModel` numerically (max abs diff 3e-8); `scripts/test_eagle3_port.py` does the same for EAGLE-3.
4. **Robustness** (`scripts/run_robust_eval.sh`, `scripts/summarize_robust.py`):
   - Each of the 10 Table 14 system prompts (`configs/table14_system_prompts.json`) replaces the default.
   - First 16 questions per benchmark (scaled down from 80).
   - Reported value: mean τ over the 10 prompts, relative to the default-prompt τ on the same 16-question subset.

## Why the headline numbers were not reproduced
- **Compute/data scale (main reason).** I used 21k training conversations instead of 532k (Table 1) or 68k (Table 2), on one GPU. The absolute τ of all our drafters is therefore about 1.8 tokens below the paper's. EDSD's relative advantage, and EDTrain's τ gain, may need more data. In our regime, entropy masking (up to 21% of tokens dropped in early epochs) and the shorter early TTT horizons appear to cost a little accuracy rather than help.
- **Baseline protocol.** The paper's EAGLE-3 numbers coincide with the *official* EAGLE-3 checkpoint, which was trained with a different data/recipe than EDSD. So the paper's EDSD-vs-EAGLE-3 comparison is not controlled for training data. When both are trained identically (our setup), the gap disappears, and so does the robustness gap.
- **Sources of mismatch I could not remove:**
  - the optimizer betas (not exposed by the release);
  - Step-n uses `ceil` in the code vs `floor` in the paper;
  - unknown global batch size and regeneration temperature.

## Codebase completeness: MISSING_CORE
The training side of EDSD (EDFuse architecture, Mask-p, Step-n) is implemented and ran **without any source edits** (CLI args only). What is missing:
- **EDSelect** (Curvature/Lidar matrix-entropy layer selection, one of the method's three named components) is absent. Layer ids must be hard-coded from Table 15.
- **No inference implementation of the EDSD draft model and no evaluation pipeline.** Neither SGLang nor EAGLE supports the EDSD architecture, and there are no Spec-Bench/benchmark scripts. The main Table 1 numbers therefore cannot be produced from the release at all → `result_match_as_released = DOES_NOT_RUN`.
- **No draft weights**, despite the paper's statement.

## Discrepancies
**Code vs. paper**
1. **Step-n rounding** (`specforge/core/edsd.py::compute_step_n`). The paper's Eq. 6 uses floor, giving n_t = 1,1,2,3,4,5,6,7 for T=8, S_max=7. The code uses `ceil` (its docstring wrongly says this is Eq. 6), giving 1,2,3,4,5,6,7,7. This affects training cost and results. Minor.
2. **Optimizer betas** (`specforge/optimizer.py`). The paper uses AdamW β=(0.9, 0.95). The code hard-codes the torch default (0.9, 0.999). Minor.
3. **Release defaults vs paper hyper-parameters.** `run_qwen3_8b_edsd_online.sh` uses 10 epochs, lr 1e-4, max length 4096; the `--drop-ratio-scale` default is 0.02 (γ=2%). The paper uses T=8, lr 5e-5, max length 2048, γ=3. I set the paper's values via CLI. Minor.
4. **Mask-p cap and entropy definition** (`_edsd_apply_curriculum_mask`).
   - The drop ratio is capped at 0.4, which the paper does not mention. It is inactive for T=8, γ=3%.
   - Entropy is computed over the target distribution renormalised over the 32k draft vocabulary (`target_head[..., t2d]` → softmax), not over the target's full 128k vocabulary as Eq. 2 / Sec. 3.2 describe.
   - Minor (same method; ranking of tokens can differ slightly).
5. **EDSelect not implemented** (whole repo). The paper's layer selection via Curvature/Lidar is absent; layers are hard-coded in configs. The Qwen3 example config uses `[23, 34]` while Table 15 lists "24, 35" (consistent only if Table 15 uses EAGLE's input-of-layer numbering; undocumented). Major (a component of the method is missing; it does not change results if the Table 15 layers are used).
6. **Weights.** The abstract says "we make our draft model weights available at github.com/KerwinKai/EDSD"; no weights exist there or on HF.

**Paper-internal**
1. Table 13 "w/o Step & Mask" (T=0): the per-benchmark τ values (5.61, 6.44, 6.19, 5.72, 4.49) average to **5.69**, but the Mean column (and Table 2) report **5.49**. This makes the EDTrain τ gain look like +4.9% instead of +1.2%.
2. The abstract says +4.0% acceptance length and +4.1% speedup over SOTA. Sec. 4.2 says +4.3% τ over EAGLE-3 (and 4.6% SR over EAGLE-3).
(Observation, not counted as an inconsistency: in Table 2, "w/o Step-n" (Mask-p only, 86.4 GPUh) costs more than "w/o Step-n & Mask-p" (80.0 GPUh), which is unexplained.)
