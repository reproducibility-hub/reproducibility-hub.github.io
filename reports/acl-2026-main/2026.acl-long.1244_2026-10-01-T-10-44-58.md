# Reproduction report: PaRSP (ACL 2026, 2026.acl-long.1244)

"Harmonizing the Past, Present, and Future: A Null-Space Constrained Region-Specific Method for Continual Learning in LLMs"
Code: https://github.com/JinhuiBot/PaRSP (linked in the paper)

## Verdict

- **Verdict: PARTIALLY_REPRODUCED**
- **Result match (after my fixes): MIXED.** For Llama-3.1-8B, the code fixed to do what the paper describes
  (null-space projection active, non-selected parameters frozen) gives FP about 10 points below the paper on both the
  Standard CL (75.97 vs 86.3) and Long Sequence (77.70 vs 88.0) benchmarks. That puts it below even the paper's own
  SeqLoRA/DATA baselines, and only about 2 points above the zero-shot Instruct model. The low-forgetting claim does
  hold (Forget −1.1 / 0.65). The Figure 3 ablations reverse: removing the null-space projection or the attribution
  mask *raises* FP. For Qwen-2.5-7B (SC Order 1, lr 3e-5) the fixed method does reproduce (FP 84.35 vs 86.0), and the
  projection reduces forgetting compared with the as-released run (Forget −0.35 vs 3.15).
- **Result match as released: TREND_MATCH.** The unmodified code never applies the null-space projection, and for
  Llama it does not freeze anything, so it is essentially full fine-tuning at lr 3e-6. It gives Llama SC FP 83.63
  (paper 86.3; within 5% relative on every order) and Qwen SC Order 1 FP 81.85 (paper 86.0), and Llama LS Order 4 FP 84.7 (paper 89.6; 5.5% relative, still above every baseline the paper reports for that order). The paper's Llama
  numbers are much closer to the buggy release than to the method it describes.
- **Coverage: SUBSET.** Done: SC Orders 1–3 and LS Orders 4–6 (Llama), SC Order 1 (Qwen), Figure 3 ablations.
  Not done: TRACE (Order 7), Qwen SC Orders 2–3 and LS, Table 2 (OpenCompass), and all baselines.
- **Codebase completeness: MISSING_SCRIPTS.** The method is implemented, but there is no driver for task sequences,
  no AP/FP/Forget computation (the README says `eval_llama.sh` computes them; it only evaluates one dataset), no
  TRACE metrics, and the ablations are not wired in. The release also needs major fixes: the null-space projection
  is dead code, and Llama freezing is inverted.

## What was attempted

Target: the paper's main result, Table 1 / Table 6 (Final Performance FP, Average Performance AP, Forget) of PaRSP on
the **Standard CL (SC) benchmark, Orders 1-3** and the **Long Sequence (LS) benchmark, Orders 4-6** with the Llama-3.1-8B
backbone. Additionally Qwen-2.5-7B SC Order 1 (Table 6), and the Figure 3 ablations (w/o Null-Space,
w/o Attribution) on SC Order 1. TRACE (Order 7) was not run (the dataset is not in the release; it has to be
obtained separately and the release has no TRACE metrics (ROUGE-L / SARI / edit-sim) evaluation code).
Table 2 (OpenCompass generalization) was not run (no OpenCompass configs released). The paper's baselines
(SeqLoRA, LoRAReplay, O-LoRA, DATA) are not in the release, so "beats baseline" claims are NOT_COMPARABLE; I only
compare PaRSP's own numbers.

Pipeline (all scripts I wrote are in the attempt directory, the released per-task scripts are called unchanged):
- `run_sequence.sh` / `run_seq2.sh` (Llama), `run_seq_qwen.sh` (Qwen), `run_seq_asrel_ls.sh` (as-released LS):
  for a task order T1..TN, task k calls `scripts/run_train_llama.py` with the hyperparameters of
  `shells/train_llama.sh` (layer_ratio 0.38, neuron_ratio 0.4, rcond 1e-6, min_ratio 0.2, 256 calibration /
  localization samples, train_size 1000, test_size 500, lr 3e-6, 3 epochs, bs 2 x grad-acc 8, paged_adamw_8bit,
  bf16, gradient checkpointing, seed 18), `--model_id` = checkpoint after task k-1,
  `--cov_dataset_name` = T(k-1) (covariance of the previous task's inputs on the model after training it; `mmlu`
  for k=1) and `--history_cov_datasets` = mmlu + T1..T(k-1) (= the paper's Sigma_gen "Task 0" anchor + all previous
  tasks, App. D.3). After the last task, `scripts/run_eval_llama.py` evaluates every task (500 test samples).
  a_{j,j} is the released post-training evaluation inside `train_llama3`.
  Qwen: `shells/train_qwen.sh` values (lr 3e-5, bs 1 x 8).
- `metrics.py`: AP = mean_j a_{j,j}, FP = mean_j a_{j,N}, Forget = AP - FP (paper Sec. 5.1).
- `agg_cov.py` (LS only, fixed code): the released code stores one 37 GB covariance file per history task
  (all nn.Linear layers, fp32); 15 tasks would need >500 GB of disk. I keep a single running-sum file instead
  (the paper's "recursive aggregation", App. A.3), computed with the released `save_cov_file`. The released
  loader averages the history files; sum vs. average only rescales the matrix and the projector construction
  (rcond * max-eigenvalue threshold, min_ratio rule on sorted eigenvalues) is scale-invariant, so the projectors
  are the same as the released code would produce.
- `eval_mmlu.py`: wrapper around the released `eval_mmlu_llama3` (Table 7 MMLU subset).
- `queue*.sh`: sequential job queues.

"As released" runs use an untouched clone (`codebase_asreleased/`) driven by the same driver scripts.

### Settings that differ from / are unspecified in the paper
- **Backbone: Llama-3.1-8B-Instruct and Qwen2.5-7B-Instruct** (paper: "Llama-3.1-8B", "Qwen-2.5-7B"). The released
  code formats every prompt with the Llama-3 / Qwen chat template (`format_llama3`, `format_qwen2`). With the base
  Llama-3.1-8B the template is not understood: training loss starts at ~11 and the dbpedia accuracy after task 1 is
  21.8% (zero-shot 19.5%), vs. 94.2% zero-shot for the Instruct model (logs: `runs/base_model_o1_aborted*`,
  `diag/`). I therefore used the Instruct models.
- Sparsity: the paper says SC uses ~5% active parameters and LS ~17% (App. D.3), but gives no
  layer_ratio/neuron_ratio values; the only released config is `shells/train_llama.sh` (0.38/0.4, i.e.
  ~12 of 32 layers x 40% neurons ~ 15-17%), which I used for all benchmarks.
- One run per order with seed 18 (the paper's "three runs" for SC/LS are the three task orders).
- No early stopping (the paper mentions one; the code has none).
- Efficiency-only changes in the fixed code: covariance accumulation and the eigendecomposition run on GPU instead
  of CPU (same math), covariance files loaded with `mmap=True` (host RAM).

Table 7 (MMLU 7-subject 500-sample check): the released `eval_mmlu_llama3` scores 97.2% for the *zero-shot*
Instruct model. The metric is `ref in pred` with a single-letter reference ("a"/"b"/...), which matches almost any
output, so this table cannot be reproduced meaningfully with the released evaluator. Not compared.

Why the fixed code learns so little for Llama: the MMLU/task covariances are full-rank (the eigenvalue threshold
`rcond=1e-6` finds 0% null directions in every layer). So the `min_ratio=0.2` rule declares the 20% lowest-variance
input directions to be the "null space". Gradients projected onto those directions barely change the outputs on any
input, including the new task's. Together with lr 3e-6, bf16 weights and the ~15% sparse mask, the model stays close
to zero-shot (FP 75.97 vs. zero-shot 74.25 on SC). The paper's Llama numbers are reached only when the projection
is off and everything is trainable, which is exactly what the released code does by accident. With Qwen's 10x larger
learning rate (3e-5) the fixed method does learn and reproduces.

## Why not fully reproduced

1. Code bugs (release). (a) Null-space projection is silently disabled (`cache_dir=None` -> TypeError swallowed).
   (b) The Llama freezing condition is inverted. Once these are fixed so the code does what the paper describes,
   the Llama numbers fall about 10 FP points below the paper. Unfixed, they come close. No configuration in the
   release reproduces the paper with the method as described.
2. Missing pieces: no CL sequence / metric pipeline, no TRACE data or metrics, no baseline code, no OpenCompass
   configs, no exact sparsity settings for SC (~5%) vs. LS (~17%).
3. Model ambiguity: the paper says "Llama-3.1-8B"; the code's chat-template prompts only work with the Instruct model.
4. Compute/time: TRACE and the full Qwen sweep were skipped. As-released LS ran for Order 4 only.

Changes I made in `./codebase` (uncommitted, see `git diff`):
- `scripts/run_train_llama.py`, `scripts/run_train_qwen.py`: pass `cache_dir=build_args.cache_projectors_dir` to

  results).

- `parsp/engine/trainer_llama.py`: added `gradient_checkpointing_enable()` + `enable_input_require_grads()` (copied

- `scripts/run_train_llama.py`: env-gated ablation switches (`PARSP_NO_NULLSPACE`, `PARSP_RANDOM_MASK`, using the

- `scripts/run_*.py`: `os.environ["CUDA_VISIBLE_DEVICES"]="0"` -> `setdefault` (do not override Slurm).

Scripts I wrote (attempt directory): `run_sequence.sh`, `run_seq2.sh`, `run_seq3.sh` (same + retry on transient

## Discrepancies

code vs. paper
1. (major, affects results) Null-space projection is never applied in the released scripts (`cache_dir=None` bug):
   the "Orthogonal Update via Null Space Projection" of Sec. 4.3 is dead code.
2. (major, affects results) `layer_division_llama` freezes nothing: the "sparse functional core" (Sec. 4.2/4.4,
   "~17% of neurons") is not enforced for Llama. The released Llama path is full fine-tuning, with masks only on the
   most important layers.
3. (major, affects Table 3 / Sec. 4.5 claims) Dual SVD, incremental basis U_hist (r≈128) and implicit projection are
   not implemented. The code stores d×d covariances for every nn.Linear (37 GB per task for Llama-8B), runs a full
   `eigh` on d×d matrices, and multiplies by a dense d×d projector in the gradient hook.
4. (minor, affects results) The null space is not the null space: with full-rank covariances, `min_ratio=0.2` forces
   the 20% smallest-eigenvalue directions to be treated as null. So ΔW·X_old = 0 (Eq. 4, "mathematical guarantee") is
   not satisfied, and nothing in the paper describes this rule.
5. (minor) History statistics are stored as one file per task and averaged at load time, not "recursively
   aggregated into a single accumulator" (App. A.3). The math is equivalent; disk use is O(T·d²).
6. (minor) Attention attribution/masking is per hidden channel (4096) rather than per head (App. B). `v_proj`
   masks keep only indices < 1024 because of GQA, and `q_proj`/`k_proj` of selected layers are unmasked.
7. (minor) Sparsity: the paper says SC uses ~5% active parameters (App. D.3); the only released config
   (`shells/train_llama.sh`, used here for all runs) is layer 0.38 × neuron 0.4 (~15–17%).
8. (minor) Early stopping (App. D.3) is not implemented.
9. (minor) The model is "Llama-3.1-8B"/"Qwen-2.5-7B" in the paper; the code's chat-template prompts need the
   Instruct models (base Llama: 21.8% on dbpedia).
10. (major, affects Table 7) The MMLU evaluator uses substring matching with single-letter references (97.2% for
    the zero-shot model). The CL metric uses the same lenient substring rule, e.g. "positive" counts as correct
    for "very positive".

paper internal
1. Sparsity for SC: App. D.3 says ~5%; Sec. 5.2 says the SC/LS results come from "updating approximately 17% of
   neurons"; the Table 5 layout lists ~5% and ~17% ambiguously.
2. Table 2 lists PaRSP FP = 86.30 "after training in Order 1", but Table 6 gives Order 1 FP = 87.0 (86.3 is the
   3-order average). The other methods' Table 2 FPs match their Table 6 Order 1 values.
3. Table 1 reports "mean ± std over three independent runs" (e.g. SC FP 86.3 ± .52), while Sec. 5.2 says the three
   runs are the three task orders. The std of the three Table 6 SC orders (87.0, 86.7, 85.2) is 0.96 (sample), not
   0.52.
