# Reproduction report: RecPO (ACL 2026, 2026.acl-long.656)

"What Makes LLMs Effective Sequential Recommenders? A Study on Preference Intensity and Temporal Context" (Ouyang, Wen, Zhang, Ye, Vosoughi)

## Verdict

**PARTIALLY_REPRODUCED** — numbers match on everything we ran, but coverage is a subset of Table 1.

- **Result match (after fixes): `NUMBERS_MATCH`.** No fixes were needed, so this is also the **as-released** result.
- **Coverage: `SUBSET`.** We ran the LLaMA-3.1-8B rows of Table 1 on 2 of the 5 datasets (LastFM, MovieLens), at the paper's scale. Each run used the full train/test data, every LLM method, and the paper's hyperparameters. Not run: Qwen preference optimization, Amazon-Books / BeerAdvocate / Steam, and the traditional baselines.
- **Codebase completeness: `RUNS_AS_IS`.** No source file was edited. Two script-level problems were worked around with command-line arguments only (see below).

All 12 LLaMA-3.1-8B Table 1 cells we ran (untrained, SFT, DPO, SimPO, S-DPO, RecPO × LastFM, MovieLens) are within tolerance for both HR@1 and ValidRatio. Some match to all four reported digits: untrained LLaMA on both datasets, and SFT on LastFM.

The paper's central claim holds on both datasets. RecPO beats SFT and every preference-optimization baseline in HR@1 while keeping ValidRatio ≥ 0.99:
- **LastFM:** RecPO 0.6820 vs best baseline 0.5668 (paper: 0.6830 vs 0.5759).
- **MovieLens:** RecPO 0.3301 vs best baseline 0.3118 (paper: 0.3451 vs 0.2974).

## What the paper claims / what was targeted

The main evidence is Table 1: HR@1 and ValidRatio for traditional recommenders, plus LLaMA-3.1-8B and Qwen2.5-7B each trained with SFT / DPO / SimPO / S-DPO / RecPO, on 5 datasets. RecPO is S-DPO (Plackett-Luce, 3 negatives) plus an adaptive margin λ·ϕ(s_p,Δt_p)/ϕ(s_d,Δt_d), with ϕ = s/Δt^0.5 and λ = 2. The ablations (Table 2, "–I –T" = S-DPO), the margin variants (Table 3), the behavioural probes (Figure 4) and the λ sweep (Figure 5) are secondary.

**What we ran.** Every LLM-based Table 1 cell for the LLaMA-3.1-8B backbone on LastFM and MovieLens:
- untrained LLaMA;
- SFT, starting from LLaMA;
- DPO, SimPO, S-DPO and RecPO, each starting from the SFT adapter.

Every model was evaluated with the released `inference.py`/`evaluate_batch.py` on the full released test sets (LastFM 981, MovieLens 3,563 users).

**Why we did not run everything.** On one H200, one RecPO or S-DPO run (3 epochs × 10k samples, 4 sequences per sample through both the policy and the reference model) takes about 8.3 h. The full grid has about 50 trainings (2 backbones × 5 datasets × SFT + 4 preference methods), roughly 200–250 GPU-hours, which can't fit in the 48 h budget. We therefore covered one backbone (LLaMA, the paper's primary one) on two datasets completely, rather than spreading partial runs everywhere.

**Optional extra.** With time left at the end, we also ran Qwen2.5-7B on LastFM: untrained, and SFT. Qwen DPO, SimPO, S-DPO and RecPO were not run (about 8 h each).

## Setup / exact commands

- **Environment.** conda env at `env/` with Python 3.10 and the pinned versions from `environment.yml`: torch 2.2.2+cu118, transformers 4.43.3, trl 0.11.1, peft 0.10.0, bitsandbytes 0.42.0, accelerate 0.33.0, datasets 2.18.0, pyarrow 18.1.0. Only the packages the code needs were installed (no jupyter etc.).
- **Data.** `huggingface-cli download zyouyang/recpo-data` (processed_data only), as the README says. The released processed JSONs were used as-is; `data/prepare_sft_data.py` was not re-run.
- **Models.** `meta-llama/Llama-3.1-8B` (base) from the shared HF cache, and `Qwen/Qwen2.5-7B` for the optional extra.
- **Wrappers.** `scripts/common.sh` defines `sft`, `po` and `evalck`, which call the released entry points with the `exp.sh` / paper hyperparameters, run from `codebase/`:
  - **SFT** (`sft.py`): lr 1e-5, 5 epochs, cosine, 5% warm-up, cutoff_len 768, QLoRA r=8 (as in the code), global batch 128.
  - **RecPO** (`rec_dpo.py`): `--loss_type sigmoid --beta 1 --margin_lambda 2 --ratio True --neg_num 3 --use_score True`, 3 epochs, lr 1e-5, prompt_cutoff 704, cutoff 768, global batch 128.
  - **S-DPO** (`softmax_dpo.py`): `--beta 1 --neg_num 3`, 3 epochs.
  - **DPO** (`dpo.py`): `--loss_type sigmoid --beta 1 --neg_num 1`, 3 epochs.
  - **SimPO** (`cpo_simpo.py`): `--loss_type simpo --beta 1 --simpo_gamma 2 --cpo_alpha 0 --neg_num 1`, 3 epochs.
  - **Evaluation** (`inference.py`): `--batch_size 16 --save_output True`, greedy decoding, full test set.
- **Run order.** `scripts/train_queue*.sh` and `scripts/eval_queue.sh` sequence the runs. Some baseline trainings were launched by hand with the same arguments so they could run concurrently with the long S-DPO/RecPO runs (commands are in this report's logs, `codebase/log/*.log`).
- **Results.** `scripts/collect.py` parses the eval logs into `results.json`.

**Claim check** (Table 1, Section 5.2: "RecPO consistently achieves the best performance"):

- **LastFM.** Ours: RecPO 0.682 > S-DPO 0.567 > SimPO 0.558 ≈ DPO 0.556 > SFT 0.508. RecPO's gain over the best baseline is +11.5 points (paper: +10.7).
- **MovieLens.** Ours: RecPO 0.330 > SimPO 0.312 > DPO 0.293 > S-DPO 0.288 > SFT 0.250. RecPO's gain over the best baseline is +1.8 points (paper: +4.8 over SimPO). The gain is smaller than in the paper but has the same direction and ranking at the top. Our SimPO and DPO came out about 1.2–1.4 points *higher* than reported, and our RecPO about 1.5 points lower; each of those numbers is individually within tolerance.

  The paper also reports SimPO beating S-DPO on MovieLens (0.2974 vs 0.2902). Ours has SimPO 0.312 > S-DPO 0.288 as well. The paper has DPO (0.281) < S-DPO (0.290), while ours has DPO (0.293) > S-DPO (0.288); that difference is 0.5 points, and both numbers are within tolerance of the paper. RecPO vs S-DPO (the "–I –T" ablation of Table 2, i.e. the effect of the adaptive margin itself) is +4.2 points in ours vs +5.5 in the paper, and +11.5 vs +11.1 on LastFM.

- **"Preference optimization > SFT" and "multi-negative > DPO".** Both hold on LastFM. On MovieLens, "multi-negative S-DPO > DPO" is not reproduced (0.288 vs 0.293), but that statement is about baselines, not about the proposed method.

- **ValidRatio.** RecPO keeps ValidRatio ≥ 0.99. SimPO has the lowest ValidRatio (0.946 / 0.943), as in the paper ("SimPO achieves higher accuracy at the cost of reduced output validity").

## Codebase completeness: RUNS_AS_IS

**No source file in `./codebase` was modified** (`git status` is clean apart from git-ignored `output/`, `log/` and `recpo-data/`). Notes:

1. **`exp.sh` aborts after the RecPO stage.** `exp.sh` passes `--eval_step 0.2` to `rec_dpo.py`, but `rec_dpo.train()` has no `eval_step` parameter. python-fire runs training, saves `final_checkpoint`, and then exits with code 2 ("Could not consume arg: --eval_step"). Because `exp.sh` uses `set -euo pipefail`, the released demo stops after RecPO, so SimPO/DPO/S-DPO training and the inference step never run. The RecPO checkpoint itself is fine. Workaround: drop the argument, or run the stages separately (we used our own queue scripts, which tolerate the non-zero exit).
2. **`exp.sh` and the README cover only LastFM with Qwen.** We ran the other configurations (LLaMA, MovieLens) by changing CLI arguments: `--model_name`, `--train_dataset`, `--prompt_path ./prompt/movie_rating.txt`. No other scripts or configs were needed.
3. **Single-GPU runs** kept the global batch of 128 via `--batch_size`/`--gradient_accumulation_steps` (CLI only).
4. **Environment.** Used the `environment.yml` pins. Only a subset of packages was installed, and pyarrow was pinned to 18.1.0 (newer pyarrow is incompatible with datasets 2.18). No other workarounds were needed; torch 2.2.2+cu118 ran on the H200.
5. **Not in the release:**
   - traditional baselines (GRU4Rec/Caser/SASRec);
   - an option or data for the Table 2 "–T" ablation: the released training scores already include the time decay, and there is no switch to use rating-only scores;
   - the Table 3 "Log Diff"/"Log Ratio" margins. `--ratio False` gives λ·log(1 + s_p − s_d), which is neither formula exactly;
   - Steam's "low-rated" probe set for Figure 4(b).

   `inference.py` hard-codes `*-cans20-test.json`, so the released MovieLens/Amazon `-test-context.json` / `-test-low.json` probe sets (Figure 4) can't be evaluated without a code edit. None of these is needed for Table 1.

Scripts we wrote (outside the release, in `scripts/`): `common.sh`, `train_queue*.sh`, `eval_queue.sh`, `wait.sh`, `collect.py`, `gen_probe.py`. These are thin wrappers or monitoring tools; they contain no method logic.
