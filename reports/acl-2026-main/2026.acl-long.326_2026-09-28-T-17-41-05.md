# MixKVQ (ACL 2026, 2026.acl-long.326): reproduction report

**Paper:** MixKVQ: Query-Aware Mixed-Precision KV Cache Quantization for Long-Context Reasoning (Zhang et al., ACL 2026)
**Code:** https://github.com/ZeroNLP/MixKVQ (linked from the paper), commit `f9c08bc`

## Verdict

- **Verdict:** `PARTIALLY_REPRODUCED`
- **Result match (overall):** `TREND_MATCH`.
  - 7 of the 10 MixKVQ numbers in Table 3 (4 benchmarks + average, for each of 2 models) are within tolerance, including both 4-benchmark averages: 14B 63.75 vs 63.10, and 32B 67.20 vs 66.04.
  - The other three differ by 3-4 points: 14B GPQA −3.0, 14B LiveCodeBench +3.8, 32B LiveCodeBench +3.9.
  - The paper's conclusion that MixKVQ stays close to BF16 on long-CoT reasoning holds in our runs.
- **Coverage:** `SUBSET`. We ran the paper's main Table 3 at full scale (all problems, same models, same sampling settings) for the two Qwen models, R1-Distill-Qwen-14B and -32B.
  - Not run: the R1-Distill-**Llama-8B** rows. The released engine only implements Qwen2/Qwen3 architectures.
  - Not run: the four quantization baselines (KIVI, KVQuant, RotateKV, KVTuner). The release does not include them.
  - Not run: Table 4 (LongBench) and the appendix tables.
- **Not comparable:** the paper's claim that MixKVQ *outperforms existing low-bit methods* (KIVI-KV2/KV4, KVQuant, RotateKV, KVTuner) can't be checked. None of these baselines is in the release, and we did not reconstruct them.

## What the paper claims (reproduction target)

The target is Table 3, pass@1 with T=0.6, top-p=0.95, G=32, R=128, on AIME 2024+2025 (60 problems), MATH-500, GPQA-Diamond (198) and LiveCodeBench (2025-01-01..2025-04-06; 182 problems).

The claim is that MixKVQ, at an effective ~2.3-2.7 bits, stays within ~1.5-2 points of BF16 on average and is better than 2-bit and 4-bit baselines. For example, the paper reports R1-Qwen-14B MixKVQ at 63.10 vs BF16 at 64.73, and R1-Qwen-32B MixKVQ at 66.04 vs BF16 at 67.84.

## What was run

All generation used the attempt's conda env (Python 3.11, torch 2.7.1+cu126, transformers 4.56.2, flash-attn 2.8.3, vLLM 0.10.1.1 for BF16 only, plus conda `cuda-toolkit` 12.6 and gcc 13 so that the release's CUDA decode kernel compiles). Everything ran on 1×H200.

- **MixKVQ runs** used the **released engine unmodified in its method logic**: `mixkvq.LLM`, the fused CUDA decode kernel, and Triton quantizers.
  - Settings: k_bits=2, v_bits=2, group_size=32, page (residual) R=128, first 32 tokens kept fp16, and the release's default tier ratios fp16/int4/int2 = 5%/30%/65% of key channels.
  - For head_dim=128 that is 7/38/83 channels, i.e. K = 3.36 bits, V = 2 bits, average ≈ 2.68 bits ("C2.7").
  - Driver: `gen.py --engine mixkvq` (our script; uses `LLM.add_request/step`).
- **BF16 baseline:** vLLM 0.10.1.1, bf16, with the same prompts and sampling. BF16 is not part of the release, but it is the standard unquantized model. We ran 2 sampling seeds for 14B and 1 for 32B.
- **Common settings:** chat template of each model; max 32,768 new tokens; T=0.6, top-p=0.95; one sample per problem (pass@1).
- **Prompts:**
  - Math: `problem + "\nPlease reason step by step, and put your final answer within \boxed{}."` (the same suffix as the release's `tests/aime_eval.py`).
  - GPQA: the question with the 4 options shuffled (fixed per-question seed), asking for the letter in `\boxed{}`.
  - LCB: the LiveCodeBench DeepSeek-R1 prompt body.
- **Scoring (`score.py`, ours):**
  - Math: the release's vendored sglang `answer_extraction` + `math_equal`.
  - GPQA: the last `\boxed{}` letter.
  - LCB: the official `lcb_runner` `codegen_metrics` (pass@1, timeout 6 s), using the cached `livecodebench/code_generation_lite` test5+test6 problems filtered to 2025-01-01..2025-04-06, which gives exactly 182 problems, matching the paper's granularity (45.05 = 82/182).
- **Commands (from the attempt directory, after `source envsetup.sh`):**
  ```
  MIXKVQ_FORCE_SLOTS=<n> python gen.py --engine mixkvq --model deepseek-ai/DeepSeek-R1-Distill-Qwen-14B --outdir runs/mixkvq_14b --gpu_util 0.95
  python gen.py --engine vllm --model deepseek-ai/DeepSeek-R1-Distill-Qwen-14B --outdir runs/bf16_14b --gpu_util 0.9 [--seed 1]
  (same for -32B)
  python score.py runs/<run>      # -> runs/<run>/scores.json
  python make_report.py           # tables below
  ```

### Settings that differ from the paper

1. **Bit budget / thresholds.**
   - The paper allocates tiers by thresholds (τ_BF16, τ_UINT4) found with Optuna: (1.52, 1.60) → 2.3 bits for Qwen-14B and (1.85, 1.58) → 2.3 bits for Qwen-32B (Appendix D).
   - The release has **no threshold mechanism and no search script**. It uses fixed per-head channel ratios (5%/30%/65%), about 2.7 bits.
   - So our MixKVQ runs use somewhat *more* bits (~2.68) than the paper's C2.3 for these two models. That is the paper's C2.7 setting, which it reports only for Llama-8B.
   - We did not guess C2.3 ratios.
2. **Channel re-selection.**
   - The paper says the importance I_d and the tiers are recomputed every R tokens during decoding, with a running query accumulator (§4.2, App. E).
   - The release computes channel tiers **once at prefill** from the prompt's queries and keeps them fixed for the whole generation (see `manager.py::ingest_prefill` and `_init_idx_from_page`).
   - We ran the release as-is.
3. **Hardware and batching.** The paper used an A800; we used an H200 with batched generation (36–128 concurrent sequences). Sampling is stochastic, and the paper reports one sample per problem, so ±5–6 points on AIME (SE ≈ 6.3 points for n=60) and ±3.5 points on GPQA are expected run-to-run noise.
4. **Max new tokens** is not stated for Table 3. We used 32,768, which is the value the paper states for its Table 9.
5. **GPQA prompt and answer shuffling** are not specified in the paper. Our BF16 GPQA for 14B comes out ~5.8 points below the paper's BF16, and both BF16 seeds agree on this.

### Restart/selection caveat and clean reruns

- **The problem.** The release's engine keeps a concatenated copy of every sequence's quantized history in memory. Memory use per in-flight token was about 115 KB for 14B and 140 KB for 32B, so large batches ran out of GPU memory.
- **What happened.** The first MixKVQ-14B run (128 slots) hit OOM after 6 h. We restarted it with fewer slots, resuming from the completed outputs. Sequences that were still in flight were discarded and regenerated.
- **Why that matters.** Sequences still in flight after hours are disproportionately long, often wrong or truncated, generations. Redrawing them can bias accuracy upward. The affected items were 3 AIME, 9 MATH, ~63 GPQA and ~52 LCB problems for MixKVQ-14B.
- **Smaller cases:**
  - A manual restart after 27 min redrew 29 AIME problems for MixKVQ-32B.
  - A restart after 20 min redrew 7 AIME problems for BF16-14B seed 0.
  - BF16-32B, BF16-14B seed 1 and the clean MixKVQ-14B and MixKVQ-32B reruns had no restarts.
- **The fix.** We reran from scratch, without any restart, **MixKVQ-14B on AIME, GPQA and LCB** (40 slots, `runs/mixkvq_14b_clean`) and **MixKVQ-32B on AIME** (40 slots, `runs/mixkvq_32b_clean`). These clean reruns are the primary MixKVQ numbers wherever available.
  - The original restart-affected runs gave 14B AIME 61.67, GPQA 56.57, LCB 45.05, and 32B AIME 63.33. The clean reruns gave 60.00, 53.54, 47.25 and 65.00. So the restart bias was within noise, but the clean numbers are the ones reported.
  - MATH-500 (9/500 affected for 14B, 0 for 32B) and 32B GPQA/LCB (no restart) use the original runs.

**Reading the results.**
- MixKVQ (released engine, ~2.7 bits) matches the paper's MixKVQ average for both models.
  - It is within tolerance on AIME and MATH-500 for both models and on 32B GPQA.
  - 14B GPQA is 3.0 points low. Our BF16 GPQA is about 5.8 points below the paper's too, which points to a GPQA prompt or format difference rather than quantization.
  - LiveCodeBench is 3.8–3.9 points *higher* than the paper for both models.
- MixKVQ stays at or near BF16 in our own runs. Our BF16 baseline comes out *lower* than the paper's on AIME (both models) and on 14B GPQA, so in our runs MixKVQ ≥ BF16 on average.
- That gap is within single-sample noise, and our MixKVQ runs use a larger bit budget than the paper's C2.3. The paper's direction (MixKVQ ≈ BF16, small or no degradation) therefore holds, but our data can't resolve a gap of 1–2 points.
- The per-row BF16 mismatches (NO_MATCH) are baseline sanity checks. They are consistent with sampling variance, since the two BF16-14B seeds themselves differ by 6.7 points on AIME and 4.4 on LCB.

## Why not fully reproduced

- **Llama-8B rows:** the release implements only `Qwen2ForCausalLM`/`Qwen3ForCausalLM` (`mixkvq/models/`), so R1-Distill-Llama-8B can't be run without writing a new model port. We did not attempt that.
- **Baselines:** KIVI, KVQuant, RotateKV and KVTuner are not in the release, so the "beats existing low-bit methods" claims are `NOT_COMPARABLE`.
- **Bit budget:** the threshold search and the C2.3 configuration are missing from the release, so we could only run the release's default ~C2.7 ratios.
- **Scope:** LongBench (Table 4), the efficiency figure (Fig. 5) and the ablations (Tables 6–9) were not run, for time reasons. Each full Table 3 MixKVQ pass took 6–15 GPU-hours on the release's engine.

## Codebase completeness: `MISSING_SCRIPTS`

The method itself (tiered channel selection, quantizers, fused decode kernel, and a small inference engine) is implemented and ran after environment fixes. The Table 3 pipeline is mostly missing:
- The only evaluation script is `tests/aime_eval.py`, for AIME 2024 on R1-Qwen-7B. Its default sampling (T=0.7, top-p=0.8, top-k=20, presence penalty 1.5) is not the paper's.
- There is no MATH-500, GPQA or LiveCodeBench pipeline.
- There is no BF16 or baseline runner, no threshold (Optuna) search, and no C2.3 config.
- There is no Llama support.

**Changes to the released code** (left uncommitted in `./codebase`, see `git diff`):
1. `mixkvq/engine/model_runner.py`, line 46: `torch.set_default_device("cpu")` → `torch.set_default_device(None)`.
   - Why: passing `"cpu"` leaves a `DeviceContext` TorchFunctionMode active, which intercepts every torch call in the Python-heavy decode loop. In our profile that was about 40% of host time.
   - `None` is semantically identical (CPU default) and is a performance-only change.
   - The first ~6 h of the MixKVQ-14B run used the unmodified line; all later runs used the change.

**Environment-level fixes** (no code change):
- Installed `cuda-toolkit` 12.6 and gcc/g++ 13 from conda, and set `CUDA_HOME`/`CC`/`CXX`/`NVCC_PREPEND_FLAGS` in `envsetup.sh`. The system had no `nvcc`, and the system gcc (>13) is rejected by nvcc 12.6.
  - Without this, the engine silently falls back to a dense-reconstruct path that is about 10× slower.
- Pinned `transformers==4.56.2` and `huggingface-hub<1.0`, which vLLM 0.10.1 needs.
- Set `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` after an OOM with 33 GB of fragmented memory.
- Set `MIXKVQ_FORCE_SLOTS` (an env knob provided by the release) because the automatic slot sizing assumes worst-case 34k-token histories.

**Scripts we wrote** (outside `./codebase`):
- `data/prep.py`: builds the datasets.
  - AIME 2024 from `HuggingFaceH4/aime_2024`, AIME 2025 from `opencompass/AIME2025`, `HuggingFaceH4/MATH-500`, and `Idavidrein/gpqa` gpqa_diamond.
  - LCB is read from the cached `livecodebench/code_generation_lite`.
- `gen.py`: generation driver for MixKVQ and vLLM. It resumes from completed outputs.
- `supervise.sh`, `queue_32b.sh`, `queue_clean.sh`: restart and queue helpers.
- `score.py`: scoring.
- `make_report.py`, `compare.py`: tables.
- `speedtest.py`, `prof.py`: throughput and profiling checks.
- The official LiveCodeBench repo was cloned into `./lcb` and is used only for its evaluator.

## Other observations

- **Engine throughput** with the CUDA kernel on the H200 is about 350–420 tok/s at short contexts, falling to about 100–150 tok/s with 8–16k-token histories. Step time is dominated by per-slot Python overhead plus the scalar decode kernel.
  - For comparison, vLLM BF16 ran the same 940 prompts in 50 min (14B) and 2 h (32B). MixKVQ took 6–15 h.
  - The paper's efficiency claims (Fig. 5) were not evaluated.
- **Memory:** the engine's actual GPU memory per cached token (~115 KB for 14B, versus 196 KB for bf16 KV) is well above the nominal 2.7-bit footprint. This is mainly because it also caches a concatenated copy of every sequence's history per layer.
