## Summary

The released scripts implement MUR as described (step-level uncertainty = mean token NLL of a step; momentum
uncertainty `M_t = αM_{t-1} + (1−α)m_t`; scale step *t* when `exp(m_t) > exp(M_{t-1})/γ`), for three TTS back-ends.
We ran them (≈2 days on one H200) and compared with Table 1.

* **Token savings — reproduced as a trend.** MUR always uses fewer backbone tokens than Per-Step Scale in
  Guided search (−17 % … −63 % per cell, −37 % overall) and φ-Decoding (−27 % … −54 %, −37 % overall); for
  LLM-as-a-critic the change is small (−16 % … +16 %, −6 % overall), as in the paper (where it is +26.3 % / −3.0 % / +0.3 % for 1.7B / 4B / 8B).
  The magnitude is smaller than the paper's (e.g. Guided search on Qwen3-1.7B: −33 % vs −70 %), mainly because our
  Per-Step-Scale runs use far fewer tokens than the paper reports (AIME: ~10–12k vs 17–20k tokens/query).
  The headline "reduces computation by over 45 % on average" is not reached (and is not what Table 1's own Δ column
  averages to either, see paper-internal discrepancies).
* **Accuracy gains — not consistently reproduced.** The paper reports MUR ≥ Per-Step Scale in every averaged
  setting (+0.33 … +3.46). Over the 24 (model, dataset, TTS) cells we ran (8 per TTS setting), MUR ≥ Per-Step Scale in 5/8 cells for
  Guided search (mean +0.9 pts), 6/8 for LLM-as-a-critic (mean +2.2 pts), but only **3/8 for φ-Decoding (mean +0.4 pts)**.
  On Qwen3-1.7B (the only model with all four benchmarks) the averaged deltas are +0.67 (paper +1.65), +3.71 (+2.15),
  −0.60 (+1.66). Most single-cell differences are within sampling noise (SE ≈ 2 pts on MATH-500, ≈3–3.7 pts on
  AIME with 120 samples, ≈3 pts on GPQA).
* **Absolute numbers.** Vanilla CoT and most MUR accuracies land within ±1–2.5 pts of Table 1 on MATH-500;
  AIME/GPQA cells scatter more (up to ~8–9 pts, partly sampling noise: SE ≈ 3–3.7 pts). Several **Per-Step-Scale baselines
  are clearly stronger than reported** (Qwen3-4B MATH-500: Guided search 84.2 vs 79.8, φ-Decoding 82.8 vs 76.8;
  Qwen3-1.7B Guided search MATH-500 75.0 vs 70.8), and Qwen3-8B Vanilla CoT on GPQA-diamond reaches 48.5 vs 39.9 reported,
  which removes MUR's advantage in those cells.

## What was attempted

**Target:** Table 1 (main results): Vanilla CoT and three test-time-scaling (TTS) settings (Guided search, LLM as a
critic, φ-Decoding), each with *Per-Step Scale* (TTS at every step) vs *MUR* (TTS only on steps flagged by momentum
uncertainty, α = γ = 0.9). Benchmarks: MATH-500, AIME24, AIME25, GPQA-diamond. Backbones: Qwen3-1.7B / 4B / 8B.
External model (critic / candidate selector): GenPRM-1.5B (`GenPRM/GenPRM-1.5B`, the code's default `genprm1.5B`).
Math answers are judged by TIGER-Lab `general-verifier` (the paper's "General Reasoner" verifier), GPQA answers
by the released `eval/eval_gpqa_cot.py` letter-matching code.

**Code:** https://github.com/yayayacc/MUR (commit 5cc3467), cloned to `./codebase`. The repo contains the six scripts
`{guided_search,llm_as_a_critic,phi_decoding}-{mur,per_step_scale}.py`, the four datasets (`data/*.json`) and two
evaluators. Environment: Python 3.11.9, vllm 0.8.5, torch 2.6.0, transformers 4.51.3, scikit-learn 1.6.0,
numpy 1.26.4, modelscope (pins from `requirements.txt`).

**Commands** (one process per data shard; shards were run 4–9 at a time on one H200 through `scripts/run_job.sh`):

```
# MUR (gamma = scaling_rate = 0.9, alpha = momentum_rate = 0.9), e.g.
python guided_search-mur.py   --data_path shards/math500_s0.json --policy Qwen/Qwen3-1.7B --critic GenPRM/GenPRM-1.5B \
       --scaling_rate 0.9 --momentum_rate 0.9 --max_steps 20 --aim_gpu 0 --file_name <tag> --policy_gpu_mem 0.055 --critic_gpu_mem 0.045
python llm_as_a_critic-mur.py ...   (same arguments)
python phi_decoding-mur.py    ...   (no critic)
# Per-Step Scale: the *-per_step_scale.py scripts with the same arguments
# Vanilla CoT: phi_decoding-mur.py with --scaling_rate 0 (the trigger exp(m) < gamma*exp(M) can never fire,
#              so this is plain step-by-step generation with the same prompt / step format)
# environment for every job: VLLM_USE_V1=0 MUR_SWAP_SPACE=1 PYTHONPATH=scripts/pyhook
# evaluation: scripts/aggregate.py --eval  (concatenates shards, runs the verifier / GPQA evaluator, counts tokens)
```

| Qwen3-8B | all 4 benchmarks | **MATH-500 and GPQA-diamond only** | compute |
| Qwen3-4B | all 4 benchmarks | **MATH-500 and GPQA-diamond only** | compute |
| Avg-uncertainty, SMART baselines; Thinking-mode (Table 2); random scaling (Fig. 3); γ sweeps | reported | **not run** | no code released for any of them |
| Sampling | T=0.6, top-p 0.8, top-k 20, presence penalty 1.5 | T=0.6 only (top-p 1, top-k off, no penalty) | the released scripts only set temperature; we ran the code as released |
| System prompts (AIME / GPQA) | used (App. B) | not used | the scripts compute `system_prompt` but never put it into the chat |
| vLLM engine | vLLM (version per requirements 0.8.5 → V1 engine by default) | vLLM 0.8.5 **V0 engine** (`VLLM_USE_V1=0`), CPU swap space 1 GiB | V1's memory profiling counts other processes' GPU memory, which makes several concurrent shards on one GPU impossible; generation settings are unchanged |
| Math verifier | General-Verifier, one call per item | same model, prompt, sampling (T=0.7) and decision rule, batched (`scripts/math_verifier_batched.py`) | the per-item loop needed ~8 s/item on the shared GPU; check on one file: identical accuracy (20/120 vs 20/120), 116/120 identical per-item verdicts (differences come from the verifier's own T=0.7 sampling) |
| #Tokens | "backbone model's average token usage" | sum of the counters the scripts write (`*policy*output*tokens`) / #queries | φ-Decoding's foresight roll-outs are **not** counted by the released code (see discrepancies), so φ-Decoding token numbers are lower bounds of the true backbone cost |

## Why not fully reproduced

* **Compute.** The released scripts handle one question at a time with several sequential `generate` calls per step
  (no batching across questions). On one H200 (shared by 4–9 concurrent shard processes) the full Qwen3-1.7B matrix
  with 4 AIME samples took ~20 h; the paper's protocol (16 AIME samples × 3 models × 7 configurations) would need
  several GPU-weeks. We therefore reduced AIME to 4 samples/problem, ran AIME only for Qwen3-1.7B, and ran the larger
  models on MATH-500/GPQA only.
* **Missing code.** Avg-uncertainty and SMART baselines, the Thinking-mode switch (Table 2), the random-scaling
  ablation (Fig. 3) and the γ/α sweeps are not in the repository; the corresponding claims ("MUR outperforms average
  uncertainty and SMART", Table 2) are NOT_COMPARABLE / not tested.
* **Result differences.** MUR's accuracy advantage over Per-Step Scale is not stable: it holds for LLM-as-a-critic,
  mostly for Guided search, and not for φ-Decoding. Several Per-Step-Scale / CoT baselines come out stronger than
  reported. Token savings are present but smaller than reported. Possible contributors: the released code differs
  from the paper in sampling parameters, system prompts, bias correction and (for φ-Decoding) the foresight prompt
  (see discrepancies); AIME is averaged over 4 instead of 16 samples; the math verifier samples at T=0.7.

   No effect on outputs.

Scripts written outside the release (in `./scripts`):

* `make_shards.py` — splits a dataset into shards (file names keep `math`/`aime`/`gpqa`, which the released scripts use
  to pick prompts); for AIME each problem is replicated 4× to emulate the multi-sample protocol (no driver for this in
  the release).
* `run_job.sh` — runs one released script on one shard with the paper's α=γ=0.9 (`--scaling_rate 0.9`;
  `guided_search-mur.py` defaults to 0.8), serialises vLLM start-up with a file lock and retries failed start-ups.
* `pyhook/sitecustomize.py` — runtime hook lowering vLLM's CPU swap space default (4 GiB → 1 GiB per engine) to fit
  host RAM; `VLLM_USE_V1=0` selects vLLM's V0 engine, whose memory profiling tolerates several processes per GPU.
* `eval_gpqa.py` — executes the released `eval/eval_gpqa_cot.py` code (which has a placeholder `"file_path"`) on a
  given prediction file.
* `math_verifier_batched.py` — batched copy of `eval/math_verifier.py` (same prompt, answer extraction, sampling and
  decision); validated against the original on one file (same accuracy, 116/120 identical verdicts).
* `aggregate.py`, `compare.py` — merge shards, compute accuracy / tokens / scaled steps, build the tables.
* Vanilla CoT = `phi_decoding-mur.py --scaling_rate 0` (trigger can never fire).
