**Summary of claims**
* **FastKron numbers.** Released code plus fixes reproduces the FastKron numbers within tolerance in every setting we could match exactly:
  * Qwen3-0.6B 4/2-bit and Qwen3-1.7B 4-bit (Table 5).
  * LLaMA-2-7B 2-bit with 35 gradient steps (Table 7): Wiki 6.67 vs 6.59, C4 8.56 vs 8.69, AVG 0.611 vs 0.608.
  * Qwen3-1.7B 2-bit comes out somewhat *better* than reported: AVG 0.527 vs 0.509, Wiki 27.4 vs 29.0.
* **Second-order information matters at 2 bits.** Reproduced strongly. NoHess 2-bit collapses:
  * LLaMA-2: PPL 39.4, AVG 0.470.
  * Qwen3-0.6B / 1.7B: PPL in the tens of thousands.
  * FastKron 2-bit stays near baseline (LLaMA-2 AVG 0.611 vs 16-bit 0.664).
  * Every NoHess and 16-bit number matches the paper almost exactly.
* **Off-diagonal elements matter.** Our extra OnlyDiag runs (diagonal of the FastKron factors) fall between FastKron and NoHess, as the paper says for LLaMA-3-8B. The paper has no OnlyDiag numbers for these models, so this is NOT_COMPARABLE and only a trend check.
* **4-bit LLaMA-2.** Our NoHess 4-bit baseline is a bit stronger than reported: AVG 0.664 vs 0.656, BoolQ +2.5 pt. See the FastKron-4-bit comparison below.
* **Claims vs YAQA/QTIP ("beats YAQA at 2-bit, 10× faster, 96% fewer tokens").** NOT_COMPARABLE. YAQA (Sketch A, 16M tokens, 50–92 GPU-h, 4-GPU torchrun, LLaMA-only Hessian code) and QTIP Hessians were not run. Also, the "0.7M tokens" budget does not match what the code consumes. A FastKron "step" is 128 FineWeb documents padded to 2048/4096 tokens. We measured ~5.1M (Qwen3) / ~6.4M (LLaMA-2) real tokens for 70 steps, 7–9× the 0.7M reported. So the token-efficiency claims (Tables 1–5 "Tokens" column, "↓94–96%") are overstated by that factor.


## What was run

Hardware: 1× H200 (141 GB), 111 GB host RAM, ~250 GB of usable disk quota (shared with other jobs). Env: `env/` (python 3.11, torch 2.5.1+cu124, transformers 4.57.1, lm_eval 0.4.9, datasets 3.6.0, cupy-cuda12x 14.2, flash-attn 2.7.4, fast-hadamard-transform and `qtip-kernels` compiled with conda gcc 12 / nvcc 12.4).

Pipeline per model (the release's own scripts, run from `codebase/` with `PYTHONPATH=codebase`; our wrappers are in `scripts/`):
1. **Calibration data.** `scripts/build_fineweb.py`: first 66,000 docs of `HuggingFaceFW/fineweb` `sample-10BT` saved to `../fineweb/sample/66K`. This is the path the collector hard-codes. It is not shipped, and the paper only says "FineWeb".
2. **Gradient collection.** `kronfwsvd/collect_fisher_weights.py --model_name M --size 1 --lr 1e-4 --max_length L [--save_pattern P]`. These are the README args plus the required `--max_length`, which is undocumented. We used L = 2048 for Qwen and 4096 for LLaMA, following the paper's "sequence length 2048 (Qwen) / 4096 (LLaMA)". One step is 128 sequences (gradient accumulation 128), and the collector was stopped after N steps (`scripts/collect_pass.sh`). Steps used:
   - **Qwen3-0.6B:** N = 70 (the paper's "0.7M tokens" = 70 steps per Table 7), one pass.
   - **Qwen3-1.7B:** N = 70, three passes (layers 0–9, 10–18, 19–27).
   - **LLaMA-2-7B:** N = 35 (Table 7's "35 steps / 330K tokens" row), six passes of ≤6 decoder layers each.
   - Why passes: all layers are trained in every pass exactly as in the release, but only the pass's layers' gradients are written. Gradients are 0.9 GB/step for Qwen3-0.6B, 2.7 GB/step for 1.7B and 13 GB/step for LLaMA-2-7B, which did not fit our disk quota in one pass.
3. **Kronecker factors.** `kronfwsvd/get_kron_factors_llama.py --model_name <pass dir> --n_grads N` (cupy `svds` on the implicit rearranged Fisher, top_k = 2). This is the algorithm as released. We only changed the driver: per-layer lazy loading instead of loading everything into RAM.
4. **Quantize + eval.** `quantize_llama/quantize_finetune_llama.py` with exactly the `run_quantizer*.sh` arguments: `--codebook bitshift --scale_override 0.9 --ft_epochs 0 --decode_mode quantlut_sym --tlut_bits 9 --L 16 --K {2,4} --V 2 --td_x 16 --td_y 16`. Then `hfize_llama.py` / `hfize_qwen1.py`, `eval/eval_ppl.py --manifest` (Wiki2/C4 at the default seqlen 4096), and `eval/eval_zeroshot.py --tasks arc_challenge,arc_easy,hellaswag,boolq,piqa --num_fewshot 0 --batch_size 4 --manifest_model`.
5. **Baselines.**
   - **NoHess:** identity factors through the same pipeline (the paper: "TCQ but omits curvature"; the release has it only as commented-out code).
   - **OnlyDiag** (extra, trend check only): `diag(XF)`, `diag(YF)` of our FastKron factors.
   - **16-bit:** the original model through the same eval scripts.

**Settings that differ from the paper**
* **LLaMA-2-7B gradient steps.** FastKron uses **35 steps** (Table 7 setting) instead of the Table 1 setting (70 steps / 0.7M for 4-bit, 150 steps / 1.4M for 2-bit). Reason: 13 GB of gradients per step on a ~250 GB quota meant 6 collection passes at ~2–5 min/step on one shared GPU, so 70/150 steps would not fit the 48 h budget. The 2-bit result is compared with Table 7's 35-step row. The 4-bit result has no 35-step counterpart in the paper; it is compared with the Table 1 row (0.7M) and marked NOT_COMPARABLE.
* **LLaMA-2 checkpoint.** `meta-llama/Llama-2-7b-hf` is gated for our token, so we used `unsloth/llama-2-7b`, the mirror named in the release's code comments. Our 16-bit numbers match Table 1 exactly.
* **Multi-pass collection.** For Qwen3-1.7B and LLaMA-2-7B the gradients came from several identical training runs (same seed and data order), each saving a subset of layers. GPU non-determinism may make the runs diverge slightly from a single run.
* **`--max_length`** is a required, undocumented argument. We used the paper's 2048 (Qwen) / 4096 (LLaMA).
* **Devset size.** For the LLaMA FastKron/OnlyDiag/NoHess-4-bit and Qwen3-1.7B NoHess-4-bit quantizations we passed `--devset_size 16 --batch_size 16 --ft_valid_size 8` to fit host RAM. With `--ft_epochs 0` the devset is only propagated, never used, so this has no effect on the quantized weights.
* **Not run:**
  - YAQA. It needs a 16M-token Sketch-A Hessian (paper: 50–92 GPU-h; `hessian_llama/` is LLaMA-only and needs multi-GPU torchrun).
  - QTIP. Its Hessians come from the separate QTIP repo; no config in this release.
  - LLaMA-3-8B, Qwen3-4B/8B, and GSM8K/IFEval (Table 4).
  - Inference-speed numbers (Table 6).
  - Clean GPU-hour timings: our runs shared the GPU between 3–6 processes.

## Discrepancies

Paper: FastKron uses 0.7M tokens (4-bit; ~70 steps per Table 7) and 1.4M tokens (2-bit LLaMA-2; 150 steps), i.e. ~10K tokens per step, '96% fewer tokens than YAQA (16M)'. Affects reported results: True.
* **code_vs_paper** — severity **minor** — *kronfwsvd/get_kron_factors_llama.py (__main__, run_parallel_kron)*. Paper: factors from 70 gradient steps (0.7M tokens) for 4-bit and 150 steps (1.4M) for 2-bit LLaMA-2 (Tables 1, 7). Code / other part: hard-codes grads[:100] (and output dir name fisher_factors_output_150), top_k=2 svds; number of steps is not configurable. Affects reported results: True.
* **code_vs_paper** — severity **minor** — *Sec. 4 'sequence length 4096 (LLaMA) / 2048 (Qwen)' vs eval/eval_ppl.py*. Paper: Qwen models use sequence length 2048. Code / other part: eval_ppl.py default --seqlen 4096 is used for all models; our Qwen3 16-bit PPL matches Table 5 only at seqlen 4096 (19.15/23.84 vs paper 19.16/23.83; at 2048: 20.96/25.43), so the paper's Qwen PPLs were evaluated at 4096. ## Wall-clock

* Started 2026-10-06 16:47 CDT. All runs finished on 2026-10-07 (see `finished_at` in status.json): about 30 h, nearly all of it GPU-bound.
* Rough cost, all on one shared H200:
  - **LLaMA-2-7B FastKron:** 6 gradient-collection passes × 35 steps took 2–3.5 h each, at 3–5 min/step with 3–6 GPU-sharing processes. The trainer runs at ~2.5 min/step uncontended.
  - **LLaMA-2-7B quantization:** each run took 3.5–10 h (≈6.5 min/layer uncontended, up to 25 min/layer contended), plus ~45 min for evaluation.
  - **Qwen3-0.6B / 1.7B:** about 40 s / 60–120 s per gradient step and 0.5–2 h per quantization.
* With enough disk to collect all layers in one pass, the paper's "5–6 GPU-h" for LLaMA-2 FastKron looks plausible for the factor + quantization part. The gradient collection is the dominant cost.

## Not reproduced / why

* **YAQA, QTIP baselines; LLaMA-3-8B, Qwen3-4B/8B; GSM8K/IFEval; Table 6 inference speed.** Compute budget: 1 GPU, 48 h, ~250 GB disk. YAQA alone is 50–92 GPU-h per model in the paper.
