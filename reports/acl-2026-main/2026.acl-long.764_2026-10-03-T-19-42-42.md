### Summary of findings
- **GSM8K (Table 1)** reproduces almost exactly. Deco-G: Llama 84.7 (paper 85.2), Qwen2.5 88.4 (88.6), Qwen3 92.0 (91.7). Format compliance is 100% for all three. Every baseline we could run (Prompt-Only NL/JSON, Outlines JSON) is also within 1 point or 5% of the paper. Deco-G is the best method for every model, so the paper's claim holds.
- **SummEval (Table 3)**: 122 of 132 per-cell numbers are within tolerance (5% relative). Deco-G has the best average correlation for Llama-3.1-8B (avg ρ 0.428 vs best baseline 0.410) and Qwen2.5-7B (0.405 vs 0.400). **For Qwen3-8B it does not**: Deco-G avg ρ/τ is 0.492/0.432, below Prompt-Only (NL) at 0.500/0.441. - **Table 4 (no HMM pruning)**: Llama 84.5 (85.4), Qwen2.5 89.8 (89.8), Qwen3 89.4 (90.8). Pruning costs little or nothing in accuracy (+0.2 / −1.4 / +2.6 for pruned minus unpruned), consistent with the paper's claim.

## What was run
Environment: conda env at `./env` with Python 3.10, `torch==2.2.2+cu121` (pip), and `requirements.txt` exactly as pinned (transformers 4.56.1, outlines 0.1.3, …), plus `pip install -e codebase --no-deps`. Models: Llama-3.1-8B-Instruct, Qwen2.5-7B-Instruct, Qwen3-8B (bf16, from the shared HF cache). Official HMMs came from `hk/decog-hmms`, which the code loads by default. Hardware: 1× H200. Jobs ran **sequentially**: running 3 at once on the single GPU was far slower than running them one after another.

Commands (run from `codebase/`; job list in `jobs.txt`/`jobs2.txt`, run by `queue.sh` → `run_job.sh`):

The Table 3 "Format" and "Avg" columns are our averages over the 4 dimensions. Deviations from the paper: none known for the settings we ran. Each job was started through `step_wrap.py`, which only monkey-patches the Deco-G logits processor to print a progress line every 500 steps.

### Not run / why
- **Table 2 (EAE on ACE05)**: the release has no EAE code (data processing, templates, flexible-trie DFA construction for role templates, F1 evaluator), and ACE05 is LDC-licensed. Not reproducible from the release.
- **Ctrl-G baseline** (Tables 1–3): no code or HMM for it in the release.
- **Outlines (NL) baseline** (Tables 1 and 3): `structured_regex` uses `[...]{50,1000}The final answer is ...`. Building the outlines-0.1.3 FSM index for this regex over the 128k Llama vocabulary reached **91 GB RSS after 26 min** and was still growing; the job's host RAM limit is about 111 GB. We killed it to avoid an OOM kill of the whole job and skipped all Outlines-NL runs (2 GSM8K runs were skipped and 1 killed; 12 SummEval runs skipped). This is a compute/RAM limitation of this machine, not a code bug. Outlines (JSON) ran fine.
- **Table 5 (latency)** was not compared: the paper used an A100, we used an H200. For reference, sequential Deco-G (k=200) on GSM8K took about 21 min for 1319 examples at batch 32 for Llama.

## Discrepancies
1. **code_vs_paper (major, affects reported numbers): SummEval correlation protocol.** Section 4.3 says "Following Liu et al. (2023), we adopt the summary-level Spearman and Kendall-Tau correlation". `eval/eval_summeval.py` instead computes one pooled correlation over all 1600 (article, summary) pairs. The paper's Table 3 numbers match the pooled metric: Llama Deco-G consistency 0.439/0.404 is reproduced exactly. Per-document (summary-level) correlations differ by about 0.01–0.05. So the reported metric is not the one the paper describes. Relative rankings are similar under both, and the Qwen3 reversal appears under both.
2. **code_vs_paper (minor): format keyphrases.** The paper describes the GSM8K Deco-G constraint as the key phrase "The final answer is" and SummEval as "The rating is …". In `deco_g/constraints.py`, Qwen2.5 uses "The final answer is: **", Qwen3 uses "Final Answer: the final answer is **", and Qwen3 SummEval uses "Thus, the rating is N.". These are per-model phrase choices the paper does not disclose.
3. **code_vs_paper (minor): γ default.** The paper uses γ=2 for Qwen models. The scripts default to `--alpha 1.0` for every model, so it has to be set by hand.
No internal contradictions in the paper were found (Table 4's deltas and Table 3's Avg columns are consistent with the per-dimension numbers).

## Codebase completeness: MISSING_SCRIPTS
- No edits to `./codebase` (`git status` is clean). GSM8K/SummEval and the Table 4 ablation ran with CLI arguments only (`--alpha 2.0` for Qwen, `--hmm_beam_size 0` for the ablation).
- Missing from the release: the whole EAE/ACE05 pipeline (Table 2) and the Ctrl-G baseline.
- Environment workaround: `OUTLINES_CACHE_DIR` was pointed at `./outlines_cache`, because the default `~/.cache/outlines` sqlite cache became corrupted mid-run ("database disk image is malformed"), most likely from concurrent jobs. That crashed 3 SummEval runs, which we re-ran.
- Scripts written outside the release: `make_jobs.py`, `jobs*.txt`, `queue.sh`, `queue2.sh`, `run_job.sh` (sequential queue + 75 GB RSS watchdog), `step_wrap.py` (progress printing only), `tb_wrap.py`/`debug_speed.py` (debugging), `aggregate.py` (runs the released evaluators and adds per-document correlations), `compare.py`/`build_status.py` (tables).
- Gotcha: outputs are written with default Python buffering. On this Lustre filesystem (`st_blksize` = 4 MB) the output file stays empty until the run finishes, which first looked like a hang.
