**Summary.**
- **What reproduces.**
  - No-pruning avg@64 and per-question token counts for DS-Qwen-1.5B and 7B match Table 2 closely: tokens within ~1–2%, accuracy 0.8–3.3 points lower.
  - STOP's token saving (~71–75% on math, ~63–68% on GPQA when pruning 64→8 at 2,048 tokens) matches to within <0.5 points.
  - On DS-Qwen-1.5B AIME24 and AIME25, STOP clearly beats no pruning: +6.3 / +5.9 points with the released checkpoint, +5.1 / +5.9 with a module I retrained using the released code and data. AIME25 matches the paper's number.
- **What doesn't reproduce.**
  - On HMMT25 and BRUMO25 (1.5B), and on most 7B math benchmarks, the gain is ~0 or not significant (BRUMO25, 1.5B, released checkpoint: −3.1).
  - GPQA-Diamond with standard shuffled options: STOP gives only +1.2 (1.5B) / +1.3 (7B), not significant. The paper reports +15.3 / +9.8.
- **The GPQA answer leak.**
  - In the released STOP GPQA training data (1.5B and 7B), the correct answer is **always option A**, and STOP learns to prefer paths that lean toward "A". Shuffled-option GPQA-D: +10–15 points on gold-A questions, −3 to −5 on the rest.
  - When GPQA-D is evaluated with the correct answer always at A, the paper's GPQA numbers are reproduced almost exactly:

    | | no pruning (ours / paper) | STOP (ours / paper) |
    |---|---|---|
    | 1.5B | 31.78 / 33.08 | 48.42 retrained, 45.64 released / 48.42 |
    | 7B | 45.28 / 45.95 | 56.44 / 55.75 |

  - So the paper's largest reported gains, on GPQA-D, appear to come from an answer-position leak, not from genuine pruning.
- **Not run.** The Type I–III baselines are not released, and the 8B/20B rows were not run (no checkpoints; compute).

## 1. Paper claims and target

Main claim (abstract, Section 4.1, Table 2): STOP (Type IV pruning: a learnable [STOP] token, a LoRA "critique" adapter and a classifier head that read the prefix's KV cache) gives a higher avg@8|64 than no pruning and than the Type I–III pruners, while cutting tokens by ~70%, across DS-Qwen-2.5-1.5B/7B, DS-Qwen-3-8B and GPT-OSS-20B on AIME24/25, BRUMO25, HMMT25 and GPQA-D.

Protocol (Section 4.1, App. C): for each question, 64 paths; prune at 2,048 generated tokens, keeping the top 8 by score. Sampling: T=0.6, top-p 0.95, top-k 40, max 16,384 tokens (1.5B/7B). Metrics are avg@64 (no pruning) and avg@8|64 (mean accuracy of the 8 kept paths), plus total tokens per question.

Reproduction target: Table 2, rows DS-Qwen-2.5-1.5B (all five benchmarks), and DS-Qwen-2.5-7B as far as compute allowed. Columns: "No pruning" and "Type IV (STOP)".

## 3. What I did

All my scripts are in `./scripts/`; logs and outputs are in `./runs/`. I made **no edits to the released code**: `codebase/` is unchanged except for an untracked `__pycache__`.

1. **Environment:** conda env with Python 3.12, `vllm==0.11.2` from PyPI (brings torch 2.9.0), `transformers==4.57.6`, `peft==0.14.0`, `accelerate==1.11.0`, `math-verify`, `wandb` (offline). requirements.txt pins torch 2.10, which vllm 0.11.2 cannot use. I used stock vLLM for generation; the modified vLLM is only needed for the AIMO `/classify` serving path. The STOP scoring uses the released HF `HarmonyTwoStageClassifier.forward`, unchanged.
2. **Generation** (`scripts/gen.py`, vLLM): 64 samples per question, T=0.6, top-p 0.95, top-k 40, max 16,384 new tokens, chat template of the DeepSeek-R1-Distill tokenizer.
   - Prompts: the paper's App. C.3 suffixes ("Please reason step by step, and put your final answer within \boxed{}." / `Please show your choice in the answer field with only the choice letter, e.g., "ANSWER": "C".`).
   - GPQA-Diamond comes from `Idavidrein/gpqa` (198 questions), with options shuffled using a fixed per-question seed (`gpqa`). A diagnostic variant `gpqa_afirst` puts the correct answer always at A.
   - Grading: last `\boxed{}` checked with `math_verify` for math; the last `ANSWER: X` for GPQA.
3. **Pruning evaluation** (`scripts/prune_eval.py`, `scripts/stop_model.py`): each path's prefix (prompt + first 2,048 generated tokens) is scored by STOP, and the top 8 of 64 are kept.
   - Pruning a path at 2,048 tokens and resuming it is distributionally identical to cutting a full sample, so I use the full samples' continuations.
   - Tokens = Σ over 64 paths of min(len, 2048) + Σ over kept paths of (len − 2048)⁺, averaged per question.
4. **STOP checkpoints evaluated:**
   - **released** STOP-1.5B. It is in an older format: the [ASSESS] embedding sits in row 151665 of a resized `embed_tokens` saved inside the adapter, and there is no `assess_token_embedding.pth`. My loader copies that row into the model's assess embedding; all other rows equal the base model's.
   - **retrained-1.5B**: the released `finetuning_harmony.py`, unchanged, launched with `accelerate launch --num_processes 1 ... --epochs 15 --learning_rate 2e-5 --lora_r 128 --lora_alpha 256 --target_modules q,k,v,o,gate,up,down --num_assess_tokens 4 --batch_size 16 --gradient_accumulation_steps 8 --dtype bf16 --max_length 5120` (paper Table 12: effective batch 128). Data: the released `1.5B_math_2048.json` + `1.5B_gpqa_2048.json`, converted by `scripts/prep_train.py`. 23,200 of 23,264 records; 64 records longer than 5,120 tokens were dropped. Final model after 15 epochs, as the script does when no validation set is given.
   - **retrained-7B**: same code with Table 12's 7B settings: r=256, α=512, lr 2e-5, effective batch 128 (8×16). For time I used the script's own validation mechanism: 300 records held out (17,415 train) and the best-val-MSE checkpoint saved each epoch. Training was **stopped after 7 of 15 epochs**, because val MSE peaked at epoch 4 (0.0425) and did not improve in epochs 5–7. The checkpoint used is from epoch 4.
5. **Analysis** (`scripts/analyze.py`): bootstrap 95% CI of the gain, majority-vote accuracy, and the GPQA letter-bias diagnostics.

**Settings that differ from the paper:**
- Single H200 instead of 8×H100, so gradient accumulation replaces data parallelism (same effective batch).
- Retrained 7B: 7 of 15 epochs, plus a 300-record validation split.
- 64 over-long training records dropped.
- My own grader and GPQA option shuffling (the paper does not describe either).
- vLLM 0.11.2 stock.
- One generation seed (as in the paper).

### 4a. GPQA letter-bias diagnostic (DS-Qwen-1.5B, shuffled options)

Within-question percentile rank of STOP scores (0.5 = chance), by the final answer each path ends up giving:

| | released ckpt | retrained |
|---|---|---|
| wrong paths that answer "A" | 0.555 | 0.600 |
| wrong paths that answer B/C/D | 0.481 | 0.476 |
| correct paths, gold = A | 0.556 | 0.564 |
| correct paths, gold = B/C/D | 0.486 | 0.478 |
| share of kept paths answering "A" (vs 20.3% of all paths) | 28.4% | 33.0% |
| avg@8\|64 on the 58 questions with gold = A (baseline 29.93) | 40.09 | 44.61 |
| avg@8\|64 on the 140 questions with gold ≠ A (baseline 32.90) | 30.36 | 28.30 |

So STOP's GPQA "gain" is pure answer-letter preference. It helps when the gold answer happens to be A and hurts otherwise. The cause is in the released training data: in `1.5B_gpqa_2048.json` (8,448 records) and `7B_gpqa_2048.json` (5,666 records), `answer` is "A" for **every** record. Prefixes that already state "ANSWER: A" have a mean soft label of 0.9998, versus ≤0.0007 for "ANSWER: B/C/D". When GPQA-D is evaluated with the correct answer at A, the paper's GPQA numbers come back: 48.42 = 48.42 with the retrained 1.5B module, and 56.44 vs. 55.75 at 7B, with the 7B no-pruning baseline 45.28 vs. 45.95.

### 4b. DS-Qwen-7B GPQA-D letter bias (retrained 7B STOP, shuffled options)

The same pattern holds at 7B. Mean within-question rank of STOP scores: wrong paths answering "A" 0.563 vs. wrong paths answering B/C/D 0.480; correct paths with gold A 0.545 vs. correct paths with gold B/C/D 0.489. Kept paths answer "A" 28.3% of the time vs. 21.2% overall. avg@8|64 is 52.37 vs. 41.06 baseline on the 58 gold-A questions (+11.3), and 48.39 vs. 51.27 on the 140 gold-B/C/D questions (−2.9).

**7B, GPQA-D with the correct answer always at "A"** (diagnostic): no-pruning avg@64 = **45.28** (paper 45.95; our shuffled-option baseline was 48.28). STOP avg@8|64 = **56.44** (+11.16, CI [8.5, 13.9]); the paper reports **55.75**. Both numbers in the paper's 7B GPQA-D row are reproduced within 0.7 points only under this answer-at-A protocol.

### Other observations
- Majority vote (cons) over the pruned 8 vs all 64, released 1.5B checkpoint: AIME24 53.3 vs 63.3, AIME25 40.0 vs 36.7, HMMT25 23.3 vs 26.7, BRUMO25 40.0 vs 46.7, GPQA 39.9 vs 39.4. Pruning 64→8 at a fixed N does not improve cons accuracy here. (The paper's scaling claims in Fig. 4 use equal-compute comparisons, which I did not run.)
- The retrained 1.5B module (15 epochs, final weights) fits its training labels almost perfectly: Pearson 0.985 on 512 training records. The released checkpoint reaches only 0.61, consistent with its name `best_checkpoint`, i.e. early selection on a validation set. Neither the paper nor the launcher documents a validation split.
- Our no-pruning avg@64 is 0.8–3.3 points (1.5B) and 1.7–3.2 points (7B) below the paper's on every benchmark, while token counts match within ~1%. That suggests a slightly stricter grader or minor sampling differences, not a different model or protocol.

## 6. Codebase completeness: MISSING_SCRIPTS

The method (STOP module) and its training code are released and ran **without any source edits**. The released 1.5B checkpoint loads and works. The main experiment's pipeline is missing, and I had to write it:
- `scripts/gen.py`: 64-sample generation with the paper's sampling config.
- `scripts/common.py`: benchmark loading, prompts per App. C.3, GPQA-D download and option shuffling, answer grading.
- `scripts/prune_eval.py` + `scripts/stop_model.py`: STOP scoring of 2,048-token prefixes through the released `HarmonyTwoStageClassifier`; top-8 selection; avg@64, avg@8|64 and token accounting. `stop_model.py` also loads the old-format released checkpoint, whose [ASSESS] embedding is stored in a resized `embed_tokens` and which lacks `assess_token_embedding.pth` / `assess_token_config.json` (both expected by `inference.py`).
- `scripts/prep_train.py`: converts the released text-only training data into the `prefix_token_ids` + `Soft_label` jsonl the training code requires. This includes reconstructing the prompt template (chat template + instruction; for GPQA, question + lettered options + suffix), since the data stores neither token ids nor prompts. The 7B math file lacks the `instruction` field, and its GPQA options are a stringified dict.
- `scripts/analyze.py`, `scripts/sanity_trainfit.py`, `scripts/make_tables.py`: analysis.
- Launch via `accelerate launch` CLI flags, because `scripts/accelerate_harmony_multi_gpu.yaml` referenced by the launcher is not in the repo.

Other release gaps:
- No GPQA-D file in `data/benchmark`.
- No Type I/II/III baseline code, so those columns of Table 2 are NOT_COMPARABLE / not run.
- The STOP-7B HF repo is empty, and there are no 8B/20B checkpoints, although the paper says the checkpoints are released.
- 64 of 23,264 1.5B training records (and 43 of 17,758 7B records) exceed 5,120 tokens, which would crash the released dataset class at the launcher's default max_length. I dropped them.
- requirements.txt pins torch 2.10, which is incompatible with the vLLM 0.11.2 it targets. I used torch 2.9.0 from the vllm wheel.
