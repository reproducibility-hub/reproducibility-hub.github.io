## 3. What we ran (commands)

Environment: `./env` (conda, Python 3.10), torch 2.6.0 / torchvision 0.21.0 (as in Appendix A), flash-attn 2.7.4.post1 (prebuilt wheel), the DART-bundled `transformers` fork (4.45.0.dev0, `pip install -e external/DART/Qwen2-VL/transformers`), `pip install -e external/DART/lmms-eval`, accelerate, qwen-vl-utils 0.0.14, pandas/matplotlib. EffiVLM-Bench's `qwen2vl` package needs transformers ≥ 4.47. We installed transformers 4.47.1 + tokenizers 0.21.0 into `env/extra_tf4471` and put it on `PYTHONPATH` only for the EffiVLM runs, as the EffiVLM README pins 4.47.1. Hardware: 1× H200 (paper: A800). Models: `Qwen/Qwen2-VL-7B-Instruct` and `lmms-lab/llava-onevision-qwen2-7b-ov`, the checkpoints recorded in the authors' result files.

* **Downsample / vanilla**, which is `scripts/dart.sh false <D>` (D = 1, 2, 3, 4, 5, 10). We used `scripts_own/run_dart.sh false <D> 0 <out> <port>`. It is the same command as `external/DART/Qwen2-VL/eval_scripts/lmms_eval.sh` (identical `model_args`), but with `--num_processes=1` and one benchmark per process.
* **DART**, which is `scripts/dart.sh true 1 <RR>` (RR = 0.75, 0.8889, 0.9375, 0.96, 0.99). We used `scripts_own/run_dart.sh true 1 <RR> ...`.
* **FastV / VisionZip / PruMerge+ on Qwen2-VL**, which is `scripts/effivlm.sh 1 <RR>`. That calls `external/EffiVLM-Bench/run_example.sh`, which is missing from the release, so we restored it (§6). Budget = 1 − RR. As released: `model_args=pretrained=Qwen/Qwen2-VL-7B-Instruct,method=<m>,budgets=<b>,use_flash_attention_2=true`, exactly what the authors' result files record. After fix: the same plus `max_pixels=2408448,min_pixels=3136` (`scripts_own/run_qwen_effivlm_maxpix.sh`), re-run only on the 4 benchmarks that contain images above the default cap (MME, OCRBench, ChartQA, MMStar). GQA, POPE and MMBench have no such image, so their outputs are identical under both settings.
* **LLaVA-OV-7B + FastV / VisionZip / PruMerge+** on GQA, MMB, MMBCN, POPE and MMStar (`scripts_own/run_effivlm_llava.sh`), with model `llava_onevision_with_kvcache` as in upstream `run_example.sh`. For PruMerge+, EffiVLM's LLaVA implementation has O(N²) Python loops and is very slow at 25 % budget. We therefore ran each benchmark as two disjoint parts (a random 1000-sample subset plus its complement) and merged them back into the full benchmark. Generation is batch-1 greedy, so this is exact.
* **Analysis**: the released `tools/analyze_results.py --all`, unmodified, on our outputs arranged in the `Data/` layout of `tools/reorganize_data.py` (`scripts_own/final_tables.py`). Then `scripts_own/make_comparisons.py` and `scripts_own/claims.py` compare against the paper.
* Orchestration: `scripts_own/scheduler.py`, `scheduler2.py`, `scheduler3.py` run 4–5 lmms-eval processes concurrently on the GPU. Logs are in `logs/` and `runs/**/run.log`; raw outputs are in `runs/`.

Settings that differ from the paper or the released scripts:
* 1 process per (config, benchmark) instead of `--num_processes=8` with all tasks per run. Each sample is generated independently with batch size 1 and greedy decoding, so the outputs are the same.
* H200 instead of A800, and flash-attn / transformers / qwen-vl-utils versions as above, which produce small numerical differences.
* MMBench `gpt_eval_score`: no OpenAI key is configured. lmms-eval's rule-based option matching handled all Qwen2-VL / LLaVA outputs; they are single letters. Our vanilla MMB 78.9 equals the paper's. VTC-Bench's own grouping (`analyze_results.py`) uses exact string matching, not GPT.

## 5. Discrepancies

1. **code_vs_paper (minor, affects results)**, `external/EffiVLM-Bench/lmms-eval/lmms_eval/models/qwen2_vl_with_kvcache.py`, `max_pixels: int = 700*28*28`.
   * Paper §3.2: "we set Qwen2-VL's max pixels and min pixels to 2408448 and 3136" for the comparison.
   * The released EffiVLM wrapper caps images at 548,800 px before FastV / VisionZip / PruMerge+ prune. The Downsample and DART runs use 2,408,448. This cap affects 45 % of MME, 30 % of OCRBench, 8 % of ChartQA and 6 % of MMStar images.
   * The authors' own released outputs were clearly produced with 2,408,448. With the code default we get FastV@75 % OCRBench 37.7 and VisionZip 36.4 (paper 42.0 / 42.1; only 73 % identical responses). With `max_pixels=2408448` we get 41.8 and 42.4 (89 % / 85 % identical responses).
   * The recorded `model_args` show no `max_pixels`, so the authors presumably edited the default locally.
2. **code_vs_paper (minor, no effect on results)**, `external/DART/Qwen2-VL/eval_scripts/lmms_eval.sh`. It evaluates `--tasks mmstar,mme,mmbench,ocrbench,chartqa,gqa` with `--num_processes=8`. The paper reports 8 benchmarks including POPE (the released outputs include POPE) and says all experiments run on one A800. Note also that `mmbench` expands to extra unused splits (cn_cc, ru_dev, test).
3. **paper_internal (no effect on results)**, §3.3: "at 93.75 % compression, downsampling achieves 66.4 % on MMBench, outperforming the best advanced method, DART, by a 24.3 % relative improvement." In Table 1, FastV (57.1) is the best method on MMB at 93.75 %, not DART (53.4); 66.4 / 53.4 = +24.3 %.
