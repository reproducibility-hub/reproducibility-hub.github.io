# Reproduction report — Pub-LawBench: Public-Oriented Benchmarking for LegalAI (2026.acl-long.1680)

## Verdict

- **Verdict: PARTIALLY_REPRODUCED**
- **Result match (after our fixes): MIXED.** 26 of 64 comparable Table-4 numbers (8 open-weight models × 8 Instant-QA columns) are within tolerance and 38 are not. Another 8 Unfair-ToS numbers are NOT_COMPARABLE, because the release has no ToS script and we had to write the prompt ourselves. A few task/model cells match well: COLIEE BERTScore for 7 of 8 models, CaseHOLD for Qwen2.5-3B/7B and SaulLM, CAIL for Qwen and Llama-3.1-8B, and QA-Corpus for half the models. Other paper numbers are contradicted: JEC-QA for Qwen (paper ≈10%, ours 30–49%), CaseHOLD for Llama (paper 6.0/1.0, ours 70.0/53.5), CAIL for SaulLM/DISC/Chatlaw, and Laws-QA/QA-Corpus BERTScore for Llama-3.2-3B and LawGPT. The ranking of the open models only partly holds. Qwen2.5-7B > Qwen2.5-3B stays at the top and the Chinese legal LLMs stay at the bottom, but the middle reorders.
- **Result match as released: DOES_NOT_RUN.** The release contains generation scripts only, with no evaluation or scoring code at all. Their paths are hard-coded to the authors' machines (or `<modelname>` placeholders), there is no Unfair-ToS script, and the Legal Gen data is missing. As a diagnostic we also scored the outputs that the *unmodified* released post-processing produces (see the "prompt-echo bug" below). Those numbers reproduce several suspiciously low paper values, e.g. JEC-QA ≈10% for Qwen/Llama and DISC CaseHOLD 21.5 = 21.5.
- **Coverage: SUBSET.** We ran all 9 Instant-QA tasks on all released data for all 8 open-weight models in Table 4. We did not run:
  - the 9 commercial models (no API keys; closed-source models being evaluated);
  - the 4 Legal-Gen (CaseGen) tasks: the data is not in the repo and their metrics (KeyCover etc.) use a GPT-4o judge;
  - Tables 5/6/7, 13–16 and Figs. 3–4, which need either commercial models or the GPT-4o judge and Legal-Gen data.
- **Codebase completeness: MISSING_SCRIPTS.** The flags are CLOSED_JUDGE_UNAVAILABLE plus the derived discrepancy flags.

## What the paper claims / what was targeted

Table 4 (performance-oriented metrics) is the main results table: 17 LLMs × 13 tasks. The only part that is runnable with the release and without API keys is the **Instant-QA block (9 tasks) for the 8 open-weight models**:

- General: Qwen2.5-3B/7B, Llama 3.2 3B, Llama 3.1 8B
- Legal-specialized: SaulLM-7B, DISC-LawLLM, Chatlaw, LawGPT

Metrics are Accuracy (CAIL, JEC-QA-KD, CaseHOLD, JEC-QA-CA, Unfair-ToS, LEdGAR) and BERTScore-F1 (COLIEE, Laws-QA, QA-Corpus). The paper's text claims we can check in this subset are:

1. Open and legal models collapse on complex tasks (most below 20, near random).
2. The ordering of open models: general Qwen > others, with legal-specialized models weaker.

## What we did

1. Read the paper and cloned https://github.com/Statistical-NLP-Lab/Pub-LawBench (commit 8252de1) into `./codebase`.
2. Created the conda env `./env` with Python 3.11, vllm 0.10.1.1, torch 2.7.1, transformers 4.55.4, sentencepiece 0.2.0, bert_score 0.3.13, rouge_score, sklearn.
3. **Mapped the scripts to tasks.** The released file names do not match their contents:

   | released file | what it actually runs | data used |
   |---|---|---|
   | `cail.py` | JEC-QA loader (`statement`+`option_list` JSONL) | `KD_train.json` (7775), `CA_train.json` (13297) |
   | `coliee.py` | generic MC CSV; writes `result_casehold_*` | `casehold_prompts.csv` (200), also used for `CAIL.csv` (199) |
   | `laws.py` | COLIEE; writes `outputs/coliee_result_*` | `coliee_prompts.csv`, of which only 199/463 rows have a reference |
   | `qa-corpus.py` | LEdGAR (100-label prompt, greedy, 10 tokens) | `ledgar_test.csv` (200) |
   | `ledgar.py` == `unfair_tos.py` (identical) | open QA JSON `{id,prompt,reference}` | `qa_corpus.json` (200), `laws_qadata.csv` (200, converted; the conversion script is not released) |
   | `casehold.py` | CaseGen Legal-Gen (4 tasks) | `data/legal_gen/CaseGen.json` is **not released** |
   | `casegen.py` | duplicate generic generator pointing at `CAIL.csv` as JSON | — |
   | *(none)* | Unfair-ToS | `unfair.csv` (200): **no script and no prompt** |

4. **Generation (`scripts/run_gen.py`, our script).** The released scripts generate one sample at a time with HF `generate`, which for ~23.5k prompts × 8 models was too slow. Our runner re-implements their loop in vLLM and copies verbatim, per script:
   - the instruction suffix, chat wrapper, and truncation length;
   - `max_new_tokens`;
   - sampling settings (T=0.2, repetition_penalty 1.1, sampling, `eos_token_id = tokenizer.eos_token_id`).

   It resolves top-p/top-k the same way HF does (explicit kwargs > model `generation_config` > HF defaults), and uses FP16. We checked equivalence by running the unmodified released `coliee.py` (CaseHOLD) with HF on Qwen2.5-3B-Instruct and Llama-3.1-8B-Instruct (`scripts/run_released.py` only injects the placeholder `MODEL_MAPPING`).
   - Qwen2.5-3B: the released outputs, with our emulated post-processing, are identical (200/200) to the HF run and give the same 21.5% accuracy.
   - Llama-3.1-8B answer part: HF 67.0 vs vLLM 70.0 (sampling noise).

   Command: `scripts/run_all.sh`, `scripts/run_rest.sh <models>`, with `VLLM_FLASH_ATTN_VERSION=2` for DISC.
5. **Evaluation (`scripts/evaluate.py`, our script; the release has none):**
   - MC accuracy: exact match of the extracted letter set (regex extraction: leading letters, then "答案/正确选项/answer is X", then the first standalone letter run), plus macro P/R/F1.
   - LEdGAR: first integer in the output (the prompt asks for the label number). A lenient name-to-index variant is also recorded.
   - Unfair-ToS: exact set match, with "None" meaning the empty set.
   - BERTScore F1 via `bert_score` with default models (roberta-large for English COLIEE, bert-base-chinese for Laws-QA/QA-Corpus), no baseline rescaling. ROUGE is also reported.
6. **Prompt-echo diagnostic (`scripts/emulate_released.py`).** Applies the released post-processing (`decode(prompt+gen, skip_special_tokens=True)`, then `replace(final_prompt,"")`, then `replace("assistant","")`) to our generations, giving the "as released" numbers.
7. Extra settings: 2 more sampling seeds (seeds 1, 2) on the 200-sample tasks, and base (non-instruct) checkpoints for the four general models.
8. `scripts/compile_results.py` produces `comparison_table.md` / `comparisons.json`. Raw outputs are in `outputs/`, `outputs_released/`, `outputs_seed{1,2}/`. Metrics are in `results*.json`.

### Interpretation

- **Prompt-echo bug in the release.** Every released generation script does `response = tokenizer.decode(outputs[0], skip_special_tokens=True)` and then `response.replace(final_prompt, "")`. For models whose prompt wrapper contains special tokens (Qwen ChatML, Llama-3 headers; DISC also fails because of SentencePiece whitespace), the decoded text no longer contains `final_prompt`. As a result, **the whole prompt stays in the saved "output"**, and `replace("assistant","")` further mangles it ("legal assistant" → "legal ."). We verified this with the unmodified `coliee.py` under HF.
  - When the output starts with the echoed prompt (options "A … E"), naive answer extraction picks letters from the prompt. Scored that way, the as-released numbers reproduce several paper values that look implausible for these models: JEC-QA ≈ 10–14% for all general models (paper 9–11; our fixed outputs give 31–49% for Qwen). For DISC, CaseHOLD 21.5 / JEC-C 10.9 / LEdGAR 2.5 / Laws-QA 58.1 / QA 58.0 are essentially exact matches to Table 4/12. The 20.0 macro-recall values in Table 12 (always the same predicted class) are another signature of this bug.
  - However, other paper numbers (Qwen CaseHOLD 59.5/68, CAIL ≈35 for Qwen/Llama) match only the *fixed* outputs. So the authors' unreleased scorer must have treated tasks differently, and no single configuration we tried reproduces Table 4.
  - The paper's claim that open-weight models are "approaching random" on complex reasoning tasks (JEC-QA, CaseHOLD) is therefore at least partly an artifact of this post-processing bug, for Qwen and Llama. Qwen2.5-7B gets 48.6% exact-set accuracy on JEC-QA-KD and 70% on CaseHOLD once only the generated text is scored.
- **LEdGAR ≈ 0–2% for all open models does reproduce,** but because the models answer with label *names* although the prompt asks for numbers. With a lenient name-to-index mapping, Qwen2.5-3B reaches 38% and Qwen2.5-7B 20%.
- **Legal-specialized models are weaker than general models** in our runs too. DISC/Chatlaw/LawGPT have the lowest averages, consistent with the paper's qualitative message.
- Base checkpoints (an extra setting) reproduce neither the Qwen nor the Llama pattern (e.g. Qwen-base CaseHOLD 4–8, Llama-3.1-8B-base JEC 9/7). See `comparison_table.md`, last column.

## Not reproduced and why

- **Commercial LLMs** (9 of the 17 models, plus all of Table 6 on CoT, Table 7 on RAG, and most of Tables 3, 5, 11, 13–16): these are closed-source evaluated models and no API keys are configured, so they are blocked.
- **Legal Gen (CaseGen Fact/Reas/Judg/Def):** `data/legal_gen/CaseGen.json` is not in the release. KeyCover, Legal-Normativity and Format-Usability need a GPT-4o judge, the National Laws and Regulations Database, THUOCL and Lawformer pipelines, none of which are released (no code). Hence CLOSED_JUDGE_UNAVAILABLE.
- **Unfair-ToS:** no released script or prompt, so our prompt makes these numbers NOT_COMPARABLE.
- **Evaluation:** no released scoring code, so the answer-extraction rules and BERTScore backbones are guessed.

## Discrepancies

**Code vs paper**
1. *major:* All generation scripts' post-processing (`response.replace(final_prompt, "")` after `decode(..., skip_special_tokens=True)`) fails to strip the prompt for chat-template models. The saved outputs contain the full prompt, which corrupts accuracy and BERTScore for Qwen, Llama and DISC. The paper describes standard per-task metrics on model answers.
2. *major:* `CAIL.csv` contains JEC-QA-style law-exam MC questions (its first item is identical to `KD_train.json` id 1_4269), not CAIL2018 fact-extraction/charge-prediction cases (Section 3.1, Table 2, App. B.1).
3. *major:* COLIEE. The paper (App. B.1) describes retrieving the statute and judging entailment, scored with ROUGE/BERTScore against the statute. `laws.py` appends "provide step-by-step reasoning … final answer (Yes/No)" to a prompt asking to quote the statute, and 264/463 rows have no reference and are silently dropped.
4. *minor:* Decoding. The paper (Sec. 4.1, App. C.2.3) says nucleus sampling p=0.9, T=0.2, and greedy decoding for discriminative tasks. The code uses sampling (T=0.2, rep. penalty 1.1, no top_p, so the model's generation_config/HF defaults apply) for all MC tasks; only LEdGAR is greedy. Only the CaseGen script sets top_p=0.9.
5. *minor:* DISC-LawLLM. The paper says FP16 with tensor parallelism across two GPUs; the code default (a single device id) loads it in 8-bit.
6. *minor:* Dataset sizes. Table 2 lists 5k–100k examples per task; the release ships ~200 examples per task (full JEC-QA train files), and the evaluated sample counts are not stated.

**Paper-internal**
1. Table 4's Legal-Gen columns are labelled "(BS)" = BERTScore, but the identical numbers appear as **KeyCover** in Tables 11/12. Table 5's KeyCover values (e.g. DeepSeek-V3 Def 81.8) also differ from Table 11's KeyCover (74.4) and agree with Table 15 (0.818).
2. Table 4 vs Table 12 for the same open-weight models. LEdGAR: Qwen2.5-7B 1.8 vs 1.0; DISC 1.0 vs 2.5; Chatlaw 0.8 vs 0.0; LawGPT 1.4 vs 2.5; Qwen-3B/Llama "-" in Table 12. CAIL: Llama 3.2 3B 36.4 vs 11.1. JEC-QA: LawGPT KD 9.5 vs 0.5, CA 8.3 vs 0.0. CaseHOLD: DISC/Chatlaw 21.5/15.0 vs "-".
3. "17 LLMs": Section 4.1 lists 8 commercial + 8 open models (16), while the tables include GPT-5.2 as a 9th commercial model. The text also mentions "Gemini-3.1" in the case study.
4. LawGPT is described as a Chinese-LLaMA/Alpaca model (App. C.1) but cited as Nguyen et al. 2023 (a GPT-3-based "LawGPT 1.0").
5. The CAIL task is described as fact extraction & charge prediction (App. B.1), but its example (Fig. 6) is a JEC-QA law-exam MC question.
