## Summary
- Figure 4 (offline speculation quality, Llama-3.1-8B; SSSD vs REST vs Lookahead warm/cold, decomposed components) reproduces almost exactly (all 22 compared points within 5%)
- Figure 6a-d / 6f end-to-end SGLang benchmarks ran with the authors' frozen sglang-sssd branch, but on an H200 instead of the paper's 48 GB L40S-class GPU, so absolute latencies are not comparable

- At large batch sizes SSSD is slower than autoregressive decoding on H200 (MT-Bench bs>=32, MATH-500 bs>=48, HumanEval bs=64, German and reasoning bs>=16), contradicting the paper's speedups at bs 64 and the claim that SSSD is the only method with speedups at large batch sizes on reasoning; a diagnostic with only 2 draft tokens shows a fixed per-step host-side overhead, not the speculation-length rule, is the cause
- Not run: Fig 6e (SWE-Bench) and Table 1 (PG-19), which need 4-GPU prefill/decode disaggregation; Fig 7 / Llama-3.3-70B (multi-GPU; source of the abstract's 'up to 2.9x'); Fig 5 Qwen3-14B multilingual (needs unreleased model-generated multilingual data)

In short:
- **Offline (Figure 4):** the algorithmic claim reproduces to within plot-reading accuracy. SSSD's datastore and input sources are complementary, and SSSD clearly beats REST and Lookahead in accepted tokens per step.
- **End-to-end on 1×H200:**
  - At low batch sizes, the paper's qualitative ranking holds on every dataset.
  - The large-batch speedups shown in Figure 6 do not appear on our hardware.
  - The Figure 6f claim that SSSD is "the only method that achieves speedups at large batch sizes" does not hold here: every speculative method, SSSD included, is slower than autoregressive decoding at batch size ≥16.
  - Our GPU differs from the paper's, and the paper notes that SSSD drafting depends on CPU performance. So this is a hardware-dependent shortfall, not evidence of a code bug.

## What was attempted

Paper: *SSSD: Simply-Scalable Speculative Decoding* (ACL 2026). SSSD is a training-free speculative decoder. It drafts from n-gram matches against the prompt/self-output trie plus a large suffix-array datastore, and it picks the speculation length from the hardware.

Code used:
- `./codebase` = https://github.com/huawei-csl/sssd_speculator (commit `cafa179`). This is the SSSD C++/pybind library, the datastore builder, and the offline evaluation (`evaluation/`) with the REST / adapted-REST / PIA (Lookahead) baselines.
- `./sglang-sssd` = https://github.com/huawei-csl/sglang-sssd, branch `sssd-v0.5.3.post3-acl26`. The README calls this "the frozen branch used for the ACL 2026 paper experiments". It holds the SGLang integration and the end-to-end benchmark scripts. Its `sssd_speculator` submodule points at commit `7a39799`, which differs from `cafa179` only in the README BibTeX. I installed the library from `./codebase`.

Hardware: 1× NVIDIA H200 (141 GB), 14 CPU cores, ~111 GB RAM (Slurm job).
The paper's single-GPU experiments (Fig. 4–6a-d, 6f) used a "48 GB GPU (165.2 TFLOPS bf16; 1008 GB/s)", i.e. an L40S-class card. Absolute latencies are therefore not comparable. I compare speedups over autoregressive decoding and the ranking of methods.

### Settings that differ from the paper

- **GPU:** H200 instead of a 48 GB / 165 TFLOPS / 1 TB/s GPU. Autoregressive decoding of Llama-3.1-8B at batch size 1 runs at 5.1 ms/token for us, versus about 16.5 ms/token in the paper. The adaptive speculation-length rule measures the GPU's FLOP/bandwidth ratio itself (capped at 192), so the speculation budgets are similar. However, the SSSD host-side work (CPU drafting, mask building) is now large relative to a 3× faster GPU step. We also had only 14 CPU cores; the paper's hosts had 96–192.
- **The Stack (python):** `bigcode/the-stack-dedup` is gated and our HF token is not authorized (HTTP 403). I substituted 110k files of the ungated `codeparrot/codeparrot-clean` (deduplicated GitHub Python), passed as a `.jsonl` input. It is sized so the final datastore is 13.4 GB, versus 14 GB in the paper. This only affects the HumanEval datastore content.
- **Draft model for STANDALONE:** `meta-llama/Llama-3.2-1B-Instruct` is gated for our token, so I used `unsloth/Llama-3.2-1B-Instruct`, a public mirror of the same weights. STANDALONE also hit a CUDA OOM on the H200 at the default memory fraction, because the draft model's KV pool did not fit. I passed `--mem-fraction-static 0.6` (CLI setting) for STANDALONE only.
- **Samples:** `SAMPLE_SIZE=1` for Fig. 6a–d, which is the released script's default; the paper does not state averaging for 6a–d. Fig. 6f uses 5 samples, as in the script and the paper.

## Why it is not fully reproduced
1. **Hardware.** The paper's single-GPU results are on a 48 GB, ~165 TFLOPS, ~1 TB/s GPU; ours is an H200. Autoregressive decoding is about 3× faster on our GPU, so SSSD's host-side per-step cost is relatively larger. That shrinks the end-to-end speedups and erases them at large batch sizes. We could not obtain the paper's GPU.
2. **Multi-GPU experiments not run** (insufficient compute: we had 1 GPU):
   - Fig. 6e SWE-Bench and Table 1 PG-19, which use prefill/decode disaggregation on 4 GPUs;
   - Fig. 7 / App. C, Llama-3.3-70B, the source of the abstract's "up to 2.9×".
3. **Missing data.** Fig. 5 (Qwen3-14B multilingual cold start) needs the authors' model-generated multilingual data, which is not released.
4. **Gated data and models** (our HF token is not authorized), substituted as described above:
   - The Stack: only affects the HumanEval datastore;
   - Llama-3.2-1B: replaced by an identical-weight mirror.
