## Verdict
* **Verdict: PARTIALLY_REPRODUCED**
* **Result match (after my additions): MIXED**. As released (unmodified released scripts): **MIXED**.
* **Coverage: SUBSET**. Table 1 for 2 of the 5 models (Llama-3.1-8B-Instruct, Phi-3-mini-4k-instruct), all 4 benchmarks, full test sets. 3-shot / SC-3 baselines for Llama only. Tables 2/3, analyses and the other 3 models were not run.
* **Codebase completeness: MISSING_SCRIPTS**. The method is fully released (residual extraction, SVCCA, steering hook, per-dataset sweep and baseline scripts), and I did not edit any released file. But the paper's model-selection pipeline is missing:
  * no dev splits for ProofWriter / FOLIO;
  * no candidate-layer selection;
  * no dev→test selection step;
  * the README's own procedure sweeps (layer, λ) directly on the test files.
  I wrote that pipeline from the paper's description. There is also a results-affecting parser bug in the released 3-shot baseline scripts.

**Bottom line.** Steering along the CCA subspace works with the released code. Greedy-CoT baselines reproduce well (Llama: 70.4 / 52.2 / 49.9 vs 70.6 / 51.4 / 50.7 on PrOntoQA / CWA / OWA).

The paper's headline gain, **Phi-3-mini on PrOntoQA +11.0, reproduces: 57.8 → 68.8 (+11.0, McNemar p<0.001)**. It holds across numeric perturbations and beats random-direction steering of the same strength (mean 59.6). However, most of it comes from LSS breaking repetition loops / runaway generations: unparsed outputs drop from 94 to 23, while accuracy on parsed outputs barely changes.

For **Llama-3.1-8B** (the paper's main model, with claimed gains of +4.2 to +9.4 on every benchmark), gains with dev-selected (layer, λ) are small, inconsistent, and not significant:
* PrOntoQA 70.4 → 71.2 / 70.0 (paper: 70.6 → 75.4);
* CWA 52.2 → 54.4 / 44.8;
* OWA 49.9 → 50.9 / 52.7;
* FOLIO 56.2 → 57.1 / 60.1.

They are of the same size as the swings caused by bf16 numerics alone. Changing only the inference backend or batch size moves single-config test accuracy by up to ±4 points.

The paper's Llama LSS numbers *are* recovered (within ~1.5 points on all four benchmarks) if (layer, λ) is picked by maximum **test** accuracy over the README's sweep, which is the procedure the README documents.

For Phi-3, CWA improves (+3 to +5), but FOLIO and OWA do not (−5 to +2).

## What was attempted

**Target.** Table 1 (main results) — Greedy-CoT vs LSS-CoT accuracy on FOLIO, PrOntoQA (5-hop),
ProofWriter-CWA (3-hop) and ProofWriter-OWA (3-hop) — for **Llama-3.1-8B-Instruct** (the paper's primary model,
used for all its analyses) and **Phi-3-mini-4k-instruct** (the model with the paper's largest gain, +11.0 on PrOntoQA).
Protocol followed from the paper (Sec. 3, 4.1, App. A, F.1):
1. residual activations of paired NL / symbolic proofs on the training split (TransformerLens, fp32, resid_pre, mean-pooled
   over proof tokens; FOLIO: whole NL-story vs FOL-story inputs incl. label sentence);
2. per-layer PCA(98% var, cap 128) + CCA(k=32) -> NL-side basis, QR -> U, P = U U^T (released `cca.py`, `--k 32 --center --shared x`);
3. grid search of (steering layer, lambda in {0.02..0.14}) on a held-out **dev** split, accuracy with no-answer counted wrong;
4. greedy CoT (1024 new tokens) on the **test** split with lambda=0 (Greedy-CoT) and the selected (layer, lambda) (LSS-CoT).

**Environment.** conda env `env/` (python 3.11), torch 2.5.1+cu124, transformers 4.46.3, transformer-lens 2.15.4,
scikit-learn 1.9.1, vllm 0.6.4.post1 (only for the fast dev sweep, see below), 1x H200.

### Settings that differ from the paper / had to be guessed
* **Dev splits rebuilt.** The release ships only the *test* subsets for ProofWriter (`{cwa,owa}_501_3hop.jsonl`, verified to come from
  the official `meta-test.jsonl`) and no FOLIO dev split. I rebuilt them as App. A describes: ProofWriter dev = label-balanced 3-hop
  subsample of the official `meta-dev.jsonl` (OWA 167/167/167, CWA 250/250, seed 42, same text format as the shipped test files;
  `scripts/make_pw_dev.py`); FOLIO = 50 random training items as dev, remaining 951 for the subspace (seed 42; `scripts/make_folio_split.py`).
  PrOntoQA train/val/test are shipped and used as is.
* **Candidate layers.** App. F.1: "8 layers with highest mean canonical correlation in the middle-to-upper part", but the paper's own
  chosen Llama/PrOntoQA layer (16, Sec. 5.4/App. J) is at the *minimum* of the correlation curve, and the README sweeps layers 10-20.
  The code for candidate selection is not released, so I swept **all layers 8..L-1** on dev and report three selection rules:
  A = paper F.1 (top-8 mean-corr layers among layers >= L/3), B = README range 10-20, C = all swept layers.
* **Dev sweep backend.** The released HF sweep needs ~10 min per (layer, lambda) config on 500 items (static batching: every batch runs the
  full 1024 steps because ~20 % of greedy CoTs loop; `torch.use_deterministic_algorithms` adds ~45 %), i.e. ~27 h for the paper's
  8x7 grid on one model. I therefore ran the dev grid with `scripts/vllm_lss.py`, a vLLM port that reuses the released prompts, chat
  template, tokenisation, parsers and label normalisation and re-implements `HFSteererNormalized` 1:1 (layer-input / resid_pre,

  CoTs diverge under any bf16 kernel change, so single-config differences of 1-2 points are numerical noise).
  Test-set numbers are reported with **both** the vLLM port and the **released HF script** (the latter is the "as released" number).
* Batch size: released default 8; the released-HF test runs used `--batch_size 128` (with `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`), 3-shot used 64. This changes only bf16 numerics.
* Baselines 3-shot-CoT and SC-3: see results section for what was run.

The chosen (layer, lambda) per setting are not reported.
* **code_vs_paper** (major; affects results: True). *Where:* prontoqa/evaluation/prontoqa_3shot_baseline.py, proofwriter/evaluation/proofwriter_3shot_baseline{,_owa}.py, folio/evaluation/folio_3shot_baseline.py: parse_truth(). *Paper:* Cases with no answer within the 1024-token budget are treated as incorrect (Sec. 4.1). *Code / other part:* parse_truth searches the full decoded text (prompt + generation); when the generation has no 'Truth value:' line it falls back to the in-context exemplars' answers, so unanswered generations get the last exemplar's label. ## Why the paper's numbers are not fully reproduced
1. **The dev→test protocol behind Table 1 cannot be recovered from the release.**
   * The paper selects (layer, λ) per model × benchmark on a held-out dev split (App. F.1) but never reports the selected values, except Llama/PrOntoQA = layer 16, λ = 0.08 (Sec. 5.4).
   * The release ships no ProofWriter/FOLIO dev splits and no selection code.
   * The README's step 4 sweeps (layer, λ) **directly on the test files**.
   * I rebuilt the dev splits per App. A and report three candidate-layer rules. Selection is very noisy: dev-optimal configs often do not transfer to test, and different rules pick different configs with different test outcomes.
2. **Effect sizes ≈ numerical noise for Llama-3.1-8B.**
   * Greedy CoT on these tasks is chaotic: ~20 % of outputs loop to the 1024-token limit, and only ~75 % of per-item predictions survive a change of attention kernel or batch size.
   * The same (layer, λ) gives e.g. 74.8 (vLLM) vs 70.0 (released HF) on PrOntoQA test, and 50.6 vs 44.8 on CWA.
   * The paper's single-run Llama gains (+4 to +9) are within the range that config selection plus numeric noise produces. My dev-selected configs reproduce them only sporadically.
   * Picking the best of the 77 README-range configs **on the test set** (the README's documented procedure; vLLM port) gives FOLIO 62.6, PrOntoQA 73.8, CWA 54.6, OWA 55.7. These are within ~1.5 points of the paper's LSS column (61.1 / 75.4 / 55.6 / 55.3), even though the average steered config is no better than greedy. The paper's Llama numbers are therefore *consistent with* test-set selection over a noisy sweep. I cannot prove which protocol the authors actually used.
3. **Phi-3 greedy baselines differ from the paper on 3 of 4 benchmarks**: FOLIO 62.1 vs 51.2, CWA 59.6 vs 37.1, OWA 54.9 vs 51.1. I found no code/config difference that explains this. I use the released prompts and decoding, including the released stop rule (stop only at `<|endoftext|>`, not at `<|end|>`).
4. **Not run (compute/time)**: Llama-3.2-3B-Instruct and Llama-2-13B-Chat (gated `meta-llama` repos with the available token; only third-party mirrors exist), Gemma-2-9B-IT (would also need a code change, see Discrepancies), Qwen3-4B, Tables 2-3, analyses. Phi-3 3-shot/SC-3 baselines were also not run.
