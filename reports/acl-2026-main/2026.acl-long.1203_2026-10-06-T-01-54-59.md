# Reproduction report — CIRAG (ACL 2026, 2026.acl-long.1203)

**Verdict: PARTIALLY_REPRODUCED** · result match (after fixes): **NUMBERS_MATCH** (on the reproducible w/o-TD subset) · result match as released: **DOES_NOT_RUN** · coverage: **SUBSET** · codebase completeness: **MISSING_CORE**

## Summary

The released code reproduces the paper's **"w/o TD" row of Table 2**: ICI retrieval + ACMG generation with a frozen
Qwen2.5-7B-Instruct and NV-Embed-v2, run on the 1000-question dev subsets of 2WikiMQA, HotpotQA and MuSiQue.
All six numbers are within tolerance (|Δ| ≤ 2.0 points, ≤ 4% relative):

| Dataset | Paper w/o TD EM / F1 (Table 2) | Ours EM / F1 | Match |
|---|---|---|---|
| 2WikiMQA | 49.8 / 59.7 | **51.8 / 60.7** | NUMBERS_MATCH (both) |
| HotpotQA | 48.8 / 62.5 | **47.9 / 63.1** | NUMBERS_MATCH (both) |
| MuSiQue | 22.2 / 33.1 | **23.3 / 34.4** | NUMBERS_MATCH (both) |

The paper's headline numbers (Table 1 "Ours", Table 2 "CIRAG" and "w/o reranker", Table 3, Tables 6–8, Figure 3)
all use the **Trajectory-Distillation (TD) student**. Its teacher is the closed Qwen-max API, and the release
includes no TD training code, no trajectories and no LoRA checkpoint. The default code path needs a LoRA server
(`finetune` on port 8001) that cannot be built from the release. Per the task instructions, TD was **not** reproduced
and no open substitute teacher was used, so every TD-dependent number is `NOT_COMPARABLE`. The Qwen-max backbone
columns of Table 1 are closed-API, so they are also not run. The paper's baselines (IRCoT, FLARE, MetaRAG, KiRAG,
DualRAG) are not in the release.

Other findings:
- The release does **not run as shipped**: it has broken `src.hipporag` imports, several missing modules and a missing config field.
- Decoding is **not greedy** in the release. No temperature is passed, so the server default T=1.0 applies, while the paper says greedy.
- Every answer goes through an **undocumented LLM answer-normalisation pass** before EM/F1 is computed.
- The full cascade has a **tuple bug** in its passage-level fallback. On 2WikiMQA it costs ≈ 2.7 EM; it has no measurable effect on HotpotQA or MuSiQue.
- Without TD, two of the paper's ablation conclusions (which it reports with TD) do not carry over. On 2WikiMQA (and MuSiQue for T→P), passage-only or T→P generation beats the full cascade. Dropping the reranker costs 8.5 EM on 2WikiMQA.

## What was run

Environment: conda env (python 3.10) at the required prefix, `pip install -r codebase/requirements.txt`
(vllm 0.6.6.post1, transformers 4.45.2, torch 2.5.1), plus `ratelimit pandas filelock pillow`, which are imported
but not listed. Hardware: 1× H200 (shared by all processes), with one vLLM server for everything.

Data: the code reads `reproduce/dataset/{name}.json` / `{name}_corpus.json`, which is the HippoRAG(-2) layout this
codebase is forked from. Neither the README nor the paper says where the data comes from. I used the public
**HippoRAG-2 release (`osunlp/HippoRAG_2` on HF)**: 1000 dev questions per dataset with IRCoT-style corpora
(2Wiki 6,119 / HotpotQA 9,811 / MuSiQue 11,656 passages). This matches the paper's description (1000 dev
questions, IRCoT corpus construction). For HotpotQA/2Wiki, `CIRAG.py` expects a `paragraphs[*].paragraph_scetence`
field that HippoRAG's files don't have; `scripts/prep_data.py` derives it from `context`. The field is only passed
through and is never used for retrieval. Because the numbers match closely, this is very likely the authors' data,
but the exact split is not confirmed by the release.

Commands (cwd `codebase/`, after `scripts/prep_data.py data_raw codebase/reproduce/dataset`):
```
# LLM server (serve_slm.sh not used: its cleanup does `ps aux | grep 'vllm serve' | xargs kill`, i.e. kills every
# vllm server on the node). Same model, also served under the alias 'finetune' (= frozen base model, i.e. w/o TD):
vllm serve Qwen/Qwen2.5-7B-Instruct --served-model-name Qwen/Qwen2.5-7B-Instruct finetune --port 8003 --gpu-memory-utilization 0.3
python scripts/forward.py 8001 8003      # the non-'FT' modes call the LoRA server on hard-coded port 8001
# main w/o-TD runs (--ab FT = integrator uses the base LLM instead of the LoRA student)
python CIRAG.py --dataset {2wikimultihopqa,hotpotqa,musique} --llm_name qwen2.5-7b-instruct --embedding_name nvidia/NV-Embed-v2 --ab FT
# Table-3-style granularity ablations, QA only on the saved ICI retrieval (scripts/run_ablations.sh)
python ../scripts/run_qa_ablation.py <dataset> {fact,sentence,passage,fact-sentence,fact-passage} query_solutions_<dataset>_..._ab_FT_1000_4_50.json
# w/o reranker, w/o TD (released --ab retri mode, integrator = frozen base via the 8001 alias)
python CIRAG.py --dataset <dataset> ... --ab retri
# diagnostics: release-default sampling (codebase_T1/ = codebase without my temperature=0 line);
# tuple-bug patch (FIX_PASSAGE_TUPLE=1) and an unpatched QA-only control (QA_JJ=1002): scripts/run_fixtuple.sh
```
Settings: L = 4 iterations, K = 10 retrieved docs/iteration, NV-Embed-v2 retriever and triple reranker,
Qwen2.5-7B-Instruct for OpenIE, integration and generation. OpenIE (NER + triples) was run once per corpus with
greedy decoding and cached. All 1000 questions were used for every dataset; nothing was scaled down.

Settings that differ from the paper:
- **Greedy decoding**: I added `temperature=0.0` to the two `VLLMServerModel` constructions, as stated in paper App. B.4. The release passes no temperature, so vLLM's default T=1.0 applies. A supplementary run with the release default is reported below.
- **Candidate triples per iteration**: the code hard-codes N = 10 (`candidate_facts[:10]` in `rerank_facts_gene_data`), while the paper states N = 30. I kept the code value.
- **No TD**: the integrator is the frozen Qwen2.5-7B-Instruct, i.e. the paper's "w/o TD" variant.

## Codebase completeness: MISSING_CORE

"CIRAG", Table 3) depend on it. The release contains no TD trajectory-generation-to-training pipeline, no training

ICI + ACMG inference pipeline is complete, and after import/config fixes it runs end to end in the w/o-TD mode (`--ab FT`).

## Discrepancies
Code vs paper:
1. **Decoding** (`VLLMServerModel` calls in `CIRAG.py`, `rerank_genedata_sllm.py`). The paper says greedy decoding for open models. The code passes no temperature, so vLLM's default T=1.0 sampling applies. This affects results: release default vs greedy is 48.0/57.0 vs 51.8/60.7 on 2Wiki and 24.8/35.4 vs 23.3/34.4 on MuSiQue. *minor*.
2. **Candidate triples N** (`rerank_facts_gene_data`: `candidate_facts[:10]`; the w/o-reranker mode uses all triples of the top-10 docs). The paper says N = 30 (App. B.4, Fig. 8). This likely affects results only slightly, since Fig. 8 reports low sensitivity to N. *minor*.
3. **Undocumented answer normalisation** (`qa_*`: every final answer is passed through `reanswer` = `extract_answer_prompt`). This is an extra LLM call that rewrites the answer into a "standard format", and its prompt includes a HotpotQA-style answer-type distribution and examples; EM/F1 are computed on its output. The paper (App. B.2) only describes EM/F1 following MuSiQue and mentions no LLM post-processing. It affects results (EM especially). *major* (evaluation protocol).
4. **Passage-level fallback bug** (`qa_ab_fact_sentence_paasage`, CIRAG.py:1711). `pred_ans = self.zzzqa_copy(...)` keeps the `(answer, docs)` tuple, so the normaliser receives the answer plus 5 raw passages. All other call sites unpack the tuple. The paper describes a(g_D) as the passage-level answer. This affects results: −3.3 EM / −2.8 F1 on 2Wiki (≈ −2.7/−2.2 against the control rerun), ≈ 0 on HotpotQA and MuSiQue. The paper's numbers appear to have been produced with the bug. I did not apply the fix to the reported numbers. *major*.
5. **ACMG sufficiency / "default" level**. The paper's Suf(a) checks a refusal ("Unanswerable"), the passage level is checked too, and it falls back to a(g_DOC) as a separate "default" (Fig. 3/5). The code checks `'No answer' in response` for triples and sentences, always accepts the passage answer, and has no separate default category. Effect on results is small or unknown. *minor*.
6. **Sentence provenance**. The paper maps each triple to its source sentence via the extraction provenance M^S. The code re-derives sentences with a word-overlap heuristic (a sentence must contain all words of ≥ 2 triple elements) and otherwise substitutes the triple string itself. The passage set is the provenance docs capped at 5 and padded with dense top-5 for the question. This affects results. *minor*.
7. **Integration prompt** (`prompt/prompts/filter.json`). The system prompt ends with "Here is an example:", but `make_template` never appends the demos stored in the same file, so the integrator runs zero-shot. The wording also differs from Fig. 11. This affects results. *minor*.
8. **Table 3 "w/o Triple" (S→P)** has no corresponding `--ab` mode in the release. It does not affect the reproduced results. *minor*.
9. **TD integrator**. The paper's main model uses a LoRA-distilled K_D. The release only contains the client for a `finetune` LoRA server; there is no training code and no checkpoint. This affects every headline result. *major*.

Paper-internal:
1. The CIRAG (with TD) 2WikiMQA result is 69.5 F1 / 59.0 EM in Table 1 but 68.1 / 58.9 in Tables 2 and 3. HotpotQA is 67.1/52.5 in Tables 1–2 vs 67.0/52.6 in Table 3. MuSiQue EM is 29.3 vs 29.5 (Table 3).
2. Appendix D (case study) says "DualRAG can dynamically retrieve information…" about what is CIRAG's case study.
