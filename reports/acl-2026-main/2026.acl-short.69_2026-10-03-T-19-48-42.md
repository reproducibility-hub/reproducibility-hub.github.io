# Reproduction report: DeGAML-LLM (ACL 2026 short, 2026.acl-short.69)

"Decoupling Generalization and Adaptation in Meta-Learning for Large Language Models" — Vetcha, Xu, Liu.
Code: https://github.com/nitinvetcha/DeGAML-LLM (linked from the paper). Generator checkpoints: HF `Nitin2004/DeGAML-LLM-checkpoints`.

## Verdict

- **Verdict: FAILED** (result match `NO_MATCH`, coverage `SUBSET`, codebase completeness `MISSING_CORE`)
- **Result match after fixes: NO_MATCH.** The released pipeline does reproduce the paper's *generalization-module* numbers well (when the code's hard-coded default generator is used), and the full RL adaptation loop matches the paper on ARC-c (52.8 vs 55.5) and comes close on ARC-e (70.1 vs 74.7). But on the other in-domain tasks the adaptation step gives far lower accuracy than reported (HellaSwag 25.0 vs 48.3, BoolQ 0.0 vs 58.7, WinoGrande 49.5 vs 52.8, SocialIQA 33.5 vs 55.1). The in-domain average the paper reports for DeGAML-LLM-0.5B is not reached: over the 5 tasks excluding PIQA, the paper has 58.0 and we get 39.5, which is below the paper's own reported numbers for MAML-en-LLM (48.8) and ABMLL (43.0) on those tasks (paper's No-Meta-Train 36.3, Union-Train 35.7). So the claimed ranking over the meta-learning baselines flips, judged against the paper's baseline numbers; we could not run the baselines ourselves. Most of the improvement over generalization that the paper attributes to adaptation does not appear: adaptation helps on ARC-c/ARC-e, but is neutral or harmful on HellaSwag, BoolQ, WinoGrande and SocialIQA.
- **Result match as released: DOES_NOT_RUN.** The unmodified repo can't run. Every adaptation script hard-codes `/home/nitin/SocraticX/...` paths. `mega.py` (the RL orchestrator) calls `/home/nitin/SAMKE/{BL,HG,TL,TS,LM,LS,PT,AC,AC_LS}.py`, which are not in the repo. Everything also depends on a "Prereqs" tree from the upstream Drag-and-Drop-LLMs (DnD) repo (LLaMA-Factory `vllm_infer.py`, `dataset_info.json`, LoRA template checkpoints, `criterion_weight.pt`, `configs/Qwen0.5`) that the release does not include. The TTS script hard-codes `tensor_parallel_size=2`.
- **Coverage: SUBSET.** Only Qwen2.5-0.5B-Instruct could be run: generator checkpoints are released for 0.5B only (7 tasks), and there is no generator-training script, so the 1.5B half of Tables 1/2 is impossible. The paper's baselines (No-Meta-Train LoRA, Union-Train LoRA, ABMLL, MAML-en-LLM) have no code. For the OOD sets other than SocialIQA there is no released generator for the target task and no recorded RL run, so we report only base, generalization and the paper's App. F.4 strategies (CodeMMLU adaptation was skipped for cost). Each setting was run once (the paper uses seed 999; vLLM sampling at T=0.95 makes runs stochastic).

## What the paper claims / what we targeted

Main claim (abstract, Table 1, Table 2): the decoupled framework consists of a prompt-conditioned LoRA *generator* (generalization module, trained offline on LoRA checkpoints) and an *RL policy LLM* that picks a test-time adaptation strategy (TTT / TTS / LoRA-mixing / latent SLOT) from 20 target-task samples, trained with ReST-EM on binary rewards. The paper claims this beats MAML-en-LLM, ABMLL and multi-task baselines on 6 in-domain and 6 OOD tasks at 0.5B and 1.5B. Table 2 also claims that both modules contribute (Base → Generalization → Adaptation).

We targeted the 0.5B rows of Table 1 (DeGAML-LLM row) and Table 2 (Base / Generalization / Adaptation): 6 in-domain tasks plus SocialIQA (the only OOD task with a released generator), and base/generalization on the other OOD tasks.

## What we ran

Environment: python 3.12, torch 2.5.1+cu124, transformers 4.49.0, vllm 0.7.2, llamafactory 0.9.2 (the DnD/LLaMA-Factory v0.9.2 pins), peft 0.12.0, accelerate 1.2.1, on 1×H200 (shared by several of our queues). Base model Qwen/Qwen2.5-0.5B-Instruct, Sentence-BERT `all-MiniLM-L12-v2` (what the code loads). All evaluations use the released inference path: LLaMA-Factory `vllm_infer.py`, `default` template, T=0.95, top-p 0.7, max 1024 new tokens. Accuracy is scored with the released `degaml/core/accuracy.py` ("AC"). Because the Latent family's scorer `AC_LS.py` is missing, every number is also given with DnD's `prepare/scripts/calculate_acc.py` first-character logic ("DnD", in parentheses). The released TTT/LoRA-mixing scripts call that scorer internally.

Protocol (as in `mega.py` and the paper's footnote 4): the generator is conditioned on the first 20 test prompts, replicated to the 128 the decoder needs. Adaptation and reward use those 20 samples (with labels, for the reward). The final number is inference on the full test split. For HellaSwag/WinoGrande/BoolQ the eval split is the labelled validation file, as in DnD's `dataset_info.json`.

1. **Base model** (no LoRA): `helpers/run_base.sh` (vllm_infer.py without adapter; the release has no script for this row).
2. **Generalization module only**: `python -m degaml.core.baseline --eval_dataset T --test_dataset T --num_samples 20 --inference_num_samples 0 --dataset_tag G` (`helpers/run_gen.sh`). G = `ARC-c` is the code default: `baseline.py` defaults to it and all adaptation scripts hard-code `qwen0.5lora__ARC-c4000.pth`. G = T is the generator trained with T held out (the paper's "leave-one-out").
3. **Full DeGAML adaptation = released RL loop**: `python -m degaml.core.mega --eval_dataset T --test_dataset T --num_samples 20 --gpu_groups 0`, with defaults of 2 iterations, 20 hypotheses and co-evolution (`helpers/run_mega.sh`). Each iteration runs: baseline on 20 samples; the policy LLM (Qwen2.5-0.5B, plus its ReST-EM LoRA from the previous iteration) proposes ≥20 JSON strategies; each is run on the 20 samples; reward = acc ≥ baseline; the best family's best config is picked; the policy is trained with ReST-EM (`train_policy.py`). After the last iteration the selected strategy is re-run with inference on the full test set. This used the code-default ARC-c generator.
   - **Fallback (documented deviation)**: for WinoGrande, ARC-e and PIQA, no iteration-2 hypothesis beat iteration 1's best, so `mega.py` *skips* the final full-test evaluation and outputs nothing. We then ran exactly what step 2B would have run for iteration 1's selected config (`helpers/mega_fallback.sh`).
4. **Adaptation with the per-task strategy the paper says the policy converged to (App. F.4)**, as a cross-check (`helpers/run_f4.sh`): ARC-e/PIQA/JAMA use TTT (25 steps, lr 1e-5); ARC-c/SocialIQA use SLOT (5 steps, lr 0.1); BoolQ/GSM/MATH use TS-LoRA-mixing (λ=0.5); HellaSwag/WinoGrande/DivLogicEval use TTS (20 adapters, max-confidence).

## Discrepancies

Code vs paper:
1. **Generator used for every task (major).** The paper says in-domain tasks are evaluated leave-one-out (footnote 7), and 7 per-task held-out generators are released. But all adaptation scripts hard-code `qwen0.5lora__ARC-c4000.pth`, and `baseline.py` defaults to `dataset_tag="ARC-c"`. That generator was trained *with* ARC-e/BoolQ/HellaSwag/PIQA/WinoGrande LoRA checkpoints. The paper's Generalization numbers match the ARC-c generator (e.g. ARC-e 64.3 vs paper 63.2) and not the held-out ARC-e generator (28.3). This affects results.
2. **Adaptation is not meta-learned across tasks (major).** Paper Alg. 2 / App. C trains the RL policy over a *batch of meta-training tasks* and applies it to unseen tasks. The released `mega.py` instead trains the policy *on the target task itself*: rewards come from accuracy on the first 20 *test* items (with labels), and the policy prompt is hard-coded to describe ARC-Challenge for every task. The README's `train_policy --meta_train_tasks ...` CLI does not exist.
3. **TS LoRA mixing (major).** The paper (App. F.1, Wu et al. 2024) describes mixing two LoRA subspaces, "(A1+A2)(B1+B2)" in the policy prompt. The code instead overwrites both halves of each `lora_A` with λ·A[:r/2] + (1−λ)·A[r/2:], so at λ=0.5 the adapter is effectively rank-4.
4. **TTS (major).** The paper says adapters are generated "from different prompt batches". The code generates N adapters from the *same* 128-prompt batch (only the order differs). Max-confidence uses the confidence of the first adapter that voted for each choice.
5. **Latent/SLOT evaluation protocol (major).** It uses a different prompt (`"Question: …\nAnswer:"`, no system prompt or chat template), greedy decoding and 128 tokens, whereas all other rows use LLaMA-Factory's template with T=0.95 and 1024 tokens. Its scorer `AC_LS.py` is missing. Under AC.py the F.4 ARC-c SLOT run scores 24.2, under DnD's first-character scorer 53.4.
6. **Missing final evaluation (major).** If no hypothesis in the last iteration beats the previous best, no full-test number is produced (WinoGrande, ARC-e, PIQA). Step 2B also re-runs the selected config without the checkpoint chaining it was selected under (BoolQ, HellaSwag collapse). In iteration 2, TTS hypotheses always fail because `mega.py` passes `--base_adapter_path`, which `test_time_scaling.py` does not accept, and `num_lora_adpt: 0` proposals are not validated.
7. **Text encoder (minor).** The paper says Sentence-BERT all-MiniLM-L6-v2; the code and README use all-MiniLM-L12-v2.
8. **Hardware/TP (minor).** TTS hard-codes `tensor_parallel_size=2`; the vLLM memory fractions are hard-coded.

Paper-internal:
1. Table 1 reports DeGAML-0.5B MATH = 24.5 but Table 2 reports Adaptation MATH = 29.2 for the same setting (the Table 1 avg 34.2 equals Table 2's avg).
2. App. G text says adaptation adds "+8.3 in-domain, +27.8 out-of-domain for 0.5B and +12.6 in-domain, +33.1 OOD for 1.5B". Table 2 has +27.8% in-domain / +33.1% OOD for 0.5B and +8.3% / +12.6% for 1.5B, and these are relative %, not points.
3. Table 2's 0.5B Base MATH is 2.8 (with Generalization 24.1, "+760.7%"), but the shipped MATH file is 4-way multiple choice, where even our base model scores 32.3 (AC) / 17.4 (DnD).

6. **Bug fix (affects results)**, `test_time_scaling.py` max-confidence: (a) Qwen emits `[A` as one token, so the released log-prob extraction never fired and every confidence was −inf; (b) questions with all −inf confidences were silently *dropped* from the output, so accuracy was computed over the few remaining questions; (c) questions with no parsable answer were dropped too. We now strip `[` from candidate tokens, fall back to majority vote when no confidence is available, and keep unanswerable questions as wrong. As released (run with the held-out WinoGrande generator), F.4 WinoGrande TTS output **1 of 1,267** questions (accuracy 0/1). Fixed, with the ARC-c generator, it gives 49.9 with all 25,340 confidences finite. The TTT fix was applied before any RL-loop run. The TTS fix landed at 23:20 on Oct 3, so TTS hypotheses evaluated earlier inside the ARC-c and WinoGrande RL runs used the unfixed max-confidence code (none of them was finally selected).
7. Environment workaround outside the repo: vLLM 0.7.2 asserts when *other* processes free GPU memory during its profiling. In the env's `vllm/worker/worker.py` this assert was turned into a warning; it doesn't affect outputs.

## Other observations

- Selection uses labelled test items (the first 20 of the test split, which are also in the reported test set), and the "Generalization" adapter is conditioned on test prompts. The policy's reward signal is computed on 20 items, so the pass/fail threshold is a 5-point step. With temperature-0.95 sampling, many selections are noise: e.g. PIQA picked TTT with lr 0.1 at "100%", and HellaSwag/BoolQ picked configs that collapse the model.
- Base WinoGrande is 35.9 vs paper 50.2: the prompt lists "[A]/[B]/[C]/[D]" for a 2-way task and the base model often answers C. Base GSM-MC is 31.5 vs 15.2, and base MATH-MC differs as noted above.
- Compute: about 20 h wall-clock on one H200, with up to 5 of our runs sharing it. The 50-adapter TTS hypotheses the policy likes to propose dominate RL-loop time, since each needs 50 separate vLLM start-ups. F.4 HellaSwag TTS (20 full passes over 10,042 prompts, each ~1–1.5 h) was split across parallel streams with `helpers/tts_parallel.py` (same per-adapter call as the script). Two of those adapter passes were OOM-killed (each TTS inference child holds ~28 GB host RAM because it keeps top-15 log-probs for every token) and were re-run. The 20 files were aggregated with `helpers/tts_aggregate.py`, which gives byte-identical output to the script's own aggregation on WinoGrande.
- Shared-GPU incidents: early on, a few vLLM start-ups failed with OOM or the vLLM profiling assertion while several runs overlapped. Affected runs were detected (no fresh result file) and re-run: BoolQ LoRA-mixing, ARC-e TTT, the first ARC-e mega baseline, and the first round of mega runs. All mega hypothesis errors in the final runs are TTS proposals with `num_lora_adpt: 0` or the iteration-2 `--base_adapter_path` incompatibility described above.
