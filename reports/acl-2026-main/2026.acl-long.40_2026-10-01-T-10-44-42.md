## 1. What the paper claims and what I targeted

Uni-MMMU is a benchmark with 8 tasks (Jigsaw, Maze, Sliding, Geometry, Science (phys/chem/bio), Code rendering). It scores text and images with:
- programmatic parsers (maze, sliding);
- DreamSim (jigsaw);
- open-weight judges: Qwen2.5-VL-72B for geometry images, science and code; Qwen3-32B for geometry text.

The main result is Table 2: 6 unified models, 3 generation-only models and 3 understanding-only models.

**Target: Table 2, row "Bagel".** This is the only fully open unified model I could set up and run end-to-end within the budget. It needs both generation and understanding; one GPU had to cover about 1,900 generated images and about 3,000 model calls.

Not run:
- **Closed models** (GPT-4.1 + GPT-image, nano-banana, Gemini-2.5 Pro, Imagen 3/4): no API keys.
- **Table 4 ablation:** GPT only.
- **OmniGen2, Ovis-U1, Qwen-Image-Edit, FLUX-Kontext, Qwen2.5-VL-72B understanding-only:** open, but the release has no sampling code for them. Each would need its own hand-written adapter and protocol guesses (e.g. the Ovis-U1 image stitching). There was not enough GPU time after Bagel.

Ranking claims across models are therefore NOT_COMPARABLE.

## 2. What I did (exact pipeline)

1. **Environment** (one conda env, python 3.10):
   - `vllm==0.8.5.post1` (torch 2.6.0), `transformers==4.51.3`, `flash-attn==2.7.4.post1`, `dreamsim==0.2.1`, `cairosvg`, `qwen-vl-utils==0.0.10`, `openpyxl`, `gradio_client`.
   - The repo's `requirements.txt` is a frozen dump of an unrelated training env. It does not pin torch or transformers and includes xfuser, jupyter, etc., so I installed only what the evaluator and BAGEL need.
2. **Data:** `data.tar` from HF, extracted into `codebase/data` as the README says. Instance counts:

   | Task | Instances |
   |---|---|
   | jigsaw | 150 |
   | maze | 150 (149 after excluding the few-shot demo) |
   | sliding | 84 |
   | geometry | 140 |
   | science | 157 |
   | code | 200 |
   | **Total** | **880** (the paper says 885) |

3. **Model under test:** `ByteDance-Seed/BAGEL-7B-MoT` through the official BAGEL repo (`bagel_repo/`, `InterleaveInferencer`) with its official default hyper-parameters (README / `app.py`):
   - **Understanding:** greedy decoding, max 1024 new tokens.
   - **Editing** (any image in context): cfg_text 4.0, cfg_img 2.0, cfg_interval [0, 1], 50 steps, shift 3.0, renorm "text_channel".
   - **Text-to-image:** cfg_text 4.0, cfg_interval [0.4, 1], renorm "global".
   - Seed 42, re-seeded before every call.
4. **Sampling:** `repro_scripts/run_sampling.py <task> bagel` (cwd `codebase/`). It executes the released `sample_code_example/gpt/<task>.py` unchanged except for in-memory substitutions:
   - output dir `outputs/gpt` → `outputs/bagel`;
   - the jigsaw path fix;
   - the sliding `data_dir` placeholder;
   - optional processing order, used only to run 2–3 workers in parallel. Cases are independent and every call is re-seeded, so the order does not change outputs.

   The undefined hooks (`generate_text_from_context`, `generate_image_from_context`, `ContextItem`, `add_text`, `add_image_path`, `PROJECT_ID`, `LOCATION`) are injected from `repro_scripts/bagel_adapter.py`. All prompts, multi-step loops and file layouts are the released ones. Up to three BAGEL processes shared the H200 (`scheduler.py`, `supervisor.py`, `filler.py`). Sampling took about 24 h.
5. **Judges:**
   - `vllm serve Qwen/Qwen3-32B` (bf16, max_len 40960).
   - `vllm serve Qwen/Qwen2.5-VL-72B-Instruct-AWQ` (`--enforce-eager`, max_len 16384). The bf16 72B checkpoint (about 146 GB) does not fit one 141 GB GPU.
6. **Evaluation:** `repro_scripts/run_eval.py --model_name bagel --tasks <task>`. It imports the released `eval_ummmu.py` and runs its evaluators unchanged. Only `LocalTextLM` / `LocalVL` (in-process HF `generate`) are replaced by OpenAI-API clients for the vLLM servers, with the same messages, greedy decoding, same `max_new_tokens`, `enable_thinking=True` for Qwen3, and the released `find_first_json_substring` parsing.
   - `repro_scripts/aggregate.py` turns the summaries into `results_bagel.json`.
   - Code S/P are reported on the 0–100 scale as avg/5×100, matching the paper's normalisation (e.g. Bagel C.S 2.2).
7. **Evaluator sanity check:** an oracle submission (GT step images + GT moves, `outputs/oracle`) scores 100% on all maze and sliding metrics.

### Settings that differ from the paper
- **Vision judge:** Qwen2.5-VL-72B-Instruct-**AWQ** (official 4-bit) instead of bf16, for memory reasons. Both judges run under vLLM instead of HF `generate`; both are greedy, so outputs differ only numerically.
- **BAGEL adapter:** my own, since none is released. The paper's Bagel sampling setup (prompt adaptation, interleaving, thinking mode, token limits) is unknown beyond "official default values".
- **Data:** 880 instances vs. 885 in the paper.

## 4. Why the numbers do not fully match (likely causes)

1. **No released Bagel sampling setup.** The only sampling code is a GPT-oriented skeleton with undefined generation calls. How the authors fed interleaved contexts to Bagel (prompt wording, turn segmentation, thinking mode, max tokens, image resolution) is unknown.
   - The largest gaps are on outputs that are sensitive to exactly these choices: answer formatting (Jigsaw T), echoing the template (Code T), and solution length or rigour (Geo T).
   - I tested merging consecutive text segments into one BAGEL turn on code rendering. BAGEL still echoed the template or the SVG, so the gap is not an artefact of how my adapter segments text.
2. **Judge quantisation.** The vision judge is AWQ 4-bit, which can shift binary judgments (Science T/I, Geometry I, Code). The Code-T hallucination is a judge weakness that a bf16 judge might share.
3. **Stochasticity.** I use greedy decoding for text and a fixed diffusion seed. The paper does not report seeds or variance.

## 5. Codebase completeness: MISSING_SCRIPTS

The evaluator (`eval_ummmu.py`) is complete and runs once the judges are served. The sampling side, i.e. running any model over the benchmark, is not implemented:

- **Missing model hooks.** `sample_code_example/gpt/*.py` call `generate_text_from_context`, `generate_image_from_context`, `ContextItem`, `add_text`, `add_image_path` and reference `PROJECT_ID` / `LOCATION`. None of these are defined anywhere in the repo, so the scripts crash with `NameError`. Even the GPT example has no API code. No scripts exist for Bagel, OmniGen2, Ovis-U1, Qwen-Image-Edit, FLUX or the understanding-only models.
  - **Written by me:** `repro_scripts/bagel_adapter.py` (BAGEL backend for these hooks) and `repro_scripts/run_sampling.py` (executes the released scripts with the hooks injected).
- **`jigsaw.py` path bug (results-affecting, silent).** `resolve_under_dataset()` prefixes `DATASET_DIR` to metadata paths that already start with `./data/jigsaw_dataset_2x2ref/`. Every item fails with `FileNotFoundError`, the error is caught, and the evaluator then scores 0.0 / 0.0 (verified). Fixed by returning the path unchanged (in-memory substitution in `run_sampling.py`).
- **`sliding.py`:** placeholder `data_dir = "path_to_ummmu"`; set to `"."`.
- **`code_rendering.py`:** `json.dumps` of the returned image path requires a `str` (a `Path` crashes). `science.py` instead calls `.relative_to()` on it, so it requires a `Path`. My adapter returns whichever type each script needs. `code_rendering.py` also imports `gradio_client` without using it; I installed it.
- **`eval_ummmu.py`:**
  - `base_path = "path-to-UMMMU-home"` and the DreamSim `cache_dir = "/mnt/petrelfs/zoukai/.cache"` are hard-coded; set via config in `run_eval.py`.
  - The judges are loaded in-process with `device_map="auto"`: Qwen2.5-VL-72B bf16 plus Qwen3-32B is about 210 GB and does not fit the stated "A100 80GB" or one H200. I replaced the backend with vLLM clients (same interface, same prompts, same parsing) and used the AWQ VL checkpoint.
- **`requirements.txt`** pins neither torch nor transformers or vllm and pulls in many unrelated packages; I installed a minimal compatible set.
- **No edits** were made to files in `./codebase`; `git status` shows only untracked `eval/` (plus git-ignored `outputs/` and `data/`). All fixes are in-memory substitutions or wrappers in `repro_scripts/`.

## 6. Discrepancies

1. **code_vs_paper, major (affects results):** maze and sliding sampling (`sample_code_example/gpt/maze.py`, `sliding.py`).
   - Paper (App. A.1.1, A.1.2): the iterative text/image loop "continues until the model outputs the final sequence of path actions".
   - Code: the loop runs exactly k = len(ground-truth path) iterations (`load_gt_moves_and_k`). The model is therefore always given the ground-truth number of steps, and the image count always equals the GT length.
2. **code_vs_paper, minor:** `sliding.py`.
   - Paper: "given the initial and goal states" as images.
   - Code: only the initial image, plus the text "Final state is exactly the same as example". All goals are the same solved state, so the information is equivalent but the protocol differs.
3. **code_vs_paper, minor:** released data has 880 instances (jigsaw 150, maze 149 + 1 demo, sliding 84, geometry 140, science 157, code 200). The paper (Fig. 2) says 885.
4. **code_vs_paper, minor (affects runnability):** the paper says the judges run on the stated hardware, and the README says "at least A100 80GB GPUs". The released evaluator loads Qwen2.5-VL-72B (bf16) and Qwen3-32B in-process, about 210 GB of weights, so it needs multiple GPUs or quantisation.
5. **paper_internal:** the Table 2 "Avg." column cannot be derived from the row values with any consistent rule:
   - mean over 14 columns, mean of per-task means, step- or sample-level variants all fail;
   - Bagel 22.0 vs 25.5 / 24.0; GPT 44.1 vs 54.1 / 50.1; only nano-banana (37.3) fits one rule.
6. **paper_internal:** the code link in the paper (`github.com/uni-mmmu/Uni-MMMU`, Sec. 5) differs from the repo given by the README and the HF dataset card (`github.com/Vchitect/Uni-MMMU`).

## 7. The paper's claims about Bagel

Claims that hold in our run:
- Bagel gets 0 on maze and sliding image metrics.
- Code image scores are very low despite much higher text-side scores (C.S/C.P about 1 on the 0–100 scale).
- Science reasoning (61.8 ≈ 63.1) is far above Science image accuracy (21.0).
- Generation is the bottleneck.
- Geometry: Bagel's Geo T (10.0) would still lead the paper's other open unified models (OmniGen2 5.7, Ovis-U1 3.5, Qwen-Image-Edit 8.5). The absolute value is about a third of the paper's 32.8.

## 8. Flags and notes
- No closed-source judge is involved: both judges are open-weight. The closed-model rows were simply not run (no API keys).
- No released predictions exist to compare against.
