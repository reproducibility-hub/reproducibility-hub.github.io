# Reproduction report — 2026.acl-long.2212
**Typology-Aware Multilingual Morphosyntactic Parsing with Joint Abstract Node Modeling** (Acar & Eryiğit, ACL 2026)

## Verdict
- **Verdict: PARTIALLY_REPRODUCED**
- **Result match (after fixes): MIXED**; **as released: DOES_NOT_RUN** (see below)
- **Coverage: SCALED_DOWN** (DEV split only, because the TEST gold is not public; ablation models trained for 10–11 of 20 epochs because of the 48 h budget)
- **Codebase completeness: MISSING_SCRIPTS**

Summary: I trained the proposed full model (multiAdpTypo) with the released code at the paper's settings (XLM-R-large, 20 epochs, lr 2e-5, batch 16, loss weights 2.0/2.0/1.5, abstract ramp 0.01→0.5, γ=2, 64-dim typology vector). Its **DEV** results (official UniDive MSP scorer, input tokenized with Stanza/UDPipe as the paper describes) match the paper's Table 1b/5b: macro MSLAS/LAS/FEATS **85.09 / 86.61 / 94.37** vs paper **85.35 / 86.85 / 94.49**. All 27 per-language numbers are within 1 point (largest gap: Turkish MSLAS −0.75). The "without abstract nodes" comparison (Table 4b/8b) is reproduced by stripping the abstract rows from the same model's output; per-language values match. The paper's own Table 4 averages are inconsistent with its per-language rows (see Discrepancies). For the ablations (Table 2b), trained for only 10–11 of 20 epochs, the full model is again the best variant, as the paper claims. However, adapters-only gives essentially no gain over the plain multilingual model (83.66 vs 83.63 MSLAS; paper 85.33 vs 85.12), and typology-only is the second-best variant (84.40) rather than the worst (paper 84.98). So the paper's account of *which* component helps is only partly reproduced. In addition, the released "URIEL" vector is a hash-based random vector (D1).
The paper's headline TEST-set claims (+3.23 MSLAS, +3.35 LAS, +1.78 FEATS over the shared-task leader) **could not be checked**: the official MSP test gold is not public (the shared-task repo only has `*.test.covered.conllu`, i.e. raw text). Test predictions were produced (`predictions/full_model/*.test.tok.pred.conllu`) but cannot be scored. The leader baseline (Améstica et al.) was not re-run (9 single-language XLM-R-large trainings would not fit the budget), so the "beats the baseline" claims are NOT_COMPARABLE. For reference, our reproduced DEV macro (85.09 / 86.61 / 94.37) is 3.5 / 3.5 / 2.2 points above the baseline DEV numbers the paper reports (81.58 / 83.08 / 92.15).

## Codebase completeness: MISSING_SCRIPTS
The method (joint model, trainer, predictor) is released and runs. The paper's evaluation pipeline is not: there is no tokenization step for the covered input, no evaluation driver over the 9 languages, no "without abstracts" switch, and no code for the Table 3 typology-internalization analysis. Several fixes were also needed (below).

Changes to the released code (uncommitted in `codebase/`, full diff in `codebase_changes.diff`):
1. `joint_msp_model/joint_model.py` — `_predict_parser`, `_predict_morph`, `_predict_abs`: copy the probability/argmax tensors to CPU (`.cpu()`) before the per-element Python loops. **Result-neutral** (byte-identical output verified on English dev). Without it, `_predict_morph` makes ~one GPU sync per (token × 671 morph labels), and prediction took >10 min per small file while a training job shared the GPU.
2. `joint_msp_model/inference/predict.py` — abstract-node head heuristic (non-Turkish): the nearest `UPOS=VERB` is now chosen only among **predicted content words**, falling back to the host token (the fallback the paper describes). As released, the nearest VERB can be a word the model predicted as *function* (HEAD `_`), and the official scorer then crashes on the whole file (`int('_')`) when that word follows the abstract node. With the full model this happens for Czech DEV (3 nodes) and Swedish DEV (1 node), so as released the Czech and Swedish DEV scores, and therefore the macro, cannot be computed. Polish and Portuguese also have 1 such node each, but there the function word precedes the node, so the file loads. The fix changes only these nodes; scores of pl/pt are unchanged to 2 decimals.

Environment / config-level:
3. `torch_struct` installed from GitHub commit 7146de5 instead of the pinned (broken) PyPI 0.5.
4. `setuptools<81` (needed for `import lang2vec`; it does not change behaviour, see discrepancy D1).
5. `codebase/official_data` symlink to the shared-task data (the manifests' relative paths).
6. README command path `joint_msp_model.training.joint_trainer` → `joint_msp_model.train.joint_trainer`.

Scripts I wrote (outside the release, in `tools/`):
- `tokenize_covered.py`, `run_tokenize.sh`: tokenization + UPOS of covered DEV/TEST (Stanza / UDPipe per the paper).
- `eval_run.sh`: runs the released predict.py per language/input.
- `score.py`: runs the official scorer, computes macro averages, and builds the "without abstracts" variant by stripping X.Y rows. It applies two output repairs **only if the official loader would otherwise raise**: (i) the abstract-head repair equivalent to change 2 (for files written before change 2: Czech DEV, 3 nodes); (ii) a sentence of >2 words in which the model predicted *no* content word at all gets its first token turned into a root content word with empty features. The scorer otherwise raises "no roots" for the whole file. This happened for Czech DEV in 2 sentences; a released-code bug, since predict.py has no such guard.
- `predict_released.py` (verbatim copy of the unmodified released predict.py) + `eval_released.sh`: as-released check.
- `paper_tables.py`, `make_comparisons.py`, `snapshot.sh`, `launch_ablations.sh`, `finish_one.sh`, `wait_dev.sh`, `abl_status.sh`, `tok_match.py`.

## Discrepancies
**code_vs_paper**
- D1 (major, affects results): *Typology input.* Paper: "URIEL feature vector … 64-dimensional URIEL vectors" (Sec. 3.1, 5). Code (`dataset.get_uriel_vector`): calls `from lang2vec.lang2vec import Lang2Vec`, but lang2vec 1.1.2 (the pinned version) has no `Lang2Vec` class (and would need ISO-639-3 codes, not 'cs'/'tr'). The resulting exception is swallowed and **every language gets a SHA256-hash pseudo-random vector** in [-1, 1]. So "typology" in multiTypo/multiAdpTypo is a fixed random per-language vector; no URIEL information reaches the model. This also undercuts the Table 3 "internalization of typology" analysis, whose code is not released.
- D2 (major, affects results): *Abstract-node head heuristic.* Paper (Sec. 4): eight languages attach the abstract node to "the nearest content word occurring above the host token"; Swedish uses the nearest verbal head, falling back to the host. Code (`predict.py`): Turkish → the host itself; all other 8 languages → nearest token with UPOS=VERB (any direction, no content check). On gold DEV, gold abstract heads equal the host in ≈100% of cases (cs/en/he/it/pt/sr), 85% pl, 94% tr; the code's nearest-VERB rule matches 83–100%, while the paper's literal rule would match only 8–46%.
- D3 (minor, affects results): *Abstract-loss ramp.* Paper Eq. 25–26: r(t)=min(1, t/T)^γ over training. Code: `T = batches_per_epoch × epochs`, but `t` is incremented on every `forward_loss` call. Flair calls it once per 2-sentence chunk (8× per 16-sentence batch), and also during dev-loss evaluation. So λ_abs reaches its maximum after ≈1/8 of training (~2.5 of 20 epochs).
- D4 (minor, affects results): *Extra per-language abstract-loss gate.* Code multiplies the abstract loss by a learnable, unregularized `sigmoid(abs_lang_gate[lang])` (init 0.5). It isn't in the paper's Eq. 24, and because it only scales a positive loss, gradient descent pushes it down (0.50→0.49 after epoch 1 at lr 2e-5).
- D5 (minor): the word-type head's "locked dropout" (Sec. 3.2) is a plain `nn.Dropout(0.5)` in the code.
- D6 (minor): predict.py reads UPOS from the input file for the VERB heuristic (gold UPOS when the input is gold-tokenized; Stanza/UDPipe UPOS for covered input). The paper doesn't mention a POS dependency.

**paper_internal**
- P1: Table 4 / Table 8 "without abstracts" macro averages don't equal the mean of the per-language rows in Table 8: DEV MSLAS/LAS/FEATS reported 82.21 / 84.14 / 90.97 vs 82.99 / 84.47 / 92.44 recomputed; TEST 82.61 / 84.63 / 91.04 vs 82.39 / 83.93 / 92.06. The text's "+3.52 FEATS on DEV, +2.76 on TEST" gains are therefore overstated (≈+2.05 / +1.74 from the per-language rows). Our stripped-abstract DEV macro (82.95 / 84.42 / 92.36) matches the recomputed values, not the reported ones.
- P2: Table 2 / Table 6 multiTypo macro averages don't equal the means of Table 6's rows: DEV 84.98 / 86.55 / 94.35 reported vs 84.74 / 86.35 / 94.22 recomputed; TEST LAS 85.71 vs 85.49, FEATS 93.55 vs 93.67.

- Training appears deterministic per seed: the seed-42 multiTypo run had exactly the same running loss at iteration 314 (4.18079479) as an earlier aborted attempt with the same config. With seed 42 that config diverged in epoch 1 (an XLM-R fine-tuning collapse); with seed 1 it trained normally.
