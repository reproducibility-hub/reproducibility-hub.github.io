# Reproduction report: FADE — Efficient Learned Data Compression via Dual-Stream Feature Decoupling (ACL 2026, 2026.acl-long.324)

## Verdict
- **Verdict: PARTIALLY_REPRODUCED**
- **Result match (after fixes): TREND_MATCH** (no fixes were needed). **As released: TREND_MATCH** (identical; no source edits).
- **Coverage: FULL.** The main compression-ratio experiment (Table 2, FADE row, all 7 datasets at full size) and FADE's efficiency row of Table 3 (Silesia) were both run. Table 8 (batch size on Silesia, bs 1024/4096) was run as an extra.
- **Codebase completeness: RUNS_AS_IS**

**Compression ratios reproduce essentially exactly.** All 7 Table-2 values are within 0.6% of the paper, 5 of them within 0.1%. Average: 3.711 vs 3.716. The extra bs=1024 and bs=4096 runs on Silesia (Table 8) also match.

**Why the overall label is only TREND_MATCH:** the throughput claims (Table 3) can't be checked number-for-number. We used an NVIDIA H200 on a 14-core Slurm allocation; the paper used an RTX 4090 with an AMD EPYC 7402. To get a fair comparison anyway, we reran the strongest baseline, EDPC, from its official code on the same node:
- FADE still has the highest **total** throughput (+7.1%) and the highest **decompression** throughput (+18.7%).
- Both margins are much smaller than the paper's +25.6% and +45.1%.
- EDPC **compresses** about 9.5% faster than FADE on our hardware. In the paper, FADE is 4.1% faster.

## What was done
- Paper: https://aclanthology.org/2026.acl-long.324.pdf. Code: https://github.com/huidong-ma/FADE (linked in the paper), cloned to `./codebase`.
- Environment: `conda create -p ./env python=3.12`, plus `torch==2.6.0` (cu126 wheel), `numba==0.62.1`, `numpy==2.3.4`, `thop==0.1.1.post2209072238` (the repo's `requirements.txt`). I also installed `gdown`, plus `absl-py` and `pandas` for the EDPC baseline.
- Data: the README's processed-dataset tarball (Google Drive `fade_datasets.tar.gz`, 7 files). File sizes match Table 1.
- Commands (paper defaults, which are also the code defaults: bs 512, timesteps 16, emb dim 32, lr 1e-3, cache dim 4096, FNR dim 8192, seed 0):
  - Silesia, run alone on the GPU with the default 8 workers, for throughput:
    - `python codebase/fade.py c hete_silesia silesia.cmp`
    - `python codebase/fade.py d silesia.cmp silesia.decmp`
    - `cmp` against the original: lossless OK.
  - The other 6 datasets were compression-only (CR doesn't need decompression), run as two parallel queues: `runs/run_queue.sh 6 <datasets...>`, i.e. `fade.py c <file> <out> -w 6`. fade.py reduces this to 4 workers because 512 % 6 ≠ 0. Worker count only affects speed, not CR.
  - Table 8 extra: `fade.py c hete_silesia s.cmp -b 1024 -w 4` and `-b 4096 -w 4`, run concurrently.
  - EDPC baseline: `python baselines_edpc/PEARencodingdic.py --input_dir hete_silesia --prefix silesia --gpu_id 0 --batch_size 512`, run alone on the node.
  - Latency / peak memory: `measure_eff.py` (my own script). It uses the same timing protocol as `fade.py` for both models: no_grad forward, 10 warm-up and 100 timed iterations at bs 512. Peak `max_memory_allocated` is taken over 3000 online-training steps.
- Settings that differ from the paper:
  - Hardware: H200 + 14 shared CPU cores, vs RTX 4090 + EPYC 7402. This affects all throughput, latency and memory numbers.
  - For the 6 large datasets, 4 workers instead of 8, and two runs shared the GPU. Speed only.
- Wall-clock time: about 11 h in total (23:24 to about 10:30). Compression runs took about 7.6 h of that.

## Codebase completeness: RUNS_AS_IS
- No source edits. The repo's `fade.py c/d` commands, the README's dataset link and default hyperparameters reproduced Table 2 directly.
- Scripts I wrote myself, outside the release:
  - `runs/run_queue.sh`: a loop calling `fade.py c` for each dataset.
  - `measure_eff.py`: same-protocol latency and memory measurement for FADE vs EDPC.
  - `make_status.py`: writes status.json.
- Baseline: the official EDPC repo was cloned to `./baselines_edpc` and run unmodified.
- Observations, none affecting the reproduction:
  - `fade.py` overwrites `CUDA_VISIBLE_DEVICES` with `--gpu` (default `0`). That would select the wrong device on multi-GPU Slurm allocations unless `--gpu` is passed; here Slurm had already set it to 0.
  - In the global stream, the rolling-cache GeGLU output is `.detach()`ed, so the GeGLU weights of Eq. 1 never receive gradients and stay at their random initialisation. The paper doesn't say whether they are trained.
  - Baselines other than EDPC (DZip, TRACE, PAC, MSDZip, SEP, gzip/7z/zstd/pbzip2) were not run. Their Table 2/3 numbers are taken from the paper.

## Discrepancies
1. **code_vs_paper (minor)**, `fade_model.py` `CoarseRefinement` vs Sec. 3.3, Eq. 7–8.
   - Code: H_mix is split into 2 branches of 256 dims, with a per-stream W_U per branch. The gate and residual use LN(H_mix) rather than H_mix. There is an extra learnable per-stream bias (B×2×256) that the paper doesn't mention.
   - Effect: the code is what produced the paper's numbers, so the results are not affected.
2. **code_vs_paper (minor)**, Table 3 "Params 15.20M".
   - The model actually has 21.77M trainable parameters.
   - 15.20M is thop's count. It omits the bare `nn.Parameter` W_U (2.10M) and the per-stream bias (0.26M). It also omits the 4.19M-parameter cache-initialisation GeGLU, which is called only at step 1.
3. No paper-internal inconsistencies were found. The average CR, the throughput improvements, and the harmonic-mean totals in Tables 2–4 are all arithmetically consistent.
