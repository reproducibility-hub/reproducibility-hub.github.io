**In one paragraph.** The benchmark, its released train/test splits and the evaluation code work. Base-model numbers reproduce almost exactly: Qwen3-VL-2B 39.14 vs. 38.84 avg, Qwen3-VL-8B 61.52 vs. 61.48. The paper's main claim is that GEVO (a 2B model after glyph-contrastive Stage 1, recognition SFT Stage 2 and 200-shot task SFT Stage 3) reaches **83.54** avg, far above plain SFT (**71.60**). That claim is not reproduced, for two reasons:

1. **The released model is not GEVO\*.** The public checkpoint `Rui1996/GEVO`, run through the authors' own evaluation code, gives **58.73** avg. Per task it matches the paper's **GEVO-Stage2 ablation row** of Table 2 (58.79) almost exactly (e.g. T2.3 89.37 vs 89.37, T3.3 95.45 vs 95.45, T2.1 28.16 vs 28.20), not the GEVO* row (83.54).
2. **No training code is released.** We re-implemented all three stages from the paper's description (Sec. 5.1, Appendix D). Our plain SFT baseline reproduces the paper's Qwen3-VL-2B-SFT: **72.56 ± 0.62** over 3 seeds vs. 71.60. Our full GEVO pipeline reaches only **68.11 ± 2.49**, *below* the SFT baseline, so the claimed +12-point gain of GEVO over SFT does not appear. Stage 1 is underspecified (τ, k, lr, which representation), so a different implementation could behave differently. But the authors' artifacts don't let anyone check that.

## What the paper claims (targets)
- Table 1 / Table 2: GEVO* (Qwen3-VL-2B + 3-stage glyph-driven fine-tuning) averages 83.54% over the 11 tasks, vs. 38.84 (Qwen3-VL-2B-Instruct), 61.48 (Qwen3-VL-8B) and 71.60 (Qwen3-VL-2B-SFT). The paper says GEVO beats SFT by more than 10 points and is significant under a Wilcoxon test.
- Table 2 ablations: GEVO-Stage1 (Stage 1 → 3) 58.31; GEVO-Stage2 (Stage 2 → 3) 58.79. Both are said to be worse than plain SFT.
- Table 3 (OOD generalisation): not attempted (see below).

## What was released
- GitHub `songruiecho/GEVO` contains `process.py` (benchmark construction), `dataloader.py`, `EVOICL_jiji.py` (zero-shot evaluation of many MLLMs), `utils.py` (accuracy), `cfg.py`.
  - **No training code**: no Stage-1 contrastive implementation, no LlamaFactory configs or data files for Stages 2/3, no CLIP negative-mining output.
- Google Drive: images (29,860 glyph images, 7,740 characters), `split_tasks` (train/test JSON for the 11 tasks plus an extra task4_1), and OOD images (148 characters). OOD *instructions* are not released.
- HF model `Rui1996/GEVO`: one revision; the card says it is GEVO built on Qwen3-VL-2B-Instruct.

## What we ran (all on 1× H200, transformers 4.57.1, torch 2.8.0, qwen-vl-utils 0.0.14)
Evaluation always uses the released pipeline (`dataloader.load_zero_shot_prompts` → `EVOICL_jiji.VICL` → `utils.cal_acc` / `utils.rank_acc`) on the released `split_tasks/*_test.json`. It uses batch size 16 and greedy decoding with max_new_tokens=20, as in the repo. It is driven by `scripts/run_eval.py`, which is the repo's `__main__` loop without the hard-coded `/home/lyj/...` path and `CUDA_VISIBLE_DEVICES="4"`:

```
cd codebase   # with symlinks split_tasks -> data/split_tasks, processed_images -> data/processed_images
../env/bin/python ../scripts/run_eval.py --name <name containing 'Qwen3-VL'> --path <model dir>
```

Training is our own re-implementation; the release has none:
- `scripts/sft.py --mode stage3`: Qwen3-VL-2B-SFT / GEVO Stage 3. 200 random training samples per task × 11 tasks = 2,200. Full-parameter fine-tuning of the language model (vision tower + merger frozen, as in LlamaFactory's defaults). lr 1e-5, 3 epochs, warmup ratio 0.1, cosine schedule, AdamW, effective batch 16 (8 × 2 accumulation), fp32 master weights + bf16 autocast. Answers use the instruction's own format; for T3.2 that is `1-楷书；2-篆文…`.
- `scripts/sft.py --mode stage2`: GEVO Stage 2. LM fine-tuning on **all** 26,874 T2.1 training samples, same hyperparameters (5,040 optimizer steps).
- `scripts/stage1_contrastive.py`: GEVO Stage 1, Eq. 1.
  - Trains vision encoder + merger; LM frozen.
  - Positives: all glyphs (5 script styles) of one character. One character per step, one epoch (7,079 characters with ≥2 glyphs). The paper's Fig. 15 shows ~7k steps.
  - Negatives: for each positive, the top-k most similar glyphs of *other* characters under CLIP ViT-B/32 (the encoder named in `cfg.py`).
  - z = mean-pooled merger output; cosine similarity.
  - Chosen hyperparameters (none are given in the paper): k=3, τ=0.1, lr=1e-6 (lr=1e-5 collapsed, see below).
- Pipelines: SFT = base→S3; GEVO-Stage1 = base→S1→S3; GEVO-Stage2 = base→S2→S3; GEVO = base→S1→S2→S3. The SFT and full-GEVO Stage 3 were run with 3 seeds (0, 1, 2; the seed changes the 200-per-task sample and the order).

The weaker Stage 1 is, the better the final model. The best GEVO configuration we found (73.33) is roughly at the SFT level (72.56 ± 0.62) and ~10 points below the paper's 83.54. Dropping Stage 1 entirely does best (77.00). So the specific contribution claimed for glyph-contrastive Stage 1 is not supported by our re-implementation.

Failed first attempt, kept for transparency: Stage 1 with lr 1e-5 and τ 0.1 **collapsed** all image embeddings to a single vector (pairwise cosine 1.000). The loss plateaued at the collapse value log((n−1+k)/(n−1)) ≈ 0.7–0.8. With that checkpoint, Stage1→Stage3 gave 29.82 avg (chance level; it predicts "金文" for every T1.1 image).
- Why it collapses: for the base model, the CLIP-mined negatives are *more* similar than the positives (mean cosine 0.948 vs 0.929). Collapsing lowers Eq. 1 from its starting value.
- The paper's Fig. 15 loss range (~0.7–1.0 smoothed) is in the same range as this collapse plateau. We cannot tell from the paper whether their run avoided it.

## Why it did not reproduce
1. The released model weights are for a different configuration than GEVO* (they reproduce the paper's GEVO-Stage2 row). The repo's own eval script evaluates a model called `Qwen3-VL-GEVO2_sft` at `saves/GEVO2_sft`, which also hints at a Stage-2 variant. Strangely, the released checkpoint's *vision* weights also differ from the base (relative L2 change 0.19%, LM 0.39%). The paper says the Stage-2 variant omits Stage 1 and Stages 2/3 only train the LM.
2. No training code, configs or training data lists are released for any of the three stages. Stage 1 is underspecified: τ, k, lr, batch composition, the representation used for z, and whether the "text char" template in App. D enters the representation. Stages 2/3 lack batch size, the number of Stage-2 samples (Fig. 16 shows only ~50 logged steps), and the scheduler. Our faithful-as-possible re-implementation gets the SFT baseline right but not GEVO.
3. Table 3 (OOD) was not run: only the OOD images are released, not the OOD instruction set the paper evaluated.

## Codebase completeness: MISSING_CORE

## Discrepancies
1. **code_vs_paper (major, affects results)**, HF checkpoint `Rui1996/GEVO`: the paper (and the model card) present it as GEVO (83.54 avg). Through the released eval code it scores 58.73, matching the GEVO-Stage2 ablation row (58.79) task by task.
2. **code_vs_paper (minor)**, HF checkpoint vision weights: the paper says the Stage-2 variant omits Stage 1 and Stages 2/3 update only the language model. The released checkpoint's vision encoder/merger weights differ from Qwen3-VL-2B-Instruct (relative change 0.19%).
3. **code_vs_paper (minor, no effect observed)**, `utils.cal_acc`: App. A says outputs with multiple candidate answers count as failures. The code uses plain substring matching.
4. **paper_internal**, Fig. 8 caption: it calls the framework "two-stage … GDEVA". The text (Sec. 5.1, App. D) describes three stages, and the method is named GEVO.
5. **paper_internal**, Table 4 MiniCPM-V-4_5 row: the reported Average is 24.96, the same as its T3.3 value. The mean of its 11 task numbers is 42.88.
