The paper's central claims hold in our runs:
1. Judge-side KV reuse breaks decision invariance. JCR is far below 100 for every reuse method in all 24 reuse cells. Our maximum is 86.2; the paper's is 89.2.
2. JCR and accuracy are decoupled. For example, on HumanEval (Progressive, no-shuffle), KVCOMM gets Acc 50.3 against 35.4 for dense prefill, while JCR is only 65.8.
3. Shuffling the candidate order sharply lowers JCR for KVCOMM and PAL-KV. This holds in all 12 method/dataset/regime pairs: 75.8→37.3 (MMLU-P), 86.2→51.0 (GSM8K-P), 65.8→21.7 (HumanEval-P), and so on.
4. Naïve reuse destroys GSM8K accuracy. We get 14–21% against 12–20% in the paper.
5. Masking cross-candidate attention under dense prefill collapses JCR to near or below chance (Table 2). We get 9.8–22.9; the paper reports 22.2–32.0.

## Why it is not fully reproduced
- **Scale-down:** GSM8K used 500 of 1,319 problems because of compute time. A first full-size attempt was killed by the shared 1 TB project disk quota, which other jobs filled; that crash is described under Problems encountered.
- **Number-level mismatch:** about 11% of compared numbers fall outside tolerance, mostly accuracies. Likely causes are small test sets, candidates regenerated in every run rather than fixed across methods (see Discrepancies), fp16 vs bf16, and a different GPU and kernel stack.
- **PAL-KV claim:** the "small but consistent no-shuffle gain" of PAL-KV over KVCOMM is not consistent here.
- **Not run:** Table 3 (EPIC, CacheClip and SamKV adaptations), Tables 4–5 and Figures 3–6 (attention diagnostics, anchor and agent counts, model scaling, pilot directions). The release contains no scripts or configs for these, so they were not attempted.

## Codebase completeness: RUNS_AS_IS
I made no edits to the released source. Notes:
- The `run_all_*.sh` scripts hard-code `CUDA_VISIBLE_DEVICES=1` and run everything serially. The GSM8K blocks are missing a trailing `\` before the `> file.out` redirect, so their output is not redirected; this is harmless. The README refers to `/home/large/KVCOMM/...` paths. ## Discrepancies
1. **Execution-side reuse and fixed candidate set** (code_vs_paper, major, affects results). §5.1 says: "we disable execution-side reuse and fix the candidate set: for each example we generate the candidates once with dense prefill and reuse the identical candidate texts for all judge-side methods." In the code, with `--execution_mode allow_kv_reuse`, the execution agents themselves run KVCOMM reuse (`KVCOMM/graph/graph.py` arun → agents' `generate_for_agent`; logs show "mode": "kv_reuse" for agents 1–4). Every method/run regenerates its own candidates, so Acc of reuse methods is not measured on the dense-prefill candidate set. JCR is still computed on identical candidates, because the dense judge pass happens inside the same run.
2. **Definition of Reuse** (code_vs_paper, major, affects the Reuse column). §5.3 says Reuse is "the fraction of candidate blocks (y_{1:N}) assembled via reuse … excludes the shared judge prefix". In the code, the judge decides reuse all-or-nothing per call; its judge-only rate is 5–52% in our runs. The paper's Reuse values match the code's cumulative reuse rate over **all agent calls**, execution agents plus judge (e.g. 44.18 vs 44.84 and 67.45 vs 66.96), which is not judge-only.
3. **Precision** (code_vs_paper, minor). §5.1 says "All models are run in bfloat16". `KVCOMM/llm/gpt_chat.py::_initialize_shared_resources` loads any model whose name contains "llama" with `torch.float16`.
4. **JCR denominator** (code_vs_paper, minor). §5.3 defines JCR as "the percentage of examples". The code (`evaluate_mmlu.py`, `run_gsm8k.py`, `run_humaneval.py`) excludes examples where either the reuse or the dense selection fails to parse (-1/None). Differences reach up to about 10 pt in a few cells, e.g. MMLU-Par KVCOMM no-shuffle 70.45 vs 60.78.

## Problems encountered (environment, not the release)
- The meta-llama repo is gated, so I used the weight-identical `unsloth/Llama-3.2-3B-Instruct`.
- The shared 1 TB project disk quota for `/scratch/user/<user>` was filled by other jobs at about 14:15 on 2026-10-10. All GSM8K runs died with `OSError: [Errno 122] Disk quota exceeded`. Partial outputs are in `old_gsm8k_quota_crash/`. I restarted GSM8K from scratch on the first 500 problems.
- With 12 runs in parallel the GPU ran out of memory. GSM8K KVCOMM/PAL-KV runs grow to about 23 GB each, and one run (`old_gsm8k_oom/`) hit CUDA OOM at launch; I restarted it from scratch. After that I used a GPU-memory-aware scheduler.
