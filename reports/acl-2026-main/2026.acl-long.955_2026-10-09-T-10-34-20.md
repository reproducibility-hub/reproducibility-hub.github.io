"Language on Demand, Knowledge at Core: Composing LLMs with Encoder-Decoder Translation Models for Extensible Multilinguality" (Bu & Feng)

Code: https://github.com/ictnlp/XBridge (linked from the paper; verified). Checkpoints: `ICTNLP/XBridge-base` (stage 1) and `ICTNLP/XBridge-SFT` (stages 1+2+3, MGSM), both LLaMA3-8B + NLLB-200-distilled-1.3B.

## What the paper claims, and what we targeted

The main claims: (1) the stage-1 cross-model mapping brings low-resource X→En / En→X translation of a frozen LLM close to the external NLLB (Table 1/4/5). (2) After stages 2+3, XBridge beats SFT / Translate-Test / MindMerger / LayAlign on MGSM (Fig. 3, Table 6), and the decoder output (XBridge_Dec) is close to the LLM's English reasoning. (3) Language-on-demand generation is stable (Tables 12, 13). Results are reported for 4 LLMs; checkpoints are released only for LLaMA3-8B, so all our experiments use LLaMA3-8B.

## What we ran (all in `env`, 1× H200)

1. **Stage-1 eval, released `XBridge-base`, FLORES-101 devtest, 10 languages, all 10×10 directions (Tables 4, 5, 12).** We used the README command (`run_stage1.sh`). The only change: `--test_langs` → `--trans_langs`, because the script's real argument name differs from the README (CLI only). Scored with spBLEU (`sacrebleu tokenize="spm"`, i.e. flores101, as in MMT-LLM's BLEU evaluator; `scripts/score_flores.py`) and COMET `Unbabel/wmt22-comet-da` (`scripts/comet_flores.py`).
2. **NLLB reference row (Table 4/5).** `facebook/nllb-200-distilled-1.3B`, greedy (`scripts/nllb_flores.py`). This was a sanity check of the metric setup. The "NLLB-200-1.3B" row in the paper is evidently the distilled 1.3B model, which is also what the released configs use.
3. **Base LLaMA3-8B 1-shot FLORES baseline (Table 4/5 "LLaMA3-8B" row).** Approximation of MMT-LLM's default setup (`scripts/llm_1shot_flores.py`): template `</E></X>=</Y>`, one random dev example with seed 43, greedy decoding, max 100 new tokens, keep the first line. The paper does not give template, seed or post-processing, so this row is marked NOT_COMPARABLE.
4. **MGSM eval, released `XBridge-SFT` (Table 6).** README command (`run_mgsm.sh`, `inference_xbridge_stage2_and_3.py`) on `juletxara/mgsm` test (250 per language). It was run twice: unmodified (stopped after English once the bug was confirmed), then with the 2-line fix (see below).
5. **Language-on-demand MGSM (Table 13)** with `XBridge-SFT`. The decoder is forced into all 10 output languages for each query language. This needed our own script (`scripts/mgsm_lod.py`), which reuses the released prompt, decoding and answer extraction.
6. **Re-training stages 2+3 from the released stage-1 checkpoint (scaled down), then MGSM eval.**
   - We wrote the missing training loop, `scripts/train_xbridge.py`. It only builds batches in the format the released `forward()` expects and runs AdamW; the losses and freezing are the released code's.
   - Data: the paper's source, the LayAlign MultilingualMath `metamath_615k.json` (Google Drive link from the README). Sampled 30K/language × 10 languages = 300K, as in the paper.
   - Stage 2: trains only `Mapping_enc` with the LLM CE loss. 1 epoch over the 300K (paper: 3 epochs); lr 2e-5, effective batch 128, linear schedule with 3% warmup; bf16 autocast over fp32 weights; gradient checkpointing; ~10.3 h.
   - Stage 3: trains `Mapping_dec` plus the decoder cross-attention with 0.5·CE_dec + 6·OT. λ values are from the released `XBridge-SFT` config.json; the paper says λ2 = 1. Data: 5K/language = 50K, with target-language responses translated from the English responses by NLLB-200-3.3B, line by line, greedy (`scripts/translate_responses.py`; the paper uses 30K/language). 3 epochs; ~1.3 h.
   - Evaluated with the (fixed) released MGSM script.

### Settings that differ from the paper

- Stage 2: 1 epoch instead of 3 (data size the same).
- Stage 3: 5K instead of 30K samples per language, our own NLLB-3.3B translation of the responses, and dec λ = 0.5 (released config) instead of 1.0.
- 1 GPU with gradient accumulation (16×8) instead of 8×H800; LR schedule and warmup not given in the paper (we used linear with 3% warmup).
- Stage 1 was **not** re-trained. It would need 3.6M trilingual samples × 3 epochs plus NLLB-3.3B translation of 3.6M sentences, which is infeasible in 48 h on 1 GPU. We used the released `XBridge-base`.
- Only LLaMA3-8B. No XL-Sum experiments: no checkpoint, and the data construction and prompt format are unreleased. No SFT / Translate-Test / MindMerger / LayAlign baselines: their code and configs are not in the release, so the "beats baseline X" claims can only be judged against the paper's own baseline numbers.

**Interpretation.**
- The released checkpoints reproduce the paper's LLaMA3-8B numbers essentially exactly: FLORES BLEU and COMET for stage 1, the 10×10 cross-lingual grid, MGSM LLM/Dec, and the 10×10 language-on-demand grid.
- The stage-1 claim holds against the paper's own (and our approximate) base-LLM row. Low-resource En→Bn rises from about 13 to 28.4 BLEU and En→Sw from about 17–19 to 34.7, approaching NLLB (32.8 / 36.3). High-resource X→En stays at the base-LLM level.
- Our own re-training of stages 2+3, which only needs the released `forward()`, gives an MGSM average of 59.8 (LLM) / 57.3 (Dec). That is above the paper's XBridge (56.7 / 54.5) and above all the paper's baselines (best: LayAlign 54.24).
- The direction of the claim therefore holds; the gap to the paper is in XBridge's favour, mostly on Bn/Ja/Sw. We do not know why it is higher. Possible causes are a different data subsample, 1 instead of 3 epochs in stage 2 (perhaps less overfitting), or LR schedule details.

## Why not fully reproduced

- **Training code is not released.** We wrote the training loop for stages 2/3 ourselves. Stage 1 (3.6M-sample trilingual OPUS-100 data built with NLLB-3.3B, 3 epochs) could not be re-run on 1 GPU in 48 h, so the stage-1 results rest only on the released checkpoint.
- **Only LLaMA3-8B checkpoints are released.** The MetaMath-7B, Aya-23-8B and Qwen2.5-7B-Instruct results, the ablations (Fig. 4, Tables 8–10), the M2M100 and NLLB-600M variants, and the 41 untuned languages (Table 11) all need stage-1 training and were not run.
- **XL-Sum (Fig. 3 bottom, Table 7) not run.** No checkpoint is released, and the data construction and prompt are not released.
- **Baselines (SFT, Translate-Test, MindMerger, LayAlign) not run.** No code or configs are in the release, so comparisons against them use the paper's numbers only.

## Codebase completeness: MISSING_SCRIPTS

The released code contains `modeling_xbridge.py`, which implements the architecture, the stage-wise freezing flags and all three losses (LLM CE, decoder CE, relaxed OT). It also has `inference_xbridge_stage1.py` and `inference_xbridge_stage2_and_3.py`. Missing: any training script, collator, data construction (trilingual OPUS data, NLLB-3.3B translated responses), stage schedule, XL-Sum evaluation and baselines.

Changes to the released code (left uncommitted in `./codebase`, see `git diff`):
- `inference_xbridge_stage2_and_3.py`, two fixes:
  - `forward()` returns a bare tensor, not a list, when only one target language is requested. The script then iterates over batch rows and `batch_decode`s them token by token, writing each row's tokens into the wrong files (`mgsm_en.{bn,de,...}.mt`). The XBridge_Dec accuracy becomes meaningless (En 0.4 vs 62.8). Fix: wrap the tensor in a list.
  - Zip the decoder outputs with `[lang]` (the query language actually requested) instead of `test_langs`.
  - The LLM-side accuracy is unaffected by the bug.

Scripts we wrote ourselves (outside the codebase, in `./scripts`):
- `train_xbridge.py` — the stage 2/3 training loop. Builds the augmentation-mask batches, decoder inputs/labels and OT `mt_labels`, then runs AdamW with grad accumulation. It loads with `device_map` because loading without it silently leaves the weights uninitialised: transformers' `base_model_prefix` handling misfires on keys starting with `model_`. It passes `output_hidden_states=True` for stage 3 and drops samples over 1,024 tokens.
- `prep_math.py` — samples 30K/language. `translate_responses.py` — NLLB-3.3B response translation for stage 3.
- `prep_mgsm.py` — converts HF MGSM to the `mgsm_{lang}.json` format the script expects.
- `nllb_flores.py`, `llm_1shot_flores.py` — reference rows. `mgsm_lod.py` — Table 13.
- `score_flores.py`, `comet_flores.py`, `mgsm_summary.py`, `build_comparisons.py` — scoring and aggregation.
- Runners: `run_stage1.sh`, `run_mgsm.sh`, `run_stage3_and_eval.sh`.
