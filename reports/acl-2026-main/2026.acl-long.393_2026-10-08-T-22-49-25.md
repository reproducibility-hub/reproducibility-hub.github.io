**Summary**
- **SP3F-7B and the baselines evaluate as reported.** Running the released eval tasks on the released **SP3F-7B** checkpoint, **Qwen2.5-7B** and **Qwen2.5-7B-Instruct** reproduces the paper's Table 1 and Table 3 numbers. All Qwen2.5-7B-Instruct numbers are within tolerance, as are 9 of 10 Qwen2.5-7B numbers.
- **One SP3F-7B number needed a longer context.** As released, the eval caps the context at 2048 tokens. With that cap, SP3F-7B's Belebele accuracy is 5 points low (62.1 vs. 67.5) because its verbose answers in bn/hi/te/yo/gu/pa get cut off before `\boxed{}`. With a 4096-token context, every SP3F-7B number matches (overall Acc 61.29 vs. 61.91).
- **The headline claim holds.** "SP3F-7B beats Qwen2.5-7B-Instruct" is true on all four tasks and on the unseen languages.
- **The RL stage (the method itself) could not be re-trained.** It needs GPT-4o-mini as the pairwise judge and no API key was available. Evidence for the method therefore comes from the authors' checkpoint, not from re-running stage 2.
- **The SFT stage (stage 1) was re-trained but does not match the paper's "+SFT" row:**
  - With the paper's learning rate (1e-5), SFT is far stronger than reported: overall Acc **50.3 vs. 21.7**. Belebele alone reaches 61.1, above Qwen2.5-7B-Instruct.
  - With the script's default learning rate (1e-4), SFT gets 24.3 overall, close to the paper, but the per-task numbers differ.
  - So the gain the paper attributes to the RL stage (+40 points over SFT) shrinks to about +11 points when SFT is run with the stated hyperparameters.

## What the paper claims / what was targeted

- **Main experiment (Table 1).** Models are evaluated on 18 training languages across 4 tasks: MGSM, MT-Math100, Belebele and Global-MMLU-Lite. Metrics are Accuracy (per-question mean over 8 samples) and Language fidelity (share of responses that are at least 70% in the target language, measured with lingua). Rows: Qwen2.5-7B, +SFT, +RLVR, SP3F-7B, Qwen2.5-7B-Instruct, and +Translate-Test.
- **Table 3.** SP3F-7B vs. Instruct on 8 unseen languages (Belebele, MT-Math100).
- **What the release contains:**
  - code: <https://github.com/lintangsutawika/sp3f> (eval tasks, SFT script, GRPO trainer with the pairwise judge);
  - training data: `neulab/SP3F-Training-Data`;
  - checkpoint: `neulab/SP3F-7B`.
- **What the release does not contain:** SFT or RLVR checkpoints.

What we ran:
1. Full Table 1 eval (18 languages × 4 tasks, n=8) for Qwen2.5-7B, Qwen2.5-7B-Instruct and SP3F-7B (released checkpoint).
2. Full Table 3 eval for SP3F-7B and Instruct.
3. Re-training of SFT stage 1 with `scripts/train_sft.sh` (1000 steps, batch 16, on the released data):
   - at the paper's LR of 1e-5;
   - at the script's default LR of 1e-4.

   Both were evaluated on Table 1.
4. A diagnostic re-eval of SP3F-7B Belebele with a 4096-token context for the 6 languages where outputs were truncated.

Not run:
- **SP3F stage-2 RL:** needs the closed GPT-4o-mini judge.
- **RLVR baseline:** 500 GRPO steps × 256 rollouts on one GPU did not fit the time budget next to the required evals.
- **Translate-Test:** no released script or config produces the self-translated inputs.
- **Tables 2 and 4, Figures 3–6:** they need the judge or models trained with it.

## What we did (commands)

- **Environment:** conda env at `./env` with Python 3.12 (yeval-harness requires Python ≥3.12). Installed packages:
  - `vllm==0.11.0`, `transformers==4.57.1`, `verl==0.5.0`, `lingua-language-detector`, `math-verify[antlr4_13_2]`, `datasets`;
  - `git+https://github.com/lintangsutawika/yaeval-harness`;
  - `hydra-core==1.3.2`, `omegaconf==2.3.0`;
  - flash-attn 2.8.3 wheel (cu12/torch2.8);
  - `pip install --no-deps -e codebase`.
- **Evaluation:** `scripts_ours/run_eval_model.sh MODEL ALIAS PORT "LANGS"`. It runs exactly the `yeval` call in `scripts/eval_task.sh` / `eval_task_math100_zh.sh`:

  ```
  yeval --model M --sample_args "n=8,temperature=0.7,top_p=0.8" --task "<task>_<lang>t//<lang>_system" --include_path tasks/ --api_base … --trust_remote_code --output_path runs/eval_scores/
  ```

  It runs against `vllm serve M --max_model_len 2048`, with one server per model and four tasks in parallel. For throughput, three servers shared the GPU (`--gpu-memory-utilization 0.29 --max-num-seqs 512`).
- **Aggregation:** `scripts_ours/aggregate.py`, `compare.py`, `tables.py`, `make_status_comparisons.py`.
- **SFT:** `scripts_ours/run_sft.sh`, the same `torchrun -m verl.trainer.fsdp_sft_trainer` command as `scripts/train_sft.sh`. Overrides:
  - `optim.lr` set to 1e-5 (paper) or 1e-4 (script default);
  - the released `train.parquet`;
  - 1 GPU, `offload_params=False`, console logger, and a 256-row validation subset.

  Each run took about 4.6 h on a shared H200.
- **Diagnostic:** `JOB_FILTER=^belebele_ VLLM_EXTRA="... --max-model-len 4096" run_eval_model.sh neulab/SP3F-7B ...` for bn/hi/te/yo and gu/pa.

**Settings that differ from the paper or the released scripts**
1. `logprobs=True` was removed from the sample args. It only feeds a logging field.
2. Qwen2.5-7B and the SFT models were evaluated on the 18 training languages only, because the paper reports no unseen-language numbers for them.
3. SFT validation used a 256-row subset; this does not affect training.
4. SFT used 1 GPU instead of 8×L40S; the global batch is still 16.
5. The 4096-context diagnostic is reported separately from the as-released numbers.

## Why not fully reproduced

- **Closed judge.** Stage-2 RL needs GPT-4o-mini as the pairwise judge and no API key is configured. We did not substitute an open judge, so SP3F training is not re-run; only the released checkpoint is evaluated.
- **SFT stage disagrees with the paper.** At the paper's stated LR it is much stronger than reported; at the script LR the per-task pattern differs.
- **Missing baselines.** RLVR was not run because of compute/time (one GPU, about 48 h total). Translate-Test has no released script.

## Codebase completeness: MINOR_FIXES

No source files in `codebase/` were edited (`git diff` is empty). An empty `codebase/.env` was created because the scripts `source` it, and hydra's run logs were moved out to `logs/hydra_outputs_sft`.

Issues found:
- **Dependencies.** Python ≥3.12 is needed because of yeval. `transformers` must be pinned below 5. `flash-attn` is needed by verl SFT but not listed. pip resolved hydra-core 0.11 / omegaconf 1.x, so these were pinned to 1.3.2 / 2.3.0. hydra needs antlr4 4.9.3 while math-verify needs 4.13.2, so 4.9.3 was put on a separate `PYTHONPATH` (`sft_pydeps/`) used only for SFT.
- **Eval script.** `scripts/eval_task.sh` doesn't parse the `-l`/`-s` flags the README uses (getopts has no `l` or `s`; the save path flag is `-d`) and never stops the vLLM server it starts. We replaced it with a job runner that issues the identical yeval command.
- **No Acc/Lang aggregation script is released.** We wrote `scripts_ours/aggregate.py` following the README and paper (0.7 threshold; zh = mean of cn and tw).
- **SFT script.** It needs config overrides: the data path (the HF dataset has no `prep_traces/...` layout) and the LR (script 1e-4 vs. paper 1e-5).
- **Math scorer quirk (as released).** `math_verify.parse` on bare LaTeX ground truths misses some correct answers on MT-Math100, costing about 1–5 points for every model. It was kept, since the paper's numbers agree with it.
- **Not runnable here.** The RL code needs an OpenAI-compatible judge endpoint. The local-judge path in `_switch_chat_template` appears broken (`response_dict` is only filled when `tokenize=False`).
