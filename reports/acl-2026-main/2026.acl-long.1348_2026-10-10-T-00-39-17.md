## Summary

- **The released code reproduces the paper's TLoRA accuracy numbers.** Every compared TLoRA number is within 1 point of the paper:
  - Math: GSM8K 55.50 vs 56.34, MATH 9.12 vs 9.08.
  - Code: HumanEval 22.6 vs 23.5, MBPP 41.0 vs 40.2.
  - Commonsense: all 8 tasks within 1 point; average 84.07 vs 84.21.
- **The standard LoRA baseline also reproduces** through the same pipeline: GSM8K 44.35/44.80, MATH 5.92/6.18, MBPP 35.7/35.7, commonsense average 83.89/83.57.
  - The exception is HumanEval: our LoRA gets 23.2 against the paper's 20.7.
- **The released code does not implement the method the paper describes.** The paper's method freezes the LoRA A matrix and trains only B (abstract, §3.2, §4.4, §4.5). In the release, `lora_A` is never frozen, so it trains about as many parameters as plain LoRA:

  | Task | Released trainable params | Paper (TLoRA) | Plain LoRA |
  |---|---|---|---|
  | Math | 318.8M | 171.71M (3-task average) | 319.8M |
  | Code | 324.3M | 171.71M (3-task average) | 319.8M |
  | Commonsense | 78.8M | 41.68M | 79.95M |

  The paper's headline efficiency claim ("significantly reducing the number of trainable parameters") therefore does not hold for the released code.
- **Freezing A, as the paper describes, gives the paper's parameter counts.** We added a 4-line `--freeze_A` flag. With it, the counts become 169.5M, 173.2M and 41.63M, essentially the paper's numbers.
  - Math and code results stay close to the paper: GSM8K 55.72, MATH 8.44, HumanEval 25.0, MBPP 40.7.
  - **Commonsense drops to 82.01 average**, which is below LoRA (83.89) on all 8 tasks.
  - So the paper's Table 2 accuracy matches the trainable-A code, while its parameter counts match a frozen-A model.
- **TLoRA's improvement over LoRA reproduces only in part:**
  - It holds clearly on GSM8K (+11), MATH (+2.5 to +3.2) and MBPP (+5).
  - On commonsense it is marginal for the released code (+0.18; paper +0.64) and reversed for frozen A (−1.9).
  - On HumanEval it flips for the released code (22.6 vs our LoRA's 23.2) but holds for frozen A (25.0). HumanEval has 164 problems, so one problem is 0.6 points.

## What we ran

Model: LLaMA-2-7B. The official `meta-llama/Llama-2-7b-hf` is gated and our access request is pending, so we used the weight-identical `unsloth/llama-2-7b` mirror (`models/llama-2-7b-hf/`). Its tokenizer and config files were restored to the original Llama-2 settings: no pad token, right padding, no `pad_token_id`.

Hardware: 1×H200, single process (`python <task>_train.py`). Effective batch sizes follow the paper: 128 for math/code (micro-batch 8 × 16 accumulation steps) and 32 for commonsense (8 × 4).

All hyperparameters are the release defaults, which match the paper's Tables 9 and 10:
- Math/code: r = α = 128, lr 2e-5, cosine schedule, warmup 0.03, 1 epoch, cutoff 512, q/k/v/o/gate/up/down, seed 42.
- Commonsense: r = α = 32, lr 1e-4, linear schedule, 1 epoch.

- Code data is the first 100K rows of `m-a-p/CodeFeedback-Filtered-Instruction`; the paper does not say how its "100K subset" was chosen.
- The commonsense evaluation script is our own.

### How we judged the claims
- **"TLoRA reaches the reported accuracy."**
  - Released code: yes, on all 12 compared metrics.
  - Paper-described frozen A: yes on math and code; about 2 points low on commonsense.
- **"TLoRA beats LoRA."**
  - Clear on GSM8K, MATH and MBPP, for both variants.
  - HumanEval: within noise; the released code loses (22.6 vs 23.2) and frozen A wins (25.0 vs 23.2).
  - Commonsense: marginal for the released code (+0.18) and reversed for frozen A (−1.88).
- **"With significantly fewer trainable parameters."**
  - Holds only with frozen A, which the release does not implement.
  - As released, the parameter count is LoRA's.
- **Overall: MIXED, both after our fixes and as released.** No single code variant reproduces both the paper's accuracy and its parameter efficiency.
- **Other baselines are NOT_COMPARABLE.** AdaLoRA, LoRA+, DoRA, OLoRA, PiSSA, LoRA-GA, CorDA and full fine-tuning were not run, because the release contains no code or configs for them. Claims of the form "TLoRA beats X" for these methods are therefore NOT_COMPARABLE.

### What we did not run, and why
- **Table 1 (T5-base on GLUE):** the release has no T5/GLUE code.
- **MT-Bench (Table 3):** needs FastChat plus a GPT-4 judge. Closed judge, no key, so not run (`CLOSED_JUDGE_UNAVAILABLE`). The chat training script exists, but its output could not be scored as the paper does.
- **Baselines other than LoRA, and full fine-tuning:** no released code or configs.
- **Appendix and ablation tables (4–6, 11–14):** out of scope given the time budget; the main tables were prioritised.

## Codebase completeness: MISSING_SCRIPTS

The TLoRA method itself (calibration, importance-based rank/alpha allocation, SVD initialisation of A) is implemented in `peft/src/peft/tuners/lora/{tlora.py,layer.py}`. Training scripts for math, code, chat and commonsense are released, as are evaluation scripts for math and code.

Missing or broken pieces:
- **No commonsense (Table 2) evaluation script.** We wrote `scripts/eval_commonsense.py`.
- **No T5/GLUE (Table 1) code** at all.
- **`peft/setup.py` is empty (0 bytes),** so the README's `pip install -e peft` fails. We worked around it with a `.pth` file that puts `codebase/peft/src` on the path (no source edit).
- **A is never frozen,** although the paper's method requires it (see Discrepancies).
- **The README's DeepSpeed launch is ineffective:** `--deepspeed` is accepted by `fire` but never passed to `TrainingArguments`.
- **README eval typos:** `python gen_vllm` and "`python math/eval_math.py`" are given for code. We used `code_process.py` followed by `evalplus.evaluate`, as the README text describes.
- **`commonsense_train.py` hard-codes the relative path** `commonsense_170k.json` for its calibration data. We ran it from `data/commonsense/`.
- **`requirements.txt`** pins unnecessary and conflicting packages (torch_xla, gptqmodel, auto_gptq, duplicate psutil pins). We installed the needed subset at the pinned versions, plus `cuda-nvcc` 12.1 into the env so that `deepspeed` (imported by transformers/trl) can load.

## Notes
- **Evidence for the parameter mismatch:**
  - `scripts/dump_allocation.py` replays the released calibration on the same 256 samples. It gives 318,834,176 A+B parameters for math. The released run reports 318,827,264; the 0.002% difference comes from tiny rank-rounding differences.
  - Its B-only counts are 169,522,432 (math) and 173,185,792 (code). These equal the frozen-A runs' counts exactly, and their average (171.4M) is about the paper's 171.71M.
  - The released allocation never assigns rank 0. Ranks range from 7 to 362 (math) and 7 to 331 (code).
- **Determinism:** all runs use seed 42 and are single runs, like the paper's.
- **Disk:** after evaluation we deleted the merged fine-tuned weights (`runs/*/model-*.safetensors`, about 13–16 GB each) to free shared scratch. Generations, eval outputs and trainer states are kept in `runs/` and `logs/`.
- **Environment:** the conda env at `env/` was removed at the end, as instructed.
