  * **Fixed-Token on CCEval-Python is far stronger than reported: 25.56 vs 22.01 EM.** The released Fixed-Token script uses the same configuration the paper calls the "Code Retrieval Context" (64-token query, 500-token chunks), which Fig. 4 / Table 1 report as 23.64.
  * As a result, **the headline "19.7% EM improvement over the best chunking method on CCEval-Python" shrinks to 3.4%** (26.42 vs 25.56 on the same 2,570 tasks). That gain is only marginally significant (exact McNemar p = 0.043; bootstrap 95% CI of the EM difference +0.12 to +1.67).
  * On the other four datasets, LC² beats Fixed-Token by only +0.25 to +0.88 EM, which is not significant (p = 0.09–0.72).
  * LC² is still ranked best on every dataset, and its gains over Fixed-Window, Split-Aggregate and Function-Level are large and significant.
* Overall: the method's absolute numbers and its first-place ranking hold. The size and significance of the gain over the strongest baseline (the paper's headline claim) does not hold, so the overall label is **MIXED**.

## Why this is not a full reproduction
1. **Headline claim.** The 19.7% EM gain over Fixed-Token on CCEval-Python depends on a Fixed-Token number (22.01) that the released Fixed-Token script does not produce: we get 25.56. The paper's own Fig. 4 / Table 1 value for the same configuration (23.64) is also lower than our re-run.
   - We found no code difference that would explain a weaker Python baseline. The same script reproduces Fixed-Token on Java, C# and RepoEval within 0.8 EM.
   - The paper may have used a different (non-asymmetric) query for this baseline, but the release does not include such a configuration.
2. **Data.** The CCEval raw repositories are not in the release (the README shows `data/cceval_rawdata` but it is absent). CCEval distributes them only by email. We reconstructed them from GitHub; 47 of 809 repos were unavailable, so CCEval baselines are on a subset.
3. **Not run.** No code is released for Table 1 (query/chunk-size sweeps), Table 3 (BM25, CodeRankEmbed, CodeRankLLM retrievers) or the Fig. 4 ablation, so those were not run.

## Codebase completeness: MAJOR_FIXES
The LC² path itself (retrieval scripts plus generate/evaluate) runs with only environment fixes. The baselines needed more.

Changes to released code (uncommitted in `./codebase`, see `git diff`):
- `retriever/treesitter.py`: added `get_function_bodies()` and a `with_body=True` option to `get_functions()`.
  - The Function-Level scripts do `for def_name, def_signature, def_body in get_functions(...)`, but the released `get_functions` yields only `(name, signature)`, and only for docstring-bearing functions, so the script crashes with a ValueError.
  - Our extractor returns every function/method definition. A docstring-only variant gave RepoEval 35.62 / 36.06 EM, far from the paper's 41.31 / 39.38. The all-functions version gives 41.38 / 39.31.
  - This fix changes baseline results, which is why the level is MAJOR_FIXES.
- `retriever/run_{cceval,repoeval}_unixcoder_function.py`: call `get_functions(src_path, with_body=True)`.

Environment-only fixes (no source edits):
- `vllm==0.11.0` (the latest vllm needs CUDA 13) and `transformers<5`.
- `VLLM_USE_FLASHINFER_SAMPLER=0`: the flashinfer JIT sampler needs nvcc, which is not present.
- `tree-sitter==0.25.2`: 0.26 segfaults in `Node.start_point`.
- faiss-cpu plus `shim/sitecustomize.py`, which makes `faiss.StandardGpuResources`/`index_cpu_to_gpu` return the CPU index. The pip faiss-gpu wheels have no sm_90 kernels ("no kernel image"), and conda `faiss-gpu=1.12.0` is built for numpy 1 and conflicts with vllm's numpy 2.

- Re-running LC² retrieval gives the same chunks as the released files. In about 10% of contexts the appended function definition differs, because the definition kept for a name depends on file glob order.

## Discrepancies
**code_vs_paper**
1. **(major) Context Expanding direction.**
   - Paper (§2.2, Fig. 2): the chunk is expanded with *preceding* content.
   - Code: `"cc": decode(ids[idx : idx + 2*CHUNK_SIZE])` appends the *following* 500 tokens.
   - Our preceding-context variant scores about the same (see the extra run above).
2. **(major) Function-Level baseline is not implemented.** The extractor the scripts call does not exist, and the scripts crash.
3. **(major) Fixed-Token on CCEval-Python.** The released script, with the 64-token query and 500-token chunks (the same as LC²'s Code Retrieval Context), gives 25.56 EM vs. 22.01 in Table 2. This changes the headline comparison.
4. **(major) Split-Aggregate block construction.** The code has `if not tmp_block:` where `if tmp_block:` is intended. The trailing partial block of each file is dropped, and an empty block is indexed whenever the last block was flushed. The query is the last 15 lines on CCEval but 10 lines on RepoEval. Our re-run of this code still matches the paper's Split-Aggregate numbers.
5. (minor) `CHUNK_SIZE = 500` and expansion of 500 tokens, versus 512 in the paper.
6. (minor) The paper says nucleus sampling with p = 0.95; `generate.py` uses temperature 0 (greedy).
7. (minor) Augmentation takes the last 3 call names and then filters them. The `called` list is never updated, so the same definition can be appended several times across the top-5 chunks.
8. (minor) Tasks with fewer than 5 cross-file chunks are silently dropped (CCEval-Py has 2,664 of 2,665 tasks; `project_cc_python/5191` is missing).

**paper_internal**
- The Fig. 4 caption says "CrossCodeEval (Python)", but the figure also plots C#.
