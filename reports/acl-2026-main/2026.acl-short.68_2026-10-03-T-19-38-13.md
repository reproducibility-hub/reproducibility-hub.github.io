## Summary
- The released code reproduces **Table 1** essentially exactly where we could run the paper's setting:
  - **Every Base number** (uncalibrated listwise reranker) that we ran on the paper's query set matches to all **4 decimals**: 27 of 27 cells (0.6B: 10/10, 8B: 7/7, 7B: 10/10).
  - **Every CapCal number** is within 1 NDCG point or 5% relative, except 0.6B Climate-FEVER, which is +1.9 points *better* than reported.
  - **Averages:** Qwen3-0.6B InD/OOD CapCal 0.5539 / 0.3567 (paper 0.5493 / 0.3560); Qwen3-8B InD 0.6896 (paper 0.6870); the 8B OOD average is not comparable because 3 of its 5 cells are 100-query subsets; Qwen2.5-7B InD/OOD 0.6614 / 0.4209 (paper 0.6623 / 0.4157).
- **The paper's claims hold:**
  - CapCal improves the 0.6B model on every one of the 10 benchmarks, by +2 to +13 points (ArguAna +13.4).
  - It gives smaller but consistent gains for Qwen3-8B.
  - Like the paper, we find it *hurts* Qwen2.5-7B on DL19/DL20 (−1.3 / −1.25 vs paper −1.23 / −1.31).
- **Two non-obvious settings were needed to get these numbers:**
  1. The placeholder string must be the paper's "This is a placeholder"; the code default is different (discrepancy 2).
  2. The DL19/DL20 candidate lists the paper evaluated are **not BM25 results**. The released loader silently falls back to the first 20 *judged* (qrels) documents, and that fallback is what reproduces the paper (discrepancy 1, **major**).

## What was attempted

**Target:** Table 1 (main results): NDCG@10 of *Base* (generative listwise reranking with constrained decoding, no calibration) vs *CapCal* for Qwen3-0.6B, Qwen3-8B and Qwen2.5-7B-Instruct on 10 benchmarks: TREC DL19–DL23 (MS MARCO v1/v2) and BEIR TREC-COVID, Climate-FEVER, NFCorpus, ArguAna, FiQA. Base and CapCal come out of the same run: the released `main.py` scores each query twice, once without calibration and once with it.

**Code:** https://github.com/USTC-StarTeam/CapCal (commit 4dcba97), cloned into `./codebase`.

**Environment:** conda env `./env` (Python 3.10), torch 2.14.1+cu130, **transformers 4.57.3** (pinned to <5 so that `from_pretrained` without a dtype loads fp32, as in the 4.x era the code targets), beir, ir-measures 0.4.x, rank-bm25, pyarrow, sentence-transformers<5 (pinned for beir/transformers compatibility). 1× H200.

**Data (all public, obtained as the loaders expect):**
- DL19/DL20: `whybe-choi/trec-dl-2019|2020` (HF) → `data/trec-dl-20{19,20}/{queries.jsonl,corpus.jsonl,qrels/test.jsonl}`.
- DL21–23: official TREC/MS MARCO files (`20{21,22,23}_queries.tsv`, `20{21,22,23}_passage_top100.txt.gz`, qrels from trec.nist.gov) + the MS MARCO v2 passage collection (`msmarco_v2_passage.tar`, 21.7 GB, gunzipped).
- BEIR: BEIR zips (queries/qrels) + BM25 top-100 candidate files `Soyoung97/beir-eval-bm25-top100` (HF), which match the file names and JSON schema that `beir_dataloader.py` auto-detects (`data/beir-eval-bm25-top100/{name}.jsonl`).

## As released vs. after fixes
- **As released** (no source edits; only CLI args, env vars and public data placed where the loaders look): DL19–DL23 and TREC-COVID run for all three models and give the numbers in the table. All of those are NUMBERS_MATCH, with either the paper's placeholder (passed via `--same_passage_text`) or the code default (0.6B DL19 0.5667, 8B DL19 0.7206; both within tolerance).
- NFCorpus, FiQA, ArguAna and Climate-FEVER **do not run as released**: `BEIRDataLoader` raises `ValueError: Unknown BEIR dataset` because `BEIR_DATASETS = ["trec-covid"]`.
- **After the fix** (whitelist extended; nothing else in the method or evaluation touched), these 4 datasets run and match the paper wherever our query set equals the paper's.

## Why not fully reproduced
Only compute. The released decoder scores identifiers with ~10 separate single-token forward passes per position, deep-copies the KV cache for each, and runs everything in fp32 and unbatched, for both the real and the placeholder prompt. That is ~800 sequential forward passes per query, about 30 s/query for Qwen3-8B on DL and 1.5–2.5 min/query on long BEIR passages with the GPU shared. The full grid (3 models × ~2,160 queries) did not fit into the 48 h budget on one H200. So Qwen3-8B on FiQA / ArguAna / Climate-FEVER was run on a 100-query sample, which is not the paper's query set.

Things that helped or that we worked around:
- **CUDA MPS** (private pipe directory inside the attempt dir) let concurrent processes share the GPU (~40% higher throughput).
- **Lustre page-cache warm-up** (`cat` of the safetensors) before each model load: mmap'd loading from the shared HF cache otherwise stalled for >10 min.
- **Silent CUDA OOM:** two runs hit CUDA OOM when too many processes shared the GPU. The code catches per-query exceptions and silently drops the query from the average. Both affected runs (8B TREC-COVID, 8B ArguAna-100) were killed, deleted and re-run with fewer concurrent jobs, and no final result contains a dropped query (`grep 时出错` over all final logs is empty).
