# Reproduction report — LiveCLKTBench (ACL 2026, 2026.acl-long.694)

## Verdict

| Field | Value |
|---|---|
| **Verdict** | **FAILED** (because codebase completeness is `MISSING_DATA`; the pipeline itself runs) |
| Result match (after fixes) | `DOES_NOT_RUN` on the paper's data. Every number is `NOT_COMPARABLE`: they come from the released 2026 data, not the paper's 2025 benchmark. The qualitative claims largely hold on the substitute data (see "Claims"). |

| Codebase completeness | `MISSING_DATA` |
| Flags | `PARTIAL_DATA` |

**Main reason.** The paper's experiments (Table 2, Fig. 3, Fig. 4) use a benchmark instance built from entities dated **2025-01-01 → 2025-08-31**, with 30 movie, 30 music and 20 sports entities (Appendix A, Table 3). That instance is **not released**. The only released data (HF `frett/Live-CLKT-Bench`) is a **different, later instance**:

- movie: 2026-01-01 → 2026-04-10, 47 entities, 35 val / 141 test QAs per language
- sports: 2026-03-20 → 2026-04-10, 48 entities, 41 val / 168 test QAs per language
- **no music domain**

The generator (`data_generation/`) needs OpenAI, TMDB/IMDB, YouTube and sports-API keys, none of which are configured here. Its LLM-generated QAs and translations could not reproduce the paper's instance in any case. I therefore ran the paper's whole evaluation protocol on the released 2026 data as a substitute.

**Most important observation.** I ran an untrained (no knowledge injection) control through the same pipeline, which the paper does not report. On the released data the untrained models score about the same as the CPT-trained ones on most settings (e.g. Gemma-2-9B movie: Overall 0.469 untrained vs 0.465 trained; Qwen2.5-7B movie: 0.416 vs 0.428). Where training does help, it is mostly because the base model refuses to answer sports questions about "unknown/future" games (parse failures), not because the facts were learned. A memorisation probe confirms how weak the injection is: after 5 epochs, the CPT'd Qwen2.5-7B completes the exact score of only 6% of its sports training documents (0% before training). So on this data the Overall/Transfer scores mostly measure what models can answer from the question and options alone, not transfer of injected knowledge.

## What was run

Environment: conda env at `./env` (Python 3.11, torch 2.13, transformers 5.17, peft 0.21.2, vLLM 0.31.0), 1× H200.

Data: `huggingface.co/datasets/frett/Live-CLKT-Bench` → `./data/hf/{movie,sports}/{en,ja,fr,es,zh}/{train_doc,val_mc,test_mc}.jsonl`.

For each model × domain × source language (`scripts/run_all.sh`):

1. **Knowledge injection, using the released `codebase/demo_experiment/cpt.py`:**
   ```
   python codebase/demo_experiment/cpt.py --model_name <hf_id> --train_file data/hf/<dom>/<L>/train_doc.jsonl \
      --output_dir models/<model>/<dom>/<L> --batch_size 1 --learning_rate 5e-4 --num_train_epochs 5 \
      --gradient_accumulation_steps 2 --rank 16 --alpha 32 --dropout 0.1        (WANDB_MODE=disabled)
   ```
   Settings are the paper's (§4: LoRA r=16, α=32, lr 5e-4, dropout 0.1, batch 1, 5 epochs). Gradient accumulation 2 comes from the README command; the paper doesn't mention it (ablation below). fp16 + GradScaler as in the code.
2. **Inference** (`scripts/vllm_lora_infer.py`, my own script): a batched vLLM replacement for `lora_inference.py`. It uses the same prompt (question + the released instruction suffix), the same chat template, greedy decoding (paper: temperature 0) and max 64 new tokens. It runs on the val and test sets for all 5 epoch checkpoints, plus the untrained base model as a control.
   - Fidelity check against the released HF `lora_inference.py` on two checkpoints (Qwen2.5-7B movie/en ep1 and sports/en ep5, val sets): identical answer letter on 174/175 and 203/205 items; accuracy HF 0.571 vs vLLM 0.566, and 0.390 vs 0.400.
3. **Scoring** (`scripts/aggregate.py`): the released `demo_experiment/eval.py::cl_kt_eval` (imported, unmodified) computes Overall = A/(A+B+C+D) and Transfer = A/(A+B) per (Ltrain, Ltest) pair.
   - **Checkpoint selection** (paper: "intermediate checkpoints are validated, and the best-performing one is selected"; no code released): per (model, domain, source language), choose the epoch with the highest mean val Overall over target languages ≠ source.
   - Table 2 mean ± std is over the 20 ordered pairs with Ltrain ≠ Ltest.
4. `scripts/analysis.py`: per-language, asymmetry and base-model analyses. `scripts/probe_memorization.py`: memorisation probe.

Models (Table 2): google/gemma-2-9b-it, Qwen/Qwen2.5-7B-Instruct, mistralai/Ministral-8B-Instruct-2410, mistralai/Mistral-Nemo-Instruct-2407, meta-llama/Llama-3.1-8B-Instruct, allenai/OLMo-2-1124-7B-Instruct.
Fig. 4 scaling: Qwen2.5-1.5B/3B/14B-Instruct and gemma-2-2b-it. Llama-3.2-1B/3B are gated and not accessible with the configured token.

| Item | Paper | Ours | Why |

## Codebase completeness: `MISSING_DATA`

- The paper's benchmark instance (2025-01→2025-08, Tables 2–3) is not released; the HF dataset is a different 2026 instance, and the **music** domain is missing entirely. Regeneration needs paid/keyed APIs (OpenAI GPT-4o-mini, TMDB/IMDB, YouTube, sports APIs) that aren't available, and LLM-based generation wouldn't recreate the same instance anyway.
- Missing scripts: no script for validation-based checkpoint selection, aggregation over language pairs or domains, Table 2, or the Fig. 3/4 plots. I wrote these myself (`scripts/aggregate.py`, `scripts/analysis.py`, `scripts/make_comparisons.py`).
- Changes to the released code (uncommitted diff in `./codebase`):
  1. `demo_experiment/cpt.py`: added explicit `target_modules=["q_proj","v_proj"]` to the non-OLMo `LoraConfig`. Under transformers 5, Ministral-8B loads as `model_type="ministral"`, which has no peft default, so training crashed (`ValueError: Please specify target_modules`). The value equals peft's default for mistral/llama/qwen2/gemma2, so behaviour for all other models is unchanged. Environment-compatibility fix.
- Scripts written outside the codebase:
  - `scripts/vllm_lora_infer.py`: batched vLLM version of `lora_inference.py`; same prompts and greedy decoding, verified against the HF script. It builds token IDs explicitly for tokenizers that use `MistralCommonBackend`: transformers 5 re-encodes the `"<s>[INST]…[/INST]"` text as plain text, which garbled the prompts. My first Mistral-family run produced mostly empty outputs (kept in `preds_buggy_mistral_tok/`). The released `lora_inference.py` would hit the same problem under transformers 5.
  - `scripts/run_all.sh`, `run_all_ga1.sh`, `queue*.sh`: drivers. `scripts/probe_memorization.py`: memorisation probe.
- Environment workarounds: `VLLM_USE_FLASHINFER_SAMPLER=0` (no nvcc for FlashInfer JIT); `WANDB_MODE=disabled`; bf16 for Gemma-2 in vLLM.
- Other notes: `cpt.py` defaults (3 epochs, GA 4, dropout 0.2) differ from the paper and had to be set on the command line. The README inference example uses temperature 0.6 while the paper says 0 (the script's default of 0.0 matches the paper).
