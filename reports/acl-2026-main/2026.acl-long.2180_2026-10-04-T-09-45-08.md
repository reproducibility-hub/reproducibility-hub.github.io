## 1. What the paper claims
- **Table 1 (main):** single-domain MS Dialog (Movie / Restaurant / Taxi). DyBBT-{0.6B,1.7B,4B,8B} trained 500 epochs; success, reward and turns reported at epochs 50/250/500. It beats EIERL and DQN baselines (e.g. Movie, epoch 500, DyBBT-1.7B: 83.42 success / 53.77 reward / 16.12 turns).
- **Table 6 (App.) and Table 2 (ablation):** multi-domain MultiWOZ 2.1 with ConvLab-3 RuleDST and rule user simulator, 40-turn cap, 10K epochs. DyBBT-1.7B: Inform 89.6, Success 81.3, Book 85.3, Turns 15.6. DyBBT-8B: 91.2 / 84.1 / 86.9 / 14.6. Ablation "w/o System 2" (8B): 85.7 / 76.3 / 80.1 / 16.8.
- **Method:** S1 = Qwen3 + LoRA, trained by SFT (confidence-calibrated augmentation) then PPO. S2 = the same frozen base model generating 3 plans. Meta-controller rule: S2 if n(c) < τ·sqrt(log T) or p_S1 < κ, with τ=1.0, κ=0.7, cumulative visitation counts over a 5-bin cognitive state. S2 decisions with confidence > 0.9 are distilled into S1 every 10 epochs.

## 2. What the release contains (and does not)
- `DyBBT/DyBBT.py` is the policy, but key parts are placeholders or heuristics:
  - `update()`, `save()` and `load()` are `pass`.
  - In `DyBBT/train.py:update()` the policy update is commented out ("placeholder - would be implemented for PPO"). The training loop only samples dialogs, so there is no RL learning in DyBBT training.
  - S1 confidence is a hand-written formula of the cognitive state plus output formatting (`_calculate_system1_confidence`), not a model-predicted calibrated confidence.
  - When the S2 LLM output can't be parsed, S2 falls back to hand-written template "strategies" (`_system2_fallback_reason`), including non-existent acts such as `general-reassure` and `general-suggest`.
- `DyBBT/finetune/sft/*` (data prep + LoRA SFT) works after an env fix.
- `DyBBT/finetune/ppo/system1policy.py` (PPO for S1) is hard-coded to `LLM-Research/Llama-3.2-1B-Instruct` via ModelScope, not Qwen3, and `predict()` uses an undefined variable `s`.
- **MSDialog (Table 1) is impossible:**
  - No MSDialog user simulator or environment is wired to DyBBT. `convlab/util/custom_util_msdialog.py` imports `convlab.task.msdialog` / `convlab.env.msdialog_env`, which do not exist.
  - `ppo_train_msdialog.py` calls the MultiWOZ `env_config`.
  - `train.py` has no dataset/domain option (the README's `--dataset msdialog --domain taxi` flags are rejected).
  - The `EIERL/` folder (the baselines' DDQ-style movie/restaurant/taxi simulators) contains no DyBBT agent.
- No trained checkpoints are released, no S1 LoRA (`./models/system1_lora_finetuned` is referenced but absent), and no Table 1/6 logs.
- `data/multiwoz/` (needed by the ConvLab-3 rule user simulator) is missing from the repo. I copied it from the public ConvLab-3 repo.

Observations:
- With the released policy logic (Run A), DyBBT never completes a task (0/30). Every S2 LLM output fails to parse, so actions come from the hand-written fallback templates, which pick the first slot of the first (alphabetical) domain and aren't DB-lexicalised.
- With the paper-aligned repair (Run B), the SFT'd S1 alone reaches only about 5–6% success.

## 5. Discrepancies (code vs paper, paper-internal)
See status.json `discrepancies`. Main ones:
1. **major:** DyBBT training loop has no policy update (`train.py:update` placeholder; `DyBBT.update/save/load` are `pass`). The paper trains S1 with SFT + PPO and RL for 500/10K epochs.
2. **major:** S1 confidence is a hand-written heuristic (`_calculate_system1_confidence`), not the model-predicted calibrated confidence p_S1.
3. **major:** SFT confidence labels are `random.uniform(0.8, 0.99)` (`sft_train.py`, `sft_train_msdialog.py`). The paper describes augmentation (20% add / 60% substitute / 20% delete) with p ← p·(1 − n_mod/n) and a composite loss λL_a + (1−λ)L_p with λ=0.7. Neither the augmentation nor the composite loss is implemented: the code uses plain causal-LM cross-entropy.
4. **major:** S2 falls back to hand-written template plans when parsing fails. It selects the path by self-reported confidence; the paper says the path is "evaluated by the ratio of filled key slots".
5. **major:** S1 inference prompt in `DyBBT.py` (cognitive-state prompt, 4-field actions, no available actions, no chat template) differs from the SFT training prompt (= paper B.4.1), so a trained S1 adapter would be queried out of distribution.
6. **major:** Visitation counts are reset every dialogue (`init_session`). The paper says they are cumulative.
7. **major:** The PPO stage (`finetune/ppo/system1policy.py`) uses Llama-3.2-1B-Instruct, not Qwen3. Its reward is a hand-shaped slot-filling reward (+20 on done, −5 invalid, +1.5 per filled slot ...), not the paper's +2t / −t / −1 per turn.
8. **major:** No MSDialog environment/simulator exists for DyBBT (Table 1 not runnable).
9. **minor:** Config τ=2.0 vs paper τ=1.0. `max_turns` 50 vs paper 40 (multi-domain) / 30 (single-domain). `epoch` 100 vs 10K/500. Default `sft_train.py` model is Qwen3-0.6B.
10. **minor:** LoRA config in code has no `target_modules` (needs peft defaults → q_proj, v_proj for Qwen3). This matches the paper's q/v only with newer peft.
11. **paper-internal:** Table 1 Restaurant LLM_DP has identical success/reward at epochs 50/250/500 (a static policy) but turns 20.16 vs 29.16.
12. **paper-internal:** MultiWOZ average turns/dialog: 13.9 in the B.1 text vs 14.0 in Table 3.
