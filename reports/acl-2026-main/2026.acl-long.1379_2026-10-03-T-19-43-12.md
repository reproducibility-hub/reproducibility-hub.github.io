## Summary

On the full PolyMath-Low split (18 languages x 125 queries) with DeepSeek-R1-Distill-Qwen-7B and the released configuration, UL-XCoT's **own numbers reproduce**: accuracy **81.11%** (paper 83.8; strict numeric scoring 80.31%) at **3077.5 tokens/query** (paper 3092). The released SC (66.3 vs 66.8), UL-CoT (66.9 vs 65.5), CoT (57.2 vs 54.0), "w/o CLS" (84.0 / 5490 tokens vs 84.4 / 5560) and "w/o all modules" (86.0 / 7943 vs 85.2 / 7518) also land close to the paper, so the setup is faithful.

The paper's **comparative claims about the method do not hold** in the same runs:
- The released CLSP baseline (`CLSP_acc`, which in the code is UL-XCoT without DCP) reaches **84.84%** vs UL-XCoT 81.11% (paired diff -3.7 pts, 95% CI [-5.4, -2.0]); the paper reports CLSP / w/o DCP = 81.4 < 83.8. DCP saves ~23% tokens (paper ~21%) but costs accuracy instead of adding it.
- Removing the logic-space projection inside DCP (lambda=0, our approximation of "w/o ULM") or reversing the pruning direction to the paper's Eq. 11 changes neither accuracy (81.2 / 81.3) nor tokens (paper: w/o ULM 79.8, i.e. ULM worth +4 pts).
- Latency: on an isolated H200 (5 queries x 18 languages, released per-query loop) UL-XCoT takes 10.2 s/query vs 9.85 s without DCP and 7.47 s for SC; DCP's per-step Python monitoring overhead cancels its token savings (paper: 24.6 s vs 30.7 s on A6000).
- Supplementary PolyMath-Medium run (55 numeric-answer queries x 18 languages, max_tokens 4096 guessed): there DCP *does* behave as claimed - UL-XCoT 46.2% at 8389 tokens vs 45.7% at 11271 without DCP (-26% tokens, accuracy on par) and SC 40.0% at 12302 tokens - so the Low-level accuracy loss from DCP does not generalise; overall result match is MIXED.
- What does hold: large gains over monolingual SC/CoT/UL-CoT (+14.8 pts over SC, CI [+12.9, +16.9]) and much higher, stable accuracy on the low-resource subset (bn/ja/ko/sw/te/th: 81.2 vs SC 46.4), and fewer tokens than SC (-27% on Low; the paper's ">65% vs SC" is an all-level average we could not measure).

As released, the evaluation script cannot produce the paper's numbers: `eval_answer.py` reads output directories 0..17 as languages although they are query indices, so it scores only 18 of 125 queries (63.3% "overall" on our UL-XCoT outputs, with per-"language" numbers that are per-query), and it needs a GPT-4o-mini key for non-numeric answers.

## What was attempted

**Target.** The paper's central claim (abstract, Sec. 3.2, Tables 1/2/4, Figs. 3/4) is that UL-XCoT on PolyMath with DeepSeek-R1-Distill-Qwen-7B reaches competitive (best-average) accuracy while using far fewer decoding tokens / less latency than sampling baselines (SC, CLSP, AutoCAP), with stable gains on low-resource languages. We reproduced the **PolyMath-Low** part of Table 1 (all 18 languages x 125 queries, i.e. the full Low split), the corresponding Table 2 ablation rows, and the token-cost comparison, with the released code, model, data and hyper-parameters.

**Not run / scaled down (and why).**
- **PolyMath Medium/High/Top (rest of Table 1, all of Table 4 DW-ACC, Figs. 3/4 averages):** not run at paper scale (only a supplementary Medium run on the numeric-answer subset, see below). (i) 57-71% of Medium/Top gold answers are non-numeric and the release scores them only with a GPT-4o-mini judge (`utils/answer_judge.py`), no OpenAI key is available here (`CLOSED_JUDGE_UNAVAILABLE`); (ii) the per-level `max_token_nums` for these levels is not given (paper: "2048-10240", only Low=2048 is in `scripts/infer.sh`); (iii) compute: the DCP pipeline processes one query x one language at a time (the VoteManager requires the whole 9-trace batch of one request), giving ~7-9 query-language calls/min on one H200 even with 6-7 workers; the full Low split for one DCP method takes 5-8 h, the harder levels would take several times longer.
- **MMLU-ProX-Lite (Table 3, Fig. 5):** not run (time; secondary benchmark).
- **AutoCAP, ST-BoN, CLP baselines:** no runnable code. AutoCAP reads `dataset/polymath/new_RL-qwen-7B_correct_0.8_0.6/autocap_auxiliary_new/10240/auxiliary_set.json` which is not released and has no generating script; ST-BoN / CLP have no implementation in the repo. Claims relative to these are `NOT_COMPARABLE`.
- **Latency:** the paper measured latency on RTX A6000; we used an H200 shared by several worker processes, so absolute latencies are not comparable. Relative latency was measured separately on a common subset with one process alone on the GPU (see latency table).

**Settings that differ from the paper:** GPU (1x H200 shared by up to 7 vLLM workers vs RTX A6000); vLLM `gpu_memory_utilization` 0.15-0.2 and `max_model_len` 6144 for co-location (released: 0.9 / 20000; prompts+2048 tokens are far below 6144, so no effect on outputs); judge replaced by numeric/rule-based scoring (Low gold answers are all numeric); SC budget 9 (paper's stated protocol; shipped script uses 1). Everything else (model, data, seed, temperature 0.8, top-p 0.8, lambda 0.4, |L_par|=9, rho=0.7 as in `infer.sh`, max tokens 2048) is the released configuration.

## Codebase completeness: MAJOR_FIXES

The method (ULM projection, CLS routing, DCP pruning inside a vLLM 0.5.5 fork that exposes per-layer hidden states, voting) and the inference entry points are released and ran. No file inside `./codebase` was edited (the only untracked additions are the regenerated routing file `dataset/polymath/routing_results_polymath_ds7b_9.json`, the compiled vLLM `.so` files copied into `hidden_vllm/vllm/`, and `results/linguistic_embedding/`, all git-ignored or data). But the released evaluation is wrong in a way that changes the numbers, so a rewritten evaluation loop was required:

Issues / changes (all implemented outside `./codebase`, in `runs/`):
1. **Evaluation bug (affects results):** `process_query.py`/`ModelInference.inference` iterate `for lang_id, queries in enumerate(extended_queries)` where the outer index is the *query* (0..124) and the inner `query_id` is the *source language*; results are saved to `<diff>/<query index>/0.jsonl` with `"query_id": <language>`. `eval_answer.py` and `get_cost.py` read only directories `0..17` and treat them as languages, voting by `query_id`. Run unmodified on our full UL-XCoT Low outputs, the released evaluator reports overall 63.3% computed on only the first 18 of 125 queries, with "per-language" accuracies that are really per-query (e.g. "ja" = 0.0, "ar" = 1.0). Fixed by `runs/evaluate.py` (same extraction/voting/numeric comparison, all 125 directories, grouped by source language).
2. **Closed judge:** non-numeric predictions are judged by GPT-4o-mini (`utils/answer_judge.py`, requires `OPENAI_API_KEY`); without a key every such case scores 0. Replaced by numeric comparison plus a deterministic normaliser (PolyMath-Low gold answers are all numeric). Medium/High/Top cannot be scored faithfully.
3. **Missing routing artefact:** `dataset/polymath/routing_results_*.json` used by all inference scripts is not released (dataset/README says it must be regenerated); regenerated with the released `get_assistant_languages.py` (needs `results/linguistic_embedding/` to exist - created).
4. **Script/config mismatches:** `scripts/get_assislan.sh` writes `routing_results_polymath_ds7b_12.json`, `scripts/infer.sh` reads `routing_results_polymath_ds7b_4.json`, `CLSP_acc.sh` `..._new.json`, `self_consistency.sh` `..._ds7b.json`; device ids hard-coded to 0/1/5/7; `self_consistency.sh` uses sampling_size 1 (the paper's SC budget is 9). Used our own wrapper (`runs/run_shard.py`, `runs/launch.sh`) with the scripts' hyper-parameters.
5. **AutoCAP baseline data missing:** `autocap`/`autocap_cost` modes and `eval_answer.py --autocap` read `auxiliary_set.json` / `auxiliary_set_scores.json` that are not released and have no generator.
6. **Environment:** `environment.yml` pins torch 2.8 while the vLLM fork is v0.5.5 (requires torch 2.4.0, built CUDA kernels). We installed the official `vllm==0.5.5` wheel (torch 2.4.0+cu121), copied its compiled `_C/_core_C/_moe_C` extensions into `hidden_vllm/vllm/` and imported the fork's Python sources via `PYTHONPATH` (the fork only changes Python files); transformers 4.57.1 + accelerate 1.10.1 (needed for `dtype=` / `device_map`); a stub `pyairports` module (the PyPI package is broken and is imported by outlines); per-process `OUTLINES_CACHE_DIR` (the shared outlines sqlite cache got corrupted).
7. **Scripts written by us** (none changes method logic): `runs/run_shard.py` (sharding/resume/memory wrapper around the unmodified `process_query.py`), `runs/batched_baseline.py` (batched generation for the non-DCP modes, re-using the released query selection, prompts, sampling params and saving), `runs/evaluate.py`, `runs/summarize.py`, `runs/latency_subset.sh`, `runs/early_stop_paper_semantics.py` (control experiment only: copy of `utils/early_stop.py` with `if gid in winners` -> `if gid not in winners`), `runs/launch.sh`, `runs/queue.sh`, chain scripts.
