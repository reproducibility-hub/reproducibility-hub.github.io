| Codebase completeness | **MISSING_SCRIPTS** (core OSA re-weighting is released and runs; the domain-adapted (DA) estimator warm-up behind Table 2's "+OSA" rows is absent, as are all non-image-text tasks) |
| Flags | `BASELINE_STRONGER_THAN_REPORTED` |

**Summary.** The released OSA training code (zero-shot CLIP ViT-B/32 estimator, MS-COCO, 5 epochs, bs 256, lr 1e-5, 500 warm-up steps) reproduces the paper's own **zero-shot-estimator numbers (Table 12, "CLIP (w/o DA)")** on MS-COCO 1K/5K at 0/20/50 % noise: all 36 numbers are within tolerance, mostly within ±0.5 points. The worst gap is 5K i2t R@1 at 50 % noise (60.9 vs 62.4). The **Flickr30K numbers (Table 9, +OSA)** at 0/20/40/60 % noise are also all within tolerance. The worst gap is t2i R@1 at 60 % (71.8 vs 74.4).

However, the **plain CLIP fine-tuning baseline** (the same released pipeline with the OSA weights set to 1) is much stronger than the paper's "CLIP" rows. On MS-COCO it is +2 to +6 R@1 better. On Flickr30K at 60 % noise it is +14.6 to +16.7 R@1 better. So OSA's improvement is real and consistent at every non-zero noise ratio, but **much smaller than the paper claims**:
- MS-COCO 5K i2t R@1 at 50 %: paper +10.6 (+8.3 w/o DA); ours **+2.1**.
- Flickr30K i2t R@1 at 60 %: paper +20.9; ours **+3.1**.
- At 0 % noise OSA and the baseline are tied (±0.4).

The ranking (OSA ≥ CLIP; OSA robust to noise) holds; the magnitude ("huge gap", "severe performance drop" of the baseline) does not. Hence **TREND_MATCH**.

The headline Table 2 "+OSA" rows are identical to Table 12's "CLIP (w DA)" rows. They therefore use a domain-adapted estimator whose code is not released, so we compare them as NOT_COMPARABLE. Our zero-shot-estimator numbers would still mostly fall within 5 % relative of them.

## What was run

Environment: conda env at `./env`, Python 3.10, torch 2.1.2+cu121, torchvision 0.16.2, ftfy, regex, tqdm, Pillow, numpy<2, scipy, setuptools<70 (for `pkg_resources`). The README recommends Python 3.8 / torch 1.13.1 (cu117), which has no Hopper (H200, sm_90) support, so a newer torch was used. 1× H200; the node was shared (load average ~75), and training was CPU/dataloader-bound at ~9 min per COCO epoch.

Data:
- Annotation/noise splits from the README's Google-Drive link (NPC splits): `data/datasets/{MSCOCO,Flickr30K,CC120K}/annotations`.

- Flickr30K images from the HF dataset `nlphuji/flickr30k` (`flickr30k-images.zip`); all 31,014 names in `image_name.txt` were present.

Commands (wrappers `run.sh` / `run_f30k.sh`; queues `queue.sh`, `queue2.sh`, `queue3.sh`), exactly the README command plus logging/worker args:

Model selection follows the code: the best epoch on the validation set (1K mean R@1), then evaluation on the test set. Each setting was run with the code's default seed 99. A second seed (1) was run for the COCO 20 %/50 % OSA and baseline runs (see "Seed variance").

Noise-detection analysis (Tables 5/6) used my own script, `noise_detect.py` (not in the release). It takes the zero-shot CLIP estimator and the same β procedure as `main_clip.py`, scores all 566,435 training pairs, and defines ground-truth noise as "caption differs from `train_caps.txt`". The `<r>_clean_index.npy` files are *not* full clean labels: they are only a partial clean subset, about 40 % of pairs at r = 0.2.

Settings that differ from the paper:
- GPU: H200 instead of RTX 3090.
- Torch version (see above).
- Flickr30K training split has 29,000 images (as in the released NPC annotations), not the 29,783 stated in Appendix A.
- Single seed per main setting; the paper does not state its number of seeds.
- Nothing was scaled down.

## Discrepancies

**code_vs_paper**
1. **Scoring function** (`main_clip.py: weight_function`, major, affects results).
   - Paper (Eq. 5/9): w = −s̃²(s̃−1) with s̃ = s(x,y) − β on raw cosine similarity.
   - Code: x = (100·cos − 100·β), clipped at 0, then **divided by the batch maximum**, and w = −x²(x−1)(x+1) = x²(1−x²). This is a different (quartic) polynomial with a per-batch normalisation: the most similar pair in each batch gets weight 0, and the weights depend on batch composition.
2. **Domain-adapted estimator** (major, affects Table 2).
   - Table 2 "+OSA" rows equal Table 12 "CLIP (w DA)", i.e. they use the GMM-selected clean warm-up of the estimator (Sec. 3.2.1).
   - The release only implements the zero-shot estimator: it copies the pre-trained CLIP weights and has no warm-up or GMM code.
3. **LR schedule** (`main_clip.py`, minor).
   - The cosine scheduler is built with `total_steps = len(dataset)*epochs` and indexed by `step = len(dataset)*epoch + idx` (dataset size, not batches). The LR is therefore a per-epoch staircase: 1e-5, 0.90e-5, 0.65e-5, 0.35e-5, 0.10e-5.
   - The paper only states AdamW, 500 warm-up steps, lr 1e-5.
4. **1K evaluation folds** (`eval.py`, minor, ≤0.1 effect). Slices `[1000*i : 1000*(i+1)-1, 5000*i : 5000*(i+1)-1]` drop the last image and the last caption of every fold.
5. **Default hyper-parameters** (`params.py`, minor). Defaults are lr 1e-6 and warmup 0. The README command (lr 1e-5, warmup 500) matches the paper, and that is what we used.
6. **Flickr30K split** (minor). Appendix A states 29,783 training images; the released annotations (NPC/NCR split) have 29,000.
7. **CLIP baseline** (minor). There is no baseline flag or config in the release, so we ran it by switching the OSA weights off. Our baseline is much stronger than the paper's "CLIP" rows (flag `BASELINE_STRONGER_THAN_REPORTED`). This is not counted as a code bug, since the paper does not describe how its baseline was trained.

**paper_internal**
1. Sec. 3.2.1/4.5 describe DA as "only optional" and say zero-shot CLIP "performs exceptionally well". Yet Table 2's "+OSA" rows are silently the **w DA** numbers (identical to Table 12 "CLIP (w DA)"), while Table 12's w/o-DA numbers are lower at 50 % noise.
2. Table 2 (and Table 11): NPC's t2i R@10 is identical to its i2t R@10 in every noise setting (98.7/98.7, 98.4/98.4, 97.7/97.7), and higher than NPC's own t2i R@5 by an implausible margin. This looks like a copy error.
3. Table 5: accuracy/recall values look swapped relative to the definitions in Sec. 4.6 (see above).

## Codebase completeness: MISSING_SCRIPTS
The core OSA mechanism (random-pair spatial debias β, scoring function, loss re-weighting, CLIP training/eval for COCO/F30K/CC120K) is released and runs from the README command. Missing:
- The domain-adaptation estimator warm-up (GMM clean selection + warm-up training), needed for the Table 2/12 "w DA" numbers. Not rebuilt: the paper does not give enough detail (GMM features, thresholds, warm-up steps).
- All code for image classification (WebFG-496), image retrieval (CARS98N), ALIGN, VSE++ (Table 4), NPC+OSA (Table 11), the scoring-function variants (Table 7) and CC3M.
- The CLIP baseline (no flag; added as `--no_osa`) and the noise-detection / mean-noise-rank analyses (Tables 5/6; written as `noise_detect.py`).

Changes made to the released code (uncommitted; see `codebase_changes.diff`):
- `main_clip.py`: removed the hard-coded `os.environ["CUDA_VISIBLE_DEVICES"] = "7"`, which would select a non-existent GPU under Slurm. Added a log line for β. Added the `--no_osa` baseline switch, which sets the weights to 1 and only runs when the flag is set.
- `params.py`: added the `--no_osa` argument.
- `clip/clip.py`: model download root is `$XDG_CACHE_HOME/clip` instead of `~/.cache/clip` (quota).
- `eval.py`: additionally logs 1K results with the full (non-truncated) folds. The released numbers are still printed and are the ones reported in the tables.
- Environment: torch 2.1.2/cu121 instead of 1.13.1 (H200), `setuptools<70` for `pkg_resources`. `--dataset_root` must be an absolute path: with a relative path, `os.path.join(image_root, image_root + name)` duplicates the prefix.

Scripts written outside the release: `run.sh`, `run_f30k.sh`, `queue*.sh`, `extract.py` (log → `results.json`), `make_tables.py` (→ `comparisons.*`), `noise_detect.py` (Tables 5/6).

As-released vs. fixed: no change touches the OSA training or evaluation logic, so the OSA numbers are what the unmodified code produces (once the GPU line is removed, which is required to run at all). `result_match_as_released` is therefore also TREND_MATCH. The baseline needed the added `--no_osa` switch.
