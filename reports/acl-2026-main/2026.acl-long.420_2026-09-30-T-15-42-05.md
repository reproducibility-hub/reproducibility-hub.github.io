# Reproduction report — VisPCO (ACL 2026, 2026.acl-long.420)

**Verdict: PARTIALLY_REPRODUCED** — result match **MIXED**, coverage **SCALED_DOWN**,
codebase completeness **MISSING_SCRIPTS**; as released: **DOES_NOT_RUN**.

## What the paper claims and what was targeted

The paper's main result is Table 1 (and its extended version, Table 8). For Qwen2.5-VL-3B on 8 benchmarks, it
compares FastV/SparseVLM/FitPrune "without VisPCO" (mean ± std over sampled pruning configurations that meet a
FLOPs budget) against the configuration VisPCO predicts, at 90%/50%/10% budgets. Headline numbers (FastV, 50%):
63.1 ± 9.5 → **71.5** average. The paper's claims are that VisPCO's configuration is far better than an average
configuration at moderate budgets, that it is only marginally better at extreme budgets, and that it approximates
the empirical Pareto frontier (Fig. 3).

The release (github.com/JHW5981/VisPCO, commit 7109fc0) implements only **Qwen2.5-VL-3B + FastV with the
single-layer p-sigmoid kernel**. So the target was the FastV rows of Table 1/8 at 90/50/10%, plus the unpruned
upper bound. SparseVLM, FitPrune, LLaVA-1.5/Gemma3 (Tables 3/4) and the multi-layer kernels (Table 5) have no
code. I did not reconstruct them.

## What I ran

1. **Data.**
   - Training data: 30K random samples (seed 42) from `liuhaotian/LLaVA-Instruct-150K/llava_instruct_150k.json`,
     with COCO train2017 images downloaded one by one. I resized them with the repo's own
     `dataset/uniform_image_area.py` (area histogram equalisation, App. C.1.1). The first 10K were used, matching
     the released `run_training.sh` (`train_10000_uniform_area_single_image.json`). The paper says 30K.
   - Evaluation data: VLMEvalKit TSVs (A-OKVQA, VizWiz, SEEDBench_IMG, MMBench_DEV_EN, MME, ChartQA_TEST,
     OCRBench, TextVQA_VAL), converted with my `scripts/build_eval_json.py`. Validation set during training: 100
     random samples per benchmark (`eval_max_100`, as in the released script). Test set: see the scale-down below.
2. **Training.** `scripts/run_train.sh` runs the released `main.py` with Table 6 hyperparameters for
   Qwen2.5-VL-3B + FastV: λ(`--sigma`)=100, α=5, ε=0.005, β=0.5, lr=1e-4, w0=1, per-rank batch 2, AdamW, bf16.
   It runs with `EMULATE_WORLD_SIZE=8 VISPCO_DETECT_ANOMALY=0` on 1 H200. The released code never wraps the model
   in DDP, so each of its 8 ranks trains an independent predictor and only rank 0's is saved. I reproduce rank 0
   exactly: its DistributedSampler shard and 625 steps of batch 2 per ALM epoch.
   - The ALM did **not** meet the code's convergence test (|val flop_loss| < 0.005 on three consecutive epochs).
     Val flop_loss per epoch: −0.10, −0.045, −0.27, +0.105, +0.077, +0.069, +0.092, +0.045, +0.022, +0.057,
     +0.042, +0.041, +0.056, while the penalty grew from 100 to 3.9e7.
   - I stopped after epoch 12 and used `predict_pruning_ratio_12.pth`. This is the checkpoint index hard-coded as
     the default in the released `eval_ours.py`. The checkpoint was fixed before any test-set evaluation.
   - Training took about 6.5 h of wall-clock time (≈37 min/epoch while sharing the GPU).
3. **Evaluation.** `scripts/eval_config.py` reuses the repo's dataset, model and metric code (`eval/eval_engine.py`
   `calculate_metric`, FLOPs formulas) with greedy decoding and max_new_tokens=64, as in `eval_ours.py`.
   - `--mode vispco`: the trained predictor at budget b ∈ {0.9, 0.5, 0.1} (code budget semantics, see the
     discrepancies).
   - `--mode base`: unpruned Qwen2.5-VL-3B.
   - `--mode fixed`: "FastV without VisPCO". These are single-layer FastV configs (prune at layer k, keep ratio r)
     built with the repo's own kernel 1+(r−1)·σ(10(i−k)). r was chosen as 1 − 36(1−b)/(35.5−k) so the config
     meets the budget, and measured FLOPs land within a few % of the target.
     - 50%: k ∈ {1,2,4,6,8,10,12,14,16,17}.
     - 90%: k ∈ {2,8,14}.
     - 10%: k ∈ {0,1,2}.

     The paper's sampled configuration set is not released, so these baselines are my guess (NOT_COMPARABLE).

**Scale-down (why coverage is SCALED_DOWN).** The released FastV model runs eager attention and materialises the
attention maps at every layer (pruning_loc = all 36 layers). With the processor's default max_pixels (12.8 MP),
evaluation ran at only 0.3–0.7 samples/s on the H200. The full 35K-question suite would take ≈20–24 h per
configuration, and Table 1 needs ≥ 20 configurations. I therefore evaluate every configuration on the **same fixed
random subset of 1000 questions per benchmark** (`pandas.sample(random_state=0)`; OCRBench is complete at 1000).
That is 8000 questions per configuration. A partial full-set run gave A-OKVQA (all 1145) = 85.1 (base) and 83.8
(VisPCO@50%), versus 84.4 and 83.3 on the 1000-question subset.

### Claim-level assessment

| Claim (Table 1 / Sec. 4.2, FastV, Qwen2.5-VL-3B) | Paper | Ours (1000/benchmark) | Verdict |
|---|---|---|---|

Overall: the central 50%-budget claim reproduces as a trend: VisPCO's configuration is far better than an average
configuration and almost matches the best one found by sampling. The 90% claim holds too (negligible differences).
At the lowest budget, VisPCO does **not** beat the average sampled configuration. Absolute numbers do not match the
paper. I therefore rate the result **MIXED**. Claims about SparseVLM/FitPrune, other VLMs (Tables 3/4) and the
multi-layer kernels (Table 5) could not be tested because there is no code for them.

* b=0.5 → layers 0–1 keep 1.0, layer 2 keeps 0.65, layers ≥3 keep 0.46 (k≈2.1, r≈0.46: the FastV default
  position).
* b=0.9 → k≈2, r≈0.83.
* b=0.1 → layer 0 keeps 0.98, then 0.07.

The predictor's output is nearly input-independent.

## Why it is not fully reproduced

* **Missing pieces of the release.**
  - No eval-data JSON or converter, no grid-sampling baselines, and no trained checkpoint.
  - Only FastV/Qwen2.5-VL-3B with the single-layer kernel is implemented.
  - `run_training.sh` crashes (`--kernel_type` is not a recognised argument), and `utils/utils.py` has a
    Python ≥3.12-only f-string even though the README asks for Python 3.10.
* **Compute.** The full benchmark suite was infeasible for ~20 configurations, so I used 1000 questions per
  benchmark.
* **Unspecified evaluation details.**
  - The prompt formats are not given beyond Fig. 5, and the system prompt in Fig. 2 is truncated.
  - The release's metric is lenient: substring match for the VQA-type sets, and MMBench without circular eval.
  - The release's default eval file suggests 100 samples per benchmark.

  Per-benchmark upper-bound numbers therefore differ from the paper's even though the 8-benchmark average agrees.
* **Training dynamics.**
  - The ALM did not converge under the code's own criterion.
  - Our single-GPU run reproduces rank 0 of the released 8-GPU job, but the paper's numbers come from whichever
    checkpoint the authors used.
