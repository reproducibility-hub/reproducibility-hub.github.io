## What the paper claims (main experiment)
- **Table 7, "Local deploy" setting**: Llama-3.1-8B-Instruct does memory extraction (and answering); Contriever does embedding.
  - **flat** = Key [S,F,K] (summary + user facts + keyphrases merged into one vector per session), Op = Add.
  - **graph** = entity-description graph, retrieval Q→K→V, ranking (Score_e, Score_g).
  - Retrieval (R@5, R@10, NDCG@5, NDCG@10) on LongMemEval-S and LongMemEval-M. The claim: graph beats flat in retrieval, with a larger gap on M.
- **Table 2**: key designs for flat retrieval.
- **Table 6**: graph re-ranking / 1-hop expansion.

## What I ran
Environment: one conda env (`./env`, Python 3.11) built from `requirements.txt`. Changes:
- vLLM upgraded from 0.5.3.post1 to 0.6.3.post1, then 0.6.6.post1, plus xgrammar 0.1.9 (see below).
- A stub `pyairports` module added to the env (PyPI's `pyairports` 0.0.1 ships no module and breaks `outlines`).
- `OUTLINES_CACHE_DIR` pointed to a local dir (the shared cache's sqlite file was corrupt).

LLM server: vLLM serving `meta-llama/Meta-Llama-3.1-8B-Instruct` locally as `llama-3.1-8b-instruct` on port 18731, OpenAI-compatible. Final flags: `--max-model-len 32768 --enable-chunked-prefill --max-num-batched-tokens 2048 --enable-prefix-caching --guided-decoding-backend xgrammar --max-num-seqs 256 --generation-config <Llama-3.1 snapshot>`. The last flag applies the model's default sampling (T=0.6, top_p=0.9) to requests that set none; see the sensitivity section.

`codebase/.env`: `OPENAI_BASE_URL=http://localhost:18731/v1`, `INDEX_LLM_MODEL=LLM_MODEL=llama-3.1-8b-instruct`, `EMBEDDING_MODEL=contriever`, `EMBEDDING_RETRIEVER=flat-contriever`, plus the repo's own defaults for extraction temperatures and token limits.

Data: LongMemEval-cleaned (`xiaowu0162/longmemeval-cleaned` on HF: `longmemeval_s_cleaned.json`, `longmemeval_m_cleaned.json`, `longmemeval_oracle.json`).
- S and the oracle were deduplicated with `python data_preprocessing/lme_deduplicate.py`.
- M was deduplicated with `scripts_repro/dedup_m.py`, which calls the repo's own `deduplicate_with_tracking()`; the released script hard-codes the S file.
- M has 237,655 session instances, 52,825 of them unique.

Commands (all from `codebase/`):
1. **Flat extraction (S)**: `bash scripts/flat_lme_build_index.sh data/longmemeval-cleaned/longmemeval_s_cleaned_deduplicate.json llama-3.1-8b-instruct`. This runs keyphrase (T=0), summary (T=0) and userfact (T=1.0, guided JSON with ICL) extraction for 19,208 sessions.
   - For M, the same script ran over 8 part-files holding only the unique sessions (`scripts_repro/m_unique_parts.py`, driven by `scripts_repro/flat_m_build.sh`), writing to a separate cache folder `expansions-llama_3_1_8b_instruct_temp1_m`. The split avoids forking a 128-worker Pool from a 20 GB parent; the per-session requests are unchanged.
2. **Flat retrieval**: `python -m src.flat.lme_run_retrieval --retriever flat-contriever ...`, then `python -m evals.lme_compute_recall`. Wrapper: `scripts_repro/run_flat_configs.sh`. Table 2 key designs map to the released flags as follows:

   | Key design | Flags |
   |---|---|
   | session | `--index_expansion_method none` |
   | session,S,F,K | `separate --use_raw_session_as_key` |
   | [session,S,F,K] | `merge_raw` |
   | session,[S,F,K] | `merge --use_raw_session_as_key` |
   | S,F,K | `separate` |
   | [S,F,K] | `merge` |

3. **Graph construction**: `python -m src.graph.lme_construct_graph --in_file <shard> --out_dir data/graph_{s,m}-llama-3.1-8b-instruct --embedding contriever`. This is the released code. Questions were sharded and run as 13–20 parallel processes (`scripts_repro/shuffle_shards.py`, `split_remaining.py`, `launch.sh`, `supervise*.sh`).
   - Crashed or interrupted questions (CUDA OOM from many Contriever processes, server restarts) were rebuilt from scratch. `scripts_repro/clean_unfinished.sh` deletes the partial graph files but keeps that question's LLM-response cache (same request gives the same cached output).
4. **Graph retrieval**: `python -m src.graph.lme_run_retrieval --embedding contriever --graphrag_mode entity,chunk --only_need_context`, then `evals.lme_compute_recall` (`scripts_repro/graph_eval.sh`). The Table 6 variants add `rank-entity`, `rank-vector` and `one-hot-expand` to `graphrag_mode`.
5. **LME-M graph subset**: questions were shuffled (seed 0) and dealt round-robin into shards, and construction was stopped after about 26 h. The 376 finished questions (317 non-abstention questions used for scoring) form the subset. Flat results were re-scored on exactly the same questions (`scripts_repro/flat_subset_eval.sh`).

Metrics are the repo's own (`evals/lme_compute_recall.py`, LongMemEval protocol): `recall_all@k` and `ndcg_any@k`. Abstention questions and questions whose evidence is only in assistant turns are excluded, leaving 419 of 500 for S and M-full, and 317 of 376 for the M subset.

## Important sensitivity finding: graph extraction sampling
The released graph code (`src/graph/_llm.py::openai_complete_if_cache`) sends the extraction request with **no temperature, top_p or max_tokens**, so the result depends on the inference server's defaults.

- With vLLM 0.6.x defaults (T=1.0, top_p=1.0; a first build of 199 S questions), Llama-3.1-8B often breaks the tuple format: `(<|entity"...`, records without parentheses, even Python code. About 5% of evidence sessions end up with no entity pointing to them.
- On the same 180 scored questions:

  | Setting | R@5 | R@10 | N@5 | N@10 |
  |---|---|---|---|---|
  | graph, T=1.0 | 0.833 | 0.850 | 0.920 | 0.922 |
  | graph, T=0.6 / top_p=0.9 | 0.944 | 0.967 | 0.970 | 0.973 |
  | flat [S,F,K] | 0.906 | 0.978 | 0.933 | 0.945 |

So whether the graph beats flat depends on this unstated setting. All reported graph numbers use the model's generation config (T=0.6, top_p=0.9), which newer vLLM versions (≥0.8) apply by default. A few extractions still produce runaway outputs up to the 32k context; the client's timeout-and-retry recovers them.

## Discrepancies
1. **code_vs_paper (major)**: App. C.4.3 says a "Prejudge Mechanism" (an LLM informativeness filter on each chunk before extraction) "is employed in all experimental configurations". No such step exists in the release: graph construction (`src/graph/_op.py::extract_entities`, `lme_construct_graph.py`) extracts every session, and the flat extractors process every session. The paper reports a small effect (Table C.8: +0.7 R@5). Our numbers still match within tolerance.
2. **code_vs_paper (minor)**: Sampling parameters for graph extraction are not stated in the paper, and the code sets none (no temperature or max_tokens), so they inherit server defaults. This strongly affects results (see above).
3. **code_vs_paper (minor)**: `evals/lme_compute_qa.py` defaults the QA judge to gpt-4o-mini (`get_stage_model('qa_eval','gpt-4o-mini')`); §4.1 says GPT-4o judges LongMemEval. No effect on our results.
4. **code_vs_paper (minor)**: `data_preprocessing/lme_deduplicate.py` only processes the S file (paths hard-coded). M needed a wrapper. `src/flat/lme_run_retrieval.py --in_file` defaults to the non-deduplicated file.
5. **paper_internal**: Tables 5 and 6 report R@5 0.9642 / R@10 0.9904 for entity activation + (Score_e, Score_g) without expansion. Table 7 (same graph config per its caption) reports 0.9356/0.9761 (Llama) and 0.9690/0.9928 (GPT). The model setting for Tables 5 and 6 is not stated.
6. **paper_internal**: Judge model. §4.1 says GPT-4o for LongMemEval and GPT-4o-mini for HaluMem; App. C.1 says "For all experiments, GPT-4o is utilized as the backbone evaluator".
7. **paper_internal**: Table D.2 "Ours" row mixes settings.
   - It reports LME-S recall "0.969/0.935" and QA "0.892/0.620". The 0.935 recall and 0.620 QA match the Llama rows of Table 7, not the GPT row.
   - It lists the QA model as gpt-4o-mini; Table 7 says the GPT setting answers with gpt-4o.
