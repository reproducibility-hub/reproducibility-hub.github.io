# Reproduction report: MDP-GRPO (ACL 2026, 2026.acl-long.1982)

**Verdict: FAILED** — the paper's own training data is not released (codebase completeness MISSING_DATA), so the trained-model results cannot be reproduced as published. On a rebuilt substitute training set, none of the method's claimed gains appear.

**Bottom line.** The evaluation side reproduces: zero-shot Gemma-2-2B-it baselines match the paper on IFEval, the custom test set, MMLU and ARC, which suggests the evaluation protocol is matched. The training side cannot be reproduced faithfully because the 3,000-prompt training set is not released. On a substitute training set of the same size, built from He et al. (2024) seeds and constraint taxonomy, **MDP-GRPO did not beat plain GRPO in any of our runs.** With the paper's prospect parameters (λ+=1.25, λ−=2.0), MDP-GRPO and DA-PT-GRPO diverge (entropy → 6–8, KL > 1) and lose 8–12 points. With the λ values the released scripts actually use (λ+=2.0, λ−=1.25, the "inverse" PTI setting in the paper's terms), training is stable but still 2–5 points below GRPO. Our GRPO is itself stronger than the paper's GRPO, so the paper's GRPO → MDP-GRPO gap is not reproduced here. Because the training data differs, this is not a clean refutation.

## What was attempted

**Paper claims targeted.** Table 1 (G=8) and Table 2 (G=4): instruction-following SSR/HSR of GRPO vs. MDP-GRPO (and ablations) on IFEval, FollowBench and the authors' 500-prompt custom test set, for Gemma-2-2B-Instruct and Llama-3.2-3B-Instruct; Tables 3/4: MMLU / ARC retention. Headline claim (abstract): MDP-GRPO outperforms standard GRPO, improving strict constraint satisfaction by up to 5.0% on Llama-3.2-3B.

**Code.** https://github.com/m-salmani78/MDP-GRPO (linked in the paper, footnote 1) cloned to `./codebase` (commit 9da3696). MDP-GRPO itself lives in a TRL fork, https://github.com/m-salmani78/trl (branch `MDP-GRPO`, commit 3b37508), cloned to `./ext/trl_fork`.

**Environment** (`./env`, Python 3.10): the repo's `requirements.txt` pins (torch 2.8.0, transformers 4.57.1, peft 0.17.1, datasets 4.2.0, accelerate 1.11.0, vllm 0.10.2, lm_eval @760639f) plus **trl==0.25.0 with the fork's `trl/trainer/grpo_trainer.py` and `grpo_config.py` copied over it** (see codebase notes: the fork as a package is not installable/importable). `VLLM_FLASH_ATTN_VERSION=2` is set because vLLM's FA3 path on H200 rejects Gemma-2 logit soft-capping.

**Data.**
- Custom test set: the released `codebase/data/data_test.jsonl` (500 prompts) — used as-is.
- IFEval / MMLU / ARC: via `lm_eval` exactly as in the README command (`--model vllm`, no chat template, `max_model_len=2048`, `dtype=auto`).
- FollowBench: not run — its evaluation uses GPT-4 as an LLM judge for most constraint categories (paper Sec. 5.1 "hybrid evaluation framework (rules and LLM judges)") and no API key is available; the repo contains no FollowBench code. FollowBench numbers are NOT_COMPARABLE (flag CLOSED_JUDGE_UNAVAILABLE).
- **Training data (3,000 prompts, `data/rlhf_train.jsonl`) is NOT released.** Substitute built by `scripts/build_train_data.py`: 1,065 constraint-injected prompts of He et al. (2024) (from the authors' own fork m-salmani78/FollowComplexInstruction, `get_data/data/data.jsonl`), keeping only seeds that do NOT occur in the released test set (377 of the 500 test prompts share a seed with He et al.'s 1,500 seeds), plus 1,935 prompts obtained by re-injecting 1–6 constraints into the same non-test seeds with He et al.'s taxonomy / gen_inst.py logic and conflict rules (keywords sampled from seed text instead of GPT-4). Constraint count distribution follows the test set (1:225, 2:459, 3:698, 4:800, 5:647, 6:171). The paper's set uses ~1/3 He et al. seeds and ~2/3 newly curated seeds (general Q&A, creative writing, material assistance) that are not available.

**Models.** `google/gemma-2-2b-it`; for Llama the gated `meta-llama/Llama-3.2-3B-Instruct` is not accessible with the available HF token, so the public re-upload `unsloth/Llama-3.2-3B-Instruct` was used (a mirror of the same instruct checkpoint; not hash-verified against the gated original, which we cannot download; generation config identical apart from an added pad token id).

**Commands.** Training: `scripts/train_run.sh <model> <run> <args>` = `python codebase/training/train.py` with the README/full_pipeline.sh arguments (`--per_device_train_batch_size 8 --gradient_accumulation_steps 4 --lora_r 32 --lora_alpha 64 --lora_dropout 0.05 --num_train_epochs 1.0 --learning_rate 1e-5`, defaults: beta=0.01, epsilon=0.2, top_p=0.9, top_k=50, max completion 1024, vLLM colocate) followed by `training/merge_model.py` on the final adapter. 750 optimizer steps (3,000 prompts × G=8 / 32) for G=8, 375 for G=4. Evaluation: `scripts/eval_custom.sh` (= `src/do_inference.py` + `src/check.py` with the arguments of `scripts/do_inference.sh` / `scripts/check.sh`, greedy, max 1024 new tokens), `scripts/eval_lmeval.sh` (README `lm_eval` command; IFEval and MMLU+ARC in separate calls). The shell wrappers were re-written only so they don't override `CUDA_VISIBLE_DEVICES` (the repo scripts hard-code `CUDA_VISIBLE_DEVICES=1`). Orchestration: `scripts/queue.sh` + `scripts/jobs.txt`; results tables: `scripts/collect.py`, `scripts/make_tables.py`.

**Method configurations run** (paper Sec. 5.5 hyper-parameters unless stated):
- GRPO: `--DA_ALPHA 0 --temperature 1.0` (train.py always uses the fork's `advantage_mode="dual_anchor"`; with alpha=0 and no prospect this is z-score GRPO with population std).
- MDP-GRPO (paper lambdas): MT `--temperature_list 0.1 0.4 0.7 1.0 0.1 0.4 0.7 1.0` (the paper gives no 8-temperature schedule; its G=4 example list was repeated), DA `--DA_ALPHA 0.2 --DA_GOAL_MU_MODE max_half_and_group_mean`, PT `--DO_PROSPECT True --prospect_beta 0.8 --prospect_lambda_pos 1.25 --prospect_lambda_neg 2.0`, asymmetric KL `--beta_by_adv_sign True` (beta_pos 0.01 / beta_neg 0.025).
- "relLam" variants: identical but with the released scripts' `--prospect_lambda_pos 2.0 --prospect_lambda_neg 1.25` (README & full_pipeline.sh).
- DA-PT-GRPO: DA + PT, temperature 1.0, symmetric KL. DA-GRPO: DA only. PT-GRPO: PT only (paper lambdas).
- `gemma_MDP_G4_released`: the exact `full_pipeline.sh` configuration (G=4, temperature_list 0.1 0.4 0.7 1.0, alpha 0.2, PT with lambda+=2.0/lambda-=1.25, asymmetric KL).
- Single seed (42) for everything (the paper also reports single runs).

### Key observations

1. **Evaluation pipeline reproduces.** For Gemma-2-2B-it zero-shot: IFEval 57.9/45.3 vs 56.7/45.1, custom 56.1/20.0 vs 54.8/18.8, MMLU 56.8 vs 56.9, ARC-C/E 50.8/81.0 vs 50.9/81.0. For Llama-3.2-3B-Instruct the custom set (61.0/21.0 vs 60.3/20.8) and ARC-C/E (43.8/75.3 vs 43.6/74.2; Table 4 column mapping inferred from the PDF text) match, (MMLU 62.3 vs 60.4 is within the 5% tolerance), but IFEval is much higher than reported (64.6/52.1 vs 54.2/46.8). The cause is unclear: we use the README's `lm_eval` command and the unsloth mirror of the weights.
2. **GRPO is stronger than reported.** On our substitute data, GRPO gives Gemma 75.4/65.2 on IFEval and 72.2/33.2 on the custom set, versus the paper's 73.7/62.4 and 68.4/29.0. For Llama it gives 74.2/62.8 and 67.1/26.4, versus 66.1/58.5 and 65.1/24.8. For Llama, our GRPO exceeds the paper's best variant in all four IFEval/custom cells (74.2/62.8/67.1/26.4 vs best 71.5/62.5/66.3/25.4). For Gemma it is within 0.6 points of the paper's best variant in each cell (75.4/65.2/72.2/33.2 vs best 75.7/65.8/71.4/33.4).
3. **MDP-GRPO / DA-PT-GRPO with the paper's λ diverge.** With (λ+, λ−) = (1.25, 2.0), the shaped advantages have a negative mean: about −0.17 per completion in a simulation of the fork's formulas (`scripts/sim_advantages.py`), versus exactly 0 for GRPO. Every update therefore pushes down the sampled sequences, and policy entropy explodes. Gemma MDP-GRPO ends with entropy 6.3 and KL 1.05; DA-PT-GRPO with entropy 8.5 and KL 2.1. GRPO ends at entropy 1.0 and KL 0.2. Downstream, MDP-GRPO is 7–10 points below GRPO, and DA-PT-GRPO 10–12.5 points below.
4. **With the λ the released scripts use, training is stable but still below GRPO.** With (λ+, λ−) = (2.0, 1.25) the mean advantage is +0.17, so entropy collapses instead (0.15–0.26). Gemma DA-PT-GRPO reaches 72.2/62.3 on IFEval and 70.2/32.4 on the custom set, close to the paper's DA-PT row (74.8/64.3, 70.8/33.4) but below our GRPO. Llama MDP-GRPO reaches 70.0/59.0 and 63.0/21.2, close to the paper's MDP row on IFEval (71.3/59.8) but below our GRPO (74.2/62.8, 67.1/26.4).
5. **Ablations (Gemma, G=8).**
   - DA-GRPO is on par with GRPO: 75.4/64.9 vs 75.4/65.2 on IFEval, 71.7/34.0 vs 72.2/33.2 on the custom set. It is close to the paper's DA-GRPO row (75.2/64.7, 70.7/32.6).
   - PT-GRPO with the paper's λ diverges (entropy 8.6, KL 2.5) and drops to 67.5/54.9 and 63.5/25.8. The paper reports PT-GRPO as its best Gemma variant (75.7/65.8). This isolates the loss-averse prospect shaping as the source of the divergence.
   - MT-GRPO (multi-temperature only) gives 72.8/61.7 on IFEval and 70.7/31.6 on the custom set, about 1.5–3.5 points below GRPO. The paper reports 73.9/63.7 and 68.6/29.6, slightly above its GRPO.
   - MDP-GRPO with the released λ (MT+DA+PT+AKL) gives 68.9/57.5 and 65.3/26.2, below DA-PT with the released λ (72.2/62.3, 70.2/32.4). So adding multi-temperature sampling and asymmetric KL hurts here.
6. **Group size G=4 (Table 2).** GRPO at G=4 reproduces the paper's G=4 GRPO row closely: IFEval 70.1/58.6 vs 69.7/58.2, custom 66.8/27.0 vs 67.3/28.6. The exact released `full_pipeline.sh` MDP-GRPO configuration gives 68.1/55.1 and 66.4/27.8, versus the paper's 71.2/59.5 and 67.8/30.4. That is below GRPO at G=4 on IFEval (−2.0 SSR, −3.5 HSR) and about even on the custom set (−0.4 SSR, +0.8 HSR). So the claimed G=4 gain of MDP-GRPO is not reproduced either.
7. **Multi-temperature sampling** makes training 3–4× slower in this implementation: G separate vLLM calls per batch, about 30–45 s/step versus about 10 s/step. Because the trainer scores tokens at T=1 while vLLM returns temperature-scaled logprobs, TRL's importance-sampling correction down-weights low-temperature samples (mean IS ratio about 0.4).
8. **General capabilities.** MMLU is unchanged by every variant (56.7–57.0 for Gemma, 62.0–62.3 for Llama). ARC is unchanged by GRPO and DA-GRPO. The PT-containing and MT-containing variants lose 1–4 points on ARC, for example Gemma MDP-GRPO (released λ) ARC-E 77.1 vs 81.1 for GRPO, and Llama MDP-GRPO ARC-E/ARC-C 72.1/41.1 vs 75.5/44.1. The paper reports ARC as preserved for all variants.

## Discrepancies

- **[code_vs_paper, major] README.md (training command) and full_pipeline.sh: --prospect_lambda_pos 2.0 --prospect_lambda_neg 1.25** — paper: Sec. 4.4/5.5: (lambda+, lambda-) = (1.25, 2.0); lambda- > lambda+ enforces loss aversion; App. C says the inverse shaping (PTI-GRPO, lambda+ > lambda-) does not yield gains — code/other: Every released training command uses lambda+ = 2.0, lambda- = 1.25, i.e. the inverse (PTI) shaping; train.py defaults are 1.25 / 1.8. In our runs the paper's values make the mean shaped advantage negative (~ -0.17 per completion) and training diverges (entropy 1 -> 6-8, KL > 1), whereas the released values train stably (affects results: True)
- **[code_vs_paper, major] trl fork grpo_trainer.py::_generate_and_score_completions (dual_anchor branch)** — paper: Eq. 4: delta_i = 2*sqrt(C(x))*(r_i - 0.5), i.e. anchor std sigma_goal = 1/(2 sqrt(C)) — code/other: goal_std = sqrt(G / (4C)) for normalized rewards, i.e. delta_i = 2*sqrt(C/G)*(r_i - mu_hat): an extra 1/sqrt(G) factor (delta is ~2.8x smaller for G=8, 2x for G=4) (affects results: True)
- **[code_vs_paper, minor] train.py DA_GOAL_MU_MODE default / full_pipeline.sh (max_half_and_group_mean)** — paper: Sec. 4.3 and 5.5: 'Unless otherwise noted, we use alpha = 0.2 and set the anchor mean mu_goal = 0.5 (neutral baseline)' — code/other: Default and pipeline use mu_hat = max(0.5, group mean) (the variant favoured in App. B.2), not the fixed 0.5 of the main text (affects results: True)
- **[code_vs_paper, minor] README.md 'Train the LoRA Adapter (MDP-GRPO)' example (run name PT-GRPO)** — paper: PT-GRPO applies prospect-theoretic shaping — code/other: The example command named PT-GRPO passes --DA_ALPHA 0 and lambda values but not --DO_PROSPECT True (default False), so it trains plain GRPO (affects results: False)
- **[code_vs_paper, minor] full_pipeline.sh (METHOD=MDP-GRPO)** — paper: Table 1 main results use G=8 for every method (Sec. 5.5 'We primarily train with a group size of G = 8') — code/other: The only released MDP-GRPO configuration uses --num_generations 4 with a 4-temperature list; no 8-temperature schedule is given anywhere (affects results: True)
- **[code_vs_paper, minor] trl fork, multi-temperature vLLM path + TRL 0.25 importance-sampling correction** — paper: Sec. 4.2: multi-temperature sampling 'without altering the underlying group-based RL objective' — code/other: Completions sampled at tau in {0.1..1.0} are scored by the trainer at temperature 1.0 while vLLM returns processed (temperature-scaled) logprobs; TRL's truncated importance-sampling correction then down-weights low-temperature tokens (mean IS ratio ~0.4 vs ~0.93 for GRPO in our runs), so the effective objective does change (affects results: True)
- **[code_vs_paper, minor] src/do_inference.py vs training/train.py** — paper: Not specified — code/other: Training feeds the raw prompt string (no chat template) to the policy, while custom-test-set inference applies the chat template with a default Llama-2-style system prompt and IFEval/MMLU/ARC (README lm_eval command) use no chat template (affects results: True)
- **[paper_internal] Table 2 caption** — paper: Table 2 is described in the text as the reduced group size G = 4 table — code/other: Caption says 'using a reduced group size (G = 8)' (affects results: False)
- **[paper_internal] Abstract vs Table 1 (Llama-3.2-3B)** — paper: Abstract: MDP-GRPO improves strict constraint satisfaction by up to 5.0% on Llama-3.2-3B over standard GRPO (README says 6.0%) — code/other: Table 1 Llama: MDP-GRPO vs GRPO HSR differences are +1.3 (IFEval), +0.4 (Custom), +0.2 (FollowBench); the largest HSR gain of any variant is +4.0 (DA-GRPO, IFEval); +5.x only appears in SSR (soft) metrics (affects results: False)

## Codebase completeness: MISSING_DATA

- **Missing data (main reason):** the 3,000-prompt training set is not released. The README just says "Copy or download your rlhf_train.jsonl here", and neither the repo nor the paper gives a link. We rebuilt a substitute (`scripts/build_train_data.py`, outside the codebase).
- **Missing code:** `src/instructions_registry.py` and `src/instruction_constants.py` are imported but absent. Without them `src/check.py` (evaluation) and `training/reward_function.py` (reward) crash at import. We added both as new files; no existing file was edited.
- **Broken dependency packaging:** `requirements.txt` pins `trl @ git+https://github.com/m-salmani78/trl.git@MDP-GRPO`.
