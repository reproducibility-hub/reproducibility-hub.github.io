## What was attempted

**Target.** The paper's central empirical claim (abstract, §6, conclusion): fine-tuning on YIELD (SFT and
offline-RL/AWR "ORL") makes LLM elicitor turns match human elicitation behaviour much better than prompting, measured by
the paper's own metrics on the YIELD test split (10,285 six-turn segments): **Table 6** (micro perplexity of real
elicitor turns, generated response length, prompt length), **Table 7** (Progression), **Table 8** (Turn-Length Ratio),
for Llama-3.1-8B-Instruct, DeepSeek-R1-Distill-Llama-8B and Llama-3.2-3B-Instruct × {prompted, SFT, ORL}, plus the

**Released artefacts used.** Code: github.com/infosenselab/yield (commit 4700a27) + PyPI package `elicitation==1.0.1`
(the metric/generation library the repo's evaluation scripts call). Data: HF `infosense/yield`
(`yield-experimental/` = the segmented experimental set; split sizes 83,181 / 9,988 / 10,285 exactly as in the paper;
`yield/test` full dialogues). Adapters: HF `infosense/yield-adapters` (SFT + ORL LoRA adapters for all 3 models).

**Settings that differ from the paper.**
- 1 × H200 instead of 3 × RTX A6000. To keep the paper's effective batch sizes: SFT `gradient_accumulation_steps`
  4→12 (4 × 12 × 1 GPU = 48 = 4 × 4 × 3 GPUs); ORL `batch_size` 4→12 (12 × 1 GPU = 4 × 3 GPUs). Consequence for ORL:
  the per-batch return/advantage normalisation is over 12 samples instead of 4 per GPU. (config values only; copies of
  `config/training_params.yaml` in `runs/*/config/`.)
- Only Llama-3.1-8B was retrained (SFT ≈ 7.8 h, ORL ≈ 12 h on this GPU with the release's 8-bit LoRA setup); the
  DeepSeek-R1-Distill-Llama-8B and Llama-3.2-3B rows are evaluated with the authors' released adapters only.
- Llama-3.2-3B-Instruct: the `meta-llama` repo is gated for the available HF token, so the weights come from the
  ungated `unsloth/Llama-3.2-3B-Instruct` mirror (same weights), combined with the tokenizer files the authors shipped
  with their adapters and Meta's original config/generation config (unsloth's pad-token tweaks removed). Prompted
  Llama-3.2-3B perplexity matches within 1.6 % (45.28 vs 46.0 on Academic, others ≤0.9 %).
- Generation: the released `elicitation.utils.generate_utterances` calls a HF `pipeline` one prompt at a time
  (`pipe(list)` without `batch_size`), which would take >30 h for DeepSeek-prompted alone. `scripts/gen_batched.py`
  re-implements it with identical prompts, model loading (fp16 + merged LoRA), decoding config and post-processing,
  but batches prompts **of identical token length only** (no padding). Two pitfalls found and fixed while doing this:
  (i) the pipeline silently applies its class default `temperature=0.7` on top of the model's generation config
  (model default 0.6), so the released code effectively samples at T=0.7/top-p 0.9 — the wrapper takes the generation
  config from an identically-constructed pipeline; (ii) left-padded fp16 batches at T=0.6 produced degenerate
  "-- the -- the" loops. Fidelity check on the same 400 judicial segments with the released SFT adapter: original
  unbatched code 0 runaways / mean 29.6 tokens; final wrapper 1 runaway / mean 33.1 (mean excl. runaway ≈ 30);
  on 300 other segments with the ORL adapter: 23.7 vs 23.9 tokens. Generation is stochastic (sampling, no seed in the
  release), so response-length means — heavy-tailed because of rare 500-token runaways — are the noisiest numbers.

Additional observations
- Real reference rows are reproduced exactly (they only depend on data + metric code), which confirms that the
  paper's Real numbers are computed on the 6-turn test segments, not on full dialogues (full test dialogues give
  e.g. TLR 2.56/4.37/1.96/9.05).
- "Shuffled" reference: shuffling utterances within each 6-turn segment gives Progression 0.714/0.742/0.746/0.750
  (≠ paper); shuffling within the full dialogue (the repo's `shuffle_yield.ipynb`) and then cutting the same 6-turn
  windows gives 0.819/0.850/0.798/0.815 (✓). Shuffled TLR depends on the random permutation (≈1 either way).
- Response-length deviations come from rare degenerate generations (e.g. "-- the -- the …" loops in Supreme-Court
  context that run to the 500-token cap). Example: released Llama-3.1-8B SFT, judicial: mean 33.0 vs paper 29.1, but
  the median is ~21 and excluding ≥400-token outputs gives ≈30. Their frequency is very sensitive to the decoding
  configuration: with the model's own config (T=0.6) and left-padded batches we observed 2.5 % runaways (judicial
  mean 41.7), with the pipeline's effective config (T=0.7) and no padding ≈0.3–1 %.
- Earlier, superseded evaluation runs (T=0.6, padded batches) are kept in `results/old_T0.6_padded/` for reference.

## Why not fully reproduced
- Coverage: only the primary model (Llama-3.1-8B) was retrained (each SFT+ORL pair costs ≈ 20 GPU-hours with the
  release's 8-bit LoRA setup on one H200; three pairs do not fit the 48 h budget alongside the 10 full evaluations).
  The DeepSeek and Llama-3.2-3B rows rely on the released adapters (they match the paper).
- Table 9 human evaluation needs MTurk workers.
- Several sampled-generation statistics fall outside 5 %, though without changing any conclusion.

## Discrepancies
1. (code_vs_paper, minor) Baseline prompt: Appendix A.5 says "You are participating in an **oral history** interview
   … build on what the **provider** just said"; `config/generation_prompt.txt` says "an interview … what the
   **respondent** just said". Prompted numbers nonetheless match.
2. (code_vs_paper, minor) AWR objective: Eq. (2)/(3) average a per-sample weighted log-likelihood over the batch and
   regress the value head on raw returns-to-go; `agent_llama.py` z-normalises returns per batch, z-normalises
   advantages, uses w = exp(0.25·Â/T) normalised by its batch mean, and averages the weighted log-prob over *tokens*
   (so longer utterances get more weight). The 0.25 factor (α) and T=1 match §6.1.
3. (code_vs_paper, minor) The training scripts load the frozen base model in 8-bit (bitsandbytes) for both SFT and ORL;
   the paper only mentions LoRA on a frozen base model.
4. (code_vs_paper, minor) TLR (`elicitation.metrics.turn_length_ratio.count_tokens`) counts tokens with
   `add_special_tokens=True` (adds a BOS token to every turn), whereas the response-length metric uses
   `add_special_tokens=False`; small systematic effect on TLR.
5. (paper_internal, no effect) Table 6 labels the prompted perplexity rows "Base" and the length rows "Prompt"; the
   code (and our exact match) shows the "Base" perplexity is computed with the prompted context (system message +
   Appendix-A.5 prompt), i.e. the same prompted model.
Not a discrepancy but worth knowing: the decoding configuration is not stated in the paper; the released generation
code samples with the HF pipeline's default temperature 0.7 (overriding the models' own 0.6), top-p 0.9 (Llama) /
0.95 (DeepSeek), max 500 new tokens.
