## What the paper claims (main experiment)
Table 1 reports fidelity and explanation size on Amazon-Products (1000-node subset), Cora, Liar and WikiCS. The base GNN is a GCN and the LLM is a frozen Llama-3.1-8B-Instruct. Values are mean ± std over 5 seeds. Table 3 adds comprehensiveness (C), the random-removal drop (R) and alignment (A). The claim is that GSPELL gives a better fidelity–size trade-off than the baselines: much smaller explanations at slightly lower fidelity, with C 2–5× larger than R.

## What I ran
Code: https://github.com/pbaghershahi/GSPELL.git (commit 983ede6). Model: `meta-llama/Meta-Llama-3.1-8B-Instruct` in bf16 from the shared HF cache. Hardware: 1×H200. The authors' artifacts were downloaded from the Google-Drive link in the README: pretrained GCN, projector, `data.pth` and generated explanations per dataset.

Environment: conda env (python 3.10), torch 2.5.1+cu124, the pyg_lib/torch_scatter/... wheels for torch-2.5.0+cu124, torch-geometric 2.6.1, transformers 4.57.1, huggingface-hub<1.0, rdkit, plus the rest of `installation.sh`.

All runs use the released `main.py` with the released config files and `-adp`, as in `run.sh`/README. Every run goes through `fast_gen.py` (batched generation, see below). Four experiment modes, each with 5 seeds (the config seed, then 2, 3, 4, 5) on each of the 4 datasets, 80 runs in total:
1. **GSPELL, full pipeline from scratch** (`scratch`): train the GCN, train the projector, generate, evaluate.
   `python fast_gen.py --gen_batch_size 128 -cff ./config/<ds>.yaml -m gspell -adp -nwdb --seed <s> -opd runs/<name>`
2. **GSPELL+ from scratch** (`scratchplus`): the same with `-pwb` (InfoNCE backward head, MI weight 1.0 from the config).
3. **GSPELL with the released weights** (`regen`): `-pdp output/<ds>-meta-llama/data.pth -pgp pretrained/<ds>-meta-llama/gcn.pth -ppp pretrained/<ds>-meta-llama/projector.pth` (the README command).
4. **LLM baseline** (`llm`): `-m llm -adp` with the released GCN and data. WikiCS uses `-mnen 50`.

Non-LLM baselines: `main.py -m {node,random,gnnexplainer,pgexplainer,tage}` on the released GCN and data (`run_baselines*.sh`), 1 run each.

Extra checks:
- Re-scoring the authors' released `GSPELL_explanations.pt` with the released code (`-gep`).
- One fully sequential run (released `generate_exp_by_llm`) on Amazon, to validate the batched generation.
- Post-hoc re-scoring of the saved explanations on the first 200 nodes (`posthoc_eval.py`, which calls the released `eval_llm_explanations`). The paper says 200 test nodes, while the configs use 500.
- Re-scoring on the first 50 WikiCS nodes, for a like-for-like comparison with the 50-node LLM baseline.

### Settings that differ from the paper
- **Generation is batched** (`fast_gen.py`, 64–128 prompts per batch, left padding). The prompts, sampling settings and output format are the same as the release. Run sequentially, the released code needs about 10 s per node even after removing `CUDA_LAUNCH_BLOCKING`, and ~2.5 min per node with it. That made the 80-run experiment infeasible in 48 h. Validation on Amazon with the released weights and seed 4978: sequential Fid 92.0 / Size 3.70 / C 8.8 vs batched 92.0 / 3.67 / 9.1.
- **Number of evaluated nodes**: the configs' defaults were used (200 for Amazon, 500 for the others). The paper says 200, so I also report the 200-node re-scoring.
- **LLM baseline on WikiCS: first 50 nodes only.** The text prompts include full keyword lists: median 10.7k tokens, up to 51k, 3876 calls for 500 nodes, which is infeasible here. Its WikiCS rows are therefore NOT_COMPARABLE. For context, on the same 50 nodes GSPELL gives Fid 90.0±4.4 / Size 8.66 vs LLM 90.8±2.0 / 15.09.
- **Non-LLM baselines: 1 run** on the released GCN instead of 5 seeds. Random/Node average 5 internal samples, as in the code.
- Seeds: the configs hold a single seed, and `-tt` is ignored when a seed list exists, so each seed was a separate invocation.

### Claim-level assessment
- **Fidelity–size trade-off (main claim)**: reproduced. On every dataset, GSPELL's size (Amazon 3.83, Cora 1.97, Liar 1.12, WikiCS 16.2, or 12.4 at 200 nodes) is far below Random (7.24 / 18.25 / 476 / 1073) and GNNExplainer (10.6 / 33.8 / 948 / 2090). It is also below the LLM baseline: 4.97 / 2.96 / 1.92, and 15.1 on WikiCS where GSPELL gives 8.7 on the same 50 nodes. GSPELL's fidelity is 1–8 points lower than LLM / GNNExplainer / Random.
- **GSPELL vs LLM on Amazon**: the paper shows GSPELL ahead on fidelity (91.1 vs 86.0). In our runs the LLM baseline reaches 93.6±1.1 vs GSPELL 90.8±1.8, so GSPELL is only smaller, not better on fidelity. This agrees with the paper's own text ("marginally lower fidelity than ... the LLM baseline").
- **Comprehensiveness 2–5× the random drop**: reproduced. Amazon 8.5 vs 3.8 (2.2×), Cora 5.0 vs 0.7, WikiCS 3.1 vs 0.04; Liar is 0/0 as in the paper. The paper's comparison with GNNExplainer (C 2–3× R) cannot be reproduced with the released GNNExplainer code: it keeps the whole neighbourhood, so C = R.
- **GSPELL+ vs GSPELL**: the paper says the InfoNCE head "further reduces explanation size, occasionally lowers fidelity". Ours: Amazon 3.65 vs 3.83 size with 89.4 vs 90.8 fidelity; Cora 1.94 vs 1.97 with 85.6 vs 86.0. WikiCS goes the other way (16.8 vs 16.2; 12.9 vs 12.4 at 200 nodes). All differences are within about one std, so this is a weak or unclear effect. The paper's Amazon fidelity gain for GSPELL+ (92.0 vs 91.1) is not reproduced: we get 89.4 vs 90.8.

## Discrepancies
**Code vs paper**
1. *(major)* Evaluation uses node indices 0..N-1, training nodes included, not the "200 held-out test nodes" (eval_utils, all eval loops).
2. *(minor)* `max_num_eval_nodes` is 500 for Cora/Liar/WikiCS (paper: 200). On WikiCS this changes the GSPELL size from 12.4 (200 nodes) to 16.2 (500 nodes).
3. *(major)* The LLM prompt contains only 1-hop neighbours (`nx.ego_graph(radius=1)`), whereas the paper describes the 2-hop computation tree. Evaluation uses the 2-hop ego graph.
4. *(major)* On Amazon (`use_bow`), the projector's context-alignment target is the node keywords **plus the GNN-predicted label name**. The paper says only "text associated with the node".
5. *(major, baseline)* GNNExplainer keeps every 2-hop node; the top-half cut is commented out. Sizes are therefore ~2× those in Table 1 (Cora 33.8 vs 17.9, Liar 948 vs 474), and C = R in Table 3.
6. *(minor, baseline)* PGExplainer on Liar returns NaN; the paper's "central node only" fallback is not in the code.
7. *(minor)* WikiCS config: `neighborhood_max_hops` = 1 (paper: 2 hops for all datasets).
8. *(minor)* Loss weights: context 1.0 / contrastive 0.5 or 1.0, i.e. β = 2/3 or 0.5, vs β ∈ {0.1, 0.5, 0.9} in the paper.
9. *(minor)* The GCN has 3 conv layers plus a linear decoder (paper: the 3rd conv layer is the classifier).
10. *(minor, no effect on results)* Hard-coded `CUDA_LAUNCH_BLOCKING=1`.

**Paper internal**
1. Table 1 GNNExplainer on Amazon (94.5 / 5.71) vs Table 8 (GAT and GIN: both 100.0 / 10.57, which is exactly what the released code gives for GCN). The tables appear to use different GNNExplainer protocols.
2. LLM size on WikiCS: 21.19 (Table 1) vs 21.14 (Table 10).
3. Sec. 5.2 says GSPELL has marginally lower fidelity than the LLM baseline, while Table 1 on Amazon shows GSPELL 91.1 > LLM 86.0.

## Codebase completeness: MINOR_FIXES
The release contains the method, the full pipeline (GNN training, projector training, generation, evaluation) and all baselines. It also provides pretrained artifacts and generated outputs via the README link. Changes and additions:
- `codebase/main.py`: commented out `os.environ['CUDA_LAUNCH_BLOCKING'] = "1"`. It only affects speed, but generation was about 15× slower with it.
- `codebase/main.py`: wrapped the module-level `login(token=...)` in try/except. The HF API rate-limited the shared account (429); the model is cached and `HF_HUB_OFFLINE=1` was used.
- `fast_gen.py` (my script, outside the codebase): a batched drop-in for `eval_utils.generate_exp_by_llm`, applied by monkeypatching before running the unmodified `main.py` via `runpy`. It reuses the released prompt builders and generation settings. Batches are capped by a token budget, it splits a batch on OOM, and it caps each process at 47% of GPU memory so two jobs can share the GPU. Validated against the sequential version on Amazon.
- Environment: `installation.sh` (apt-get + venv) replaced by a conda env; transformers pinned to 4.57.1 and huggingface-hub <1.0; rdkit added because TAGLAS imports it unconditionally.
- Other scripts I wrote: `launch_regen.sh`, `run_job.sh`, `queue_runner*.sh`, `run_baselines*.sh` (orchestration), `aggregate.py` (mean/std over seeds), `posthoc_eval.py` (re-scoring on the first N nodes with the released evaluator, no LLM), `make_tables.py` and `finalize.py` (tables and status).
- No program logic in the codebase was changed. `git diff` in `codebase/` shows only the two edits above.

## Notes on failures and workarounds
- A first attempt ran 8 sequential-generation processes in parallel. It was far too slow (WikiCS ~14 h per run) and was stopped; batched generation replaced it.
- Three runs hit CUDA OOM while sharing the GPU: scratchplus_products_s4978, scratchplus_cora_s1925 and the first llm_wikics. After adding the memory cap and OOM splitting they were re-run, and all 80 runs completed. The failed attempts are kept as `runs/failed_oom_*`.
- `regen_wikics_s2` was restarted once (pre-emptively, before the memory cap); the first WikiCS LLM-baseline run at 500 nodes was stopped after ~30 min with 19 of 3876 calls done; it is kept as `runs/killed_llm_wikics_s1234_500nodes`.
- The node is shared, and other users' load (load average up to ~190) slowed the CPU-bound evaluation (Steiner trees).
