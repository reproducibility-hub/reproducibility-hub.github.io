## What was run

**Code:** https://github.com/why0129/TalkLoRA, cloned to `./codebase` (commit 777dc0b). It is a fork of the HiRA codebase.

**Data:** downloaded from LLM-Adapters, as the README instructs:
- `ft-training_set/commonsense_170k.json`
- `dataset/{boolq,piqa,social_i_qa,hellaswag,winogrande,ARC-Easy,ARC-Challenge,openbookqa}/{train,test}.json`

I ran the repo's own `data_file/llm_adapt/commonsense_170k/do_train_val_test_split.py` to create the split: seed 58, 120 validation examples, the rest for training.

**Model:** `meta-llama/Meta-Llama-3-8B`, symlinked as `./models/llama3`. The code's pad-token logic needs the model path to contain "llama3"; the README says the last path component should be named `llama3`.

**Environment:** conda env with Python 3.10, torch 2.2.1+cu121, transformers 4.41.1, accelerate 0.27.2, datasets 2.18.0 (pyarrow 15), deepspeed 0.14.0. These are the versions from `talklora.yml`; torch is the cu121 build because the GPU is an H200.

**Training command** (from `codebase/`; same as `train.sh` apart from batch size, see below):
```
python train_talklora.py --peft_type=talklora --model=../models/llama3 --r_ab=32 --enable_grad_ckpt \
  --epoch=2 --lr=3e-4 --batch=32 --grad_acc=1 --dataset=common_170k --seed=36 --warmup=100 \
  --eval_strategy=steps --eval_steps=80 --output_folder=../runs_r32 \
  --target_module=q_proj,k_proj,v_proj,up_proj,down_proj
```
- The r=16 run is identical with `--r_ab=16` and `--output_folder=../runs_r16`.
- The ablation run is the r=32 command with the environment variable `TALKLORA_NO_TALK=1` and `--output_folder=../runs_notalk_r32`.
- The best checkpoint is chosen by validation loss on the 120 validation examples (the code's `load_best_model_at_end`), as the paper describes. The selected checkpoints were:
  - r=32: step 7200 of 10644
  - r=16: step 4640
  - w/o Talking: step 8880

**Evaluation:**
- `scripts/eval_ckpt.sh <run_dir>` runs exactly the commands in `run_eval_decoding.sh`, i.e. `train_talklora.py --dataset=<task> --batch=16 --ckpt=<run> --beam_size=4` for each of the 8 tasks. The only change is that it drops the hard-coded `CUDA_VISIBLE_DEVICES=2`.
- Decoding is beam search with 4 beams and 16 new tokens. Note that the code's evaluation batch size is `batch/4`, i.e. 4.
- Scoring uses the official `eval_commonsense.py`, through `scripts/run_official_eval.py`. That wrapper only fills in the `eval_folder_path` variable, which the README tells users to set by hand.
- `scripts/make_status.py` collects the CSVs into `status.json`. The full CSVs are in `runs_*/runs_*_results_all.csv`.

**Settings that differ from the paper or the repo:**
- **Effective batch size 32**, taken from the paper's Table 6. `train.sh` uses `--batch=8 --grad_acc=2` on one GPU, which gives 16. The paper ran on 4×3090 GPUs.
- **Seed 36**, taken from `train.sh`; the paper gives no seed.
- **Hardware:** one H200 instead of 4×3090.

Everything else matches Table 6:
- r = 32 / 16, 4 experts
- lr 3e-4, linear schedule, 100 warmup steps
- 2 epochs, AdamW
- dropout 0.05
- adapters on Q, K, V, Up, Down
- evaluation every 80 steps, best checkpoint selected

- **The ablation trend is reversed.** The paper says removing the Talking Module costs 1.1 points. We see it **gain** 0.84 points, and the no-talk variant is better on all 8 tasks.
- **Caveat: one seed each.** Seed-to-seed variation for this setup is unknown, but a total swing of about 2 points between the two papers' gaps is large.

Comparing the two, the trained C differs from its random initialization by only about 9% (median relative Frobenius change 0.087, max 0.19; `logs/c_drift.txt`). The "learned" communication matrices in the paper's Figure 4 are therefore mostly random Kaiming-uniform mixing matrices.

## Codebase completeness: MINOR_FIXES

The method and the full experiment pipeline (data split, training, best-checkpoint selection, decoding, scoring) are all released, and they reproduce the main LLaMA3-8B numbers. The only things I had to change:

1. **`codebase/talklora/tuners/talklora.py`, `LoraModel.add_adapter`:**
   - **Problem:** the output dimensions of the layer-shared B matrices are hard-coded for Qwen2.5-7B. The LLaMA3-8B and LLaMA2-7B blocks are present but commented out. As released, LLaMA3-8B fails with a shape mismatch, even though LLaMA3-8B is the paper's main model and the target of `train.sh` and the README.
   - **Fix:** I commented out the Qwen block and un-commented the existing `#llama3-8b` block. No new logic.
   - **How I count it:** I treat this as a model-config toggle, so the as-released result match is still `NUMBERS_MATCH`. Strictly speaking it is a source edit.
2. **Same file, `Linear.forward`:**
   - **What:** I added an opt-in environment flag. With `TALKLORA_NO_TALK=1` the router reads the expert features `A x` directly instead of the communicated `(C ⊗ I)·A x`. That is the paper's description of the "w/o Talking" ablation (§4.5). I also added the `import os` this needs.
   - **Effect on the main runs:** none, because the flag is off by default.
   - **Why:** the release has no ablation code.
3. **Model path:** the tokenizer pad-token logic only works if the model path contains `llama3`. For any other LLaMA3 path it falls back to `unk_token`, which LLaMA3 does not have. I symlinked the model as `models/llama3`, as the README hints.
4. **`run_eval_decoding.sh`:** it hard-codes `CUDA_VISIBLE_DEVICES=2`. I wrote `scripts/eval_ckpt.sh` with the same commands minus that variable.
5. **`eval_commonsense.py`:** the user has to edit `eval_folder_path`. `scripts/run_official_eval.py` does that substitution in memory and then runs the file unchanged.
6. **Data:** I downloaded it from LLM-Adapters, as the README instructs. The split script ships with the repo.
7. **Environment:** the same versions as `talklora.yml`, except torch is the cu121 build and pyarrow is pinned to 15.0.0.

Other observations, which did not need changes:
- **Expert count is hard-coded:** `expert_num = 4` in `LoraModel.__init__`. TalkLoRA* (8 experts) and Table 9 (2 and 3 experts) need a source edit.
- **Silent evaluation fallback:** `_load_best_model` only logs a warning if the best checkpoint path is missing, then evaluates the base model. I hit this during a test with a copied run directory; it does not affect the normal flow.
- **Baseline code is absent:** the repo ships stale compiled files (`talklora/tuners/__pycache__/{moelora,teamlora,lora,molora,molora_1,molora_2,molora2,molora3}.cpython-310.pyc`) without sources or configs. MoELoRA† / TeamLoRA† therefore cannot be re-run from released code, and I did not try to resurrect them from bytecode.
- **Scaling factor α is never applied:** `scaling_ab = alpha / r` is computed but not used in `forward`. With the paper's α = r it equals 1 anyway, so this has no effect.
- **Dropout is applied in three places:** on the input, on the routing weights (after softmax), and on the combined expert output.
