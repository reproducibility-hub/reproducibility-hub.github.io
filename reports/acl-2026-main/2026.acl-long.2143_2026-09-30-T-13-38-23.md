## 1. What the paper claims and what I reproduced

The paper uses SAP self-paced reading data (Huang et al. 2024): 5 constructions, D+ (ambiguous) vs. D− (unambiguous). Layer-wise logit-lens surprisal comes from 19 LMs (GPT-2 ×4, OPT ×7 up to 66B, Pythia ×8 up to 12B).

1. **Exp. 1 / Fig. 2.** RoI slowdowns are estimated from surprisal via a linear regression trained on filler sentences. Every layer underestimates the human slowdown, and later layers estimate it better.
2. **Exp. 2 / Table 2 (and Fig. 3).** Pearson r between layer depth and PPP (ΔLL) in {D+, D−}×{RoI, ¬RoI}. It is positive specifically for D+∩RoI.
3. **Exp. 3 / Fig. 4, Tables 6–12.** Probability-update measures (surprisal update, KL, JS) between the first and last layer improve the fit (PPP). Adding JS to last-layer surprisal helps further (Table 12). The slowdowns these measures predict are tiny (Tables 9–11).

The repo ships everything needed: the preprocessed SAP data (`data/`), scripts for surprisal/KL/JS, regression/PPP/slowdown scripts, a notebook with the aggregation logic, and the authors' own result files (`results/`).

## 2. What I ran

The environment is `conda create -p ./env python=3.11.10`, then `pip install -r requirements.txt` (torch 2.8.0, transformers 4.55.0, tuned-lens 0.2.0, bitsandbytes 0.46.1). It installed without problems.

Commands (drivers `run_all.sh`, `run_tuned.sh`; they mirror `scripts/*.sh`), run from `codebase/`:

```
python src/run_surprisal.py -m <model> -d SAP_SPR -c $HF_HOME/hub [-b 2 | -q 8bit | -q 4bit]   # same -b/-q as scripts/run_surprisal.sh
python src/run_kl.py --divergence both --aggregation sum -m <model> -c $HF_HOME/hub [same -b/-q]
python src/calc_ppp.py -m <m>;  python src/calc_ppp_surprisal_update.py -m <m>
python src/calc_ppp_kl.py -m <m> --aggregation sum [--divergence js];  python src/calc_ppp_kl_delta.py -m <m> --divergence js
python src/calc_slowdown.py -m <m>;  python src/calc_slowdown_surprisal_update.py -m <m>;  python src/calc_slowdown_kl.py -m <m> --aggregation sum [--divergence js]
# tuned lens (App. B.1):
python src/run_surprisal.py -m <model> -d SAP_SPR --method tuned-lens -c $HF_HOME/hub [-q 8bit for pythia-12b];  python src/calc_slowdown.py -m <m> -l tuned-lens
```

Aggregation into the paper's tables uses `aggregate.py`, which re-implements notebook cells 5/6, 8, 11/14/17, 22 and 24. Paper numbers were extracted from the PDF by `parse_paper.py`; Table 8 was typed in by hand because its extracted text is garbled. Comparisons are in `compare.py`, `claims.py`, `fig2_summary.py` and `build_outputs.py`. I checked `aggregate.py` on the authors' released result files: it reproduces paper Tables 2, 7, 8, 9, 10, 11 and 12 **exactly**. That confirms both the aggregation logic and the column ordering.

Settings that differ from the paper:

- **Quantization.** None beyond what the release itself does. `scripts/*.sh` load OPT-13b and Pythia-2.8b/6.9b/12b in 8-bit and OPT-30b/66b in 4-bit; the paper does not mention this. I kept the release's settings.
- **Model list.** The eval scripts list `opt-350m`, which is never computed and is not in the paper, so I skipped it.
- **Table 6 layer.** Table 6 was additionally computed with the first layer set to 0 (see §4). Everything else is exactly the released configuration.

## 4. Why "as released" is TREND_MATCH: Table 6

`calc_ppp_surprisal_update.py` hard-codes `first_layer = "1"`, i.e. the output of the first Transformer block. With it, the released code gives the released `ppp_surprisal_update.csv`, which does **not** match paper Table 6: only 18/190 cells match, with signs and magnitudes similar.

With `first_layer = 0` (the embedding layer), my replica of the script (`scratch/su_layer0_all.py`) reproduces paper Table 6 **exactly** (190/190, diff 0.0) on the authors' released surprisals. On our re-computed surprisals, 139/190 cells are within tolerance, the rest within 1.7 ΔLL, and 178/180 significance markers agree.

The replica is otherwise identical: with layer 1 it reproduces the released CSV with 0.0 diff. Table 9 (SU slowdown) and Tables 7/8 (KL/JS, via `run_kl.py`'s `first_layer_id = 1`) do use layer 1, so the paper is internally inconsistent here. This is a one-constant difference (minor).

## 5. Codebase completeness: MINOR_FIXES

**No source file in `codebase/` was edited** (`git diff -- src scripts visualization` is empty). Fixes and additions, all outside the code or via CLI:

1. **Data path.** The scripts read `data/SAP_SPR/*`, but the repo ships the files in `data/`. I added symlinks `codebase/data/SAP_SPR/{all.txt.averaged_rt, all.txt.averaged_rt.annotation, tokens.json}` pointing to `../`.
2. **Cache dir.** `src/config.py` has `CACHE_DIR=""`, which would make HF cache into the CWD. I passed `-c $HF_HOME/hub` instead.
3. **KL/JS aggregation flag.** `scripts/eval_ppp.sh` and `eval_slowdown.sh` call `calc_ppp_kl.py` / `calc_slowdown_kl.py` without `--aggregation`. Their default is `first`, which reads `kl_divergence.json`, a file `run_kl.sh` never writes: `run_kl.py` defaults to `sum`, so both blocks of `run_kl.sh` produce `*_sum.json`. As released, these lines crash. I passed `--aggregation sum`, matching the paper, the notebook and the released CSVs.
4. **opt-350m.** Listed in the eval scripts but never computed; skipped.
5. **Table 6.** Needs `first_layer = 0` (see §4); computed with the external replica script.
6. **Scripts I wrote.** Drivers `run_all.sh` and `run_tuned.sh`. `aggregate.py`, because the notebook uses author-local/relative paths and nbconvert isn't installed; the notebook's logic was re-implemented, and it is verified exact on the released files. Also `parse_paper.py`, `compare.py`, `claims.py`, `fig2_summary.py`, `build_outputs.py` and `download_models.py`.
7. **Bug, not fixed in the main run.** `run_surprisal.py::correct_prob` subtracts `log2` end-of-word probabilities from surprisals in **nats** (`CrossEntropyLoss`), so the whitespace-trailing correction is scaled by 1/ln 2. I tested a fix (natural log) on 5 models (`scratch/fixrun`, `agg_fix.json`):
   - Table 2 correlations change by ≤ 0.32. There is one sign change, GPT2-xl NPS D+∩RoI −0.07 → +0.13, which moves toward the paper's claim.
   - Figure 2 maximum slowdowns change by < 0.4 ms.
   - Conclusions are unchanged. The paper's numbers were produced with the buggy version, so the main run keeps it.
8. **Results files.** Running the pipeline overwrote the tracked `codebase/results/` files. The authors' originals are kept in `./released_results/`.
