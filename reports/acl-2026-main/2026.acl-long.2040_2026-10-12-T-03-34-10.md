## Summary

- MTA's own Table-1 numbers reproduce well on 4 of 5 LaMP tasks. Averaged over 3 seeds with the paper's Table-4
  hyper-parameters:
  - **within tolerance:** LaMP-1 acc/F1 (.537/.536 vs .542/.541), LaMP-3 MAE (.198 vs .198), LaMP-4 R-1/R-L (.228/.212 vs .240/.213), LaMP-5 R-1/R-L (.506/.447 vs .529/.466);
  - **higher than reported:** LaMP-2 acc/F1 (.500/.369 vs .444/.259);
  - **worse:** LaMP-3 RMSE (.483 vs .435; seed spread .445–.520). This is also worse than the best baseline RMSE the paper reports (PROPER .4746).
- The baselines (RAG, OPPU, PER-PCS, PROPER) are not in the release, so the "MTA beats SOTA" claims could only be
  checked against the paper's printed baseline numbers. Our MTA numbers exceed the paper's best printed baseline on
  LaMP-1 (marginally: acc .537 vs PER-PCS .534, F1 .536 vs .529), LaMP-2, LaMP-3 MAE and LaMP-4, but **not** on LaMP-3
  RMSE (.483 vs PROPER .475) and **not** on LaMP-5 (R-1/R-L .506/.447 vs PROPER .512/.449).
- **Ablation (Table 2, supplementary):**
  - Merged-Only ≫ Adapt-Only reproduces.
  - The paper's claim that the final stacked LoRA gives a "significant performance jump" over Merged-Only does **not**
    reproduce: Merged-Only is as good as or better than full MTA on LaMP-1 (.559 vs .537), LaMP-3 MAE (.189 vs .198),
    LaMP-4 (.229 vs .228) and LaMP-5 (.509 vs .506). It is slightly worse only on LaMP-2 (.486 vs .500) and LaMP-3 RMSE.
- **Bugs and inconsistencies found:**
  - the merge weights are swapped relative to Eq. 6;
  - `run_experiment.sh` hard-codes 1 epoch / 5e-5 instead of Table 4;
  - evaluation uses a 4-bit NF4 model;
  - the scholarly and news eval scripts skip the chat template used in training, which makes LaMP-5 Adapt-Only collapse to ROUGE-1 0.02.
  None of these changes the main MTA numbers much (see Discrepancies and supplementary runs).

## What was attempted

Target: **Table 1 (main results), MTA column**, on the LaMP tasks the paper uses (LaMP-1 citation, LaMP-2 movie tagging,
LaMP-3 product rating, LaMP-4 news headline, LaMP-5 scholarly title), with Meta-Llama-3-8B-Instruct, the released
`test_100` test users, and the released pipeline. Ablations of **Table 2** (Merged-Only / Adapt-Only) were also run
(supplementary) since they are cheap once the bank exists. Baselines (RAG, OPPU, PER-PCS, PROPER) are **not** in the
release and were not run, so "MTA beats X" claims are judged `NOT_COMPARABLE`.

Pipeline, per task (all with the released code unless noted):
1. **Data**: the repo ships `data/<task>/test_100/test_100.json` but not `user_anchor_candidate.json`. The README says
   processing "follows Per-Pcs"; Per-Pcs publishes its processed LaMP data (Google Drive id
   `1KyiQGWGxNVcqoRXqgMqaq11xEiVJ2Axn`, linked from the Per-Pcs README), which contains exactly
   `<task>/user_anchor_candidate.json`. Its statistics match the paper's Table 3 for LaMP-1/3/4/5
   (e.g. LaMP-1 max 607 / min 40 / avg 88.4; LaMP-3 1021/97/202.5; LaMP-5 911/47/94.3; LaMP-4 945/7/31.3), so this is
   very likely the authors' pool. (LaMP-2 does **not** match Table 3: the Per-Pcs movie pool has max 333, avg 12.3 vs
   paper 1289/204.5.) The MTA test users of LaMP-1/3/5 are all inside this candidate pool (5 for LaMP-2, 0 for LaMP-4);
   since the paper states test and bank users are disjoint, I removed the test users from the pool
   (`scripts/make_candidates.py`).
2. **Anchor selection**: `python select_anchor.py --candidate_path ./data/<task>/user_anchor_candidate.json --task_name <task> --k 50`
   (DeBERTa-v3-large mean embeddings + K-Means, most active user per cluster). Run through `scripts/run_tf32.py`
   (only enables TF32 matmuls, for speed). For **product_rating** the full run (2.66M reviews through DeBERTa-large) was
   infeasible (~25 h), so I used `scripts/select_anchor_subsample.py` = identical script except the user embedding
   is the mean over the user's **first 20** history items (anchor = still the most active user of the cluster, trained on
   the full history) -> **scaled-down anchor selection for LaMP-3**.
3. **Meta-LoRA bank**: `python prepare_meta_lora.py --task_name <task> --top_k 1` and the generated
   `run_<task>_k1_training.sh` (LLaMA-Factory v0.9.2, LoRA r=8, 3 epochs, lr 1e-4, bs1xGA2). The identical
   `llamafactory-cli train <yaml>` commands were run several at a time on the one GPU (`scripts/run_bank_parallel.sh`,
   `scripts/run_bank_priority.sh`). For scholarly_title and product_rating only the anchors that are retrieved (top-2) by
   at least one test user were trained (48/50 and 38/50) — the other anchors never enter any merged model, so this does
   not change any result.
4. **Retrieval**: `python dense_retrieval_matcher.py --task_name <task> --top_k 2` (bge-small-en-v1.5).
5. **Merge -> stack -> evaluate**: `run_experiment.sh` does per user: `simple_lora_merger.py` -> `llamafactory-cli export`
   (writes a 16 GB merged model) -> `llamafactory-cli train` (rank-4 LoRA) -> `eval/<task>/evaluate_<task>.py` ->
   `aggregate_results.py`; ~2 min/user. To fit 5 tasks x several settings in the time limit I wrote
   `scripts/mta_fast_runner.py`, an in-process equivalent: same merge formula, same data scripts (it calls the released
   `create_training_data.py` / `create_eval_data.py`), same LoRA/Trainer hyper-parameters and LLaMA-Factory tokenization
   (llama3 chat template parsed from the tokenizer, loss on the response only, cutoff 2048), and it calls the **released
   evaluation scripts' `main()`** with only model loading patched to the in-memory model (their 4-bit NF4 loading is
   emulated by NF4 quantize->dequantize of every decoder Linear, as `BitsAndBytesConfig` defaults). Aggregation uses the
   released `aggregate_results.py`.
   **Validation**: on the first 3 movie_tagging users, the released `bash run_experiment.sh movie_tagging 3` and the fast
   runner (same hyper-parameters) gave identical predictions for all 3 users and training losses 0.8299/0.8529/0.9099
   vs 0.8256/0.8590/0.9131 (`logs_released_movie_tagging_3users.txt`, `codebase/final_eval_results/hybrid_movie_tagging`
   vs `codebase/fast_runs/movie_tagging_val_released_hp`).

## Why not fully reproduced
- LaMP-3 RMSE is ~11 % worse than reported, with high seed variance, and LaMP-2 is much better than reported. These
  differences are plausibly caused by the anchor pool and bank: the Per-Pcs pool does not match the paper's LaMP-2
  statistics, 9 vs 50 anchors for LaMP-2, and scaled-down LaMP-3 anchor selection. No released anchors or checkpoints exist to check this.
- The stacked-LoRA (adapt) stage, which the paper presents as crucial, gives no measurable gain over the merged model on
  4/5 tasks in our runs.
- Baselines are not released, so comparisons with them are NOT_COMPARABLE.
- Compute/time: LaMP-3 anchor selection had to be scaled down to fit the 20 h job limit.

## Discrepancies
- **[code_vs_paper/major] run_experiment.sh (Stage 1 alpha computation) + simple_lora_merger.py** — paper: Eq. 6: anchor i gets weight sim(u,s_i)/sum_j sim(u,s_j), i.e. the top-1 anchor gets s1/(s1+s2) — code/other: alpha = s1/(s1+s2) is passed to simple_lora_merger.py, which gives weight (1-alpha) to --lora_path1 (top-1 anchor) and alpha to --lora_path2 (top-2 anchor): the weights are swapped (top-1 anchor gets s2/(s1+s2)) — affects results: True
- **[code_vs_paper/minor] run_experiment.sh, Stage 4 llamafactory-cli train arguments** — paper: Table 4: stacked-LoRA epochs/LR per task: LaMP-1 2/5e-5, LaMP-2 3/1e-4, LaMP-3 1/5e-5, LaMP-4 3/1e-4, LaMP-5 2/5e-5 — code/other: hard-coded --num_train_epochs 1 --learning_rate 5e-5 for every task (with 10 training samples, LaMP-2/LaMP-4 users get a single optimizer step) — affects results: True
- **[code_vs_paper/minor] eval/{citation,movie_tagging,product_rating,scholarly_title}/evaluate_*.py** — paper: No mention of quantization; models are fine-tuned in bf16 (Sec. 4.1 / App. D) — code/other: the merged base model is loaded in 4-bit NF4 (BitsAndBytesConfig load_in_4bit) for evaluation; news_headline is evaluated in bf16 — affects results: True
- **[code_vs_paper/major] eval/scholarly_title/evaluate_scholarly_title.py and eval/news_headline/evaluate_news_headline.py run_evaluation()** — paper: Same prompt templates (App. E) for training and inference — code/other: these two scripts tokenize the raw instruction text without the Llama-3 chat template, while the stacked LoRA (and meta-LoRAs) are trained by LLaMA-Factory with the chat template (and the other three eval scripts use apply_chat_template); for scholarly_title the un-merged base model + adapter then emits placeholders such as '_______' (Adapt-Only ROUGE-1 0.03 vs paper 0.49) — affects results: True
- **[code_vs_paper/minor] dense_retrieval_matcher.py** — paper: Sec. 3.3: concatenated history is encoded 'using the dense encoder' (the DeBERTa-v3-large encoder introduced in Sec. 3.2) — code/other: retrieval embeddings use BAAI/bge-small-en-v1.5 (sentence-transformers) — affects results: True
- **[code_vs_paper/minor] select_anchor.py** — paper: Sec. 4.1: test users and Meta-LoRA-bank users are completely disjoint; V anchors (one per K-Means cluster) — code/other: the candidate pool is used as-is (the released test users of LaMP-1/3/5 are all contained in the Per-Pcs user_anchor_candidate.json pool; no exclusion), and clusters whose most active user has <=10 history items get no anchor (movie_tagging: only 9 of 50 clusters yield an anchor) — affects results: True
- **[paper_internal] Sec. 4.1 / App. B vs Table 1 (LaMP-2)** — paper: 'for the test set of each task, we randomly select 100 users' — code/other: the LaMP-2 numbers in Table 1 are multiples of 1/72 (e.g. .2917=21/72, .4444=32/72), matching the released LaMP-2 test file, which has 72 users — affects results: False
