# Reproduction report — PIAST: Rapid Prompting with In-context Augmentation for Scarce Training data (ACL 2026, 2026.acl-long.515)

## Verdict

- **Verdict: PARTIALLY_REPRODUCED**
- **Result match (after fixes / re-scoring): MIXED** · **Result match as released: MIXED**
- **Coverage: SCALED_DOWN**
- **Codebase completeness: MISSING_SCRIPTS**. The released code was run **without any source edits**. Pipelines for DeepMath, MATH500 and MedQA (Tables 4 and 5) are absent, and the release contains a SARI bug.

In one paragraph: the released code (https://github.com/Batorskq/PIAST, linked in the paper) runs as-is for the 7 classification tasks, SAMSum, ASSET and GSM8K with Qwen2.5-7B-Instruct.
- **What reproduces:**
  - limited-budget PIAST on classification (Table 2), summarization (Table 3) and GSM8K (Table 5);
  - the PIAST(I) ablation;
  - PIAST(E) on GSM8K and on 6 of 7 classification tasks.
- **What doesn't:**
  - Text simplification: the paper reports SARI 54.52 and SOTA. The released code gives about 34, and about 45 after fixing the reference handling. Both are *below* the instruction-only zero-shot prompt (47.5 with the fixed metric).
  - PIAST(E) on TREC: 65.27 vs 78.40.
  - Because of TREC, our PIAST(E) 7-task average is 80.91. That is below the 82.14 the paper reports for PRL, so the "new state of the art on classification" claim is not supported, although the average itself is within the numeric tolerance of the paper's 82.79.

## What was run

- **Model:** Qwen/Qwen2.5-7B-Instruct, used for all three roles (proposer, improver, evaluator) as in the paper. vLLM 0.10.1.1 with bf16. Decoding is the released code's own: proposer T=0.6, improver T=0.7, evaluator greedy.
- **Hardware:** 1× NVIDIA H200, shared by 4–6 concurrent vLLM processes. The paper used one A100, so wall-clock times are not comparable.
- **Hyper-parameters:** the paper's Table 11 / README values, passed on the command line: k=16, s=70, m=10, r=5, P=3. I=15 for PIAST and I=150 for PIAST(E); PIAST(I) uses I=0.
- **Command:** each (task, seed) ran as its own process, so the hard-coded seed-1 early-stop could not drop seeds:
  ```
  cd codebase && ../env/bin/python <task>.py --run-grid-search --grid-k 16 --grid-infer-sizes 70 \
     --grid-craft-iters {15|150|0} --grid-refine-cands 10 --grid-replay-add 5 --shapley-permutations 3 \
     --eval-on-test --use-vllm-for-evaluator --grid-seeds {1|2|3} --gpu-mem-util {0.17|0.2} \
     [--dataset-path dataset/subj_test.jsonl --infer-dataset-path dataset/subj_infer.jsonl] \
     --grid-results-csv ../results/<task>_<L|E|I>_s<seed>.csv --shapley-log-dir ../logs/shap/<task>_<tag>_s<seed>
  ```
  Here `<task>` ∈ {sst2, cr, mr, sst5, news, trec, subj, sum, sim, gsm8k}. The job list is in `jobs.json` (generated by `make_jobs.py`) and was run by `scheduler2.py`. Logs are in `logs/` and per-seed CSVs (including final prompts) in `results/`.
- **Data:** the `dataset/*.jsonl` files shipped in the repo. The test sets are the same as the authors'; note that the GSM8K test file has 2000 items.
- **Extra analyses written by the reproducer, outside the codebase:**
  - `sim_rescore.py` regenerates ASSET test outputs from the saved prompts and scores SARI two ways: as released, and with the 5 references split into separate reference streams. It also scores the instruction-only zero-shot prompt.
  - `gsm8k_strict_eval.py` regenerates GSM8K test outputs from the saved prompts and scores them with a strict metric: the integer after the last `Final Answer:`, compared with the gold answer with commas removed.

| Item | Paper | Ours | Why |
|---|---|---|---|
| Seeds | 3 runs everywhere | 3 seeds (1,2,3) everywhere, **except GSM8K PIAST(E): 2 seeds (2,3)** | GSM8K I=150 takes about 20–30 h per seed here. The replay buffer grows by r=5 items every iteration, so iteration cost grows linearly. Seed 1 was killed at iteration 69 to fit the 48 h budget. |
| PIAST(E) on SAMSum / ASSET | reported (Tables 3, 10) | **not run** | compute budget; the ASSET verdict wouldn't change because the limited run already fails |

| Baselines (MI, NI, APE, APO, GA, DE, GRACE, PRL, PromptWizard) | reported | **not run** (except a zero-shot instruction-only sanity check on ASSET) | not in the release, so claims of the form "beats X" are judged against the paper's own baseline numbers only |
| GPU | A100 | H200 shared by several processes | — |
| `--grid-seeds` | — | ran one seed per process | avoids the hard-coded seed-1 early-stop, which skips the other seeds |

## Why it is not fully reproduced
1. **Simplification (ASSET):**
   - *Code bug* (`sim.py::eval_sari_on_items`): the test file stores the 5 ASSET references per sentence as one tab-joined string, and the code passes that string to `easse.corpus_sari` as a *single* reference. This gives SARI ≈ 34. Crafting uses the infer split, which has a single reference per item, so only test-time scoring is affected.
   - With references split correctly, the same prompts score ≈ 44.8 — still about 10 points below the paper's 54.52.
   - The zero-shot instruction "Simplify the text." without any examples scores 47.5 (36.3 with the released metric), so PIAST examples hurt in our runs.
   - We found no configuration in the release that yields ≈ 54.5.
2. **TREC with I=150** degrades in all 3 seeds (66.0, 64.2, 65.6). The examples are reduced to 9–10, and the long Shapley loop on 70-item subsets plus a growing replay buffer appears to overfit. The paper reports 78.40±1.22. Cause unknown; possibly run-to-run differences in the stochastic proposer.
3. **Scale-down:** the main source of cost is the replay buffer, which is never truncated. After t iterations the evaluation set has 70+5t items, so I=150 costs about 42× an I=15 run, not 10×. GSM8K PIAST(E) therefore ran with 2 seeds, and SAMSum/ASSET PIAST(E) were skipped.
4. **Missing parts of the release:** no DeepMath, MATH500 or MedQA pipelines, and no baseline code.

## Codebase completeness: MISSING_SCRIPTS
- No changes were made to any file in `./codebase` (`git status` is clean; the `__pycache__/` left by imports was deleted).
- **Environment:** the repo has no requirements file. We used Python 3.11, `vllm==0.10.1.1` (torch 2.7.1+cu126), `transformers==4.55.4` (transformers 5.x is incompatible with vllm 0.10), `rouge`, and `easse` from git.
- **Missing scripts:** DeepMath (data present), MATH500 and MedQA (data absent) — all part of Tables 4 and 5.
- **Bug affecting results:** SARI multi-reference handling in `sim.py` (see above).
- **Metric leniency:** GSM8K scoring in `gsm8k.py` counts an answer correct if the gold integer appears anywhere in the output, and the gold answer is parsed with a first-integer regex (`"1,200"` → `1`, 19 of 2000 test items). Strict re-scoring lowers accuracy by about 1.8 points (limited) and 1.8 points (extended).
- **Early-stop:** the seed-1 early-stop thresholds are hard-coded (e.g. acc 0.68 in cr/mr/sst2, 0.764 in trec, 0.54 in sst5, SARI 45). Below threshold, the remaining seeds are skipped and the prompt is not saved; this happened to `sim_L_s1`, whose prompt therefore couldn't be re-scored.
- **Config defaults that differ from the paper:** `--grid-seeds 1,2,3,4` (paper: 3 runs), `--shapley-permutations 1` (5 in `subj.py`; paper P=3), and grid defaults that are search ranges. The paper's values were passed explicitly.
- **Wrong paths:** `subj.py` default data paths point to non-existent `dataset/subjectivity_*.jsonl`.
- **README flag:** the README uses `--grid-seed`, which works only through argparse prefix matching of `--grid-seeds`.
- **Dead code path:** `gsm8k.py` `main()` non-grid path uses the undefined `crafted_examples` (NameError). The README command doesn't hit it.
- **Reproducer-written helpers** (all outside the codebase): `make_jobs.py`, `scheduler2.py`, `aggregate.py`, `make_report.py`, `finalize.py`, `sim_rescore.py`, `gsm8k_strict_eval.py`.

## Discrepancies
- **code_vs_paper (major)** — `sim.py` SARI uses a single tab-joined reference instead of the 5 ASSET references. This affects the reported simplification numbers.
- **code_vs_paper (major)** — the GSM8K metric is lenient: the gold integer can appear anywhere in the output, and the gold is parsed with a first-integer regex. The paper only says "accuracy". Inflation is about 1.8 points.
- **code_vs_paper (major)** — DeepMath, MATH500 and MedQA results are reported, but no code exists for them (and no data for MATH500 or MedQA).
- **code_vs_paper (minor)** — the defaults (4 seeds, P=1 or 5) differ from the paper's 3 runs and P=3. The README command also uses 4 seeds.
- **code_vs_paper (minor)** — the early-stop on seed 1 can silently drop seeds from the "average over three runs".
- **paper_internal** — the abstract says PIAST is "third-best on MedQA", while Section 4.2 says "second-best accuracy". Table 4 has PRL > PIAST(E) > PIAST.
