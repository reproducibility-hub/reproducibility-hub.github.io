# Reproduction report — SADA: Bridging In-Context Learning and Fine-Tuning via State-Aligned Distillation Adapters (ACL 2026, 2026.acl-long.1046)

## Verdict

**PARTIALLY_REPRODUCED.** Result match `MIXED`, coverage `SCALED_DOWN`. As released, the code does not run (`DOES_NOT_RUN`): it imports a module that is missing from the repo.

* **NLU post-training claim: reproduced** (Table 1 NLU columns, Table 3 loss ablation, Qwen2.5-1.5B, 20-shot).
  * SADA, after the released two-stage training: **87.08 Seen / 58.38 Unseen**. Paper: 86.50 / 56.68 (Table 1) and 87.38 / 57.16 (Table 3).
  * Loss ablation: w/o L_MSE 85.43 / 56.98 (paper 85.84 / 56.32); w/o L_LM 81.55 / 59.74 (paper 79.90 / 55.46). The ranking Full > w/o MSE > w/o LM holds on Seen and on the average.
  * SADA beats full-prompt ICL on Seen (87.08 vs 83.42) and falls short of it on Unseen (58.38 vs 61.14), as the paper describes.
  * Our ICL baseline is stronger than the paper reports (Unseen 61.14 vs 57.48; Seen 83.42 vs 80.22). That shrinks SADA's Seen gain over ICL from +6.3 to +3.7 and widens its Unseen gap from −0.8 to −2.8 (flag `BASELINE_STRONGER_THAN_REPORTED`).
* **PG19 long-context claim: not reproduced** (Fig. 3, Qwen2.5-1.5B). After Stage I training with the released code and config, SADA does **not** lower PG19 perplexity relative to the plain sliding-window model. It is tied at 2K and worse from 4K to 128K, by up to +0.35 PPL. The paper claims SADA is lowest at every length, with gains growing with context. This held under two evaluation protocols. On the released validation split the result is the same: student PPL 17.02 at step 200 vs 16.99 for the untrained model, with memory switched off in effect because meta_lora_B is zero-initialised.
* **Efficiency (Fig. 4):**
  * Peak-memory trend reproduced: SADA stays at about 4.5–5.8 GB while ICL grows with length.
  * Decode-latency claim only partly holds. In our eager implementation SADA (~27 ms/token, flat) is slower than ICL up to 32K (18–21 ms) and faster only at ≥64K.

Not run:
* 3B and 7B backbones.
* Summarization and QA columns (Table 1 GovReport/QMSum, Table 2): the training data is not released or described.
* StreamAdapter, GenerativeAdapter, SnapKV and fine-tuning baselines: not runnable from the release.
* Fig. 5 shot sweep, and the feature-source ablation (Table 3, lower half; not implemented).

## What was run (all on 1× H200, Qwen2.5-1.5B-Instruct, bf16, FlashAttention-2)

Environment: conda env (py3.10), torch 2.5.1+cu124, transformers 4.44.2 (required by the old Qwen2 attention API the model file uses), deepspeed 0.16.4, flash-attn 2.7.3 wheel, plus `rouge` and `python-Levenshtein` (imported by `metrics.py` but missing from `requirements.txt`). DeepSpeed needs `CUDA_HOME` set (module CUDA/12.6.0) even with `torch_adam`.

1. **Data.** None is released and there are no preparation scripts, so I wrote all of it:
   * `repro_scripts/prep_pg19.py` builds the expected `pg19_chunks_8192_0.9_{train,test}.jsonl`: non-overlapping 8192-token chunks, with the first 90% as the compressed prefix and the last 10% as the student/target segment. Train: 14,689 chunks from PG19 train shards 0–1 (≤8 per book). Validation: 187 chunks from the test split.
   * `repro_scripts/prep_nlu.py` builds K=20-shot NLU files in the `create_dataset` format.
     * Seen tasks SST-2/BoolQ/CB/RTE/COPA: training on the train splits (8,610 instances, each with 20 randomly drawn train demos); test on the validation splits (BoolQ subsampled to 2,000).
     * Unseen tasks ARC-e, ARC-c, HellaSwag (2,000 sampled), OBQA, PIQA, WinoGrande: validation splits, with a fixed set of 20 demos from each task's train split.
     * Chat templates follow paper Appendix C. Of the 20 demos, 18 are compressed into memory and the last 2 stay as an explicit prefix (Sec. 4.3).
2. **Stage I (SWSD, PG19)** — `repro_scripts/run_stage1.sh` uses the released `scripts/train.py` with the flags of `examples/train_pg19.sh` (kl 1, mse 1, lm 0, T=3, lr 6e-5, chunk 64, 16 queries, rank-head 16, targets q/o/up/gate/down, max_len_per_forward 512). Differences: 1 epoch (paper App. B.2; the script uses 5), 1 GPU with grad-accum 64 (global batch 64, as in the paper), paper optimizer/scheduler (see config fixes). 229 optimizer steps, ~8 h.
3. **Stage II (TAD, NLU 20-shot)** — `repro_scripts/run_stage2.sh` uses the released `train.py`, dataset `nlu_20`, loss L_LM + L_MSE (kl 0, mse 1, lm 1), lr 6e-5, 3 epochs, global batch 64, initialised from the Stage I checkpoint (399 steps). The two Table 3 ablations were trained identically with mse=0 and with lm=0, respectively.
4. **Evaluation drivers** (not in the release; written by me on top of the released functions):
   * `repro_scripts/eval_nlu.py`: released `create_dataset` → `prepare_nlu_dataset_test` / `prepare_nlu_icl_dataset` → released collators → released `_test` (mean option log-prob multiple choice). Modes:
     * `sada`: memory warm-up + use_memory.
     * `icl`: all 20 demos explicit (released ICL preprocessing).
     * `nomem`: only the 2 explicit demos.
   * `repro_scripts/eval_pg19_long.py`: PG19 test books with ≥128K Qwen tokens (18 books), using the first L tokens.
     * Protocol A: stride 512, explicit window 1024. Sliding Window = window only; SADA = window + memory of every evicted token, compressed in 512-token forwards through the released `update_memory`.
     * Protocol B: stride = window = 1024, which matches the training student exactly (no explicit context before the segment).
     * Full-context reference up to 32K.
   * `repro_scripts/eval_efficiency.py`:
     * ICL: chunked prefill into a KV cache, then 64 decode steps.
     * SADA: compress all but the last 1024 tokens into memory, then decode with memory.
     * Peak memory from `torch.cuda.max_memory_allocated`.

## Settings that differ from the paper

* **Scope:** only Qwen2.5-1.5B-Instruct (no 3B/7B) and only K=20.
* **No baselines from the release:** StreamAdapter, GenerativeAdapter, SnapKV and Fine-tuning were not run. The release does not contain runnable code or configs for them (see codebase notes). Claims of the form "beats StreamAdapter/GenerativeAdapter" are therefore NOT_COMPARABLE.
* **Data built by me:** the paper does not specify Stage I/II data sizes, test-set sizes, demo selection, aggregation (I use the macro mean over tasks) or prompt details beyond Appendix C.
  * Stage I: 14.7K PG19 chunks of 8K tokens (~120M tokens), 1 epoch. The paper's Stage I corpus size is unknown, and its total training took ~11 h on 8×40GB GPUs.
  * Stage II: 8,610 training instances.
* **Single GPU:** grad-accum 64 instead of 8 GPUs × 8.
* **Speed-only change:** `torch.compile` of `MetaLinear.update_meta_weight`, enabled through the env flag `SADA_COMPILE_UPDATE=1`, used for Stage I and PG19 eval. Training losses are identical to eager at the 4th decimal.
* **Not run:** summarization/QA (GovReport/QMSum/HotpotQA/2Wiki). These require a "fine-tune the PG19 checkpoint on downstream Sum/QA tasks" step whose data is not described or released. The released `longbench` registry entry uses the LongBench *test* file as its training file.

Nothing runs as released. `pscan` implements the gated recurrent state update of Eq. 6, so a piece of the method's core is absent. I reconstructed it as `src/meta_hf/ops.py`: sequential scan H_t = A_t·H_{t−1} + X_t, unambiguous given how it is called. `gen_meta_linear.py` (GenerativeAdapter variant) is also missing.
2. **No datasets and no data-preparation scripts** for any experiment: PG19 chunks, NLU K-shot files, LongBench/summarization training data.
3. **No evaluation pipeline for Fig. 3 (long-context PPL across 2K–128K) or Fig. 4 (efficiency).**
   * The `nlu_icl` / `nlu_unseen_icl` registry entries crash in `train.py`: KeyError on `prepare_func` / `train_data_path`.
   * Dataset paths in `dataset_info.py` are relative to the CWD. `DATA_DIR` / `make_paths_configurable` are never applied, so I ran from the data directory.
4. **Baselines and feature-source ablations not runnable.**

   * `StreamAdapterLinear` is present but not wired into the model (forward/update dispatch only handles `MetaLinear`).

5. **DeepSpeed config does not work as released:** `train_batch_size: "auto"` and `warmup_max_lr: "auto"` are never resolved, so training crashes. I wrote `repro_configs/ds_zero2_bf16_paper.json`:
   * removed `train_batch_size`;
   * paper optimizer: AdamW betas (0.9, 0.95), eps 1e-6;
   * WarmupCosineLR with linear warmup;
   * `torch_adam: true`, because the fused_adam JIT build failed.
