**In short:** the repository implements only the memorization-measurement stage. Training, the client datasets, and
checkpoints are missing, and the Dialog client partition cannot be rebuilt (the category labels are not public). I
rebuilt the data and wrote the FedAvg / FedProx / CL training myself, then ran the released measurement code (after
a crash fix and speed-only changes) at the paper's scale (n = 4000 prefixes per client) for the main Qwen2.5-3B
experiments (Tables 1–5).

A key, undocumented training detail decides the outcome. If only LoRA adapters are trained, the model never learns
to emit `<|im_end|>`, because that token's embedding is untrained in the Qwen2.5-3B base model. It then rambles to
the 2048-token cap, and every MR is 5–15× the paper's, with non-zero memorization in classification. When the
embeddings/LM head are trained too, generations stop, as the paper's Table 6 implies.

In that regime, the qualitative findings mostly reproduce:
- MR_Intra > MR_Inter in all tasks.
- Classification MR = 0.000.
- top-p gives the most memorization.
- FedProx > FedAvg in all four tasks.
- No consistent CL-vs-FL direction.

Absolute values are 1.5–2.5× the paper's for summarization, dialog and QA, and the prefix-length trend only partly
holds. Because the data had to be rebuilt or substituted, all comparisons are labelled NOT_COMPARABLE.

`https://github.com/tinnakitudsa/FL_memorization_framework` (linked from the paper) contains **only the memorization-measurement
stage** of the framework (Fig. 1 C: prefix/suffix split → generation → Elasticsearch top-10 retrieval → PAN2014
verbatim/paraphrase/idea detector) plus a result-aggregation script. It does **not** contain:

- any FL / CL training code (FedAvg, FedProx, centralized), configs, LoRA/full-FT choice, or checkpoints
  (paper App. C only says "LLaMA-Factory, lr 2e-4, bf16, batch 64, 3 rounds");
- data-processing code for the 4 tasks × 3 clients, or the client splits themselves;
- the task-performance evaluation (ROUGE-L / BLEU / accuracy) used in Tables 2, 15, 17, 18.

## What I did

1. **Data** (`scripts/prepare_data.py`): rebuilt the 4 tasks × 3 clients (30K each, 27K train / 3K test) from the
   public sources in App. B:
   - arXiv (staeiou/arxiv_archive per-category TSVs, primary category);
   - PubMedQA (`qiaojin/PubMedQA`, MeSH-tag groups exactly as in App. B.3);
   - PubMed-200k-RCT (Dirichlet α=5 label split);
   - HealthCareMagic (UCSD MedDialog raw files). **The Dialog grouping cannot be rebuilt**: the
     HealthCareMagic category labels in App. B.2 are not in any public release I could find. I substituted a k-means
     (k=3, TF-IDF) non-IID partition.
   Input-length medians match Table 6 (dialog 86 vs 86, QA 328 vs 325, summarization ≈180 vs 184).
2. **Training** (`scripts/fl_train.py`, written from scratch): FedAvg / FedProx (μ=0.01, not given in the paper) /
   centralized, 3 clients, 3 rounds × 1 local epoch (CL: 3 epochs), lr 2e-4, batch 64, bf16. LLaMA-Factory-style
   qwen chat template, loss on the response only, LoRA r=8/α=16 on all linear layers, cosine schedule. Two variants:
   - **A (LoRA-only)**: embeddings frozen and tied.
   - **B ("emb")**: LoRA plus trainable, untied `embed_tokens`/`lm_head` (as LLaMA-Factory `additional_target`).
     Variant B was added after finding that, in Qwen2.5-3B *base*, the embedding rows of `<|im_start|>`/`<|im_end|>`
     are untrained (L2 norm 0.38 vs 1.09 average). Variant A therefore never learns to emit `<|im_end|>`:
     p(`<|im_end|>` | prompt + gold title) = 3e-4 after training, versus 0.87–0.97 for variant B. Variant A models
     continue every memorization prompt to the 2048-token cap (median generated length 1995 tokens), while variant B
     models stop (summarization median 86). Only the short-generation regime is compatible with the paper's Table 6
     (median generated length 1–78 tokens) and with its explanation of the 0.000 classification result. So **variant B
     is the primary comparison**, and variant A is reported as a sensitivity result.
3. **Memorization measurement**: the release's `src/memorization.py` pipeline (same arguments as `eval.sh`) with
   n = 4000 sampled training prefixes per client, top-k (k=40) / temperature 1.0 / top-p 0.8 decoding, prefix
   lengths 10/30/50/100, `max_generated_length` 2048. Metrics come from the release's own counting code
   (`convert_result2table.get_pair_mem_count`): MR_Intra / MR_Inter are means over same-client / cross-client pairs
   (equal client sizes), and MR_Total is the union over pairs (App. D).
   - Variant A: because every generation hit the cap, the decoding/prefix ablations, FedProx and the A-variant
     Table 1 rows were run with `max_generated_length 512`, to fit the time budget. The 512 rows of the main config
     are derived by truncating the 2048 generations, which has the same distribution. 2048 runs were done for all
     4 FedAvg mains.
   - Variant B: everything at the release's 2048 cap.
4. **Task performance** (`scripts/perf_eval.py`, written by me): greedy decoding on 1000 test samples per client.
   ROUGE-L/BLEU-4 follow LLaMA-Factory's predict metrics (jieba + rouge-chinese, NLTK BLEU-4 with smoothing method 3).
   For classification, accuracy uses the first upper-case word of the answer (variant A never stops generating).

## Changes made to the released code (uncommitted diff in `./codebase`)

- `src/memorization.py`: `--batch_size` was parsed as `str`, which crashes `chunk_list` (TypeError); changed to `int`.
  **The release does not run without this fix.**
- `src/prepare_elasticsearch.py`: added `generate_suffixes_vllm`, a vLLM generation path with the same sampling
  settings as `get_decode_parameters` plus HF defaults (top_k 50 / top_p 1 / T 1 unless overridden), the same
  2048 total-length cap, stop at eos, bf16. HF `generate` in fp32 with batches waiting for 2048-token stragglers
  needed ~150 s per 16 prefixes.
- `src/federated_pipeline.py`:
  - `SINGLE_PASS`: the release loops over the 3 clients and, for a single global model, regenerates and re-scores
    all 9 pairs 3 times, keeping only the last pass. I run one pass.
  - `GEN_ONLY` split, so the GPU and CPU stages can be pipelined.
  - `federated_memorization_parallel`: same computation, with the 9 pairs × 250-prefix shards evaluated in a
    process pool. RoBERTa paraphrase scoring runs on CPU; `src_id` is re-offset so the per-prefix de-duplication
    is unchanged.
  - Reuse of an existing generation file regardless of client name.
- `src/PAN2014.py`: exact-output caching only: the Punkt sentence tokenizer (nltk 3.9 rebuilt it on every call),
  Porter stems, and the spaCy NER pipeline (the release reloaded `en_core_web_sm` for every sentence pair).
  This gave ~8× speed-up with no change in output.
- `src/convert_result2table.py`: the repetition filter read `li[i]["source_string"]`, which verbatim records don't
  have (KeyError as soon as any verbatim match exists). It now falls back to `string`.

## Why the result is not a clean reproduction

1. **Missing data (MISSING_DATA).** Client splits are not released. The Dialog partition depends on
   HealthCareMagic category labels that no public release contains, so I substituted k-means groups. The other three
   tasks are rebuilt from public data following App. B, but the exact samples differ.
2. **Missing scripts.** FL/CL training, data processing and performance evaluation are absent, so I wrote all of
   them. The training recipe is underspecified: LoRA vs. full fine-tuning, FedProx μ, cutoff length, whether
   embeddings are trained. The choice of whether embeddings are trained alone changes MR by an order of magnitude
   (variant A vs. B).
3. **The release does not run as-is.** `--batch_size` crashes generation, and `convert_result2table.py` crashes on
   any verbatim match. As released, its HF fp32 generation with a 2048-token cap plus single-threaded PAN2014
   (which reloads spaCy and Punkt on every call) was far too slow for 12K prefixes × ~30 configurations on one GPU,
   so I added an equivalent vLLM path, parallelism and caching.

## Scale and reductions vs. the paper

- Variant A ablations, FedProx and the 512-row Table 1 entries used `max_generated_length` 512 instead of 2048
  (compute); 2048 was used for the 4 FedAvg mains. All variant-B runs use 2048.
- Task performance was evaluated on 1000 instead of 3000 test samples per client, with greedy decoding and an
  answer-length cap. The paper's decoding for performance is unspecified.
- Single seed (0) everywhere; the paper does not report seeds or variance either.
- Not run: Llama-3.2-3B, GPT-2 XL, model-size and communication-round ablations (appendix), and LoRA-only CL.
