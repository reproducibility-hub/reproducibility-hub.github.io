# Reproduction report: LightEdit — "Towards Scalable Lifelong Knowledge Editing with Selective Knowledge Suppression" (2026.acl-long.145)

## Verdict
- **Verdict: PARTIALLY_REPRODUCED**
- **Result match (after fixes): MIXED**. Result match as released: **DOES_NOT_RUN**.
- **Coverage: SUBSET.** We ran the LightEdit rows of Table 1 (LLaMA) and Table 10 (GPT-J) on all three datasets at full scale (1,000 sequential edits), the α sweep of Table 2 (LLaMA, all 3 datasets), the Table 3 ablation (ZSRE), and α=0 vs α=0.2 for GPT-J (Table 11). Not run: the baselines (not in the release), Tables 4/5/9/12–14, and Figures 3/4.
- **Codebase completeness: MAJOR_FIXES.**

Summary of findings:
1. **The release does not run as shipped.** `train.py`, which trains the edit-aware selector (XLM-R-large), crashes with four bugs, and no trained selector is released. With minimal crash fixes, the unmodified `eval.py` reproduces LLaMA ZSRE (AVG 0.969 vs 0.966) and GPT-J Counterfact (0.903 vs 0.899). It is far off on RIPE (LLaMA 0.490 vs 0.982; GPT-J 0.586 vs 0.986) and on LLaMA Counterfact (0.845 vs 0.930).
2. **The RIPE failure comes from two bugs.**
   - *Evaluation leak:* the hooked forward decodes the teacher-forcing input (prompt plus every target token except the last) as the "query". Retriever, selector and LLM therefore all see a partial answer. RIPE prompts have no "?" for `build_prompt` to cut at, so the LLM is asked e.g. "...employer of X is Instituto de Biología Agrícola de M?" and answers only "Mendoza". The bag-of-tokens metric then scores this 0.2.
   - *Selector training data:* `train.py` cannot build RIPE training examples as written. Choosing the RIPE generality/locality types that the evaluator actually uses (selector variant B) fixes RIPE locality (0.33 → 0.9995).

   With both fixes, LLaMA RIPE reaches 0.953 vs 0.982 in the paper.
3. **Results with the fixed pipeline (selector B + leak fix, α=0.2, k=5):**

   | Model | Dataset | Ours (AVG) | Paper (AVG) | Match |
   |---|---|---|---|---|
   | LLaMA | ZSRE | 0.967 | 0.966 | match |
   | LLaMA | RIPE | 0.953 | 0.982 | within 5% relative |
   | LLaMA | Counterfact | 0.824 | 0.930 | no match (below the paper's LTE baseline, 0.875) |
   | GPT-J | ZSRE | 0.880 | 0.978 | no match (0.924 with selector variant A) |
   | GPT-J | Counterfact | 0.887 | 0.899 | match |
   | GPT-J | RIPE | 0.870 | 0.986 | no match |

4. **The in-context decoding (ICD) claim is not reproduced.**
   - The paper (Tables 2, 3 and 11) reports that α=0.2 beats α=0 by 3–6 AVG points and is the best setting.
   - In our runs, α=0 is as good as or better than α=0.2 on every LLaMA dataset: ZSRE 0.972 vs 0.967, Counterfact 0.825 vs 0.824, RIPE 0.957 vs 0.953. The same holds in the crash-fix-only pipeline (0.975 vs 0.969).
   - On ZSRE and RIPE, performance falls steadily as α grows above 0.1. Counterfact is flat across α.
   - For GPT-J, ICD helps only on Counterfact (+2.7 points). It hurts on ZSRE (−0.9) and RIPE (−3.6).
5. **The edit-aware selector ablation reproduces in direction, even more strongly than reported.** Without the selector, ZSRE locality drops to 0.15 (paper: 0.46) while reliability and generality stay high.
6. **Results are sensitive to the selector.** Two selectors trained from the same released script, differing only in which RIPE types are used, give GPT-J ZSRE 0.924 vs 0.880 and LLaMA Counterfact locality 0.90 vs 0.84.

## Why it is not fully reproduced
- **Code bugs.**
  - `train.py` cannot run as released, and no selector checkpoint is provided.
  - The evaluator leaks the target prefix into the query. This makes RIPE meaningless as released.
  - We fixed both, but had to choose which RIPE relation types to use as selector training data, because the released code has no working path for it.
- **Remaining gaps after fixes.** LLaMA Counterfact (−10.5 AVG points; locality 0.84 and generality 0.70 vs 0.98 and 0.81), GPT-J ZSRE (−9.7) and GPT-J RIPE (−11.7) are still well below the paper. We found no further bug that explains them. The selector is a major source of variance (see above). The authors' actual selector and their exact training-data sampling are unknown: the paper says 1,000 random instances in total, but the code takes the first 1,000 of each dataset.
- **ICD effect.** The α claim did not reproduce in either pipeline with LLaMA, and only partly with GPT-J (Counterfact only).
- **Baselines.** The release contains none of the baselines (FT, ROME, MEMIT, GRACE, R-ROME, AlphaEdit, LTE, RECIPE), so we did not run them. Claims that LightEdit beats them are not comparable from our runs. Against the paper's *reported* baseline numbers, our LightEdit would rank below LTE on LLaMA Counterfact (0.824 vs 0.875), below RECIPE on GPT-J ZSRE (0.880 vs 0.961), and below LTE on GPT-J RIPE (0.870 vs 0.901).

## Discrepancies
- **[code_vs_paper, minor]** `utils/utils.py model_path_map` — Paper: Sec 5.1: LLaMA checkpoint 'meta-llama/Llama-3.1-8B' (base). Code/other: 'meta-llama/Llama-3.1-8B-Instruct' (config named llama-3.1-8b-it); we used the code's Instruct model. Affects results: True.
- **[code_vs_paper, major]** `evaluation/editor_eval.py accuracy_and_prediction` — Paper: App. B.2: metrics follow Chen et al. (2024): Reliability/Generality = I[f*(q)=o*], Locality = I[f*(q)=f(q)]. Code/other: When facts are selected: fraction of target tokens that appear ANYWHERE among up to 16 greedily generated tokens (torch.isin bag-of-tokens); when no fact is selected: teacher-forced argmax tokens, again checked with isin over all positions (incl. prompt positions). This is more lenient than exact match / RECIPE's teacher-forced token accuracy. Affects results: True.
- **[code_vs_paper, major]** `editors/lightedit/lightedit.py register_model_forward_hook (query = decode(input_ids))` — Paper: Sec 4: selector and LLM receive the user query q. Code/other: The evaluation feeds prompt+target[:-1] (teacher-forcing input) to the hooked forward, so the retriever/selector query contains all but the last target token; build_prompt only strips text after "?", so for prompts without "?" (all RIPE prompts, ZSRE nq-locality prompts) the target prefix is also put into the LLM question. On RIPE this truncates generations (model outputs only the missing last word) and lowers Reliability/Generality to ~0.54/0.52. Affects results: True.
- **[code_vs_paper, minor]** `train.py build_examples / main` — Paper: App. B.3: selector fine-tuned on a total of 1,000 randomly sampled instances from ZSRE/CF/RIPE train sets (random_state=42). Code/other: Takes the FIRST data_n=1000 instances of EACH dataset (3,000 instances -> 9,000 query-fact pairs), not random; 20% held out by train_test_split(random_state=42). Affects results: True.
- **[code_vs_paper, minor]** `editors/lightedit/lightedit.py PriorSuppressionProcessor / prefill_hook` — Paper: Eq. 8-10: l_prior = mean over selected facts of log p(x_o | s, r) (first token of original object given (s, r)); log p'(x1) = l_new - alpha*l_prior. Code/other: l_prior is the full-vocabulary log-softmax at the position preceding each new object inside the full in-context prompt (conditioned on all preceding facts), averaged over facts, and is subtracted from the raw first-step logits (not log-probs; argmax-equivalent under greedy decoding). Affects results: False.
- **[code_vs_paper, minor]** `utils/data.py TestSampleList.ripple_effect` — Paper: RIPE evaluates ripple effects (Logical Generalization, Compositionality I/II, Subject Aliasing; Relation Specificity, Forgetfulness). Code/other: The loop resets ns['generality']['rephrase'] / ns['locality']['loc1'] for every type, so only the LAST type (Subject_Aliasing for generality, Forgetfulness for locality) is evaluated, and samples where that type is empty get no generality (271/1000) or locality (472/1000) query.
